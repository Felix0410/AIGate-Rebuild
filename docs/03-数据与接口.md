# AIGate 领域、数据库与接口设计

> **设计合同；数据库和 API 尚未实施。** 本文整合领域模型、数据表、核心事务、安全和对外 API，供本地 AI 在对应 Phase 严格执行。数据库字段和 API 一旦与本文件冲突，先由总控更新合同，不让本地 AI 自行拍板。

## 一、实现环境与约定

Java 21、Spring Boot 4.1.x、MySQL 8.4/InnoDB、Flyway、MyBatis-Plus、Spring MVC。单企业部署；主键建议 BIGINT，瞬时时间 DATETIME(6) 按 UTC 保存；内部积分 DECIMAL(20,6)，外部金额 DECIMAL(20,8)，Java 使用 BigDecimal 而非 double。初期每百万 Token 为计价单位，按已确认的输入/输出/缓存类别和调用时价格版本分别计算，单请求汇总后按 HALF_UP 舍入。

**这些精度/单位/舍入是重建版的设计默认**，不是用户已确认的真实供应商价格，正式编码前不得编造公司预算与 Provider 单价。

## 二、核心领域实体

| 领域 | 核心对象 | 关系与不变量 |
|---|---|---|
| 组织与身份 | Team、Employee、Application（Agent）、AgentApiKey、EmployeeCredential、RoleAssignment | 每 Employee 有当时的主 Team；Agent/Application 1:1；两个凭证必须独立验证 |
| 权限与模型 | EmployeeAgentPermission、AgentModelAllowlist、Provider、LogicalModel、ModelDeployment、PriceVersion | Employee N:M Agent；Agent N:M Model；Model 1:N Deployment；定价版本不可覆盖历史 |
| 权威账务 | WeeklyBucket、TeamPool、GrantRequest、TeamExtraGrant、FundingAccount、EmergencyApproval、Reservation、ReservationAllocation、Settlement、LedgerEntry、ReconciliationCase | Agent 免费→个人基础→有效 Grant；账户实际余额/预留不能透支 |
| 网关 | Invocation、RoutingDecision、UpstreamAttempt、SSESession | 请求唯一幂等键，同一次可收费的上游发送只授权一次 |
| 安全治理 | SafetyPolicy、PolicyRevision、SafetyDecisionAudit | 发布版本不可覆写，审计只存风险分类等元数据 |
| 分析 | OutboxEvent、InboxReceipt、DailyUsage、DailyGrantExpense、CostAlert | 派生视图可以延迟/重建，不能写权威资金余额 |

## 四、账务事务：明确执行顺序

**A. Team 发放**：验证 TeamManager 对发放 Team 的权限、接收人和申请状态 → 以唯一 grantOperationKey 去重 → 锁 Team 池 → 校验足额 → 同事务扣池、创建 Grant、写 Ledger 和 Outbox → 提交。主动发放没有审批 ID 也必须有唯一操作 Key。重复批准不得再次扣费。

**B. 调用预留**：已认证 Employee+Agent，获准 Model，已通过出站安全检查 → 校验 Idempotency-Key、body 摘要、有效价格与最大风险上限 → 依固定顺序锁 Agent 周免费桶、个人基础桶、Grant、公司批准的保底或紧急账户 → 合计足额才一次性增 reserved 并写 Allocation；不够则整体回滚。**余额语义：available=balance−reserved；预留只增加 reserved，结算才从 balance 扣实际金额。**

**C. 最终结算**：可信 Provider Token 分类 × 本次捕获的价格版本 → 锁 Reservation/Allocation → 使用实际应扣额更新来源 balance、释放完整 reserved、写唯一 Settlement/Ledger、把 Invocation 标为 SETTLED，Outbox 同事务提交。已结算重复到达只能返回旧结果。

**D. 网络失败/取消**：可证明未调用 Provider 则释放 reserved 并 CANCELLED；Provider 可能已收费、用量无可信来源时标记 PENDING_RECONCILIATION，保留受控预留和证据，日后管理员根据可信账单/证据 SETTLE 或证明零费用后 RELEASE；**不得定时把未知费用自动清零**。

同一个逻辑请求绝不在持有 DB 事务时等待 Provider I/O。所有多账户锁有稳定排序以降低死锁；MySQL 余额必须满足 available 非负。Grant 到期而存在预留时需保持账务来源可追溯，不能删旧 Grant 或把预留视为未使用返还。

## 五、认证与密钥合同

运行时头：`Authorization: Bearer agk_<随机密钥>` 与 `X-Employee-Key: empk_<独立随机密钥>`；收费请求另带 `Idempotency-Key`。Key 由服务端 SecureRandom 签发，创建时明文返回一次，数据库仅保存安全摘要/短前缀、有效期、撤销状态。建议 HMAC-SHA256 加部署环境 Pepper，定长安全比较；可读明文密钥、Pepper 和 Provider 凭证不进入 Git/日志。

P1/P2 管理接口使用来自环境变量的独立高熵 bootstrap Admin 凭证，后续 P4 引入员工管理角色体系。管理凭证不能用于模型调用；Agent Key 不能操作管理员 API。Provider 凭证用 AES-GCM 加密，主密钥经受控环境配置；Provider URL 限定 HTTPS 和允许的 host，禁止随意重定向及 SSRF。前期 P2/P3 的模型代理只允许 Mock Provider/test profile；**完整双身份和模型权限在 P4 验收前不开放真实付费出站**。

## 六、HTTP API 合同

统一管理 API 前缀 `/api/v1`，运行时 `POST /v1/chat/completions`。JSON 错误格式 `{code,message,traceId,details?}`；分页 `page=1,size=20`，最大 100，返回 `{items,page,size,total}`；时间 UTC ISO 8601。

| 资源 | 主要 API | 关键请求字段/约束 |
|---|---|---|
| Team / Employee | POST/GET/PATCH /teams、/employees；GET /employees/{id} | team name；Employee code/displayName/primaryTeamId；禁用无权访问 |
| 员工凭证 | POST/DELETE /employees/{id}/credentials[/{keyId}] | 过期时间；创建结果唯一一次返回 empk 明文 |
| Agent 与凭证 | POST/GET/PATCH /agents；POST/DELETE /agents/{id}/keys[/{keyId}] | teamId/name、expiresAt；只创建时返回 agk |
| 权限 | PUT /employees/{id}/agents/{agentId}；PUT /agents/{id}/models/{modelId} | `{enabled:boolean}`；幂等、检查对象状态 |
| Provider / Model / Deployment | POST/GET/PATCH /providers、/models、/deployments | modelId/providerId/endpointUrl/weight/status；响应不得返回 Provider Key |
| 价格版本 | POST /prices | targetType/id、INTERNAL_POINTS 或 PROVIDER_PURCHASE、币种、分类 Token 每百万价、生效时间 |
| 员工额度 | GET /me/quotas | 仅返回本人周额度、可用 Grant、可用保底 |
| Team 发放 | POST/GET /grant-requests；POST /grant-requests/{id}/approve；POST /teams/{id}/grants | 申请人、发放 Team、points、expiresAt；审批或主动发放都必须幂等 |
| 用量/紧急/对账 | GET /invocations；POST /emergencies、/emergencies/{id}/approve；POST /reconciliations/{id}/resolve | 分页与范围鉴权；资金和结算只经业务命令 |
| 安全治理 | POST/GET /safety/policies；POST /safety/policies/{id}/publish | 作用范围、规则集、版本；只增不改历史 |
| FinOps | GET /finops/reports、/finops/alerts | groupBy（员工/Team/Agent/Model/Deployment）、metric（三种口径）、币种/日期 |

运行时请求最少含 `model`、`messages`、`max_tokens`、`stream`；Provider 其他参数必须白名单转发，不允许传入任意 Provider URL。非流式返回兼容 OpenAI 的 choices/usage/model；流式使用 `text/event-stream` 的增量 chunk，正常完成才发送 `[DONE]`，终止后可信 usage 才能结算。中途断开不可虚构 usage。

**幂等键范围**：(agentId,employeeId,idempotencyKey)。同 Key 不同请求摘要 409；同 Key 执行中 409；曾经可能出站收费的调用不可用同 Key 再次发起。SSE 完成后默认不存储完整响应，不能承诺可重放旧流。错误含 400 参数错误、401 认证失败、403 无权/安全拒绝、402 额度不足、409 幂等冲突、429 限流、503 Provider 不可用、504 超时，且不得泄密。

## 七、最终实施边界

用户确认了积分来源、Team 发放和 FinOps 三口径；上面的密钥格式、金额精度、管理员引导等是**本轮设计默认**。接口最小字段/表约束在开始对应 Phase 前由总控审查冻结，**本地 AI 不得自行引入新资金来源、协议或微服务架构**。

## 八、P0 设计冻结缺口（2026-10-21，尚未满足全量设计条件）

当前表格是**核心表字典，不是完整可直接执行的全量 DDL**；API 清单是路径/最少 DTO，不是每个端点的请求、响应、角色、错误、幂等和分页细节均已冻结。用户要求**所有设计先完成**，因此本阶段必须补齐如下内容，而不是编码时让本地 AI 自行决定。

1. 对全部表确定逐列 SQL 类型、NULL/默认、枚举状态、FK/删除行为、唯一索引、并发锁顺序与迁移版本；补足管理员角色、Key Pepper 轮换、价格版本有效区间的无重叠策略、授额和余额的拆账来源。
2. 对每个公开 API 确定完整 DTO、示例 JSON、安全角色、错误映射、更新/禁用/吊销语义、幂等 Key 和分页契约。明确 management bootstrap 与生产员工/管理员角色的切换和禁用边界。
3. **双预算**：员工/Team **内部积分账本**与企业/Provider **对外采购费用风险账户**必须分开，单价和硬限额至少按生效采购价格和原始供应商币种处理，不可把 points 当成现金。需要确定独立采购余额、按请求风险预留、结算、退款/待对账、跨币种禁止直接加总、现金不足时阻断出站的事务设计。
4. 对 Provider 限制、max_tokens、输入长度、SSE 中断无 usage、PriceVersion 捕获及首次 dispatch 后幂等写法冻结“失败时谁持有预留”的具体状态机与恢复动作；未知账单不得自动归零。
5. 对 Governance 规则版本发布、缓存失效、异常授权范围、数据最小审计，以及 Redis 失联、RabbitMQ 消息积压、Outbox 重放、FinOps 去重的失败边界写出可执行合同和测试。
6. 逐业务块建立完整自动验收案例与测试固定数据/Mock，确保用户要求的“该块一次实现全部必要功能”可客观核查。
