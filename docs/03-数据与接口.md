# AIGate 领域、数据库与接口设计

> **设计合同；数据库和 API 尚未实施。** 本文整合领域模型、数据表、核心事务、安全和对外 API，供本地 AI 在对应 Phase 严格执行。数据库字段和 API 一旦与本文件冲突，先由总控更新合同，不让本地 AI 自行拍板。

## 一、实现环境与约定

Java 21、Spring Boot 4.1.x、MySQL 8.4/InnoDB、Flyway、MyBatis-Plus、Spring MVC。单企业部署；主键建议 BIGINT，瞬时时间 DATETIME(6) 按 UTC 保存；内部积分 DECIMAL(20,6)，外部金额 DECIMAL(20,8)，Java 使用 BigDecimal 而非 double。初期每百万 Token 为计价单位，按已确认的输入/输出/缓存类别和调用时价格版本分别计算，单请求汇总后按 HALF_UP 舍入。

**这些精度/单位/舍入是重建版的设计默认**，不是用户已确认的真实供应商价格，正式编码前不得编造公司预算与 Provider 单价。

## 四、账务事务：明确执行顺序

**A. Team 发放**：验证 TeamManager 对发放 Team 的权限、接收人和申请状态 → 以唯一 grantOperationKey 去重 → 锁 Team 池 → 校验足额 → 同事务扣池、创建 Grant、写 Ledger 和 Outbox → 提交。主动发放没有审批 ID 也必须有唯一操作 Key。重复批准不得再次扣费。

**B. 调用预留**：已认证 Employee+Agent，获准 Model，已通过出站安全检查 → 校验 Idempotency-Key、body 摘要、有效价格与最大风险上限 → 依固定顺序锁 Agent 周免费桶、个人基础桶、Grant、公司批准的保底或紧急账户 → 合计足额才一次性增 reserved 并写 Allocation；不够则整体回滚。**余额语义：available=balance−reserved；预留只增加 reserved，结算才从 balance 扣实际金额。**

**C. 最终结算**：可信 Provider Token 分类 × 本次捕获的价格版本 → 锁 Reservation/Allocation → 使用实际应扣额更新来源 balance、释放完整 reserved、写唯一 Settlement/Ledger、把 Invocation 标为 SETTLED，Outbox 同事务提交。已结算重复到达只能返回旧结果。

**D. 网络失败/取消**：可证明未调用 Provider 则释放 reserved 并 CANCELLED；Provider 可能已收费、用量无可信来源时标记 PENDING_RECONCILIATION，保留受控预留和证据，日后管理员根据可信账单/证据 SETTLE 或证明零费用后 RELEASE；**不得定时把未知费用自动清零**。

同一个逻辑请求绝不在持有 DB 事务时等待 Provider I/O。所有多账户锁有稳定排序以降低死锁；MySQL 余额必须满足 available 非负。Grant 到期而存在预留时需保持账务来源可追溯，不能删旧 Grant 或把预留视为未使用返还。

## 五、认证与密钥合同

运行时头：`Authorization: Bearer agk_<随机密钥>` 与 `X-Employee-Key: empk_<独立随机密钥>`；收费请求另带 `Idempotency-Key`。Key 由服务端 SecureRandom 签发，创建时明文返回一次，数据库仅保存安全摘要/短前缀、有效期、撤销状态。建议 HMAC-SHA256 加部署环境 Pepper，定长安全比较；可读明文密钥、Pepper 和 Provider 凭证不进入 Git/日志。

P1/P2 管理接口使用来自环境变量的独立高熵 bootstrap Admin 凭证，后续 P4 引入员工管理角色体系。管理凭证不能用于模型调用；Agent Key 不能操作管理员 API。Provider 凭证用 AES-GCM 加密，主密钥经受控环境配置；Provider URL 限定 HTTPS 和允许的 host，禁止随意重定向及 SSRF。前期 P2/P3 的模型代理只允许 Mock Provider/test profile；**完整双身份和模型权限在 P4 验收前不开放真实付费出站**。

## 六、HTTP API 合同

统一管理 API 前缀 `/api/v1`，运行时 `POST /v1/chat/completions`。JSON 错误格式 `{code,message,traceId,details?}`；分页 `page=1,size=20`，最大 100，返回 `{items,page,size,total}`；时间 UTC ISO 8601。

| 资源 | 主要 API | 关键请求字段/约束 |
|---|---|---|
| Team / Employee | POST/GET/PATCH /teams、/employees；GET /employees/{id} | team name；Employee code/displayName/primaryTeamId；禁用无权访问 |
| 员工凭证 | POST/DELETE /employees/{id}/credentials[/{keyId}] | 过期时间；创建结果唯一一次返回 empk 明文 |
| Agent 与凭证 | POST/GET/PATCH /agents；POST/DELETE /agents/{id}/keys[/{keyId}] | teamId/name、expiresAt；只创建时返回 agk |
| 权限 | PUT /employees/{id}/agents/{agentId}；PUT /agents/{id}/models/{modelId} | `{enabled:boolean}`；幂等、检查对象状态 |
| Provider / Model / Deployment | POST/GET/PATCH /providers、/models、/deployments | modelId/providerId/endpointUrl/weight/status；响应不得返回 Provider Key |
| 价格版本 | POST /prices | targetType/id、INTERNAL_POINTS 或 PROVIDER_PURCHASE、币种、分类 Token 每百万价、生效时间 |
| 员工额度 | GET /me/quotas | 仅返回本人周额度、可用 Grant、可用保底 |
| Team 发放 | POST/GET /grant-requests；POST /grant-requests/{id}/approve；POST /teams/{id}/grants | 申请人、发放 Team、points、expiresAt；审批或主动发放都必须幂等 |
| 用量/紧急/对账 | GET /invocations；POST /emergencies、/emergencies/{id}/approve；POST /reconciliations/{id}/resolve | 分页与范围鉴权；资金和结算只经业务命令 |
| 安全治理 | POST/GET /safety/policies；POST /safety/policies/{id}/publish | 作用范围、规则集、版本；只增不改历史 |
| FinOps | GET /finops/reports、/finops/alerts | groupBy（员工/Team/Agent/Model/Deployment）、metric（三种口径）、币种/日期 |

运行时请求最少含 `model`、`messages`、`max_tokens`、`stream`；Provider 其他参数必须白名单转发，不允许传入任意 Provider URL。非流式返回兼容 OpenAI 的 choices/usage/model；流式使用 `text/event-stream` 的增量 chunk，正常完成才发送 `[DONE]`，终止后可信 usage 才能结算。中途断开不可虚构 usage。

**幂等键范围**：(agentId,employeeId,idempotencyKey)。同 Key 不同请求摘要 409；同 Key 执行中 409；曾经可能出站收费的调用不可用同 Key 再次发起。SSE 完成后默认不存储完整响应，不能承诺可重放旧流。错误含 400 参数错误、401 认证失败、403 无权/安全拒绝、402 额度不足、409 幂等冲突、429 限流、503 Provider 不可用、504 超时，且不得泄密。

> 决策状态：**PROPOSED**。方案冻结后替代本文件第八节“缺少公司外部采购风险账户”的阻塞点，但其他完整 DDL/API 细节仍需继续设计。

### 9.1 采购风险预算表（仅新增采购预算，不替代现有 Points 账本）

**provider_spend_budget**，设计默认字段（MySQL 8.4）：
- `id BIGINT PK`；`scope_type VARCHAR(16) NOT NULL`（第一版只 COMPANY）；`scope_id BIGINT NOT NULL DEFAULT 0`；
- `currency CHAR(3) NOT NULL`（供应商报价原币种，ISO 4217）；
- `period_start DATETIME(6) NOT NULL`、`period_end DATETIME(6) NOT NULL`（以公司 ZoneId 计算自然月边界，再转换 UTC）；
- `limit_amount DECIMAL(20,8) NOT NULL`、`settled_amount DECIMAL(20,8) NOT NULL DEFAULT 0`、`reserved_amount DECIMAL(20,8) NOT NULL DEFAULT 0`；
- `status VARCHAR(16) NOT NULL`（ACTIVE/FROZEN/CLOSED）、`version BIGINT NOT NULL DEFAULT 0`、created_at/updated_at；
- 唯一索引 `(scope_type,scope_id,currency,period_start)`；
- 强制 `limit_amount>=0`、`settled_amount>=0`、`reserved_amount>=0`；准入条件 `limit_amount-settled_amount-reserved_amount >= estimated_max_exposure`。**不是供应商已付现金账户**。

**provider_spend_reservation**（同一 invocation 至多一笔实际收费 Provider 尝试，禁止盲目重复出站）：
- `id BIGINT PK`、`invocation_id BIGINT NOT NULL UNIQUE`；
- `budget_id BIGINT NOT NULL`，`deployment_id BIGINT NOT NULL`、`provider_price_version_id BIGINT NOT NULL`；
- `currency CHAR(3) NOT NULL`、`reserved_amount DECIMAL(20,8) NOT NULL`、`settled_amount DECIMAL(20,8) NULL`；
- `status VARCHAR(32) NOT NULL`（RESERVED/DISPATCHED/SETTLED/RELEASED/PENDING_RECONCILIATION/OVERRUN）；`reason_code VARCHAR(64) NULL`、created_at/updated_at；
- budget/currency/价格快照与 Invocation、内部 Points Reservation 一致；不在两套预算间使用不同 invocationId。

附加的企业 Provider 采购支出流水应具 `business_type,invocation_id,budget_id,event_type` 幂等键，并分别记录预留、确认费用、释放和异常超额。实际供应商价格来源/币种/有效版本可审计；暂不把预计费用误记为已支付发票。

### 9.2 双预算状态转移和不变量

- 内部 Points 账户依已有定义：`available_points=balance_points-reserved_points`；公司采购预算：`available_purchase=limit_amount-settled_amount-reserved_amount`，且正常准入绝不可为负。
- **先校验选择目标逻辑 Model/Deployment + 出站安全政策/真实员工权限，再原子预留**。确定会使用哪个 Provider 及其报价币种后，捕获生效内部积分和 Provider 采购价版本，以及有界 Token/费用风险上界。
- 一个短事务内按系统约定的稳定锁顺序 `provider_spend_budget → 其他需要的资金账户按固定表级顺序及 PK` 执行锁定/校验/预留；任何一套不足则完全回滚（请求不得出站）。
- 在确认可能已发出付费请求前记录 Invocation DISPATCHING/DISPATCHED 的持久状态/唯一执行令牌；**不以网络超时自动假设请求未发出**。
- 正常结算在一个事务同时释放 Points 和采购预算的原预留，按可信 usage × 冻结价格版本实际扣 Points、累加 `settled_amount`，写唯一结算/资金流水及 Outbox，然后 Invocation SETTLED。价格更新不影响已开始请求。
- Provider 确认零费用且没有计费出站时两边释放；未知时两边 PENDING_RECONCILIATION，保持原先期间的风险占用（跨月保留），直到可审计的可信证据消除。
- 若 Provider 最终真实费用意外超预留：记录 **OVERRUN**、供应商实际/可信估计值及超出金额，冻结相应采购风险预算并阻止新收费调用，进入人工核对；**不能用截断为保留金额的方式隐藏超额，也不能声称供应商实际账单不可能超出预算**。资金账户允许异常申报超限，但正常准入不再通过。
- 一个 Provider 消费报价币种无预算配置或币种不符：拒绝付费出站；公司级采购预算按自然月和币种独立，不能无汇率把多币种合并成“统一公司总金额”。

### 9.3 管理 API 设计增量（待冻结请求/响应全 DTO）

- `POST /api/v1/provider-spend-budgets` 管理员创建 COMPANY 某币种某月份的不可负额度（不允许重叠/重复，预算调低不得低于已结算+已预留）。
- `GET /api/v1/provider-spend-budgets?currency&periodStart&page&size` 查询上限、已确认估算支出、已预留、可批余额及状态；仅 ADMIN/FINOPS_READER 可读，写 ADMIN。
- `PATCH /api/v1/provider-spend-budgets/{id}` 调整未结束预算的限额、冻结/解冻（操作审计、乐观版本、不能抹除历史流水）；货币和月份一旦被请求使用不得修改。
- `GET /api/v1/reconciliations` 应显示关联的**积分和 Provider 费用两种预留/期间**；人工 resolve 必须按同一 invocationId 协调完成双账结算或释放，禁止只处理其中一套后默默认为完成。
- Runtime 用现有 `/v1/chat/completions`，不由用户请求体指定采购预算 ID 或任意 Provider 采购价。

### 9.4 风险评估算法（阶段合同）

候选 Deployment 在上游调用之前确定；先校验授权/政策。根据受控请求体、Model 上下文上限、服务端输出上限、供应商支持的计量字段与对应**最大适用**单价计算保守的 `max_points_exposure` 和 `max_provider_purchase_exposure`。本地 tokenizer 估测只能供预估或告警，不得伪装成供应商计价的可靠上界。支持明确验证上界的 Provider 合同才允许进入收费出站；不支持的模型请求先拒绝，不能悄悄用估算值绕过企业上限。

### 9.5 需进一步冻结的关联问题

- 每个 Provider 可确认的 Token 上限/计价维度（上下文缓存、工具/音频/图像等未支持收费类型须禁止请求）、兜底计价保护和价格更新原子性；
- 现金预算被 Provider 实际超扣后的异常申报如何影响月度报表、财务核对和新增额度审批；
- Grant 到期但有在途预留时的准确释放/结算及周额度跨周处理；
- 多币种如果要提供全公司的本位币单个硬限额，必须新增可审计汇率与缓冲策略，当前不提供虚假的跨币种统一硬阈值；
- 分布式服务拆分后同步现金/积分双预留不能靠 MQ 最终一致分两处分别扣款，先保持同一 MySQL 事务写主。

本方案没有创建表或执行迁移。本模块若按建议重排，新 P4 的完整账务块需要包含**普通付费请求的两套资金预留能力**，新 P9 才增加企业保底/多实例限流政策，不能先开发会产生付费费用的 Runtime 再补外部采购预算。

## 十、P0 D-02：API Provider 与企业自部署类型及资源许可模型（业务已确认；物理结构待冻结）

### 部署层数据

扩展 `model_deployment`：
- `hosting_mode VARCHAR(24) NOT NULL` = THIRD_PARTY_API 或 SELF_HOSTED（是管理方/资源类型，不是 HTTP 协议类型）；
- `cost_model VARCHAR(32) NOT NULL` = PER_TOKEN_API / INTERNAL_RESOURCE（首版），并验证与 hosting_mode 的合法组合；
- `endpoint_url`、`remote_model_name`、`status`、`model_id` 和 `provider_id` 仍统一保留；自部署端点必须受网络白名单和凭证保护；
- `max_concurrent_requests INT`、`max_queue_size INT`、`max_input_tokens INT`、`max_output_tokens INT`、`capacity_policy_version BIGINT`（自部署必填）；
- 外部 API 需绑定有效采购单价和原币种预算，SELF_HOSTED 不绑定逐次 API 采购单价而可配置`operating_cost_profile_id`（仅当真实成本源存在）；
- `model_deployment` 能力与 Agent logical Model allowlist 仍独立：能部署≠该员工能用。

保留 MySQL local_capacity_policy 作为推理池并发、等待和超时的版本化配置；ACTIVE、WAITING 和租约等高频运行态改由 Redis Lua 统一协调。MySQL 保存 Invocation 派发意图、账务、策略和审计；不再制作 MySQL 容量热计数/等待队列的临时实现。

本地基础保底候选 `local_fallback_quota`：每 Employee、Agent、周期、Policy 的已用/预留 Token 或等价服务额度，唯一期间 Key，防止积分耗尽后出现无限无付费 API 额度的本地推理。

### 路由和计费合同

1. 每次 Invocation 记录实际 `deployment_id`、`hosting_mode`、`cost_model`、调用时员工 Team 快照及内部积分价格版本。
2. THIRD_PARTY_API：有有效 Provider 采购价时，按照 D-01 规则必须拥有同 invocationId 关联的 **PointsReservation + ProviderSpendReservation**；需要同一 MySQL 短事务提交。
3. SELF_HOSTED 常规：同 invocationId 需 **PointsReservation + 有界 LocalCapacityLease**；无逐次供应商 API 风险时，`provider_spend_reservation` **不创建**，不能硬性强加一个 0 USD 假消费。按 D06 最终顺序，Redis 排队及容量许可在前、MySQL 资金预留在后；若得到许可但资金预留失败则释放许可，不发生上游出站。排队阶段不产生需要退款的积分预留。
4. SELF_HOSTED 补贴保底：`LocalFallbackQuotaReservation` + `LocalCapacityLease`，不要求普通 Points 或 Provider 采购风险预留，但必须记录员工/Agent、权限、Token/请求额度及过期条件；如本地用量无法确认需按可验证的 Token 或请求上界保留补贴用量风险，不得无限赠送。
5. 自部署服务正在处理但客户端断开：释放占用容量的**实际运行任务**应尽力由推理服务确认取消；如不能确认，则容量许可保持至超时/协调回收，资金按实际可信 Token/补贴上限最终处理，不可瞬时假设推理服务停止。
6. `self_hosted_operating_cost`（P11 FinOps 可选维度）：部署/算力池 ID、统计期间、采购云 GPU 时长/账单、能耗/设备折旧/运维费用、金额/原币种、来源证据与分摊方法；“单次自部署模型估算成本”必须明确采用 GPU 秒、推理占用或经允许的 Token 比例等估算方法，不能冒充精确发票。

### 对外接口增加

- 管理 `POST/GET/PATCH /api/v1/deployments` 的 DTO 增 `hostingMode`、`costModel`；仅 SELF_HOSTED 接受 `capacityPolicy` 与 `localServiceCredential`（敏感凭证只写入，不返回原文）。
- `GET /api/v1/deployments/{id}/capacity`（ADMIN/可授权运维只读）：可用健康/在途/排队、数据来源及采样时间，断连或未提供观测时标 UNKNOWN，不能把 UNKNOWN 说成健康。
- `GET /api/v1/finops/reports` 补充明确 `costSource = PROVIDER_API | SELF_HOSTED_OPERATING`，保留外部 API 采购成本估算与自部署算力运营费用两个现金费用来源的分列，避免一笔云租赁成本按 token 再双计。
- `/v1/chat/completions` 保持同一端点、同一双身份和逻辑 Model ACL，由网关**内部**根据部署类型执行不同准入，不让 Agent 自行指定可绕过资金的 hostingMode。

**业务模式与资金归属已确认**。本节物理字段、容量租约、补贴精度和数据存储方案为设计候选；待 D-03 及完整 DDL/API 审查后方可冻结，不表示已存在任何表。



## 十一、D03 详细实现：Redis 容量许可 + 本地周补贴（方案待冻结）

业务规则已确认：普通自部署消耗 Points，批准的基础保底跨 Agent 使用同一 Employee 周 Token 补贴账户。Redis 直接作为多实例入场与推理容量协调基础设施，不承担权威账本。

### 数据与归属

- MySQL local_fallback_quota：id BIGINT 主键，employee_id BIGINT 非空，period_start/period_end DATETIME(6)，limit_tokens/used_tokens/reserved_tokens BIGINT 非负，version BIGINT。UNIQUE(employee_id,period_start)，可用额度 = limit-used-reserved。跨 Agent 同一员工只生成一个周桶。
- MySQL local_fallback_reservation：invocation_id UNIQUE、quota_id、reserved_tokens、actual_tokens nullable、state、时间戳；RESERVED、SETTLED、RELEASED、PENDING_RECONCILIATION 四种状态。正常结算将实际 Token 计入 used 并释放全部 reserved；用量未知保留预留，不记 0。跨周请求仍结算原周桶。
- MySQL local_capacity_policy：capacity_pool_id、包含的 Deployment、max_active、max_waiting、max_queue_ms、max_run_ms、status、policy_version；仅保存配置及版本，不保存高频活跃许可计数。共享物理 GPU 的多个 Deployment 必须关联同一池。
- MySQL invocation：保留 deployment_id、pool_id、quota_reservation_id、dispatch_intent_at、唯一 attempt_token、upstream_task_id（若上游支持）、state；用于崩溃恢复与对账证据，不能用 Redis 租约取代执行事实。
- Redis：单 Pool 的 active ZSET（member=invocationId+leaseToken、score=过期时间），normal/fallback 两个 WAITING ZSET（score=全局序号，FIFO），以及有界任务状态哈希/脚本配置版本。相关多键统一使用 {poolId} 的 Cluster hash tag；任何一次原子 Lua 脚本只触及同槽键。

### Redis 脚本操作

1. acquireOrQueue：以 invocationId 幂等检查，容量空闲且无更高优先等候则领取 ACTIVE；否则在 max_waiting 范围内加入 WAITING；队列满直接拒绝。NORMAL 优先于 FALLBACK，同时可通过有界等待年龄提升防止低档永久饥饿。
2. promote：在 Lua 中原子选择未超时的队首任务发放 ACTIVE，不能让晚入队请求绕过已有等待票；获取的 leaseToken 与一次 invocation 绑定。
3. renew：仅同一 invocationId 和随机 leaseToken 可以续约；进程重启或旧客户端不能续他人的租约。
4. release：同一 invocationId+leaseToken 才能幂等释放许可和等待票；客户端超时只能触发任务核查，不能将 Redis TTL 视为 GPU 实际停止。
5. Redis 不可用或重启丢失运行态时新收费或本地推理入场应 fail closed；需恢复关联真实推理任务与 MySQL Invocation 状态后开放新许可。推理服务本身强制并发/队列/最大运行时才是最后物理容量保护。

### 请求顺序与补偿

双身份/权限/治理前置筛查 → Redis 全局速率准入并进入有界 WAITING 队列 → Redis 获得 ACTIVE 名额 → 派发前再次鉴权和确定 Deployment、账务来源与价格 → **此时才** MySQL 原子预留 Points/本地保底 Token/收费 Provider 月度采购份额 → 持久写入唯一派发意图 → Provider JSON/SSE → 可信 usage 结算或待对账 → 上游任务确认结束后释放 Redis 许可。等待阶段**不占用**资金；原“先预留再等待”方案被 D06 替代。

Redis 与 MySQL **不共享事务**。排队失败/过期且可证明未出站，按 invocationId 幂等退还额度；已写派发意图但真实发送情况不明时不得盲目重发。推理服务已结束但 MySQL 结算失败，可以释放容量，保留待重试结算/对账。Redis 丢失 ACTIVE 状态不等于 GPU 任务已停止；须使用上游任务查询/取消确认，若该服务没有任务状态接口则依其真实强制最长运行时采取保守恢复窗口，不能假造查询能力。

**本节是架构实施候选，而非用户已批准的所有参数**：具体超时/TTL、脚本状态编码、输入 Token 上界、上游推理协议和测试固件仍须 P0 统一冻结。

## 十二、P0-D04：多额度来源资金状态机与数据库合同（业务确认，物理 DDL 待冻结）

**周额度唯一键**：quota_bucket 使用 owner_type、owner_id、agent_scope_id（NOT NULL，非 Agent 桶固定为0）、period_start 的四列唯一索引；Agent 免费桶的 agent_scope_id=真实 agentId。balance_points 和 reserved_points 都用 DECIMAL，正常可用 = balance-reserved。另存 period_end 与版本，禁止用 nullable agent_id 唯一键绕过并发初始化。

**Team Grant**：每笔成功发行有唯一 grant_operation_key、issuer_team_id、recipient_employee_id、issued_points、balance_points、reserved_points、expires_at 及状态。能否接受新请求必须检查预留时间早于 expires_at；已在有效期内成功预留的资金可在到期后结算。已过期金额不能重新开放消费或返还原 Team 池，保留历史与待对账记录。

**逐来源预留分配**：reservation_allocation 以 invocation_id、source_type、source_id 唯一，保存 priority_order、reserved_points、settled_points、released_points。单 invocation 的 allocation 之和必须等于 total_reserved。业务选择先 Agent 周免费、后 Employee 基础、再按 Grant expires_at/id；但物理行锁**统一固定顺序**，不得按请求临时拼出不同锁顺序引发死锁。

**短事务 Reserve**：先验证身份/Agent 权限/内容安全并确定 Deployment、两种有效价格和可信最高风险；在一个 MySQL 事务中锁定所有使用资金及对应的 Provider 币种月预算、验证充足、更新各 source 的 reserved 并写唯一 Allocation。某一方失败整个回滚且付费 Provider 出站0。网络调用不持资金行锁。

**短事务 Settle**：以唯一 invocationId 锁定本次 Reservation、Allocation 和来源，用冻结价表计算实际费用；按资金优先级将真实消费重新分配到已预留的各来源，并逐源执行 balance 减实际、reserved 减原本完整预留，差额形成释放审计。过期/跨周都只在原 sourceId 结算，绝不将多余释放计入新周，也不二次扣 Team Pool。对于第三方 API，积分与 Provider 原币种月采购预算在**同一事务**结束结算并写 Ledger/Outbox。

**取消/未知**：可证明未出站则幂等释放原账户预留；已可能收费但无可信 Token 则保留原账户 pending，直到可信对账；与发放 Team 的 Grant 历史及已失效周期可以共存，不可直接物理删除。旧价格和当时员工主 Team 快照不可被管理员后续修改追溯覆盖。

本节是具体物理合同提案，全部 DDL 列型、索引、迁移版本及外部 API DTO 仍待 P0 统一冻结。

## 十三、P0-D05：企业保底/紧急池与采购预算分区（已认可，结构细节待冻结）

此节补充 D01 企业 Provider 采购月预算总账户、D04 多来源预留。金额仍使用 DECIMAL(20,6) Points 或 DECIMAL(20,8) 供应商币种。预算账户与期初额度按公司时区确定期间、实际时间存 UTC；所有账户采用短 MySQL 事务及唯一 invocationId 幂等。

### 账户设计

| 表/实体 | 关键字段 | 唯一键与业务 |
|---|---|---|
| corporate_fallback_pool | id,period_start,period_end,limit_points,used_points,reserved_points,status,version | 公司月度保底内部积分池，正常可用=limit-used-reserved；按 period_start 唯一 |
| employee_fallback_weekly_cap | id,employee_id,period_start,period_end,limit_points,used_points,reserved_points | UNIQUE(employee_id,period_start)，员工每周公司保底使用上限；这是限制器，不是可以转赠的余额 |
| corporate_emergency_pool | id,period_start,period_end,limit_points,used_points,reserved_points,status,version | 独立公司月度紧急积分池，不能用公司普通保底额度代替 |
| emergency_authorization | id,approval_operation_key,task_id,employee_id,agent_id,allowed_model_ids,limit_points,used_points,reserved_points,valid_from,valid_until,status,approved_by | UNIQUE(approval_operation_key)，对获批任务限额，不是发放给员工的普通 Grant |
| provider_spend_budget_partition | id,budget_id,service_class,limit_amount,settled_amount,reserved_amount,version | UNIQUE(budget_id,service_class)，service_class=NORMAL 或 EMERGENCY；两类份额合计不得超过对应币种月度总限额 |

原 D01 的 provider_spend_budget 继续作为**公司按币种/月的总预算**。新设分区不再给同一请求产生新的外部费用：一次真实采购金额只记一笔，仅同步更新总预算和所属服务档分区的 settled/reserved。NORMAL 和 LOW 共用 NORMAL 分区，EMERGENCY 使用专门 EMERGENCY 分区。管理员调整份额不允许低于已确认+预留额，分区限额合计不得大于总限额，未知费用仍保留原分区预留。此结构是 D05 提案，不表示已执行迁移。

### 路由、优先级和资金预留

**NORMAL**：所选 Model 在正常员工来源中足额预留后才能派发；若是第三方收费 API，另锁定总 Provider 月预算 + NORMAL 费用分区，并双预算原子提交。

**LOW（降级）**：NORMAL 的上界预留失败先整体回滚，不允许部分扣费；管理员允许且 Employee-Agent/Agent-Model/Governance 再核验的廉价 fallback Model 与 Deployment 重新计算两种上界。新事务内按 D04 来源顺序先预留可用个人正常积分，不足部分预留公司 fallback_pool，并且**公司 fallback 部分的实际/预留值都增加 employee_fallback_weekly_cap**。同事务预留采购 NORMAL 分区（只有第三方收费 API）；若任意资金不足则不派发。即使价格变低后完全由员工个人积分支付，也仍然以 LOW 档排队，因为实际执行了降级选择。

**EMERGENCY**：验证 taskId、员工、Agent、允许 Model、有效期与批准状态；选择具体部署。新事务同时对 emergency_authorization 的任务余额和 corporate_emergency_pool 做授权/资金预留；若第三方收费 API，再同时对 Provider 总月预算及 EMERGENCY 份额预留原币种采购风险。不碰员工普通来源、TeamPool 或 corporate_fallback_pool。任务授权只限制可花上限，不能在审批时提前扣公司紧急池；与 Team Grant 成功发放即扣池不同。

**锁顺序**：先固定锁 invocation 的幂等行，随后按明确全局表级优先顺序锁 Provider 总预算、Provider 份额、公司资金池、员工周上限、员工普通桶/Grant、任务授权；在相同表内按主键排序。事务之间不可一个先锁 Employee、另一个先锁 Provider。完成确定资金和采购两套准入后提交，网络 I/O 不持锁。

### 最终结算与异常

LOW 使用真实冻结价按原 Allocation 顺序分配员工积分与 fallback_pool 的实际值，未使用预留完整释放；employee_fallback_weekly_cap 仅按公司 fallback 实际分担金额增加 used，释放原 reserved。EMERGENCY 一次实际消费同时更新任务 approved cap 和公司 emergency pool；采购费在总预算+该档分区各结算一次，不产生双份采购支出。若用户断开、费用可能发生而 usage 未知，则该次调用的所有 Points、任务授权、员工周上限和货币预算份额**同步待对账**。

紧急审批过期阻止新调用，但原已预留事务最终在原 task/期间结算；请求跨月以首次出站预留时归属的采购月份为准。付费硬预算不足不能因 Redis LOW/EMERGENCY 优先调度而出站。若第三方 Provider 可能违反上界导致外部真实超额，冻结相关币种预算并进行异常对账，不能隐藏差额。

### 管理与运行 API 追加（完整 DTO 仍需 P0 冻结）

- ADMIN：配置公司月度 fallback/emergency Points 资金池及对应员工周 fallback 限制策略；查询余额、预留、已使用和告警。
- ADMIN：创建/调整每个 Provider 原币种月度采购 NORMAL/EMERGENCY 份额，必须检验总额约束，更新有审计。
- 负责人提交/ADMIN 审批紧急任务授权（taskId、employee、agent、允许 Model、金额上限、有效期）；审批不预扣公司紧急池，实际 Invocation 才占额。
- Runtime 使用服务端受信任的获批 taskId 关联授权，不能靠任意请求体自称 EMERGENCY；向调用方反馈实际 model、serviceClass、traceId 和可用的受控错误信息。

**D05 业务方案已获用户认可**；资金表逐列 DDL、预算与审批完整 DTO、可核对的金额配置等仍在 P0 设计冻结范围。P1 未启动。

## 十四、P0-D06：紧急审批、三级队列与派发前资金预留（详细设计提案）

### 14.1 新增/精化关系表

**emergency_request（业务申请）**：
- id BIGINT PK；requester_employee_id、beneficiary_employee_id、agent_id、task_ref、reason_code、reason_description、requested_max_points、valid_from、valid_until、status、idempotency_key、created_at、updated_at。
- 状态 PENDING / APPROVED / REJECTED / CANCELLED；同一申请不可重复审批，idempotency_key 范围按 requester_employee_id 唯一，管理权限须符合 Employee 或 TeamManager 的真实角色。
- reason_description 为最小必要业务说明，禁止包含原始 Prompt 和密钥。

**emergency_authorization（已审批、不可任意覆盖的授权）**：
- id BIGINT PK、request_id BIGINT UNIQUE NOT NULL、beneficiary_employee_id、agent_id、task_ref、allowed_model_scope（建议独立关联表）、approved_limit_points DECIMAL(20,6)、used_points、reserved_points、valid_from、valid_until、status、approved_by、approved_at、revoked_at、policy_revision。
- 状态 ACTIVE / REVOKED / EXPIRED，实际能否用需以可信公司时区转换后的当前 UTC 时间校验。唯一有效任务键 Employee+Agent+taskRef，只允许同时一份未撤销/未到期授权；MySQL 不能简单依赖含 NULL 的唯一索引或无法表达的动态 WHERE 唯一约束，须显式设计活跃槽表或相应受锁申请状态保证。
- 不允许同一真实用户同时创建和批准同一任务（设计默认双人复核）。批准时不增加公司紧急池的 reserved/used；真正派发前预留资金才计入。
- 修改额度、Model 或截止时间创建新申请及新授权版本，不覆盖已有流水；REVOKED 阻止新派发，但此前已成功预留的 Invocation 仍按原授权结算或待对账。

**emergency_authorization_model**：authorization_id、model_id 联合主键，关联 LogicalModel；即使在此表中，也必须再通过 Employee×Agent、Agent×Model 和 Governance 策略的当前授权。

**invocation 扩展**：service_class NORMAL/LOW/EMERGENCY、emergency_authorization_id nullable、capacity_pool_id、enqueue_at、queue_deadline、capacity_lease_token（仅内部）、dispatch_intent_at、dispatch_at、funding_period_start、routing_revision、upstream_attempt_token、queue_outcome 和 traceId。记录执行与融资的**时间归属**，不信任用户自报的 class。

### 14.2 API 完整入口合同（本节新增部分）

- POST /api/v1/emergencies：Employee 或有授权的 TeamManager；请求体为 {beneficiaryEmployeeId,agentId,taskRef,allowedModelIds,requestedPoints,validFrom,validUntil,reason}，Employee 只能为自己申请；TeamManager 为被批准管理的员工/Agent 申请。返回 {requestId,status:"PENDING",createdAt}，相同申请人+Idempotency-Key 不能重复建单。
- GET /api/v1/emergencies?page&size&status&beneficiaryEmployeeId：Employee 只能看自己的，Manager 只能看授权范围内员工，Admin 可过滤全部。
- POST /api/v1/emergencies/{id}/approve：仅 Platform Admin；请求体 {decision:"APPROVE"|"REJECT",approvedPoints?,validUntil?,allowedModelIds?,reason}，需要 Idempotency-Key，审批人不可与 requesterEmployeeId 相同。批准金额不得超过请求上限、批准时间不得超出已审查的请求期限；返回 requestId、authorizationId、status、approvedLimitPoints 和有效期。审批必须为同事务唯一状态转移；重复批准只能返回旧授权而不重复创建。
- POST /api/v1/emergencies/{authorizationId}/revoke：仅 Platform Admin，{reason}；撤销记录 actor/时间/版本，阻止新入队及派发，已预留调用沿原账处理。
- GET /api/v1/emergencies/{authorizationId}/usage：获授权的受益员工/审批管理员查看批准/已用/已预留/剩余 Points 和预计失效时间，不显示原始 Prompt。
- Runtime POST /v1/chat/completions 如需紧急档，使用额外头 X-AIGate-Emergency-Authorization: <server-issued authorizationId>；服务端严格匹配已认证 Employee/Agent、task、允许 Model、状态和时窗，绝不接受 body 中的 serviceClass、employeeId 自报成为资金权限。没有头是普通路径；无效头直接 403，不静默走普通额度。

### 14.3 Redis 三档共享容量队列

每个实际物理推理池共享三个有界等待 ZSET（EMERGENCY、NORMAL、LOW）及一个 ACTIVE 租约索引；同档 FIFO，靠全局唯一序号（由同池 Lua/INCR 生成）排序，不能依靠多个网关各自本地时间决定先后。Redis key 使用 {poolId} 同槽，Lua 每次只做有限键数的检查/更新且不等待网络。

**设计默认：权重 EMERGENCY:NORMAL:LOW = 4:2:1**，每次释放许可时按加权轮转指针挑选有资格的下一档；该档为空可分配给其它档，同档按队首顺序。它只影响**名额授予次数**，不是绝对 GPU 计算时间/秒级 SLA。每员工和 Agent 有同时 WAITING/ACTIVE 数量限制，整个 Pool 有 maxWaiting/maxActive，等待时间超过上限必须取消；正在 RUNNING 的上游任务不得被低级别请求或新紧急任务抢占。

两个不同逻辑 Model/Deployment 共享 GPU 池必须引用相同 Pool；外部 Provider 使用自己的 RPM/并发/Token 约束，不调用内部 GPU 池队列。管理端更改权重、容量及版本时，通过已审计策略变更更新 Redis 快照；不受信的缓存状态不能自行放宽硬限额。

### 14.4 修正 D03 的先后顺序（避免排队锁定资金）

1. 认证与权限/内容前置校验；根据已存在的紧急授权或额度/降级策略初步决定请求档位和目标逻辑 Model。Redis 对 Employee/Agent 入口 RPM 作共享准入，负面结果不发 Provider。
2. 选定健康 Deployment 的容量池或外部 Provider 的受控并发通道，在 Redis 进入**有界等待队列**；此阶段只持有短期排队票，**尚未锁定员工积分、公司保底/紧急资金或采购币种预算**。
3. 调度器为请求取得 ACTIVE 执行许可后，再根据**此刻**身份禁用、Agent/Model 白名单、Governance 发布版本、紧急授权有效期、Deployment 状态和价格版本做最后校验。无法获批立即释放许可。
4. 在一个 MySQL 短事务内，按本次决定的 NORMAL/LOW/EMERGENCY 规则完成 Points、任务/员工周限制及收费 Provider 采购总月预算+对应 class 份额的原子预留。**派发时对应公司账务周/月**作为期间归属。如果无资金立即释放许可并拒绝，不向 Provider 发送请求。
5. 若原 NORMAL 路由因排队期间余额变化而不足，且仍允许 D05 LOW 付费保底，可在本次 invocation **最多一次**重新选择获批准的低价 Model，递增 routing_revision，重新检查权限/安全并进入 LOW 队列；不能重新派发已经发出上游的请求。
6. 写入唯一 DISPATCH_INTENT/attempt_token 并提交后，才出站发送一次 HTTP/SSE；金额已冻结。结果可信则原账结算、未知用量保持原账 pending；确认上游任务完成后释放容量。即使 Redis 自己已经丢失许可状态，也不能消除 MySQL 账务风险。

**并发原子性边界**：同一 Pool Redis Lua 保证该 Pool 的有限键状态一致，不声称跨 Redis Cluster 不同哈希槽的所有 Employee/Agent/Provider 限流键可用一个 Lua 跨槽原子修改。跨不同准入维度按确定顺序执行，失败不得留下可重复使用的容量租约；资金仍由 MySQL 统一保证。Redis 故障丢失队列/许可时新入场 fail closed，以 MySQL Invocation + 真实推理任务状态核验后恢复。

### 14.5 关联资金的一致性

- D05 公司 NORMAL/EMERGENCY 采购分区在**收到执行许可后**才开始预留，避免长时间等待占用紧急采购预留。
- 申请已批准不等于有积分保留；同时间多个获批任务可能争用公司紧急资金池，只有派发时原子预留成功者才实际开始，审批并不承诺一定有 GPU 或现金可用。
- 排队跨周/月以准许实际出站的派发时刻来判断额度所属期间；旧周/旧月已经成功预留的在途请求仍按 D04/D01 原期间结算。
- 撤销审批或安全策略升级发生在排队途中时，不得因为 Redis 之前允许入队就跳过派发前复检。
- 故障恢复不得仅根据 Redis 过期推断上游任务结束，也不得因审批撤销而对已出站未知账单直接退款。

**状态：D06 PROPOSED。** 审批双人复核、权重4:2:1、排队后预留资金和单次 LOW 重排是具体实现候选。所有 API 入参边界、默认超时及 Lua 脚本行为需通过设计一致性检查和测试后冻结。

4. 允许安全换部署的场景仅限可以证明**尚未发送任何上游请求字节**、没有产生可能收费的推理执行。换到不同 Pool 必须先按 lease token 归还旧许可，重新入队但不可延长最初的队列总截止时间。一个 Invocation 正常路由最多1次派发前重选（D06 单次跨逻辑 Model LOW 降级另有更严格的策略边界，不可相互叠加成无限循环）。
5. DISPATCH_INTENT 已持久化、上游可能已经收到请求但结果未知：不自动发往同一个或另一个 Deployment。若可靠证明没有发出而存在资金预留，才可经事务按原来源安全释放/取消；否则进入 PENDING_RECONCILIATION，保留真实价表和原预算预留。SSE 已流出时禁止透明拼接另一上游的输出。
6. HEALTHY 证据过期转 UNKNOWN 不是“永久冷启动死锁”：允许管理员授权的单并发有预算试运行（正常计费），成功后补充可信被动健康样本。第三方不提供免费非生成探测端点时，禁止为维持 HEALTHY 自动消耗采购月预算进行探测。

  "model": "model-code",
  "messages": [
    {"role": "system", "content": "简洁回答。"},
    {"role": "user", "content": "你好"}
  ],
  "stream": true,
  "max_tokens": 128,
  "temperature": 0.7,
  "stream_options": {"include_usage": true}
}
~~~

必填字段为 model、messages、stream、max_tokens；messages 是非空数组，初始设计每请求最多64条，整个请求 JSON 的 UTF-8 字节数设计默认不得超过64 KiB（可按经过测量的内存预算配置）。每条 content 必须为非空文本；role 限 system/user/assistant；max_tokens 为正整数并且不超过模型与实际部署所允许的最高输出 Token，输入不得超过受控上下文。temperature/top_p 为可选、且只有 Adapter 标记支持才能转发。stream_options 仅 stream=true 时允许；客户端是否提出 include_usage 不改变网关**对上游强制请求可信 usage**的要求。max_completion_tokens、n>1、logprobs、工具、多模态等不在首版合同内，统一拒绝而不是冒险额外收费。具体温度参数范围、代理兼容字段、单次字节上限和错误路径将在 P0 用 Fake Provider 契约测试冻结。

### 17.2 Provider Adapter 合同与可信度

每个 Deployment 保存接口协议版本、鉴权方案、请求字段映射、最大输入/输出/总 Token 硬界、stream usage 能力、usage 可信来源、支持的额外收费类别、错误码归类与安全终止方式。Adapter 只能选择由 Catalog 管理、通过 HTTPS/SSRF 白名单验证的 Endpoint；不得转发员工 Key/Agent Key 给供应商，实际供应商 Key 由密钥管理安全注入。禁止自动跟随危险重定向，禁止在日志记录 Prompt、Response、Provider 密钥或完整 Authorization。

无论客户端是否要求，支持此能力的 OpenAI 风格上游 SSE 都应发送 stream_options.include_usage=true。该协议常见的最后 usage chunk 中 choices 为空，随后才是 data: [DONE]；并非所有兼容 Provider 都实现此能力，必须按部署做兼容测试。Adapter 不得自己根据文字长度伪造 Token 统计；可以配置经过认可的供应商结算/对账来源。

**可信 usage 需满足**：来自允许的认证上游和受支持的契约，Token 值非负且符合 Provider 的字段关系；至少含 prompt_tokens 和 completion_tokens，若有 cached_tokens 只作为 prompt_tokens 的子集，不可再次加总；模型/请求关联能够对应本次 invocation，来源/版本可审计。遇到字段缺失、相互矛盾、费用类别不受支持、usage 格式错误或上游可能多收费用时，不能正常确认为0消费，转 PENDING_RECONCILIATION 或明确异常案件。Provider 出现的供应商请求 ID、实际 usage 证据摘要、证据类型与价格版本需保留，但 Prompt/完整 Response 不保存。

### 17.3 成本与预留上界

排队时只做前置身份/策略/资源选择，**不锁资金**。Redis 获得 ACTIVE 后，重验身份/模型/政策/Deployment，按 Server 能验证的输入 Token 最大值（受支持且版本匹配的 Tokenizer，或 Provider 真正强制的输入上限）与已明确的 max_tokens 输出上限、所有可能收费类别的最高合法单价，计算最大内部 Points 与第三方采购原币种风险，再通过 MySQL 同事务完成来源 Allocation 与外部采购预算（如果收费）。如果 Provider/Model 无法证明上下文上限/输出上限被实际执行，或包含不可计价的工具/多模态附加费用，**拒绝付费调用而不是低估风险**。

默认内部 POINTS 单价绑定 LogicalModel PriceVersion；第三方采购价绑定真实 Deployment + 原币种版本；自部署普通按内部积分，获批准本地基础保底按独立 Token 周额度；已有 D01～D07 的账务、Grant 过期、采购 NORMAL/EMERGENCY 份额和跨周/月结算语义均适用。客户端断开或上游返回错误不直接解除已可能发生费用的预留。

### 17.4 非流式 JSON 响应

无论 Provider 如何命名真实 remoteModel，客户端看到的是原 LogicalModel.code；返回对象至少为 id、object="chat.completion"、created（Unix 秒）、model、choices[{index=0,message{role:"assistant",content},finish_reason}]、usage（有效时有 prompt_tokens/completion_tokens/total_tokens 和获支持的明细）。正常 Model 生成完成但无可信用量时允许返回已经生成的纯文本结果，usage=null，同时账务 PENDING_RECONCILIATION，不得谎报已结算；响应头 X-AIGate-Invocation-Id 和 X-AIGate-Billing-Status 显示查询依据。对不受控错误返回标准安全 Error JSON，绝不透传 Provider 堆栈/Key 或 Prompt。

**注意**：HTTP 200 与生成完成并不代表已经入账。可信生成与会计结算使用不同状态轴；如数据库最终结算暂时失败，保留可恢复的 SettlementJob，不可把完整输出的请求变成“已经免费”。


### 17.5 SSE 下行协议与连接资源（规范化输出）

响应 Content-Type: text/event-stream; charset=utf-8，Cache-Control: no-cache，使用受控异步 Servlet 输出及有界线程/连接/队列资源。只有完成入口身份、Redis 排队准入、MySQL 预算预留、且确认可以建立受控上游 HTTP 调用之后，才向客户端提交 SSE 响应头，避免尚未确定的 401/402/429/503 变成不正确的 SSE 200。

使用标准 data: 开头、空行结尾的 SSE 帧，UTF-8 增量解析与 flush，不得缓冲整段回答才返回。网关把供应商特定模型名替换为当前逻辑 Model.code，并生成对客户端稳定的 Invocation ID；choices[0].delta 只允许受支持的文本与角色字段。一个正常流示例：

~~~text
data: {"id":"chatcmpl-gw-42","object":"chat.completion.chunk","created":1792620000,"model":"model-code","choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"id":"chatcmpl-gw-42","object":"chat.completion.chunk","created":1792620000,"model":"model-code","choices":[{"index":0,"delta":{"content":"你好"},"finish_reason":null}]}

data: {"id":"chatcmpl-gw-42","object":"chat.completion.chunk","created":1792620000,"model":"model-code","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: {"id":"chatcmpl-gw-42","object":"chat.completion.chunk","created":1792620000,"model":"model-code","choices":[],"usage":{"prompt_tokens":8,"completion_tokens":3,"total_tokens":11}}

data: [DONE]

~~~

以上为**格式示例而非真实计费证据**。支持 include_usage 的 Provider 最终 usage chunk 通常发生在 [DONE] 前，choices=[]，普通增量 chunk 里的 usage 通常为空。网关只有在收到真实可信的 usage 时才传播或转换该字段，不自行补造 usage。即使 Provider 已正常 [DONE]，若真实 usage 不存在，**[DONE] 仍可代表文本流正常结束，而账务标记 PENDING_RECONCILIATION**；客户端以 Invocation 查询接口获知最终账务状态，[DONE] 不保证结算成功。

客户端断开、发送失败、Provider 中途断线、JSON 分块不完整或网关总超时时：
- 尽力取消/关闭上游连接并释放网关资源；对 SELF_HOSTED 以真实推理服务停止确认决定是否释放物理并发许可。
- 上游可能已经收费/推理的，两种账务风险预留继续保持 PENDING_RECONCILIATION；不把“客户端没收到最终 token”判断成 Provider 没消费。
- SSE 已提交响应头后无法再合法改成 HTTP 502/504。尽量发送单个受控 data: {"error":{"code":"UPSTREAM_INTERRUPTED","message":"流式调用中断","traceId":"..."}} 事件并结束连接，**不发送虚假的 [DONE]**；若客户端已关闭无法送达错误帧，只在 MySQL 存安全状态并通过查询接口提供。
- 必须限制每实例并发 SSE 数、下游写入缓冲、最大单帧体积、上游连接/首 Token/两 Token 之间的空闲/总运行时长。客户端读取速度慢时在受控缓冲上限内背压，超过限制关闭连接、尝试取消并进入安全资金状态；**不允许内存无界累积**。
- 可发 SSE 注释心跳作为保活，但心跳不能被误当成 Provider 实际完成 Token，也不能刷新服务端对上游真正停滞的超时限制。
- 每个请求的 Redis capacity lease 由执行侧受控续期/释放；失去客户端不代表上游已停。响应关闭与账务结束、推理任务真正结束分别记录。

### 17.6 双状态轴、MySQL 持久化和幂等

**执行状态**：VALIDATED → QUEUED → ADMITTED → RESERVED → DISPATCH_INTENT → UPSTREAM_RUNNING → OUTPUT_COMPLETED / UPSTREAM_FAILED / CLIENT_DISCONNECTED / UNKNOWN_DELIVERY。状态转换单调，所有实际可能派发的尝试与同一 invocationId 绑定唯一 attempt_token。OUTPUT_COMPLETED 不表示财务完成。

**账务状态**：NOT_RESERVED → RESERVED → SETTLED / RELEASED / PENDING_RECONCILIATION / OVERRUN。待对账可凭可信 Provider 使用量或被证明的零收费证据转 SETTLED 或 RELEASED；不能靠定时器或 Redis TTL 直接清零。

推荐追加或确保存在以下持久信息：invocation.id, agent_id,employee_id,idempotency_key,payload_hmac,logical_model_id,deployment_id,route_policy_revision,service_class,started_at,dispatched_at,upstream_request_id,attempt_token,execution_state,billing_state,stream_last_chunk_at,stream_terminal_seen,usage_evidence_type,usage_evidence_digest,usage_received_at,provider_price_version_id,internal_price_version_id,trace_id,updated_at。外部请求唯一执行意图通过 (invocation_id,attempt_token) 唯一键限制，最终 Settlement/Ledger/Outbox 使用 invocationId/业务类型做唯一键去重。

**幂等策略（两个模式一视同仁）**：
- Idempotency-Key 的唯一业务作用域为已认证 agentId + employeeId + key。payload_hmac 使用服务端密钥对规范化后、去除无关空白的受控请求 JSON 及逻辑请求关键标识计算；不能只对低熵短 Prompt 使用未加密普通 SHA256 向外泄漏猜测。
- 首次 Key 原子创建唯一 Invocation；同 Key 不同请求内容返回409；同 Key 同请求只要存在未过期的幂等收据，无论 QUEUED/RUNNING/已完成/未知账务，**在幂等收据保护期内绝不派发第二次模型请求**。由于首版默认不存完整回复内容，重复的正常 JSON 和已完成 SSE 也返回409及安全 invocationId/status，而不是假装可以重放原响应。
- 客户端可以在 409 返回中得到 invocationId，使用 GET /v1/invocations/{id} 携带相同双身份 Key 查询自己 Agent 下的安全元数据（运行状态、账务状态、Model/Deployment、可信 Token、traceId、更新时间），不能看到其他员工/Agent 请求，也不返回 Prompt/全文/Provider Key。已取消/超时也不得以相同 Key 盲目重发。
- 已预留但尚未写入 DISPATCH_INTENT 的调用，经过持久化并发 fencing 和可证明没有出站的恢复流程才可 RELEASE；写下派发意图后网络发送不确定时，不得再次调用同一个或其他收费上游。
- 历史幂等收据与资金流水的保存期限必须覆盖全部可能的对账、审计及重复发送风险。第一版建议持久保留紧凑 key 哈希收据至少365天（待业务正式确定）；超过保存期不承诺无限期幂等，删除政策必须经审计和业务确认，不得任意定时删除未结算/未知账单记录。

### 17.7 错误映射与时限

入口未认证401、未授权/安全拒绝403、JSON/能力/参数错误400、积分/采购预算不足402、幂等冲突409、Redis速率/队列/并发限制429、上游无健康合规Deployment或共享服务异常503、上游延迟超限504、供应商协议错误502。只有在 HTTP 头未提交时才发送这些 HTTP 状态；SSE 启动后错误用数据帧/断连加查询接口表达，不能伪装HTTP成功结算。

初始部署默认上界（**配置提案**）：连接 5 秒、首 Token 30 秒、上游空闲 60 秒、整次推理 180 秒、下游每次写等待 10 秒，实际必须与自部署服务 maxRunMs、Provider 可承诺窗口、Redis lease 续期及账务风险上界相容。禁止无期限连接或无限等待；若某个受支持模型合法运行更久，应通过经过审批的 Deployment 配置提升限额并重新验证内存、并发、预算与测试，而不是在源码中无限放宽。

### 17.8 待统一冻结的接口与恢复问题

完整的 JSON DTO/错误码字典、Provider Adapter 的可信 usage 格式白名单、HTTP 配置超时、Input Token 上界验证流程、不同类别供应商 cache/其他 Token 定价、MySQL 表的所有外键与迁移顺序、持久化 invocationId 的外部格式、完整可执行测试 JSON 固件都要在 P0 全量审核冻结。当前 D08 是完整业务行为设计，**不是已经签发的本地 AI 开工合同**。

参考协议依据：OpenAI Chat Completions stream_options.include_usage 的最后 usage chunk 可能因断流缺失；vLLM 对 OpenAI API 提供兼容服务，但字段与独立部署的认证/任务控制必须实测。官方资料：https://platform.openai.com/docs/api-reference/chat/object 和 https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/ 。


## 十八、P0-D09：治理数据模型、接口、策略状态与安全决策合同（提案）

### 18.1 分类与权限矩阵（与业务文档 D09 一致）

effectiveClass = max(来自服务端的可信 Agent/业务数据标签, 本次完整 messages 扫描规则产生的类别)；客户端或 Prompt 声称 PUBLIC 无权降低。类别 PUBLIC<INTERNAL<CONFIDENTIAL<RESTRICTED，凭证高风险命中设独立的 hardDeny=true，不是能够通过提高可用积分解决的错误。

矩阵：PUBLIC→经批准第三方/本地均可；INTERNAL→第三方须 Agent明确授权+Provider/region批准，本地须受控部署；CONFIDENTIAL→第三方 API 拒绝，仅获准自部署、只支持 stream=false 和输出缓冲审查；RESTRICTED/高置信凭证→首版全部模型拒绝。即使同一 LogicalModel 的两个 Deployment 分别属于第三方/自部署，也应使用**各自具体 Deployment 的 egress 决策**，不只在 Model 层审一次就直接路由。

### 18.2 MySQL 持久数据（完整物理 DDL 待 P0 总冻结）

**governance_policy**：id BIGINT PK，company_scope_id BIGINT（首版单公司可为固定作用域），active_revision_id BIGINT NULL，version BIGINT、created_at/updated_at，UNIQUE(company_scope_id)。最后出站授权事务读取并校验这一权威指针，不用 Redis 缓存代替。

**governance_policy_revision**：id、policy_id FK、revision_no BIGINT、status DRAFT/UNDER_REVIEW/APPROVED/PUBLISHED/SUPERSEDED/REJECTED、base_revision_id nullable、config_json（只允许受校验的规则配置，不存任何 Prompt）、content_digest、created_by、approved_by nullable、published_by nullable、approved_at、published_at、created_at；UNIQUE(policy_id,revision_no)。发布后的 revision、对应 rule 集与关联的安全例外历史不可原地改写；新变更创建新版本并在短事务更新 active_revision_id。设计默认 reviewer 与 proposer 不是同一用户。

**governance_rule**：id、revision_id FK、rule_code VARCHAR(64)、rule_kind（CLASSIFY/SECRET_HARD_DENY/EGRESS_DENY/OUTPUT_REVIEW）、severity、detected_class nullable、expression_ref 或受审查的内置规则参数、exemptible BOOLEAN、enabled BOOLEAN、rule_order；UNIQUE(revision_id,rule_code)。不允许客户端上传未经审核的任意耗时正则；输入扫描必须有有界执行预算。禁止直接持久化敏感命中文本。

**agent_egress_approval**：id、agent_id、provider_id、allowed_data_class_max、allowed_regions（建议另建规范化关联表）、approved_by、valid_from、valid_until、status、policy_revision、created_at；同 Agent+Provider+region 的生效授权在业务事务上排除冲突。允许 INTERNAL 出外部的批准不是所有 Provider 自动生效；批准不取代 Employee-Agent/Agent-Model ACL。

**deployment_data_boundary**：deployment_id UNIQUE、approved_data_class_max、trusted_region、trust_mode、security_approval_status、approval_valid_until、provider_data_processing_approved、log_retention_policy_ref、approved_by、version；SELF_HOSTED 不因私有 URL 自动获 CONFIDENTIAL 能力。THIRD_PARTY_API 无允许级别/地区/数据处理审批则不参加实际路由。

**governance_exception_request**：id、requester_employee_id、employee_id、agent_id、logical_model_id、rule_code、reason_code、reason_text（不得放敏感 Prompt）、requested_valid_until、status PENDING/APPROVED/REJECTED/REVOKED/EXPIRED、reviewer_id、reviewed_at、created_at、policy_revision、idempotency_key；索引按 employee、agent、status、valid_until、rule_code。例外只允许经审核的 exemptible 误报检测规则，且必须匹配具体 Employee+Agent+Model；真实凭证 hard deny、RESTRICTED、可信来源数据标签及第三方出站不允许范围均不可豁免。审批人不得审批自己的例外申请。

**governance_decision_audit**：id、trace_id UNIQUE（如一次请求有多个派发前审查，另有 decision_phase/version 或复合 key）、invocation_id nullable、employee_id、agent_id、requested_model_id、deployment_id nullable、policy_revision_id、effective_class、decision（ALLOW/DENY/REQUIRE_BUFFERED_RESPONSE）、decision_phase（PREQUEUE/PREDISPATCH/OUTPUT_REVIEW）、matched_rule_codes（只存安全规则标识）、reason_code、input_hmac_digest、scanner_version、actor_type、decided_at、created_at。**不存 Prompt、回复、密钥、命中片段或声称可还原这些内容的非加密摘要**。安全审计与资金/Invoker 状态都可通过 traceId 关联，但不得以该 ID 作为 Prometheus 高基数标签。

### 18.3 管理 API 合同（仅管理员治理控制面）

- POST /api/v1/governance/policies/drafts：POLICY_EDITOR，body 含 {baseRevision,classificationRules,egressMatrix,outputReviewRules,reason}；返回 {draftId,revision,status:"DRAFT"}；拒绝未知规则类型、过大配置、危险正则、未受信任的任意程序代码。
- POST /api/v1/governance/policies/{draftId}/submit：POLICY_EDITOR，将 DRAFT 改 UNDER_REVIEW，返回版本和待审状态；同版本不得自批。
- POST /api/v1/governance/policies/{draftId}/publish：SECURITY_APPROVER 且审批者≠创建人，body {expectedActiveRevision,decision:"APPROVE",reason}；单事务批准并 PUBLISHED，旧版 SUPERSEDED、policy.active_revision_id 更新及操作审计，不发生部分发布；如果并发版本已变化返回409。
- GET /api/v1/governance/policies/active：受授权管理员只读已生效摘要、revision、允许来源/等级与 updatedAt；不返回可以泄漏规则机密的完整原文匹配字符串。
- POST /api/v1/governance/exceptions：Employee/合资格 Manager 请求只针对被标记可豁免的误报信号，body {agentId,modelCode,ruleCode,reason,validUntil}；不能提交原始泄漏内容。
- POST /api/v1/governance/exceptions/{id}/review：SECURITY_APPROVER，{decision:"APPROVE"|"REJECT",reason,expectedVersion}；不能自批，不能批准 hardDeny/RESTRICTED/来源可信分类或第三方禁止边界；审批记录不可抹除。
- POST /api/v1/governance/exceptions/{id}/revoke：SECURITY_APPROVER，reason，阻止后续派发；并发请求由派发授权点决定。
- GET /api/v1/governance/decisions?page&size&agentId&decision&from&to：POLICY_EDITOR/SECURITY_APPROVER/Platform Admin 的受控可视范围，只返回最小审计元数据；Employee 通过 GET /v1/invocations/{id} 查自身的公共安全拒绝类别，不查看敏感规则文本。
- Agent/Provider/Deployment 的数据处理批准信息通过 Catalog 管理 API 的明确安全审批入口写入，不能让普通 Agent 自己标记 permittedClass/region 或任意指定第三方端点。

### 18.4 实时评估、竞态与失败

1. **PREQUEUE**：双身份、模型权限、完整请求解析后，在接收网关内存中扫描**每一条消息**，得到分类与 hardDeny，按已发布策略判断候选类型和 stream 是否允许。RESTRICTED、凭证、禁止的 CONFIDENTIAL 第三方、CONFIDENTIAL stream=true 返回受控 403/422，**Redis 不进队、MySQL 不预留、Provider 收到0**。此阶段拒绝时记录最小审计。
2. **QUEUED**：Redis 只存 invocationId/归属 owner/截止/策略版本参考，不存 messages、匹配片段、EmployeeKey。原消息仅由接收 Gateway 进程有界内存持有并受统一请求截止时间约束。该实例崩溃时队列票据清理并将 Invocation 标记不再自动恢复执行，因排队期间尚未预留资金。
3. **PREDISPATCH**：取得 Redis ACTIVE 许可、确定最终 Deployment 后，重新获取 MySQL activeRevision；若从入队以来规则/部署安全边界发生变化，则**对仍在内存中的原始 messages 用最新策略重新分类并决定**。版本不一致、不存在有效批准、扫描器异常/超时、所选地域不合规则 fail closed，释放容量且不进行资金预留。
4. **同事务授权截止**：在财务预留与持久 DispatchIntent 授权提交之前，用 MySQL 对 governance_policy.active_revision 指针作已发布版本一致性校验，策略发布/撤销应当原子更新该指针。指针竞态不通过则回滚预留、禁止出站、重新评估或受控拒绝。数据库事务提交与随后的外部网络发送之间仍有时间差；该提交时刻是“已获批准在途调用”的业务边界，不能声称新政策对已提交发送意图的请求物理瞬时生效。
5. **OUTPUT_REVIEW**：CONFIDENTIAL 只允许已批准内部 Deployment + JSON buffered review；全文输出在安全内存里完成扫描，阻断则不返回正文（403/受控错误，或按实际已提交 HTTP 状态相容处理），仍应根据可信 upstream usage 正常结算或待对账。普通 PUBLIC/INTERNAL 的 SSE 不承诺流出前可审查完整内容。
6. **故障**：无已发布策略、MySQL 权威指针不可核对、部署安全批准失效、规则超时、Redis 队列异常均 fail closed。对新请求不把网络/策略错误称为免费已出站；已记录派发意图且费用未知则按 D08 保留资金待对账。政策修改不重写旧 Invocation 的已冻结安全证据。

统一安全错误（建议）：GOVERNANCE_DENIED / SENSITIVE_CONTENT_DETECTED 用 403 且不回显命中片段；BUFFERED_RESPONSE_REQUIRED 用422；POLICY_UNAVAILABLE 用503；POLICY_REVISION_CONFLICT 用409（管理面版本冲突，运行面可受控重评或503），所有返回安全 traceId。完整 DTO/错误体模板与权限枚举在 P0 API 字典一并冻结。

### 18.5 本地实现取舍及遗留合同

安全词库及确定性规则使用 Java 受限匹配即可完成真实可验证的初版，暂不引入外部 AI 审核/DLP/全文检索。不可承诺识别全部未知 PII/商业秘密，初版的保障来自业务可信标签+限制 ThirdParty API 出站+Rule 引擎+发布审批+审计的多道门禁。正式例外有效期、审计保留期、敏感区域、正则超时与内容分类由企业策略配置，不能随意猜测真实合规要求。**本节是待确认 D09 提案，当前不存在上述物理表和 API。**

## 十九、P0-D10：FinOps 事实、Outbox/Inbox、汇总与报表 API（物理设计提案）

### 19.1 职责与业务时间

四个**可核对的独立指标**：

- EMPLOYEE_USAGE_POINTS：成功结算的 Invocation 真正消耗积分，单位 POINTS，维度为 Employee、调用时主 Team 快照、Agent、LogicalModel、Deployment、FundingClass；附员工普通来源/企业 fallback/紧急承担份额，汇总的总额**不与份额再相加**。
- TEAM_GRANT_ISSUED_POINTS：已提交的 Team Grant 发放 Ledger，单位 POINTS，issuerTeamId 决定发放 Team 归属，recipientEmployeeId 只是接收者；消费、过期、补偿不重复记发行事件。
- PROVIDER_API_COST_ESTIMATE：有可信 Token usage 和采购 PriceVersion 时结算的第三方费用，供应商原币种、实际 Deployment/Provider，**不是供应商付款凭证**。公司 ProviderSpendBudget 总额和 NORMAL/EMERGENCY 分区只算同一个供应商采购事实一次。
- SELF_HOSTED_OPERATING_COST：有来源的自部署资源费用，例如 GPU 月租/折旧、能源/运维，按 resourcePoolId、原币种、servicePeriod、expenseCategory 统计；月租由分配到不同 Agent 的分析份额可以作为另一张**分摊视图**，不得和月租原始费用重复相加。

额外展示 LOCAL_FALLBACK_TOKENS_USED（自部署基础保底消耗的资源 Token）及 PENDING_RESERVED_EXPOSURE（权威账本的待对账积分/外币风险，分别展示并非 confirmed expense）。报表按公司配置 ZoneId 的业务日进行 bucket；调用结算的 usage/Provider 估算按 dispatchAt 所在业务日，Team 发放按 issuedAt，算力运营费按对应实际服务期间。对账很晚才拿到 usage 时仍修订原 businessDate；reportProcessedAt/observedAt 记录生成时间，用于解释迟到。

### 19.2 权威事件和发布队列表

**outbox_event**（P4/P5 就建立）：
- id BIGINT PK AUTO_INCREMENT；event_id CHAR(36) UNIQUE NOT NULL；business_event_key VARCHAR(192) UNIQUE NOT NULL（例如 INVOCATION_USAGE_SETTLED:invocationId:revision）；aggregate_type VARCHAR(48)、aggregate_id BIGINT、aggregate_revision BIGINT、event_type VARCHAR(64)、schema_version SMALLINT、company_scope_id BIGINT、occurred_at DATETIME(6)、payload_json JSON、payload_digest CHAR(64)；
- publish_state VARCHAR(20) NOT NULL（PENDING/CLAIMED/PUBLISHED/RETRY/QUARANTINED）、publish_attempts INT、next_attempt_at、owner_token VARCHAR(64)、lease_until、last_error_code、published_at、created_at/updated_at；
- 索引 (publish_state,next_attempt_at,id)、(lease_until,publish_state)、(aggregate_type,aggregate_id,aggregate_revision)。payload 只包含可公开给授权 FinOps 工作进程的业务ID、已确认数量、冻结价表引用、日期与最小维度快照；**不包含 Prompt/Response/Key/命中安全片段**。
- 账务/发放/运营费用证据事务同事务插入 outbox_event；禁止发送 MQ 后再补业务账本。一次 settlement 的 usage 与 Provider cost 如分别生成两个事件，使用不同 business_event_key，仍同一次权威账务事务写入，且对应的真实采购费用仅生成一份 cost fact。

**finops_processed_event**（Inbox）：consumer_name VARCHAR(64)、event_id CHAR(36)、schema_version、processed_at、PRIMARY KEY(consumer_name,event_id)。消费时先在同一 MySQL 事务内尝试 INSERT，主键冲突视作已处理、直接 ACK；正常事务同时产生 fact 与 aggregate，保证 crash 后重复投递不会多计。

**finops_fact**（重建依据的不可变派生事实）：
- id BIGINT、source_event_id UNIQUE、source_ledger_id 或 source_expense_id、source_revision、fact_type、business_date DATE、company_scope_id、employee_id NULL、usage_team_snapshot_id NULL、issuer_team_id NULL、recipient_employee_id NULL、agent_id NULL、logical_model_id NULL、deployment_id NULL、provider_id NULL、service_class NULL、currency CHAR(3) NULL；
- confirmed_points DECIMAL(20,6) NULL、employee_source_points DECIMAL(20,6) NULL、corporate_fallback_points DECIMAL(20,6) NULL、emergency_points DECIMAL(20,6) NULL、confirmed_amount DECIMAL(20,8) NULL、local_fallback_tokens BIGINT NULL、event_revision、created_at、processed_at；
- **source_rev 同名变更通过新的 correction event 和独立 fact 实现**。原事件不修改/删除。POINTS 事实只填 points，货币事实必须有币种；不同 metric_type 的值不得用一条模糊的 amount 混加。

**finops_daily_aggregate**：
- company_scope_id、business_date、metric_type、currency_or_unit、employee_id/usageTeamId/issuerTeamId/agentId/modelId/deploymentId/providerId/serviceClass 的归一化 ID（无该维度填**统一0哨兵，不使用 NULL 参与 MySQL 多列唯一键**）；
- confirmed_points DECIMAL(20,6)、confirmed_amount DECIMAL(20,8)、token_count BIGINT、fact_count BIGINT、updated_at；
- 唯一索引覆盖上述完整粒度（按实际查询审视索引宽度并使用受控 dimension_key/hash+碰撞校验方案可替代），**只为每个 event 生成一个对应粒度 aggregate 行**，不要为所有维度子集做指数级物化 Cube。查询按过滤条件 SUM/GROUP BY 聚合，可按真实压测增设常用 Team/Day 索引。
- 消费者在 Inbox+Fact+Aggregate 同一事务里 INSERT/ON DUPLICATE KEY UPDATE 原子增加对应指标值。更正事件的 delta 写到同业务日期原聚合键；原币种、归属和发生日期须来自对应原始可信 Ledger 快照。

**self_hosted_operating_expense**（拥有正式证据的权威运营费用）：
- id、resource_pool_id、expense_category（GPU_RENT/DEPRECIATION/ELECTRICITY/HOSTING/OPERATIONS）、service_period_start/end UTC、currency、amount DECIMAL(20,8)、source_kind（CLOUD_BILL/RENTAL_CONTRACT/ACCOUNTING_ADJUSTMENT）、external_source_ref、evidence_digest、status DRAFT/APPROVED/VOIDED、source_revision、approved_by、created_by、approved_at、created_at；
- UNIQUE(source_kind,external_source_ref,resource_pool_id,expense_category,service_period_start) 或由正式企业费用单 ID 做更严格去重，防止同一云账单重复导入。只有 APPROVED 版本才能写 SELF_HOSTED_OPERATING_COST 事实/Outbox。VOID/更正需要反向引用原凭证的新调整事实，不能修改已发布历史。
- 防止同一台租赁 GPU 同一期间同时按 GPU_RENT 和 DEPRECIATION 重复登记同一种经济成本；配置 expenseCategory/会计来源互斥检查。分摊的资源池/Agent 费用另建 allocated_view，必须符合 allocation sum = 原批准总额（原币种、同资源服务期间、精度误差可核对），在公司原始总额中不再重复加总。

### 19.4 Outbox Relay / Consumer 状态机及事务

**Relay**：以 SELECT FOR UPDATE SKIP LOCKED 按到期/ID 顺序短事务 claim 一批 PENDING/RETRY 或 lease 过期 CLAIMED 行，写唯一 ownerToken、leaseUntil、CLAIMED 并提交。通过 Spring AMQP 发布持久消息到 durable exchange/queue，强制 mandatory routing，关联 eventId publisher confirm + returns；只有 broker ACK 且没有 returned message 才以 eventId+ownerToken 条件更新 PUBLISHED。失败/超时/无 route 则有限次数 RETRY/QUARANTINED 并有指数退避/告警，不能在长 MySQL 事务内等 RabbitMQ。Lease 过期后另一 relay 可重领并重复发布**同 eventId**。Relay 重试不创建新的业务事件，不重新扣 Points。

**Consumer**：RabbitMQ manual ack、有限 prefetch。解析 V1、校验来源后用 Inbox 唯一键 + finops_fact + finops_daily_aggregate 在 MySQL **同一个事务**提交，之后 ACK。同 eventId 重投只 ACK 不再加总；可恢复错误按有限次延迟重投，确定永久错误进 DLQ/隔离后发报警，不默认 ACK 丢掉。相同原始事实修改仅能使用 revision + correction delta（或受控全量重建），不能消费者看到同一 eventId 就自行改算。

**一致性与顺序**：跨不同 aggregateId 的 MQ 消息可乱序，同一个 aggregateId 亦不应把 Broker 到达顺序当业务真相。报表事实有 source revision，纠错事件须有前驱事实存在或等待/回补处理，不得先对尚未出现的旧事实应用 delta。Outbox/Inbox/聚合是“至少一次发送、最多一次数据库投影效果”，不宣称物理 RabbitMQ exactly-once。

### 19.5 查询和受控运维 API

- GET /api/v1/finops/summary?from=2026-10-01&to=2026-11-01&teamId=5&currency=USD：ADMIN/FinOpsReader 的获授权公司/Team 视图；返回 {dateRange,metrics:[{metricType,unit,currency?,confirmedValue,serviceClass?}],analyticsProcessedAt,oldestPendingEventAt,pendingEventCount,readModelStatus}。不得把 POINTS/不同币种值合并显示一个金额；无币种参数时按币种分别列行。
- GET /api/v1/finops/trends?from&to&granularity=DAY&metricType&teamId&modelId&providerId&currency：按业务日汇总，支持分页或有界日期跨度，缺少真实自部署运营成本为无证据/未配置，不得填0并宣称实际成本为0。
- GET /api/v1/finops/facts?page&size&metricType&employeeId&agentId&providerId&serviceClass：分页查已确认事实的受控安全摘要、源账本引用和原业务日；FinOps Reader 权限限域，Team Manager 和 Employee 使用自身专属视图不跨团队泄漏。
- GET /api/v1/finops/pending-exposure?currency&serviceClass：直接**查询 MySQL 权威 Reservation/ProviderBudget** 得到 points/currency 独立待对账风险与 OVERRUN，返回 source=AUTHORITATIVE_LIVE；这不是异步确认费用统计。仅 Admin/获准 FinOps。
- POST /api/v1/finops/operating-expenses：ADMIN 经财务审批身份提交自部署算力费用草稿及引用凭证（金额、币种、resourcePool、servicePeriod、sourceRef）；POST /api/v1/finops/operating-expenses/{id}/approve 由有权人员审核，确认后在 MySQL 同事务写费用事实及 Outbox。明确避免重复来源/重复折旧与租赁。
- GET /api/v1/finops/outbox-status：仅 Admin 读取待发/最老待发时间/隔离数/消费积压与读模型过期状态，不暴露 raw payload；受控重投隔离记录需要审计及源事实版本校验，不能由管理人员任意伪造费用 event。
- POST /api/v1/finops/rebuilds（ADMIN，带审核理由、幂等键与版本）：异步在独立读模型版本中从**权威财务事实**重建、比对后切换，不能在线删除权威账本或直接清空唯一已处理ID 造成双计。

**同日迟到事件**：report analyticsProcessedAt 只是最近成功消费/聚合时间，**不是严格保证所有早于此刻事件都已处理的无缺口 watermark**。同时显示 oldestPendingEventAt、pendingCount、DLQ/隔离状态及 readModelStatus (FRESH/DELAYED/REBUILDING/UNKNOWN)，否则容易把缺少事件伪装成0。

### 19.6 约束与仍需冻结的参数

财务更正 API 必须通过权威账本/审批而非直接改 FinOps 聚合。运营费用来源证据与审批人角色如何对接真实公司会计系统需要单独确认；无公司云费用源可以仅用 Fake 数据验收，并标明非真实 GPU 成本。分区设计、Outbox relay 每批数量、lease/backoff/retry 上限、MQ durable/quorum 类型、Fact 维度索引、财务证据保留期及完整 HTTP 错误 DTO 等要在 P0 统一冻结，当前没有物理表或 RabbitMQ 工程。
