# 管理API · P1～P3（组织、运行身份、Catalog）

> 文档性质：**唯一实施合同候选**。所有字段、API、状态、错误、鉴权由Core授权校验，严格遵循[API总约定](../06-api-design.md)。P1/P2已有真实本地回归，P3最终结果以[Progress](../10-progress.md)和对应测试报告为准。

## 1. P1～P3接口总合同


 > **规范权威**：P1～P3请求/响应以本API分册和[API总则](../06-api-design.md)为准；真正的列、索引、状态及迁移分别以[Core V1](../database/core-v01.md)、[Core V2](../database/core-v02.md)、[Core V3](../database/core-v03.md)为准；Gateway方法以[白名单](./gateway-routes.md)为准。历史Dxx草稿不再作为实现优先级。仅 P1～P3，本节**不代表 FZ-02 全部 P1～P12 已完成**。下列 JSON 均为合法性测试 fixture，ID、时间与价格是假数据，不是生产事实。

## 无例外的序列化、鉴权与幂等规则

- 外部 JSON 以 camelCase；DB snake_case 只在 Mapper/SQL；JSON body 必须是对象，禁止未知字段、重复 JSON key、非有限数、科学计数 ID、把数字放在字符串字段或把布尔写成字符串；必填字段不能缺省或 null；可选字段**缺省**代表不修改，显式 null 禁止用于 P1～P3 PATCH（不提供清空能力）。所有 POST/PATCH JSON 请求声明 Content-Type: application/json。无 body 的 PUT/DELETE/GET 不接受有业务含义的 JSON body。
- ID 使用 JSON 正整数，Java Long，DB BIGINT UNSIGNED 虽可大于 Long.MAX_VALUE，但应用必须拒绝超出 Java Long 的请求/已分配 ID（部署增长达到边界前需独立 ADR）；version/expectedVersion 为从0起的非负长整数，不允许负数、浮点或字符串；响应时间统一 UTC ISO-8601 Z，缺省可空字段统一显式 null（不因 Jackson NON_NULL 配置随机消失）；分页 page从1起、size 1～100、默认20，id ASC，total 是**权限过滤后**的总数。
- P1～P3 管理入口一律通过 Gateway 显式 path+method allowlist → Core 自身 mgt_ 有效凭证、ACTIVE Employee/Team、当前 ROLE scope 鉴权。P1 Bootstrap 仅允许 bst_ 且运维模式/来源也要匹配。P2/P3 当前只有 GLOBAL PLATFORM_ADMIN 写/读相关安全资源，P1 TeamManager 只保留已明示的 Team/Employee 只读范围。网页/API 的 id/path/teamId 不能代表授权事实。
- 通用失败格式 `{"error":{"code":"VERSION_CONFLICT","message":"The resource was modified","requestId":"r-001","retryable":false}}`；400 输入类型/字段非法，401 所有无效/吊销/过期管理凭证，403 已认证但越权或禁用，404 可见范围内资源不存在，409 唯一键/版本/无效状态冲突，503 依赖无法安全完成。不得返回 SQL、Hash、ProviderSecret、Core URL 或不同 Key 是否存在的侧信道。
- P1 创建管理 Key、P2 创建/轮换 agk_/empk_、Bootstrap 两个运维动作：Idempotency-Key 为8～128可见 ASCII，业务物理唯一作用域按 V1/V2 表已有 UNIQUE；**同一签发者跨 Owner/操作复用 key 也不得另签密钥**。重复相同键签发返回409 KEY_ALREADY_ISSUED_NOT_REVEALABLE（Bootstrap 可用 IDEMPOTENCY_REPLAY_NOT_REVEALABLE）；不同 body 同键冲突409 IDEMPOTENCY_CONFLICT，均不能再次回显秘密。管理普通修改必须记录同事务审计；PUT 授权及 DELETE 撤销使用目标关系唯一键，重复为204/204（首次 PUT 为201）。
- 创建资源 201 返回对象；普通 PATCH 200 返回新对象且 version+1；单查200；分页200 Page；DELETE/幂等重复授权204**无响应 body**。除首次凭证签发201外的所有响应不得出现 `key`、`secret`、`encryptedSecret`、`secretDigest`、`pepper` 字段。敏感201和403/401均添加 Cache-Control: no-store。

## P1 实体 DTO、所有写操作 Body

**安全 DTO（响应白名单）**：
- `TeamDTO`：`{id:long,name:string,status:"ACTIVE"|"DISABLED",version:long,createdAt:instant,updatedAt:instant}`。
- `EmployeeDTO`：`{id:long,employeeCode:string,displayName:string,primaryTeamId:long,status:"ACTIVE"|"DISABLED",version:long,createdAt:instant,updatedAt:instant}`。
- `RoleAssignmentDTO`：`{roleCode:"PLATFORM_ADMIN"|"TEAM_MANAGER"|"FINOPS_READER",scopeType:"GLOBAL"|"TEAM",scopeId:long}`；不暴露内部 row id 或多态审计。
- `ManagementCredentialMetadataDTO`：`{id:long,keyPrefix:string,expiresAt:instant,revokedAt:instant|null,createdAt:instant}`；首次签发 `IssuedManagementCredentialDTO`：`{credentialId:long,key:string,keyPrefix:string,expiresAt:instant}`。
- `AuditMetadataDTO`：`{id:long,actorType:string,actorId:long,action:string,targetType:string,targetId:long,changedFields:string[],traceId:string,occurredAt:instant}`；`changedFields` 来源 DB changed_fields_json，但只包含**字段名**，不包含新旧敏感值。
- `Page<T>`：`{items:T[],page:integer,size:integer,total:long}`；空集 items=[]、total=0；`/me/profile` 响应 `{employee:EmployeeDTO,roles:RoleAssignmentDTO[]}`。

**Bootstrap 双运维 API**：POST /api/v1/bootstrap/initialize 必填 `{teamName:string,employeeCode:string,displayName:string,managementKeyExpiresAt:instant}`；POST /api/v1/bootstrap/recover-management-key 必填 `{targetEmployeeCode:string,managementKeyExpiresAt:instant,reasonCode:"ADMIN_KEY_LOST"}`；两者都要独立 bst_、Mode、运维网段、Idempotency-Key。首次初始化201 `{team:TeamDTO,employee:EmployeeDTO,managementCredential:IssuedManagementCredentialDTO,initializedAt:instant}`；恢复201 `{employeeId:long,managementCredential:IssuedManagementCredentialDTO,recoveredAt:instant}`。已初始化再次INIT=409 BOOTSTRAP_ALREADY_INITIALIZED；普通 mgt_ 不可调用这两个运维端点。这里的返回结构只增加公开安全 DTO，不要求数据库新字段。

## P2 双运行凭证和 Agent ACL 字段闭合

**响应 DTO**：`AgentDTO={id,applicationCode,displayName,ownerTeamId,status,version,createdAt,updatedAt}`；`KeyMetadataDTO={id,keyPrefix,validFrom,expiresAt,supersededAt,graceExpiresAt,revokedAt,createdAt}`（后三时间可为null）；`NewKeyDTO={credentialId,key,keyPrefix,validFrom,expiresAt,oldCredentialGraceExpiresAt}`（非轮换场景 oldCredentialGraceExpiresAt=null）；`AgentEmployeePermissionDTO={employeeId,agentId,status,version,grantedAt,revokedAt}`。所有P2 Key明文只在201出现，Agent与Employee Key分别有独立Pepper及 DB 唯一签发键。

**所有P2签发/轮换** `expiresAt` 必须在 Core now+1h～90d，签发者+Idempotency-Key 在 **agent_api_key** 或 **employee_credential** 各表唯一；旋转锁 Owner →旧凭证并写新凭证与旧 grace 同事务；旧与新最多两把当前可认证的Key，若超过则409 KEY_LIMIT_EXCEEDED。禁用 Agent/Employee/归属 Team 使该主体两类Key即刻不能通过下一次认证，但不会物理删除签发记录。ACL只能由管理员PUT/DELETE修改；只改变Key不授予ACL。

~~~

`POST /agents/11/keys` 带 `Idempotency-Key: demo-issue-0001`，body `{"expiresAt":"2026-11-01T00:00:00Z"}`，首个201允许一次 `{"credentialId":18,"key":"agk_<REDACTED_TEST_SECRET>","keyPrefix":"agk_test","validFrom":"2026-10-22T03:01:00Z","expiresAt":"2026-11-01T00:00:00Z","oldCredentialGraceExpiresAt":null}`；此处占位字符串**不是**真实CSPRNG Key，自动化测试必须现场生成真随机模拟值，不允许将占位值作为生产密钥。重交同键409，明文不回显，DB只存digest/keyPrefix。

## P3 Catalog 字段白名单、价格发布与凭证遮蔽

**通用列表/单项**：表中资源的 GET 返回各自白名单 DTO/ Page，ID、status、version、createdAt、updatedAt 与 Core 权威列一致，不返回 encryptedSecret/iv/明文密钥。价格草稿DTO返回 `{id,revision,status,pointPer1kInput,pointPer1kOutput,effectiveFrom,publishedAt}` 或采购DTO `{id,revision,status,currency,amountPer1kInput,amountPer1kOutput,effectiveFrom,publishedAt}`；所有 Decimal **固定刻度字符串**：POINTS 六位、采购八位，草稿有效时间 null。父对象 `activePointsPriceVersionId` / `activePurchasePriceVersionId` 可null且须匹配所属同一父对象已发布价。

**P3响应白名单**：Deployment默认返回仅`capabilityRevision`与`hasApprovedAdapterCompatibility`等安全metadata，不回完整adapterCompatibility内部配置/证据链接原文；受控管理调试接口可在同一现有GET单项经ADMIN权限显示不含秘密的校验结果，**任何普通Agent/Employee不获未经批准的Provider内部识别信息**。ProviderDTO=`{id,code,name,hostingMode,status,version,createdAt,updatedAt}`（host policy及审批细节只允许单独受控管理员读取，不作为安全默认的普通列表字段）；LogicalModelDTO=`{id,modelCode,displayName,modelFamily,immutableModelRevision,capabilityProfile,status,activePointsPriceVersionId,activeRoutingRevisionId,version,createdAt,updatedAt}`；DeploymentDTO=`{id,logicalModelId,providerId,deploymentCode,remoteModelName,hostingMode,regionCode,capabilityRevision,costModel,status,routingPriority,routingWeight,maxConcurrent,capacityPoolId,activePurchasePriceVersionId,hasActiveCredential,hasApprovedAdapterCompatibility,version,createdAt,updatedAt}`（默认不回显完整 endpointUri；如运维确需看经批准的host，由单独管理员安全只读元数据授权）；ProviderCredentialMetadataDTO=`{id,deploymentId,credentialKind,credentialRevision,status,createdAt,rotatedAt,revokedAt}`；AgentModelPermissionDTO=`{agentId,modelId,status,version,grantedAt,revokedAt}`。可空字段按53.1用null明示。

**兼容约束（不得让实现AI选择）**：
1. `baseUrlHostPolicy` 与 `capabilityProfile` 严格使用本册下方 v1 封闭结构，全部字段必填，禁止任意 Map 透传。P3 的安全 endpoint SSRF 校验须先在登记时执行，P7 在使用时再次解析域名/IP检查。
2. Deployment 允许在 DRAFT/ACTIVE/DISABLED/MAINTENANCE 间以 expectedVersion 更新；每次进入 ACTIVE 必须验证 Model/Provider 当前 ACTIVE 状态、可证明的Endpoint和受支持能力、必要的密钥和已发布价格，不应将 ACTIVE 当成 P6 已批准的机密数据许可。历史价格旧PUBLISHED 不修改；current pointer 用父Version CAS，避免两管理员都发布成功。
3. P3 缺少真实 Provider 价格的测试系统可以用**假配置价格**检验草稿/发布，但这不是授权真实付费调用。没有可验证费用上界/可信用量时 P7 一律422 BILLING_BOUND_UNVERIFIABLE，不因测试常数冒充采购价。
4. D44 仅列出资源集合，不是方法规范：**本节 method/path 是 P1～P3 Gateway 的显式注册清单**；同一路径 GET+POST 必须分别允许指定方法，未列出的方法返回405（不暴露内部路由）；所有 `/internal/**` 仍然不可公网代理。

这个 Fixture 假定 ModelVersion 在进入发布前仍为0；并发发布旧 expectedModelVersion 必须409 PRICE_VERSION_CONFLICT。额外写入 `effectiveFrom` 或把 `pointPer1kInput` 传为 JSON number 均400；已发布 revision 再修改价格不开放 PATCH/PUT 路由。



## 2. Catalog结构化JSON与ProviderSecret幂等


**修订原因**：D45 首次跨表/API 校对发现两类真正的实现缺口：（1）`provider.base_url_host_policy` 与 `logical_model.capability_profile_json` 仅声明 JSON 数据类型，会迫使执行 AI 自创安全配置格式；（2）D33 强制所有 Secret/Key 创建操作有幂等保护，而 V3 原 `provider_credential` 仅有 (deployment_id,credential_revision) 唯一键，不足以防**同管理员跨Deployment、跨revision重复提交同一创建命令**。本节直接把 V3 规范 DDL 修正为多四列 + 一个复合唯一键 + Employee FK/CHECK（已同步修改上文 D31 的规范 SQL），**仍然是Core V3同一张表，Core 55 表设计总数不变**。这些列已包含在本次首次实际交付的V3迁移中，没有改写已运行V1/V2；V3上线后只能通过新Flyway迁移演进。

## baseUrlHostPolicy v1（P3 Provider 创建/安全更新）

该字段**只允许**以下结构；未知成员与显式 null 一律400，不能直接把外部任意 Map 转入路由：

~~~json
{
  "schemaVersion": 1,
  "allowedHostnames": ["api.vendor.example"],
  "allowedPorts": [443],
  "tlsRequired": true,
  "allowPrivateNetwork": false,
  "approvedPrivateCidrs": []
}
~~~

- `schemaVersion` 必须是 integer 1；`allowedHostnames` 为 1～32 个去重后小写 ASCII IDNA规范化的**准确 FQDN**，每项1～253字节，禁止IP字面量、`*`/通配符、用户信息、URL scheme/路径、尾部点歧义与空字符串；不按任意子域 suffix 自动放行。`allowedPorts` 1～8 个 1～65535整数并去重；`tlsRequired` 固定 **true**；`allowPrivateNetwork` 是布尔；`approvedPrivateCidrs` 为0～16个经安全管理员审查的 CIDR 文本。
- THIRD_PARTY_API 固定 `allowPrivateNetwork=false`、`approvedPrivateCidrs=[]`、端口首版只允许443；禁止 loopback/link-local/RFC1918/IPv6 ULA/metadata IP、DNS rebinding 与代理绕过。SELF_HOSTED 可以 `allowPrivateNetwork=true`，但必须非空的 `approvedPrivateCidrs` 和受控部署网络，不允许把 `0.0.0.0/0`、`::/0` 或云元数据服务视为安全网段。这些 CIDR 在 HTTP 中只是申请配置；可信批准来自下述 Core 启动注入的 Catalog Approval Manifest。管理请求及其审计事件不能自动变成审批事实。
- 登记时校验 `endpointUri` 的 HTTPS/hostname/port 与 Provider 当前策略匹配；P7 **每次连接及每次DNS解析后**校验所有 A/AAAA 结果落入真实批准 IP 范围，禁止HTTP自动跟随重定向、禁止自定义用户代理/代理变量绕过受控解析和连接地址核验。只在P3登记做DNS检测无法对P7派发时的 DNS rebinding 给出安全保证。
- Policy变更必须 P3 管理 Service 锁 Provider + 受影响 ACTIVE Deployment 才允许；若更新后任一 ACTIVE Deployment 的端点或批准摘要不再有效，返回409 HOST_POLICY_CONFLICT，保持原配置；管理员需先停用受影响部署再变更，不以配置更新绕过 P6 未来治理。真实网络栈的连接前校验依赖真实测试，P0只冻结协议。

## capabilityProfile v1（P3 LogicalModel 固定模型能力）

~~~json
{
  "schemaVersion": 1,
  "chatCompletions": true,
  "streaming": true,
  "toolCalling": false,
  "maxInputTokens": 4096,
  "maxOutputTokens": 1024,
  "maxTotalTokens": 4096
}
~~~

- 全部七字段**必填、无 null、无额外字段**：`schemaVersion=1`；`chatCompletions=true`（现阶段仅实现聊天补全）；`streaming` 布尔；`toolCalling=false`（当前网关**不编排**工具调用；后续只有新协议/ADR 才能改变）；`maxInputTokens`、`maxOutputTokens`、`maxTotalTokens` 是1～2,000,000的正整数，满足 input≤total、output≤total。上例为**仅测试元数据**，不声称特定供应商实际上限。
- 真正使用时必须同时受 Deployment `capabilityRevision`、实际Provider Adapter 测试证据、真实上下文窗口和客户端 `max_tokens` 约束；`capabilityProfile` 不是受信 tokenizer，也不是自动可计费的证明。P7 对不可证实的输入/附加类别风险上界拒绝收费出站；P6 安全政策仍优先于能力声明。P3 PATCH 不开放修改此JSON，语义变更需新 Model 身份/受控新Revision与 ADR。
- `routingWeight`、`maxConcurrent` 属 Deployment 的路由/容量元数据，**不**出现在 Model capability JSON 中；AgentModel授权针对逻辑 Model，而不是一张 JSON 里的任意字符串。

## ProviderCredential 请求幂等权威、错误与审计

V3规范表新增 `issued_by_employee_id`、`issue_idempotency_key`、`issue_request_hmac`、`issue_hmac_key_id`。POST /api/v1/deployments/{id}/credentials **必须**带 Idempotency-Key 8～128 可见ASCII，唯一作用域精确为 `(issued_by_employee_id,issue_idempotency_key)`、**跨 Deployment/credentialRevision 仍然互斥**。同 Actor/Key 首次创建：先锁 Deployment 父行→查询并锁签发 receipt→检查目标版本与当前 ACTIVE 凭证→生成 AES-GCM ciphertext/nonce→插入 credential 与审计→更新父 active_credential_id 并递增父 version（仅选择当前凭证，不自动将 DRAFT/DISABLED 变成 ACTIVE）→一次本地事务提交，201 只回安全 Metadata；事务回滚不得返回创建成功。

`issue_request_hmac` 使用**Core内部独立的 ProviderCredentialIssue Pepper**（不同于加密主密钥、管理Key/运行Key Pepper）对 **canonical(HTTP method, deploymentId, credentialKind, credentialRevision, secret存在性及其原字节, 已认证的签发者)** 算HMAC-SHA256；`issue_hmac_key_id` 保存用于合法轮换后验证旧收据的密钥版本。**不**存明文 secret、普通 SHA256 短Secret摘要或可反解请求原文。相同Actor+Key+相同HMAC重放200原安全Metadata，绝不重新加密/创建/换激活指针；不同HMAC重放409 IDEMPOTENCY_CONFLICT。另一管理员的相同RawKey在物理上独立，仍须按 Deployment 行锁/credentialRevision 唯一键判冲突。持久 receipt 至少覆盖凭证的有效历史审计期，不因撤销即删除。

- NONE 凭证仅允许真实经安全批准的无鉴权 SelfHosted；`secret` 缺省且不得null/空字符串。BEARER/API_KEY_HEADER 必须是受控长度1～4096 UTF-8字符串，禁止 JSON null/空串，Core只保存AES-GCM密文/IV/加密KeyId。V3数据库不能静态检查密文字节对应合法供应商凭证，靠 Service 字段校验、端到端 Fake Provider 验证。
- P3 部署状态为 ACTIVE 并不自动许可真实HTTP：P6治理、P7双身份/两ACL/双预算、一次性Permit都还未上线。凭证吊销引发当前 active 指针不可用时须通过父锁/CAS使新出站拒绝，保留旧凭证的历史证据。
- **锁序与响应一致性验证**：两并发相同Actor+Key仅一条 provider_credential 和一次审计；相同Key不同 Deployment/revision 返回409；不同Actor同 Deployment+revision只允许一个成功；两次同请求不再次暴露secret；实测使用MySQL8.4和真实加密/签名库，当前状态全部 NOT RUN。

## P3 实施闭合合同（2026-10-26）

本节由用户明确授权补齐，服务端 ID、独立批准、密钥配置和价格事务是当前实施合同；不增加 V3 表，不提前引入 P6/P7 的治理、资金或出站能力。

### Deployment 创建和适配配置

- 创建请求的 `adapterCompatibility` **不允许 deploymentId**；Core 在同一事务内取得自增 ID 后回填持久 JSON 的 deploymentId。客户端不能指定、预占或更换它。其余字段按 [Adapter 协议](../protocols/provider-adapter.md) 封闭校验，未知/缺失/null 字段400。
- `remoteModelIdentity` 固定为 `modelCode + "@" + immutableModelRevision`，真实端点别名由 remoteModelName 单独绑定；不同型号或修订不能靠 OpenAI 兼容协议混为同一 Model。maxInput/Output/TotalTokens 为1～2000000且不超过 Model 对应上限；supportsJson=true，支持 streaming 时 Model 也必须支持；两种 usageEvidenceMode 分别匹配 THIRD_PARTY_API/SELF_HOSTED。tokenizerId<=128、tokenizerRevision/compatibilityRevision<=96，非空且无首尾空白。compatibilityRevision=capabilityRevision，evidenceRef=adapterEvidenceRef，引用最长256、无秘密，verifiedAt 为不晚于 Core 当前时刻的 UTC 微秒时间。
- billingCategories 精确为 INPUT_TOKENS、OUTPUT_TOKENS；extraChargesPossible/providerSupportsIdempotency 必须 false；其它枚举取值以 Adapter 协议为准。缺可信批准可登记 DRAFT，不能 ACTIVE。`hasApprovedAdapterCompatibility` 纳入 DeploymentDTO 精确白名单，其含义只是当前配置匹配尚未到期的批准证据。
- Provider/Model/Deployment code 采用大写字母开头的 `[A-Z][A-Z0-9_-]+`，上限分别64/96/96。名称、family、immutable revision 长度按 V3 列。PATCH 不接受不可变字段，返回400；重复 code 为409 DUPLICATE_RESOURCE。
- Endpoint 仅 HTTPS、精确 FQDN 和允许端口，禁止 userinfo/query/fragment、IP字面量、通配符及歧义路径。登记和 ACTIVE/eligibility 检查重新解析**全部** A/AAAA；解析超时或失败503。禁止 loopback、link-local、metadata、保留/组播地址；SELF_HOSTED 私网只允许落在声明的 RFC1918/ULA CIDR，且进入 ACTIVE 还要命中批准清单。DNS 校验不复用应用层上一次放行结论；JDK/OS DNS缓存可能延迟外部变化观测，P3不承诺连接级IP固定。检查不打开 HTTP 连接；P7 必须在真实连接时固定并核验最终地址、禁止重定向/环境代理。

### Core 受保护的 Catalog Approval Manifest

`AIGATE_CATALOG_APPROVALS_FILE` 是 Core 专用可选文件路径；缺省为空清单，所有部署缺批准；不自动生成生产批准文件。部署方需保护文件及父目录并保留审批文件的发布版本/审查证据。文件只由独立安全运维在 HTTP 之外提供，不经过普通管理 API。文件须为非符号链接的普通文件，禁止 group/other 写权限；启动只读加载，变更/撤销需要重启 Core，绝对 validUntil 到期在下一次检查立即拒绝。无效文件使 Core 拒绝启动，不回显文件内容。此机制只负责 P3 技术配置批准，不能代替 P6 数据出境与机密级别审批。

```json
{"schemaVersion":1,"approvals":[{"approvalRef":"SEC-2026-001","configDigest":"64个小写十六进制字符","approvedBy":"security-operator","approvedAt":"2026-10-26T00:00:00Z","validUntil":"2026-11-26T00:00:00Z","allowNoAuth":false}]}
```

清单与条目均封闭校验，引用和审批人非空且<=128；approvedAt<=当前时刻，validUntil>approvedAt。同一 configDigest 不得重复。最多512条、文件最多1MiB。审批文件不是 Secret 存储。

`configDigest` 是以下固定顺序的规范 UTF-8 JSON 的 SHA-256 小写十六进制：`schemaVersion=1,providerCode,hostingMode,modelCode,modelFamily,immutableModelRevision,hostPolicy,endpointUri,remoteModelName,regionCode,capabilityRevision,adapterCompatibility`。hostPolicy 使用服务端标准化的域名/CIDR/端口有序集合，adapterCompatibility 使用协议固定字段顺序且不含 deploymentId；JSON 无缩进。摘要不含 ProviderSecret。Core 提供相同规范算法；测试用现场假配置生成清单，不得把测试清单声称为生产批准。

批准必须精确匹配全部配置，Adapter verifiedAt<=批准 approvedAt。无鉴权 NONE 还必须 SELF_HOSTED 且匹配条目 allowNoAuth=true；BEARER/API_KEY_HEADER 不因 allowNoAuth 自动免密钥。外部 POST 的 evidenceRef/verifiedAt/私网 CIDR 只有被该清单绑定才具有可信批准含义。

### 价格、凭证及一致性

- 价格请求必须是固定6/8位小数的非负十进制**字符串**，总精度<=20；revision 是1～Integer.MAX_VALUE整数。publishedAt/effectiveFrom 由服务端同一时刻写入；发布须锁父记录并 CAS expectedModelVersion/expectedDeploymentVersion，失败409 PRICE_VERSION_CONFLICT。已发布版本禁止修改；相同版本再次发布409 INVALID_STATE，不伪装为幂等成功。GET 历史按 revision ASC。
- AES-256-GCM 使用32字节主密钥、每次随机12字节 IV、128位 tag；AAD 固定绑定 deploymentId、credentialKind、credentialRevision、encryptionKeyId。1～4096 **UTF-8字节**原样加密，不能 trim、截断或保存普通摘要。密文最长4112字节。解密/认证失败只给安全错误。
- Core 注入 `AIGATE_PROVIDER_ENCRYPTION_KEY_ID/KEY`、`AIGATE_PROVIDER_ISSUE_PEPPER_KEY_ID/PEPPER`；可选 `AIGATE_PROVIDER_PREVIOUS_ENCRYPTION_KEY_ID/KEY`、`AIGATE_PROVIDER_ISSUE_PREVIOUS_PEPPER_KEY_ID/PEPPER` 保留历史解密/收据追验。AES 材料恰32字节，Issue Pepper至少32字节，所有当前/历史材料不得跨用途复用或与 P1/P2 Pepper 重复。缺少当前配置、部分历史配置、无效编码均拒绝启动，错误不含配置原文。历史 keyId 不受信时不能重签/默认成功；返回503 CREDENTIAL_HISTORY_UNAVAILABLE，保留收据。
- Issue canonical 使用大端整型及长度前缀 UTF-8：method字符串POST、deploymentId(long)、kind字符串、revision(int)、secret存在性(boolean)、原secret字节(无secret时空)、actorId(long)。每个字符串/字节块前写4字节长度，HMAC-SHA256按收据保存的keyId追验。
- 首次签发201；相同 actor+key+原请求重放200同一凭证的当前安全 Metadata（吊销后仍为REVOKED，不恢复或重新激活），不重新加密、不改变指针/版本、不增加审计；不同请求409 IDEMPOTENCY_CONFLICT。创建新凭证更新父当前指针和 version，旧凭证保留历史，不自动获得新出站许可。吊销当前凭证清空指针、将部署置DISABLED并递增 version，同事务记录审计；重复吊销204无额外审计。吊销非当前历史凭证不切换回旧凭证。
- 所有管理写先沿用 P1 bootstrap_control 协调锁并复查全局管理员，再锁对应父对象/凭证；事务内审计失败整体回滚。此锁保守串行化管理写，尚不承诺高吞吐。密钥、HTTP header、密文、IV均不得出现在公开 DTO、日志和审计中。

P3 内网 eligibility 的唯一请求/响应合同见[内部 RPC](./internal-rpc.md#p3-目录就绪检查)。P3 所有管理/API 和内网检查均不得发送 Provider HTTP，Gateway 的聊天和凭证领取入口继续关闭。
