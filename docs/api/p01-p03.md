# 管理API · P1～P3（组织、运行身份、Catalog）

> 文档性质：**唯一实施合同候选**。所有字段、API、状态、错误、鉴权由Core授权校验，严格遵循[API总约定](../06-api-design.md)。真实HTTP/集成测试NOT RUN。

## 1. P1～P3接口总合同


> **约束与优先级**：本节把 D12/D18/D19/D20/D33/D44 分散接口归并为可实施 DTO；如旧章节中的示例字段、旧错误包络、价格生效规则与本节矛盾，以 D30/V1、D19/V2、D31/V3 的**实际物理列名与约束**、D33 的错误格式及本节为准。仅 P1～P3，本节**不代表 FZ-02 全部 P1～P12 已完成**。下列 JSON 均为合法性测试 fixture，ID、时间与价格是假数据，不是生产事实。

## 无例外的序列化、鉴权与幂等规则

- 外部 JSON 以 camelCase；DB snake_case 只在 Mapper/SQL；JSON body 必须是对象，禁止未知字段、重复 JSON key、非有限数、科学计数 ID、把数字放在字符串字段或把布尔写成字符串；必填字段不能缺省或 null；可选字段**缺省**代表不修改，显式 null 禁止用于 P1～P3 PATCH（不提供清空能力）。所有 POST/PATCH JSON 请求声明 Content-Type: application/json。无 body 的 PUT/DELETE/GET 不接受有业务含义的 JSON body。
- ID 使用 JSON 正整数，Java Long，DB BIGINT UNSIGNED 虽可大于 Long.MAX_VALUE，但应用必须拒绝超出 Java Long 的请求/已分配 ID（部署增长达到边界前需独立 ADR）；version/expectedVersion 为从0起的非负长整数，不允许负数、浮点或字符串；响应时间统一 UTC ISO-8601 Z，缺省可空字段统一显式 null（不因 Jackson NON_NULL 配置随机消失）；分页 page从1起、size 1～100、默认20，id ASC，total 是**权限过滤后**的总数。
- P1～P3 管理入口一律通过 Gateway 显式 path+method allowlist → Core 自身 mgt_ 有效凭证、ACTIVE Employee/Team、当前 ROLE scope 鉴权。P1 Bootstrap 仅允许 bst_ 且运维模式/来源也要匹配。P2/P3 当前只有 GLOBAL PLATFORM_ADMIN 写/读相关安全资源，P1 TeamManager 只保留已明示的 Team/Employee 只读范围。网页/API 的 id/path/teamId 不能代表授权事实。
- 通用失败格式 `{"error":{"code":"VERSION_CONFLICT","message":"The resource was modified","requestId":"r-001","retryable":false}}`；400 输入类型/字段非法，401 所有无效/吊销/过期管理凭证，403 已认证但越权或禁用，404 可见范围内资源不存在，409 唯一键/版本/无效状态冲突，503 依赖无法安全完成。不得返回 SQL、Hash、ProviderSecret、Core URL 或不同 Key 是否存在的侧信道。
- P1 创建管理 Key、P2 创建/轮换 agk_/empk_、Bootstrap 两个运维动作：Idempotency-Key 为8～128可见 ASCII，业务物理唯一作用域按 V1/V2 表已有 UNIQUE；**同一签发者跨 Owner/操作复用 key 也不得另签密钥**。重复相同键签发返回409 KEY_ALREADY_ISSUED_NOT_REVEALABLE（Bootstrap 可用 IDEMPOTENCY_REPLAY_NOT_REVEALABLE）；不同 body 同键冲突409 IDEMPOTENCY_CONFLICT，均不能再次回显秘密。管理普通修改必须记录同事务审计；PUT 授权及 DELETE 撤销使用目标关系唯一键，重复为204/204（首次 PUT 为201）。
- 创建资源 201 返回对象；普通 PATCH 200 返回新对象且 version+1；单查200；分页200 Page；DELETE/幂等重复授权204**无响应 body**。除首次凭证签发201外的所有响应不得出现 `key`、`secret`、`encryptedSecret`、`secretDigest`、`pepper` 字段。敏感201和403/401均添加 Cache-Control: no-store。

## P1 实体 DTO、所有写操作 Body

**安全 DTO（响应白名单）**：
- `TeamDTO`：`{id:long,name:string,status:"ACTIVE"|"DISABLED",version:long,createdAt:instant,updatedAt:instant}`。
- `EmployeeDTO`：`{id:long,employeeCode:string,displayName:string,primaryTeamId:long,status:"ACTIVE"|"DISABLED",version:long,createdAt:instant,updatedAt:instant}`。
- `RoleAssignmentDTO`：`{roleCode:"PLATFORM_ADMIN"|"TEAM_MANAGER"|"FINOPS_READER",scopeType:"GLOBAL"|"TEAM",scopeId:long}`；不暴露内部 row id 或多态审计。
- `ManagementCredentialMetadataDTO`：`{id:long,keyPrefix:string,expiresAt:instant,revokedAt:instant|null,createdAt:instant}`；首次签发 `IssuedManagementCredentialDTO`：`{credentialId:long,key:string,keyPrefix:string,expiresAt:instant}`。
- `AuditMetadataDTO`：`{id:long,actorType:string,actorId:long,action:string,targetType:string,targetId:long,changedFields:string[],traceId:string,occurredAt:instant}`；`changedFields` 来源 DB changed_fields_json，但只包含**字段名**，不包含新旧敏感值。
- `Page<T>`：`{items:T[],page:integer,size:integer,total:long}`；空集 items=[]、total=0；`/me/profile` 响应 `{employee:EmployeeDTO,roles:RoleAssignmentDTO[]}`。

**Bootstrap 双运维 API**：POST /api/v1/bootstrap/initialize 必填 `{teamName:string,employeeCode:string,displayName:string,managementKeyExpiresAt:instant}`；POST /api/v1/bootstrap/recover-management-key 必填 `{targetEmployeeCode:string,managementKeyExpiresAt:instant,reasonCode:"ADMIN_KEY_LOST"}`；两者都要独立 bst_、Mode、运维网段、Idempotency-Key。首次初始化201 `{team:TeamDTO,employee:EmployeeDTO,managementCredential:IssuedManagementCredentialDTO,initializedAt:instant}`；恢复201 `{employeeId:long,managementCredential:IssuedManagementCredentialDTO,recoveredAt:instant}`。已初始化再次INIT=409 BOOTSTRAP_ALREADY_INITIALIZED；普通 mgt_ 不可调用这两个运维端点。这里的返回结构只增加公开安全 DTO，不要求数据库新字段。

## P2 双运行凭证和 Agent ACL 字段闭合

**响应 DTO**：`AgentDTO={id,applicationCode,displayName,ownerTeamId,status,version,createdAt,updatedAt}`；`KeyMetadataDTO={id,keyPrefix,validFrom,expiresAt,supersededAt,graceExpiresAt,revokedAt,createdAt}`（后三时间可为null）；`NewKeyDTO={credentialId,key,keyPrefix,validFrom,expiresAt,oldCredentialGraceExpiresAt}`（非轮换场景 oldCredentialGraceExpiresAt=null）；`AgentEmployeePermissionDTO={employeeId,agentId,status,version,grantedAt,revokedAt}`。所有P2 Key明文只在201出现，Agent与Employee Key分别有独立Pepper及 DB 唯一签发键。

**所有P2签发/轮换** `expiresAt` 必须在 Core now+1h～90d，签发者+Idempotency-Key 在 **agent_api_key** 或 **employee_credential** 各表唯一；旋转锁 Owner →旧凭证并写新凭证与旧 grace 同事务；旧与新最多两把当前可认证的Key，若超过则409 KEY_LIMIT_EXCEEDED。禁用 Agent/Employee/归属 Team 使该主体两类Key即刻不能通过下一次认证，但不会物理删除签发记录。ACL只能由管理员PUT/DELETE修改；只改变Key不授予ACL。

~~~

`POST /agents/11/keys` 带 `Idempotency-Key: demo-issue-0001`，body `{"expiresAt":"2026-11-01T00:00:00Z"}`，首个201允许一次 `{"credentialId":18,"key":"agk_<REDACTED_TEST_SECRET>","keyPrefix":"agk_test","validFrom":"2026-10-22T03:01:00Z","expiresAt":"2026-11-01T00:00:00Z","oldCredentialGraceExpiresAt":null}`；此处占位字符串**不是**真实CSPRNG Key，自动化测试必须现场生成真随机模拟值，不允许将占位值作为生产密钥。重交同键409，明文不回显，DB只存digest/keyPrefix。

**P3响应白名单**：Deployment默认返回仅`capabilityRevision`与`hasApprovedAdapterCompatibility`等安全metadata，不回完整adapterCompatibility内部配置/证据链接原文；受控管理调试接口可在同一现有GET单项经ADMIN权限显示不含秘密的校验结果，**任何普通Agent/Employee不获未经批准的Provider内部识别信息**。ProviderDTO=`{id,code,name,hostingMode,status,version,createdAt,updatedAt}`（host policy及审批细节只允许单独受控管理员读取，不作为安全默认的普通列表字段）；LogicalModelDTO=`{id,modelCode,displayName,modelFamily,immutableModelRevision,capabilityProfile,status,activePointsPriceVersionId,activeRoutingRevisionId,version,createdAt,updatedAt}`；DeploymentDTO=`{id,logicalModelId,providerId,deploymentCode,remoteModelName,hostingMode,regionCode,capabilityRevision,costModel,status,routingPriority,routingWeight,maxConcurrent,capacityPoolId,activePurchasePriceVersionId,hasActiveCredential,version,createdAt,updatedAt}`（默认不回显完整 endpointUri；如运维确需看经批准的host，由单独管理员安全只读元数据授权）；ProviderCredentialMetadataDTO=`{id,deploymentId,credentialKind,credentialRevision,status,createdAt,rotatedAt,revokedAt}`；AgentModelPermissionDTO=`{agentId,modelId,status,version,grantedAt,revokedAt}`。可空字段按53.1用null明示。

**兼容约束（不得让实现AI选择）**：
1. `baseUrlHostPolicy` 与 `capabilityProfile` 的**内部嵌套子字段/schema**仍须由总控补充完整枚举/长度/默认：本节已冻结**顶层 API 字段边界**，但这两个结构不是任意 Map<String,Object> 透传。P3 的安全 endpoint SSRF 校验须先在登记时执行，P7 在使用时再次解析域名/IP检查。
2. P3 Deployment 只有 DRAFT→ACTIVE 的明确管理员 PATCH，但 ACTIVE 必须验证 Model/Provider/Deployment 状态、可证明的Endpoint和受支持能力、必要的密钥和已发布价格，不应将 ACTIVE 当成 P6 已批准的机密数据许可。历史价格旧PUBLISHED 不修改；current pointer 用父Version CAS，避免两管理员都发布成功。
3. P3 缺少真实 Provider 价格的测试系统可以用**假配置价格**检验草稿/发布，但这不是授权真实付费调用。没有可验证费用上界/可信用量时 P7 一律422 BILLING_BOUND_UNVERIFIABLE，不因测试常数冒充采购价。
4. D44 仅列出资源集合，不是方法规范：**本节 method/path 是 P1～P3 Gateway 的显式注册清单**；同一路径 GET+POST 必须分别允许指定方法，未列出的方法返回405（不暴露内部路由）；所有 `/internal/**` 仍然不可公网代理。

这个 Fixture 假定 ModelVersion 在进入发布前仍为0；并发发布旧 expectedModelVersion 必须409 PRICE_VERSION_CONFLICT。额外写入 `effectiveFrom` 或把 `pointPer1kInput` 传为 JSON number 均400；已发布 revision 再修改价格不开放 PATCH/PUT 路由。



## 2. Catalog结构化JSON与ProviderSecret幂等


**修订原因**：D45 首次跨表/API 校对发现两类真正的实现缺口：（1）`provider.base_url_host_policy` 与 `logical_model.capability_profile_json` 仅声明 JSON 数据类型，会迫使执行 AI 自创安全配置格式；（2）D33 强制所有 Secret/Key 创建操作有幂等保护，而 V3 原 `provider_credential` 仅有 (deployment_id,credential_revision) 唯一键，不足以防**同管理员跨Deployment、跨revision重复提交同一创建命令**。本节直接把 V3 规范 DDL 修正为多四列 + 一个复合唯一键 + Employee FK/CHECK（已同步修改上文 D31 的规范 SQL），**仍然是Core V3同一张表，Core 54 表总数不变**。旧版原始 V3 尚未实际执行，不属于修改已发布迁移；将来代码已上线以后则只能通过新 Flyway ALTER。

## baseUrlHostPolicy v1（P3 Provider 创建/安全更新）

该字段**只允许**以下结构；未知成员与显式 null 一律400，不能直接把外部任意 Map 转入路由：

~~~json
{
  "schemaVersion": 1,
  "allowedHostnames": ["api.vendor.example"],
  "allowedPorts": [443],
  "tlsRequired": true,
  "allowPrivateNetwork": false,
  "approvedPrivateCidrs": []
}
~~~

- `schemaVersion` 必须是 integer 1；`allowedHostnames` 为 1～32 个去重后小写 ASCII IDNA规范化的**准确 FQDN**，每项1～253字节，禁止IP字面量、`*`/通配符、用户信息、URL scheme/路径、尾部点歧义与空字符串；不按任意子域 suffix 自动放行。`allowedPorts` 1～8 个 1～65535整数并去重；`tlsRequired` 固定 **true**；`allowPrivateNetwork` 是布尔；`approvedPrivateCidrs` 为0～16个经安全管理员审查的 CIDR 文本。
- THIRD_PARTY_API 固定 `allowPrivateNetwork=false`、`approvedPrivateCidrs=[]`、端口首版只允许443；禁止 loopback/link-local/RFC1918/IPv6 ULA/metadata IP、DNS rebinding 与代理绕过。SELF_HOSTED 可以 `allowPrivateNetwork=true`，但必须非空的 `approvedPrivateCidrs` 和受控部署网络，不允许把 `0.0.0.0/0`、`::/0` 或云元数据服务视为安全网段。安全批准证据由受控管理员审计记录，P3 不给普通管理请求自动安全审批权限。
- 登记时校验 `endpointUri` 的 HTTPS/hostname/port 与 Provider 当前策略匹配；P7 **每次连接及每次DNS解析后**校验所有 A/AAAA 结果落入真实批准 IP 范围，禁止HTTP自动跟随重定向、禁止自定义用户代理/代理变量绕过受控解析和连接地址核验。只在P3登记做DNS检测无法对P7派发时的 DNS rebinding 给出安全保证。
- Policy变更必须 P3 管理 Service 锁 Provider + 受影响 ACTIVE Deployment 才允许；现有 Deployment若不再符合策略应阻止新派发，不以配置更新绕过 P6 未来治理。真实网络栈的连接前校验依赖真实测试，P0只冻结协议。

## capabilityProfile v1（P3 LogicalModel 固定模型能力）

~~~json
{
  "schemaVersion": 1,
  "chatCompletions": true,
  "streaming": true,
  "toolCalling": false,
  "maxInputTokens": 4096,
  "maxOutputTokens": 1024,
  "maxTotalTokens": 4096
}
~~~

- 全部七字段**必填、无 null、无额外字段**：`schemaVersion=1`；`chatCompletions=true`（现阶段仅实现聊天补全）；`streaming` 布尔；`toolCalling=false`（当前网关**不编排**工具调用；后续只有新协议/ADR 才能改变）；`maxInputTokens`、`maxOutputTokens`、`maxTotalTokens` 是1～2,000,000的正整数，满足 input≤total、output≤total。上例为**仅测试元数据**，不声称特定供应商实际上限。
- 真正使用时必须同时受 Deployment `capabilityRevision`、实际Provider Adapter 测试证据、真实上下文窗口和客户端 `max_tokens` 约束；`capabilityProfile` 不是受信 tokenizer，也不是自动可计费的证明。P7 对不可证实的输入/附加类别风险上界拒绝收费出站；P6 安全政策仍优先于能力声明。P3 PATCH 不开放修改此JSON，语义变更需新 Model 身份/受控新Revision与 ADR。
- `routingWeight`、`maxConcurrent` 属 Deployment 的路由/容量元数据，**不**出现在 Model capability JSON 中；AgentModel授权针对逻辑 Model，而不是一张 JSON 里的任意字符串。

## ProviderCredential 请求幂等权威、错误与审计

V3规范表新增 `issued_by_employee_id`、`issue_idempotency_key`、`issue_request_hmac`、`issue_hmac_key_id`。POST /api/v1/deployments/{id}/credentials **必须**带 Idempotency-Key 8～128 可见ASCII，唯一作用域精确为 `(issued_by_employee_id,issue_idempotency_key)`、**跨 Deployment/credentialRevision 仍然互斥**。同 Actor/Key 首次创建：先锁 Deployment 父行→查询并锁签发 receipt→检查目标版本与当前 ACTIVE 凭证→生成 AES-GCM ciphertext/nonce→插入 credential 与审计→更新父 active_credential_id（如已满足上线前置）→一次本地事务提交，201 只回安全 Metadata；事务回滚不得返回创建成功。

`issue_request_hmac` 使用**Core内部独立的 ProviderCredentialIssue Pepper**（不同于加密主密钥、管理Key/运行Key Pepper）对 **canonical(HTTP method, deploymentId, credentialKind, credentialRevision, secret存在性及其原字节, 已认证的签发者)** 算HMAC-SHA256；`issue_hmac_key_id` 保存用于合法轮换后验证旧收据的密钥版本。**不**存明文 secret、普通 SHA256 短Secret摘要或可反解请求原文。相同Actor+Key+相同HMAC重放200原安全Metadata，绝不重新加密/创建/换激活指针；不同HMAC重放409 IDEMPOTENCY_CONFLICT。另一管理员的相同RawKey在物理上独立，仍须按 Deployment 行锁/credentialRevision 唯一键判冲突。持久 receipt 至少覆盖凭证的有效历史审计期，不因撤销即删除。

- NONE 凭证仅允许真实经安全批准的无鉴权 SelfHosted；`secret` 缺省且不得null/空字符串。BEARER/API_KEY_HEADER 必须是受控长度1～4096 UTF-8字符串，禁止 JSON null/空串，Core只保存AES-GCM密文/IV/加密KeyId。V3数据库不能静态检查密文字节对应合法供应商凭证，靠 Service 字段校验、端到端 Fake Provider 验证。
- P3 部署状态为 ACTIVE 并不自动许可真实HTTP：P6治理、P7双身份/两ACL/双预算、一次性Permit都还未上线。凭证吊销引发当前 active 指针不可用时须通过父锁/CAS使新出站拒绝，保留旧凭证的历史证据。
- **锁序与响应一致性验证**：两并发相同Actor+Key仅一条 provider_credential 和一次审计；相同Key不同 Deployment/revision 返回409；不同Actor同 Deployment+revision只允许一个成功；两次同请求不再次暴露secret；实测使用MySQL8.4和真实加密/签名库，当前状态全部 NOT RUN。
