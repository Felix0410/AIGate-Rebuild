# 运行及管理API · P7～P12

> 文档性质：**唯一实施合同候选**。所有字段、API、状态、错误、鉴权由Core授权校验，严格遵循[API总约定](../06-api-design.md)。真实HTTP/集成测试NOT RUN。

## 1. 分阶段接口合同


本节以 D42 六RPC、D44公开Method白名单、D25～D29业务和 Core V7～V10/FinOps V1 物理列为权威约束。**只定义用户可见 Gateway 路径**，不允许因为本节写有业务查询就把 `/internal/**` 注册为公网路径。所有 DTO 使用 JSON camelCase、Decimal 固定刻度字符串、Instant UTC、日期按公司ZoneId转换、页从1起最大size100、强制未知字段400；可空字段在安全响应里显式null；任何权限/成本未知都不变成金额0。

### 1.1 P7：首次 Runtime 与公开 Invocation 视图

`POST /v1/chat/completions` 只允许 `Authorization: Bearer agk_...` + `X-Employee-Key: empk_...` + `Idempotency-Key`（16～128受限可见ASCII），`Content-Type:application/json`。规范输入 `ChatRequestV1`：`{model:string,stream:boolean,messages:TextMessage[],max_tokens:positiveInt,temperature?:decimalNumber,top_p?:decimalNumber,stream_options?:{include_usage:true}}`；`TextMessage={role:"system"|"user"|"assistant",content:string}`；消息1～64条、原UTF8 Body<=64KiB、`max_tokens`必须为正且不超过已批准Model/Deployment输出上界，temperature在[0,2]、top_p在(0,1]，省略温度/top_p按D42 CanonicalDTO默认归一化，不可把explicit-null当缺省；stream_options仅可在stream=true给出，若上游支持用量统计必须主动请求。**禁止** client传 employeeId、deploymentId、providerURL、serviceClass、fundingSource、n>1、tools、tool_choice、多模态内容或未知body字段。P9才可增加 `fallback_mode`；P10才允许独立受信紧急授权Header。

成功非流式200 `{id,object:"chat.completion",created:unixSeconds,model:requestedLogicalModelCode,choices:[{index:0,message:{role:"assistant",content:string},finish_reason:string}],usage:{prompt_tokens:int,completion_tokens:int,total_tokens:int}|null}`，另有响应头 `X-AIGate-Invocation-Id`、`X-AIGate-Billing-Status`。若上游合法完成但可信usage未到，`usage:null`、账务PENDING，不假造零费。成功流式200 SSE严格D08/D42：增量 choices[].delta、可信usage可独立帧、正常 `data: [DONE]`；已开流后错误只发送安全 error 事件/断流、不发伪DONE或HTTP新状态，必须可通过GET恢复元信息；未预留成功绝不提交SSE200。

`GET /v1/invocations/{publicInvocationId}` 只用**当前重新验证的同对 agk_/empk_**，200 `{invocationId,requestedModelCode,actualModelCode,serviceClass,executionState,billingState,fundingMode,usedPoints,supplierCost,createdAt,updatedAt}`；未获得可信usage时usedPoints/supplierCost=null，不显示Prompt、完整回复、ProviderSecret、AttemptToken、其他员工请求。复用同 Idempotency-Key POST：409且只给可查询invocationId与安全状态，不再做任何Provider发送；原RPC ACK丢失的 COMMITTED 不意味着第二张出站券。P7只允许 NORMAL，P9/P10以后通过Core当前授权合法激活LOW/EMERGENCY。

~~~json
{"model":"TEXT-Q4-STABLE","stream":false,"messages":[{"role":"user","content":"Hello"}],"max_tokens":128,"temperature":0.5,"top_p":1.0}
~~~

### 2.1 资源池创建、绑定、激活与阻断

**发现**：D53设计了Redis Pool Guard/Lua及V7`capacity_pool_policy`五字段上限，但D44原P7只有Chat/Invocation两个用户接口，**未定义平台管理员如何建立受限Pool、批准真实物理容量及把P3 Deployment挂到Pool**；把它留给执行AI就会出现硬编码无限池/随意Redis初始化。现确定P7统一由Core管理，Gateway仅注册下面严格方法；管理身份mgt_且仅GLOBAL PLATFORM_ADMIN，Core做当前ROLE/Team状态复核及Audit同事务，不能从用户Chat消息动态创建Pool。

V7 `capacity_pool_policy`规范SQL已直接修订：新增`capacity_evidence_ref VARCHAR(256) NOT NULL`（仅存受控容量证据引用，不存原证书/Provider密钥）；`status`默认**DISABLED**而非ACTIVE（创建不会自动开户），已有`admission_epoch/version`作为运行代次与CAS。总表数仍62。

| 公开Path+Method | DTO / Query | 结果和安全状态 |
|---|---|---|
| POST /api/v1/capacity-pools | `{poolCode,scopeKind:"PROVIDER"|"SELF_HOSTED",resourceIdentityCode,capacityEvidenceRef,maxActive,maxWaiting,maxQueueMs,maxRunMs,rpmLimit}`；poolCode只允许`[A-Z][A-Z0-9_-]{1,95}`，capacityEvidenceRef为受信管理员登记的批准证据ID | 201 `CapacityPoolDTO` status=DISABLED,epoch=0,version=0；不向Redis放任何可用ACTIVE席位 |

**R10新增容量证据输入校验**：`resourceIdentityCode`为公司受控的稳定安全资源代码，匹配`[A-Z][A-Z0-9_-]{1,127}`；`capacityEvidenceRef`是8～256字符的受信批准票据代码，不能是URI、原合同正文、个人信息或Key。Core根据批准记录验证资源身份与该证据相符，两个字段不得凭客户端自报即证明通过真实物理身份审核。

`CapacityPoolDTO={id,poolCode,scopeKind,resourceIdentityCode,capacityEvidenceRef,maxActive,maxWaiting,maxQueueMs,maxRunMs,rpmLimit,status,admissionEpoch,version,guardState,observedAt}`，普通列表里guardState可为UNKNOWN，绝不根据Redis不可达填OPEN；`capacityEvidenceRef`仅返回安全审计引用码，绝不提供完整合同或商业凭证URL。管理Config仅在CoreDB持久，Gateway只有对应Pool ID和当前真实Lease可被Core核验。P3当前Deployment创建不需要P7Pool存在，P7上线前其`capacity_pool_id`保持NULL；P7收费派发前必须绑定真实Pool、Pool status=ACTIVE且Guard OPEN。

**Pool Activate的跨MySQL/Redis安全提交顺序**：
1. Core短事务锁Pool`FOR UPDATE`，确认当前Admin/expectedVersion/Capacity证据/实际任务清单，状态设置DISABLED并`admission_epoch+1,version+1`提交；本阶段不能发Provider。
2. Core经受信Redis维护调用在**新epoch**初始化BLOCKED Guard/队列，检查当前Redis真实runId；历史UNKNOWN物理GPU或已有未结旧epoch Permit应维持Block/隔离并明确报告，不能直接恢复。
3. Core再次CAS版本/DB状态成ACTIVE后提交短事务；随后仅Core能把同epoch/runId Guard原子转OPEN，并立即独立INSPECT以验证。任何步骤失败都保守DISABLED/Guard BLOCKED或INCONSISTENT，**Core最终Permit要求DB ACTIVE∧Guard OPEN∧epoch一致**，不会因部分提交就发包。下一次重试必须先诊断前次是否已经推进epoch，不能盲再加一次运行代次。
4. `block`在DB先把status改DISABLED并版本+1后，再尽力关闭Guard；Core Permit必须读取并锁住真实Pool status才能继续资金事务，因此Block提交之后没有新的Permit；已提交Permit可能发送过Provider必须保留费用风险。

**实现落点**：Pool号代表经过管理员审查的唯一**真实物理/供应商限额共享域**，相同实际GPU/Provider上限的多个Deployment必须绑定同一个受控Pool（不能分别建两个池来制造额外容量）；D53`maxActive`以可核实批准物理并发上限为硬上界，单个Deployment还受其V3`maxConcurrent`限制。若多个Pool疑似指向同一物理身份、相关凭证缺失或管理员无法证明Provider上限，Core不得激活收费Pool，而不是由代码自动猜测。P8选Deployment仍须从同Pool真实ACTIVE中竞争，没有新建免费ResourceLease后门。

**测试合同**：P7-CAP01 创建默认DISABLED/无证据拒绝activate；CAP02双管理员并发CAS、同expectedVersion重放、绑定错误scope；CAP03 两Gateway同时进一个容量1池只PROMOTE一个；CAP04 Redis Guard初始化到DB ACTIVE之间注入故障，保证Provider HTTP=0；CAP05 旧物理任务未停止阻止开启；CAP06 BLOCK与Permit并发及旧状态Races。所有全部NOT RUN。

**R04管理端点幂等说明**：P7尚未新增P12专用的AdminAudit操作收据列，故容量池activate/block首版**只提供强制expectedVersion的CAS去重**，不要求无物理存储的Idempotency-Key，也不承诺相同POST安全响应重放；收到504应先GET容量池核对epoch/状态，然后以当前版本执行新的安全管理动作，不能盲目再次激活。P12真正持久化运维收据才使用V11 AdminAudit新列。Pool不变量仍保持。




## 3. 跨Phase版本发布与关联约束

### 3.1 治理、模型发布的双CAS与费用草稿版本

**并发问题与最终合同**：P6 Governance Publish只传旧activeRevision指针，却引用了`governance_policy.version`；P8 Routing Publish同样只传旧revision，无法可靠捕获父模型的其他已提交修改；P11创建Expense响应写revision=0，而FinOpsV1该字段真实DEFAULT 1。现将P6发布固定为`{expectedPolicyVersion,expectedActiveRevisionId}`双比较、P8发布固定为`{expectedModelVersion,expectedActiveRoutingRevisionId}`双比较。两者在同一父行锁下CAS，更新成功令父version+1；并发旧版本409、父状态与已发布Price/Policy不做不相关写入。

P6为了首次发布也可获得真实版本，`GET /governance/policies/active`在已初始化但尚无activeRevision时返回200 NOT_CONFIGURED+policyVersion0+null指针；**此响应仅用于管理页面和发布CAS，不允许Runtime把NOT_CONFIGURED视为可用安全Policy**。Governance draft/review拥有独立revision.version与审核当前Status约束，发布还要验证APPROVED及SecurityApprover不是创建者。P8模型GET返回`version`及V3预留`activeRoutingRevisionId`（P8前null），客户端不必猜活跃revision number。P11 D49费用草稿初始revision=1（与V1 DEFAULT1和后续expectedRevision一致），真实审批首次CAS=1、审批后revision=2；这些操作必须在FinOps实际数据库本地事务实现，不允许响应版本与物理列漂移。



### 3.2 P3与P7容量池跨版本关系

**发现与修正**：P3 Deployment POST曾将可选`capacityPoolId`开放给客户端，尽管Core V3的相关Pool在V7才创建；从P3非法/不应输入的ID也能进入后续状态，这不是一个可验证的外键来源。现D45接口定义明确P3 POST**不接受capacityPoolId**（未知字段400），P3新Deployment`capacity_pool_id=NULL`；P7容量池准备好后只允许R04的受控PUT绑定再激活收费使用。Core V7建成Pool后既有FK才生效。D45逻辑模型安全DTO补可空`activeRoutingRevisionId`，P3～P7必为null，P8才由受控发布策略填充；P8 POST Publish传`expectedModelVersion`及该指针的期望值，双比较防覆盖P3价格或其他模型配置变动。原稿中`P3不得强制外键引用未来P7池`不是允许客户端绕过阶段，**现在有明确无此输入字段的硬合同**。



### 3.3 紧急审核版本与物理去重

**审批版本与P10审核幂等**：V6`governance_policy_revision/governance_exception_request`和V10`emergency_request`均已有新`version`字段；D48/D49对应创建/审核/撤销响应必须回显更新后的version，使客户端合法提交下一次`expectedVersion`。V10请求的`allowedModelIds`持久化为`emergency_request.requested_model_ids_json`，批准子集必须校验并落到FK授权模型表。P10 `/emergencies/{requestId}/review`在该Phase仅依赖**expectedVersion CAS+UNIQUE emergency_authorization.request_id**实现一次审核，不要求无物理操作收据的Idempotency-Key；同审核HTTP重放得到409 VERSION_CONFLICT，不创建第二授权。需要可恢复200同body重放时必须由总控设计新的物理收据方案，不能让执行AI猜。

## 4. P11 FinOps 管理收据与强幂等

### 4.1 Draft 与 Rebuild 的持久幂等

**约束起因**：D49的`POST /api/v1/finops/operating-expenses`及`POST /api/v1/finops/rebuilds`都要求`Idempotency-Key`。原FinOps V1的Draft只有sourceRef唯一、Rebuild只有单例buildingBuildId，**不能防同Actor跨不同sourceRef复用相同操作键，以及已经完成重建后相同操作键再次创建Build**。不能仅靠Gateway不重试或本地内存去重宣称持久幂等。

**规范字段已并入FinOps V1 SQL**：
- `self_hosted_operating_expense`新增必填`creation_operation_key`、`creation_request_hmac`、`creation_hmac_key_id`，唯一`(created_by,creation_operation_key)`，长度CHECK。首次201草稿，**同Actor+Key+相同规范请求重放200只回安全草稿Metadata，不创建第二草稿/审批事实**，不同body409 IDEMPOTENCY_CONFLICT，另一Actor对同源仍由已有source唯一键保护。
- `finops_management_audit`新增可空`build_id`、`operation_key`、`operation_request_hmac`、`operation_hmac_key_id`，唯一`(actor_employee_id,operation,operation_key)`，HMAC trio同NULL/同非NULL。只有REBUILD操作首次必须写非NULL Key/HMAC/KeyId及逻辑build_id；其他旧审计行仍允许NULL。相同Actor+REBUILD+Key同请求重放安全返回既有`{buildId,status}`（排队返回202；已经完成返回200和最新已验证状态），不同body409；**不得分配新的buildId**。
- 两类收据的HMAC都由**FinOps独占OpsReceipt Keyring**计算，不传给Gateway，不存用户凭证/请求原文。Canonical包含actorId、operation、scope、requestBody确定字段（Draft包含resourcePool/服务月/原币种/amount/sourceKind/SourceRef/evidenceDigest；Rebuild包含from/to/reasonCode），不包含每次HTTP自动生成的requestId；同Key不同Owner/金额/窗口/理由等必须409。Core在调用前完成当前RBAC授权；FinOps同一DB本地事务首先查收据/锁Singleton或目标业务行，写Draft/BuildingPointer+Audit/Fact相应事务后才能报告成功。
- FinOps费用`APPROVE/VOID`使用既有`self_hosted_expense_revision.operation_key`物理唯一及`expectedRevision`对象CAS，第一次成功回200，下次相同操作键不得生成另一个Revision/Fact；重放查询持久revision语义判冲突，不能把FinOps audit仅有requestId当业务幂等键。
- P11测试必须覆盖：同Key不同费用来源/金额、两线程同Key并发首次草稿、Rebuild完成后相同Key再发、同Actor和另一Actor相同key、Core授权撤销后的重放；需保持“同Key重放不执行新事务”和安全错误包络。**仍NOT RUN**。本次修订不增加新表，仍为Core55+FinOps7=62。



## 5. P12恢复检查API与受信证据

### 5.1 ReadinessProbe 输入、证据与RecoveryReview闭环

**安全背景**：D55让管理员在`recovery-review`请求中提交`readinessEvidenceIds`，D56要求这些ID指向真实、30秒内受信检查记录，但在之前的公开路径表中**没有哪个操作能够触发并存储这些检查**。本地AI若自行添加端点或只信任客户端随便上传的ID会直接突破P12全局安全恢复。

**最终公开入口（更新D44 P12白名单）**：`POST /api/v1/operations/readiness-probes`。仅GLOBAL PLATFORM_ADMIN +当前有效mgt_；请求`{referenceId:string,expectedAdmissionVersion:long,checkKinds:["CORE_DB","POOL_REDIS","GOVERNANCE","PROVIDER_RISK","GATEWAY_COMPAT","OUTBOX_DURABILITY"]}`。六个checkKinds必须恰好一次全部列出，顺序不影响规范摘要；referenceId为安全工单引用码1～96字符（不得含Prompt/密钥），必须与随后恢复review相同。Core通过受信真实客户端执行只读检查，最长10秒、无任何新Provider调用；普通用户不可以把请求字段中的`checkKinds`替换为自称PASS的结果。响应201：

~~~json
{
  "probeId": 1201,
  "referenceId": "incident-2026-10-23-01",
  "status": "READY",
  "observedAt": "2026-10-23T08:00:00Z",
  "validUntil": "2026-10-23T08:00:30Z",
  "checks": [
    {"kind":"CORE_DB","status":"PASS"},
    {"kind":"POOL_REDIS","status":"PASS"},
    {"kind":"GOVERNANCE","status":"PASS"},
    {"kind":"PROVIDER_RISK","status":"PASS"},
    {"kind":"GATEWAY_COMPAT","status":"PASS"},
    {"kind":"OUTBOX_DURABILITY","status":"PASS"}
  ]
}
~~~

如果任一项UNKNOWN/FAIL，仍201返回真实状态`NOT_READY`，**绝不返回伪造的READY**。Core在结果完全取得后以当前管理员`actor_type='EMPLOYEE'`、`action='P12_READINESS_PROBE'`、`target_type='RUNTIME_ADMISSION'`、`target_id=1`向已有V1 `admin_audit_event`插入一行，产生唯一`probeId=admin_audit_event.id`；`changed_fields_json`存**安全检查收据对象**：

`{probeSchemaVersion:1,referenceId,observedAt,validUntil,admissionEpoch,admissionVersion,checkResults:[{kind,status,observedAt}],evidenceKeyId,evidenceHmacHex}`。

audit DTO普通GET仍只展示字段名/安全结果码，不能把底层原始诊断、Provider请求、GPU密码、Redis连接凭证返回客户端。收据是Core内部独立`ReadinessEvidenceKeyring`以固定canonical JSON+ActorID签署的HMAC-SHA256；不拿D50 RequestDigestKey复用，不能由Gateway/用户自己生成。证据摘要与KeyID保存在已有审核JSON列，不新增表；在V11单例的`last_readiness_digest`记录最终批准证据的合成摘要。为防几十秒内多次重复触发不必要资源探测，Gateway/Core对同Admin+工单做每10秒最多一次速率限制，**但重复检查不是任何收费业务，也不会改变global epoch/资金状态**，不强加一个不存在的持久管理写入幂等Key。

**六种检查的可执行语义**：CORE_DB检查同一受信数据库可写、V11版本/状态读取成功、真实资金Reservation不会被丢弃；POOL_REDIS从Core客户端独立读取受信runId及所有受当前业务使用Pool epoch/Guard和UNKNOWN物理任务隔离情况，任一不可信→UNKNOWN；GOVERNANCE验证当前真正发布安全Revision与必要Key/审批仍有效；PROVIDER_RISK校核Core ReconciliationCase已分类，无法安全隔离的大范围未知出站阻止恢复（单独可解释且已隔离的历史案件不必让公司永久停机）；GATEWAY_COMPAT证实所有仍接公网流量的Gateway/可给Permit的Core均使用支持V11门禁的兼容协议版本，旧Core仍可受公网访问则FAIL；OUTBOX_DURABILITY确认Core新Ledger/Outbox能同事务提交，不要求RabbitMQ/FinOps当前FRESH。任何检查异常/超时不得产生PASS。

**与recovery-review的闭环**：`readinessEvidenceIds`长度1～8、无重复，至少含一份`status=READY`且六项全PASS的真实Core审计记录；Core锁V11单例之前验证该行来源、受信HMAC、当前Employee权限/工单/30秒有效期/原global epoch和version，随后**最终短事务**再次校验当前state/epoch/version与关键DB/Pool栅栏；过期或状态变化拒绝恢复，而不是借旧PROBE重用证据。可选多ID只用于同一referenceId多次真实检查记录的因果追踪，不能用一份FAIL+另几份PASS拼造一个完整通过。恢复成功同事务存`last_readiness_digest`、AdminAudit带R05操作收据和version+1、epoch+1。检查结果记录属于历史安全审计，不能让客户端DELETE或编辑。

**测试**：R09-P12-01从BLOCKED触发NOT_READY/READY、CoreAudit实际ID和签名不可篡改；02使用另一Actor/工单/旧版本的probeId或者过期证据→409/403；03模拟Redis runId切换发生在Probe与Commit之间→不得SERVING；04带旧Core或旧Gateway进程→FAIL；05真实RabbitMQ/FinOps down但Core事务Outbox完好→视必要依赖区分；06所有敏感日志脱敏、CoreAudit仅留安全元数据。全部属于P12真实E2E，当前NOT RUN。


## 6. 已定稿的跨模块字段/安全要求

### 6.1 密文容量、Grant审计和容量身份的规范约束

1. **AES-GCM密文容量**：P3 ProviderSecret允许最多4096 UTF8字节，但16字节GCM Tag意味着同长VARBINARY(4096)无法保存最大合法明文；规范V3 provider_credential.encrypted_secret改为VARBINARY(8192)，明文上限不增加，IV仍独立BINARY(12)。需在P3实测4096字节极限、Tag、非法IV、加密Key轮换、超长拒绝；当前NOT RUN。
2. **Grant原因可审计**：V5 team_grant增加issued_reason_code必填、revoked_by/at/revoke_reason_code三列可空，revoked_by FK→employee，撤销时status与三字段受CHECK配对；P5发放与撤销body reasonCode分别在同事务持久化，重复撤销204不改写历史、不退款、不抹去在途Reservation。新列属于原表，不增第63张。
3. **真实容量身份不可复制**：V7 capacity_pool_policy增加resource_identity_code VARCHAR(128) NOT NULL及UNIQUE(scope_kind,resource_identity_code)，P7创建体加入resourceIdentityCode，不开放PATCH改它。身份码是经管理员审批的安全代号，不能使用真实Provider账号/Key。唯一约束只识别相同身份码，不能自动证明不同伪名不指向同一GPU；启用时必须核验capacityEvidenceRef与物理/供应商真实共享限额，多个Deployment共享同一Pool。
4. **P7不得依赖未来P12的ReadinessEvidence API**：R04 Pool Activate请求删去readinessEvidenceIds（该证据机制仅P12 R09引入），P7只接受expectedVersion、reasonCode。Core自行在锁外核验受信容量/真实Redis运行代次/未知上游任务/风险状态，在既有admin_audit_event记录安全检查结果，再以R04的两次CAS及Guard原子OPEN流程启用；失败保持DISABLED或Guard BLOCKED。不可让客户端提交自称PASS的检查值。P7 Fake环境只允许Fake容量审批并严格标TEST。

以上都是字段/业务合同修正；Core55+FinOps7=62表不变，真实构建/数据库/中间件验证仍NOT RUN。
