## 二、项目的决策状态

**已经确认的产品事实**：Agent 是已有软件，不开发 Agent 工作流；Agent/Application 1:1；必须有真实 Employee 与 Agent 双身份；每员工×Agent 和员工个人周免费额度；周一统一公司时区刷新；Team 发放时扣池，过期不返；超额资金硬限制；SSE 最终目标；安全治理和 FinOps；员工使用归员工、Team 发放归发放 Team、Provider 采购成本单独估算。

**本轮设计默认，进入具体 Phase 前需技术审查**：管理员 bootstrap 认证、具体 Key 表示和 HMAC 摘要/密钥加密参数、BigDecimal 精度/舍入、默认时区 Asia/Shanghai、初期 RabbitMQ 引入时机；Redis 已决定直接引入、SseEmitter/服务隔离方案。业务需求的批准不等于已经批准依赖安装或必须拆五个微服务。

**尚未确定**：各公司真实预算数字/配额、价格、供应商密钥、真实自部署模型是否存在、供应商可靠 Token/结算证据细节、最终微服务数量与性能。不得让本地 AI 填写虚假的真实财务事实。

## 三、协作分工

**总控（本对话）**：负责所有 docs 内容、产品事实、架构设计、实施默认、ADR/关键决策与工作包；Review 本地 AI 实现；每完成一次交付解释本次具体业务、技术原理、流程、表和接口。任何与文档矛盾的实际代码由总控裁决、更新合同。

**本地 AI（快速编码）**：只在用户批准了某一 Phase 的具体任务之后，按合同编写源代码、测试、迁移 SQL、Docker/CI 配置。它**不修改 docs、不自行增加中间件/设计领域、不自行开启下一 Phase**。工作包必须由总控先确定到具体表、字段、索引、接口/DTO、失败语义、测试、允许修改的文件。

**用户**：决定业务范围、重大架构取舍和 Phase 开始/关闭；重点掌握实际业务、每个技术存在的原因、执行流程及架构代价，能够面试独立解释。

## 四、给本地 AI 的统一交付格式

收到任务时先确认：Phase、Task、业务目标、范围及明确不做、主流程、架构边界、接口/表合同、允许新技术、验收样例。

提交后汇报：
- 本次实现的业务行为、修改/新增文件列表、Git commit SHA；
- 新接口、请求/返回样例，新增/修改表与 Flyway 版本；
- 实际运行的测试命令和准确通过/失败/跳过数；
- 复现步骤、失败路径、并发与安全检查；
- 遗留风险、技术债、任何不明确文档点。

发现需求冲突必须反馈“哪个文件、哪条规则、当前实现有什么影响”，不能默默替换技术或私自编辑文档。

## 六、技术学习与面试路线

P1：Spring MVC/DI、MySQL、Flyway、CI；P2：Spring Security、HTTP/密钥、Adapter；P3：SQL 索引、分页和元数据记录；P4：双身份与授权；P5：MySQL ACID、锁、BigDecimal、幂等；P6：审批状态机与事务；P1：Redis 环境；P7：Redis/Lua 与双实例容量/限流；P8：SSE/Java 并发/监控/部署路由；P9：优先级调度/舱壁；P10：安全规则、策略版本与审计；P11：RabbitMQ/Outbox/重试/最终一致；P12：JVM/JFR、压测和条件式微服务演进。

讲解每个新概念按：**业务背景 → 真实问题 → 技术是什么 → 为什么出现 → 核心原理 → 执行流程 → 替代方案 → AIGate 的实际用途 → 对照本次代码**。不一次性强灌全部技术，更不为丰富技术栈强装依赖。

## 七、决策/变更记录约定

重大架构决策使用本文附录持续维护（不单独建几十个 ADR 文件），每项保留**背景、问题、候选方案、决定、理由、收益、缺点和未来影响**。当前两项设计基线：
- **ADR-001 单体先行**：在需求复杂、真实并发未知的情况下选择模块化单体；好处是资金事务容易验证，代价是部署耦合；先双副本压测再考虑微服务。
- **ADR-002 权威账本与派生分析分离**：MySQL 同事务账本+Outbox，MQ 仅派生报表；好处是 Broker 中断账本不丢，代价是重复投递、重试、最终一致。

本轮目标是将文档压缩为 **7 份核心中文文件**。保留必须讲得清楚的合同和决策，不另建大量专项笔记；新业务重大修改要同步更新相关核心文件。

## 十、P0 D-01 确认 / D-02 自部署模型分类方案（2026-10-21）

用户回答“可以”确认 **D-01 业务决议：按原币种、公司时区自然月分立 Provider API 采购费用风险预算，付费模型调用与员工积分同时进行原子预留**；明确这控制的是 AIGate 已批准新请求的采购风险，不是对第三方供应商最终发票的绝对保证。

用户进一步提出**模型有第三方 API 与公司本地部署两种来源**，总控形成 D-02 待确认的设计：两类模型共享 Agent+Employee+Model ACL/安全/SSE 入口；THIRD_PARTY_API 用 Points+Provider 费用预算；SELF_HOSTED 通常用 Points+本地推理容量，不占第三方逐次 API 采购风险账，低优先级基础本地模型可使用额外且有限的员工周补贴额度；运营成本按 GPU 租赁/折旧、电费/维护等在 FinOps 单独汇总，不能冒充逐次供应商 API 账单。按部署记录 hostingMode/costModel、能力、容量健康与本地服务凭证，避免用“是否 HTTP API”错误分类。D-02 业务规则已在后续决议中获用户明确批准。

P0 其余全量数据库字段、API DTO、各业务块具体可执行任务和测试数据仍未冻结；不交本地 AI 开发。

## 十二、D02 已确认与 D03 已确认业务边界（2026-10-21）

用户已明确认可 D02：第三方付费 API 用员工积分及公司采购预算；常规企业自部署模型消耗员工积分且执行推理容量准入；获批的自部署基础保底模型采用独立、有限的员工周补贴额度，不能被当作零成本无限使用。网关共用双身份、权限及安全治理。用户随后认可 D03 的业务边界：同一员工的本地保底周额度跨 Agent 共用，设置单次 Token、速率及并发上限；额度或容量不足时拒绝，不自动切回收费 API。

当前正在细化 D03 的数据库唯一键、许可状态、补偿与待对账处理、单实例与多实例的容量来源和完整测试。具体 TTL、心跳、排队阈值等数值尚未冻结。P0 未冻结，不授权编码。
