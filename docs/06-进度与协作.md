## 二、项目的决策状态

**已经确认的产品事实**：Agent 是已有软件，不开发 Agent 工作流；Agent/Application 1:1；必须有真实 Employee 与 Agent 双身份；每员工×Agent 和员工个人周免费额度；周一统一公司时区刷新；Team 发放时扣池，过期不返；超额资金硬限制；SSE 最终目标；安全治理和 FinOps；员工使用归员工、Team 发放归发放 Team、Provider 采购成本单独估算。

**本轮设计默认，进入具体 Phase 前需技术审查**：管理员 bootstrap 认证、具体 Key 表示和 HMAC 摘要/密钥加密参数、BigDecimal 精度/舍入、默认时区 Asia/Shanghai、初期 RabbitMQ 引入时机；Redis 已决定直接引入、SseEmitter/服务隔离方案。业务需求的批准不等于已经批准依赖安装或必须拆五个微服务。

**尚未确定**：各公司真实预算数字/配额、价格、供应商密钥、真实自部署模型是否存在、供应商可靠 Token/结算证据细节、最终微服务数量与性能。不得让本地 AI 填写虚假的真实财务事实。

## 三、协作分工

**总控（本对话）**：负责所有 docs 内容、产品事实、架构设计、实施默认、ADR/关键决策与工作包；Review 本地 AI 实现；每完成一次交付解释本次具体业务、技术原理、流程、表和接口。任何与文档矛盾的实际代码由总控裁决、更新合同。

**本地 AI（快速编码）**：只在用户批准了某一 Phase 的具体任务之后，按合同编写源代码、测试、迁移 SQL、Docker/CI 配置。它**不修改 docs、不自行增加中间件/设计领域、不自行开启下一 Phase**。工作包必须由总控先确定到具体表、字段、索引、接口/DTO、失败语义、测试、允许修改的文件。

**用户**：决定业务范围、重大架构取舍和 Phase 开始/关闭；重点掌握实际业务、每个技术存在的原因、执行流程及架构代价，能够面试独立解释。

## 四、给本地 AI 的统一交付格式

收到任务时先确认：Phase、Task、业务目标、范围及明确不做、主流程、架构边界、接口/表合同、允许新技术、验收样例。

提交后汇报：
- 本次实现的业务行为、修改/新增文件列表、Git commit SHA；
- 新接口、请求/返回样例，新增/修改表与 Flyway 版本；
- 实际运行的测试命令和准确通过/失败/跳过数；
- 复现步骤、失败路径、并发与安全检查；
- 遗留风险、技术债、任何不明确文档点。

发现需求冲突必须反馈“哪个文件、哪条规则、当前实现有什么影响”，不能默默替换技术或私自编辑文档。

## 十六、P0-D06：紧急审批与三级流量调度细节设计（2026-10-21）

用户认可 D05 方向后，继续明确紧急任务/优先级业务：员工或 TeamManager 申请，Platform Admin 审批/拒绝或撤销；默认申请人与审批人不同；审批授权包含 Employee、Agent、Task、允许逻辑 Model、有限 Points 与时窗。审批不立即扣公司紧急池，实际运行前才在 MySQL 同一事务检查任务剩余额、公司紧急池与付费 Provider 原币种 EMERGENCY 专属份额。客户端只能提交可验证的 authorizationId 作为权限选择器，不能传 priority=EMERGENCY 直接越权。

Redis 三档 EMERGENCY/NORMAL/LOW 队列推荐**4:2:1 加权轮转 + 同档 FIFO + 总/个人有界队列 + 超时清理**；不抢占已经运行的 SSE/JSON 推理任务、不保证绝对 GPU 时间份额。更强紧急时延 SLA 需另审专属容量资源及成本。P7 开始就用同一个三档调度框架，P10 才开放带审批的紧急任务，不在中间替换队列算法。

**重大执行顺序修正**：D03 草案的“先 MySQL 预留额度，再在 Redis 等待”已改为**认证/准入并排队 → 获得执行许可 → 派发前再次校验权限/有效期/策略和价表 → MySQL 原子预留当时周/月的两类预算 → 持久唯一派发意图 → 上游调用/结算/待对账**。这样排队期间不锁钱，也不错误使用队列进入时的旧月份预算；预算不足释放容量许可且 Provider 0 次出站。Normal 在派发前资金不足且仍可安全保底时，最多一次重算/改选 LOW 模型重新排队，不能重试已送到上游的调用。故障协调仍以 MySQL Invocation 和推理服务真实状态为依据，Redis 许可过期不证明 GPU 已停止。

已在《01-业务与规则》《02-架构与技术》《03-数据与接口》《04-阶段与任务》《05-测试与验收》记录 D06 方案和 PRI-01～PRI-17 测试案例。用户回复“不错”认可 D06 的总体方案方向；双人复核、4:2:1 和具体超时属于 P0 待统一冻结的设计默认，不应理解为实测生产 SLA。P0 仍未冻结，P1～P12 没有代码。
