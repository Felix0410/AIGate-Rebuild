# AIGate 全量设计与业务块开发计划

> **P0：设计中 / 未冻结 / 禁止编码。** 自 2026-10-21 起采用“**完整设计先冻结，按业务块完整实现并同步测试**”的开发方式，不再为快速打通单独实现临时 Happy Path。下文是**开发依赖顺序的建议方案，尚待用户确认**；既有产品能力、成本规则和五领域边界均不删减。

## 一、与旧开发方式的根本区别

- **设计一次完成**：P0 要完成所有业务规则、总体架构、模块数据所有权、表/列/类型/约束/事务/索引、每个 API 的 DTO/权限/状态/错误、SSE/Provider 契约、MQ 事件结构、配置、边界失败策略、全部业务块和自动测试用例。不能留下“等开发到这里再做业务设计”的空白。
- **按业务块全量交付**：一个业务块交付该块所有已承诺功能，同时包含必要参数校验、角色授权、错误语义、幂等、并发、事务、数据迁移、单测、集成测试、API E2E、失败恢复和运维最小指标。不是先写成功接口、再另外立阶段补权限/异常。
- **依赖先行**：例如在可信员工+Agent 身份、额度预留和出站安全政策未准备好之前，**不开发可公开调用的收费 Provider Runtime**。可以独立完整交付账户、策略、模型目录等领域模块，并用公开 Facade/测试 Fake 验收。
- **实现不是一口气生成整个项目**：本地 AI 每次领取一个完整业务块（必要时一个业务块拆为多个可合并的实现任务），业务块验收一次完成。禁止同时跨模块自由设计、提前合并未完成的功能或擅自进入下一块。
- **架构演进仍有技术证据**：完整设计不等于把五个业务领域机械拆成五微服务。**D15 已批准 P1 直接两个真实服务、P11 第三个 FinOps 服务**，其数据边界和跨进程测试见《02-架构与技术》；逐业务块可以同时完成该块所需的高阶保护，不等于为了技术而堆依赖。

## 三、每块“全量完成”统一 Definition of Done

一个业务块完成须同时满足：

1. 该业务块的**完整需求**、角色/权限、端到端状态流（成功、失败、取消、重试、过期）全部实现；
2. API/DTO/认证/错误码、Flyway DDL、索引、事务边界与唯一键均符合冻结设计；
3. 影响余额/外部账单的操作完整实现幂等、并发/锁、补偿/待对账，绝不只测成功；
4. 自动单元、MySQL 集成、HTTP E2E、需要的消息/Redis/网络故障测试全部通过；
5. 代码已提交，提供 **测试命令、通过/失败/跳过数、迁移版本、接口清单、运行方法、已知技术债**；
6. 总控完成 Code Review、架构/安全/资金检查、技术教学和面试复盘，用户确认验收后推进。

## 四、编码任务如何分派

**编码之前就完成所有业务块的任务合同**：对每个 Phase 在本文冻结 Business Goal、Scope、Main Flow、Architecture、Tasks、Acceptance Criteria、Knowledge Points，另外在《03-数据与接口》给出完整表字段/请求响应；在《05-测试与验收》给出每块明确测试编号与期望结果。本地 AI 只执行一个已冻结的业务块；它可以内部提交多次，但直到全部验收项通过，业务块都标记 IN PROGRESS，不算交付。

任务执行过程中不能新增未审查的业务规则/中间件，也不能把必要的鉴权、异常、并发留到其他阶段。只有真正**跨业务块的独立增强能力**（如后续智能路由、独立 FinOps）才允许作为后续完整块，而不是同一业务块的欠账。

## 六、验收与学习

每个 Phase 结束依次做功能检查、Code Review、测试、架构、技术债、进度、架构决策、知识整理和面试表达；等待用户确认才进入下一 Phase。

用户重点学习这次业务做了什么、调用链、表和接口、为什么采用 Java/数据库/Redis/MQ/SSE、它们如何失败及替代方案。本地 AI 写代码不是用户必须亲手重写每一行代码的前提。

## 七、已接受的技术路线调整：Redis 从第一天纳入（2026-10-21）

用户明确提出避免明知有用仍先做临时方案，并同意 Redis 直接引入。**设计决定**：P1 基础环境创建 Redis 连接/配置与 Testcontainers 集成验证；P7 Gateway 完整业务块直接使用 Redis Lua 实现跨实例 RPM、SELF_HOSTED 容量许可和有界等待；P9 在已有 Redis 设施上完成保底多档流控与共享策略，禁止先实现单实例 Semaphore/MySQL 计数等待队列再重构。Spring Data Redis + Lua 为既定方案，不另加分布式锁框架。

但 Redis 不进入权威账本、Team Grant、供应商采购预算的资金事务；这些始终由 MySQL 保证 ACID。Redis 不可用则新限流/容量准入 fail closed，已执行或待对账资金不能被 Redis 状态删除。P1～P12 仍为待批准的依赖排序，P0 未冻结前不编码。

## 八、P0-D06 对所有业务块的合同影响（待确认）

**先排队、后资金预留**现为总体实施设计提案：P7 的完整 Gateway 业务块必须从第一次实现就采用 Redis 全局入场与有界三档调度框架，不再做 P7“先资金预留再等待”和 P10“替换调度器”的返工。P9 只添加已批准的公司保底资金和多档入场策略；P10 只添加真实紧急审批生命周期/独立资金与对已存在三档调度的授权激活，属于独立可验收业务能力。

P10 完成的定义包括：审批人权限、不可自批、Employee/Agent/Model/Task 精确匹配、申请/批准/拒绝/撤销、到期与并发幂等、公司 Points 与 Provider 专属币种月预算、Redis 加权公平与队列期限、权威 MySQL 全部失败测试。所有业务块不能把必要鉴权/资金控制/队列清理推到下一块。

编写本地 AI 的任务时须明确测试 PRI-01～PRI-17、FAL-01～FAL-13 以及涉及 D03/D04 的链路集成。P0 全部文档详细冻结和用户批准前，本设计没有授权任何代码实施。

## 九、P0-D07 对模型目录、调用和路由业务块的影响

P3 完整交付 LogicalModel/Provider/Deployment 的管理合同，包括模型身份与版本、托管类型（THIRD_PARTY_API/SELF_HOSTED）、区域/数据安全、接口能力、价表版本、凭证保护、端点白名单及策略发布/回退；不能简单把两个不同模型因 API 协议一致当作等价部署。

P7 的第一次完整 Gateway JSON/SSE 实现就必须使用 D07 的模型候选过滤、正确部署的 Redis 容量许可、派发前二次授权/价表锁定、同一模型多部署的有界安全重选和不可确认已出站请求禁盲重试，不能先开发“随机挑 Deployment、过段时间再补账务”的中间方案。

P8 是完整独立的**健康/成本/负载自适应治理能力**：完善观测和评分、路由策略发布、指标告警、双实例/故障压测；不应把 P7 所需的基本有效性、类型/预算检查留作 P8 的欠账。要把 RTE-01～RTE-12 与具体模拟 Provider 固件纳入工作包测试。

仍然坚持 P0 全部业务设计完成并获批准后才编码。

## 十、P0-D07.1：路由算法与健康规则的业务块交付合同

已给出的初始算法按“硬过滤 → HEALTHY 优先 → 管理路由优先级 → Redis 共享负载标准化 → 可靠延迟 → 同币种费用 → Deployment ID”稳定排序。初始熔断规则为60秒窗口、至少20样本、错误率20%降级/50%熔断、连续3故障直接熔断、30秒冷却、健康证据120秒过期、单并发受控探路；这些数值均需要 P0 统一审查后冻结，并不是已经经过真实负载验证的线上阈值。

P3 Model/Provider/Deployment 业务块必须一次交付逻辑模型身份/版本与唯一内部积分价的配置合同、Provider/Deployment 采购原币种价表、发布/禁用/区域/能力规则与配置校验测试。P7 Gateway 业务块必须一次交付同 Model 候选硬过滤、Redis 许可、派发前路由和价格双重校验、统一积分价、原币种采购预算及不安全重试阻断，并有 RTE/ALG 测试。P8 完整交付动态健康窗口、熔断/探路与费用/延迟负载的可配置路由治理、运维报表和负载故障验收；P7 的必要路由安全和基本健康判断不能留到 P8。

P0 尚需冻结完整管理 API 的 JSON 请求/响应字段、价格版本有效区间 SQL 约束、健康事件具体归属、Profile 版本、重选总等待截止与全部 RTE/ALG 可执行测试输入。不能让本地 AI 自行编造评分公式、跨币种换算、计费上限或上游重试行为。

## 十一、P0-D08：Provider JSON/SSE 完整业务块交付合同

### 18.2 P1 工作包和验收增量（覆盖 D12 只有单应用的局部假设）

**Business Goal**：从第一个真正可运行的业务块开始，就拥有独立的 API Gateway 和 Core 两个可运行/可重启的微服务。不是只建两个 package 或两个启动类用相同 DB。

**Scope**：P1 原有 5 张业务/管理表和15个管理 API 不删；D18 为并发初始化安全增加第6张 bootstrap_control 表和2个受控运维 Bootstrap API。新增 Maven 多模块/共享最小 DTO、独立 Gateway/Core Spring Boot、独立健康端点、Gateway 管理路由、内部 Docker Compose 网络、Core 内外端口限制、环境配置和服务边界 E2E。P1 不启用模型 Runtime、P11 RabbitMQ 或 FinOps 空进程。

**Main Flow**：用户 HTTP → aigate-gateway (/api/v1/teams 等) → Spring Cloud Gateway MVC 内部 HTTP 转发 → aigate-core Spring Security mgt_ Key 认证/RBAC/DB 写操作+审计 → JSON 返回 Gateway → 用户。用户直接请求 /internal/v1/** 或未授权尝试直达 Core 均不能得到业务数据。

**Architecture / Tasks**：
1. 先由总控冻结多模块 pom、Boot4.1.1、Spring Cloud2025.1.2 Gateway MVC Starter、MyBatis-Plus Boot4 3.5.17、Flyway core+mysql、MySQL8.4、Redis8.4、Maven Wrapper/Compose/Testcontainers 的具体可编译合同；版本冲突要回 ADR，不让本地 AI 自选框架。
2. Core 独占 core_db，实施 D12/D18 六表/15个普通管理 API+2个 Bootstrap 运维 API 与事务审计；Gateway 不得引入 Core 的 Mapper/Entity/JDBC 账号；Core 不把 mgt_ 权限交给 Gateway 的代理 Header。
3. Gateway 用单一 /api/v1/** 显式安全转发至 Core（P11 FinOps 外部 API 仍由 Core 接口承接授权代理，D17），请求方法、Authorization、Idempotency-Key、Content-Type、HTTP status 和安全错误原样保留；拒绝 /internal/** 及未知危险路径，并限制请求体/超时/响应头泄密。
4. Compose 首次真实启动两个 Spring Boot 应用+MySQL+Redis；Core 的内部服务地址可配置、只有 Gateway 暴露业务外部端口，Core 不公开映射给宿主网络默认对外用户。
5. P1 原有 P1-01～P1-24 仍必须经 Gateway 的外部端口跑同一套管理 E2E；新增 MSC-01～MSC-08（独立启动/路由/权限/故障/隔离）见《05-测试与验收》。所有管理业务仍无真实 Provider 出站。

**Acceptance Criteria**：两个不同进程、两个独立 Spring Boot App、可分别 stop/restart、固定独立 Maven module、Gateway 外部管理请求经过 HTTP 才进入 Core；Core 业务变更全部有审计；Gateway 绝不写 DB/越权放行；正常503/超时/日志脱敏可验证。P1 不以“一个进程里分 controller package”冒充微服务。

**Knowledge Points**：进程隔离、独立部署与业务领域概念区分、Spring Cloud Gateway Server WebMVC 与 AI Model Router 区分、HTTP 反向代理/请求头、Docker Compose DNS、服务端再鉴权、超时与故障传播、Spring Cloud BOM 和 Boot4 兼容、服务边界测试。

### P1-EDGE（归属原 P1 的完整增量，禁止委托本地 AI 补设计）
