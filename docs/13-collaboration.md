# 开发协作与文档治理

## 1. 单一事实来源

文档以主题而非聊天/时间顺序组织：Requirements → Architecture → Domain → Database → API → Protocols → Roadmap → Module → Tests → Progress → ADR。一个字段只有一个权威持久定义；阶段任务引用规范而不拷贝多份可漂移版本。旧追加式D01～D56/R01～R10文档在Git历史中留存，**不继续作为最新实现指令**。

## 2. 职责边界

- **总控（ChatGPT）**：所有需求、数据、接口、协议、测试、ADR的设计和仓库文档维护；发布精确阶段任务，审查代码/提交结果。
- **本地AI**：仅从用户签收P0后，在P1～P12根据完整Phase合同写/测源码、迁移、Java、Redis Lua、Docker、CI；不得自己选架构/增加业务字段/写正式docs。**P0全程由用户在IDEA亲手搭建和验证，不交给本地AI。**
- **用户**：P0在IDEA中亲自操作并完成工程兼容验证；P1起运行/验收AI产物；判断Phase启动/完成，批准重大架构决策。

## 3. 不允许的行为

本地AI不得把未定实体字段假设成默认值、把UNKNOWN费用记0、把Redis重启后的空集合当物理资源空闲、跳过SecurityApprover、自动额外调用付费Provider、修改已运行Flyway版本、删除其它Phase设计、扩大Gateway allowlist或进入下一Phase。

如发现合同自相矛盾，停止相关子任务，提交「业务场景→冲突的两个定义→实际DB/API/网络证据→受影响测试」，由总控更新规范及必要ADR。

## 4. Phase交付

每个实施包必须交付：修改文件清单、接口与迁移、运行命令、pass/fail/skip、风险与技术债、Code Review、知识点和面试表述。该Phase结束后等待用户批准再推进。

## 5. 规范状态约定

`DESIGN_REVIEWED` = 静态检查；`NOT_RUN` = 未运行；`PASS/FAIL/BLOCKED` = 有日志的工程检查；`FROZEN` = 用户确认的稳定规范。两者不能混用。

## 6. 文档审查清单与交付输入

当前全部规范的文件名和职责以[文档总清单](./document-inventory.md)为准。启动某Phase时，执行包至少包含该Phase的`pNN.md`、首次需要的Core/FinOps数据库版本、相应API与RPC、受影响协议、专项测试分册和已有未关闭技术债。执行AI不能只读`README.md`或从历史Dxx编号自行拼业务。

Phase完成后的真实PR/提交与测试记录由总控审阅、更新Progress/Architecture/必要ADR/知识与面试表达；用户确认前不得修改下一Phase为STARTED。静态设计、测试NOT_RUN和真实PASS需要明确区分。

## 7. 实际开发工作流：唯一执行闭环

项目采用**设计由总控维护、P0由用户在IDEA亲手搭建（总控一步步教学）、P1～P12源码由本地AI实施、真实环境由用户运行、提交由总控审查、Phase由用户签收**的流程。全过程不因使用AI而跳过实际测试，也不让执行AI自行提出新业务方案。固定主链如下：

```text
当前Phase允许启动
   ↓
总控准备当前Phase一次完整实施合同（仅风险极高时插入检查点）
   ↓
P0用户在IDEA逐步操作；P1起本地AI完成当期最小Happy Path
   ↓
当期执行者补齐本阶段的安全/异常/幂等/并发/测试
   ↓
用户在IDEA运行真实依赖/测试；阶段内必要时修复，原则上一次Git交付
   ↓
总控读取Git提交和变更，进行Code Review＋业务合同校验
   ├─ 有问题 → 总控出精确修改任务 → 本地AI修复 → 再提交与复核
   └─ 通过 → 总控解释本次业务变化/接口/表/技术选择
                      ↓
                当前Phase整体完成则进入关闭审查；若未完继续修复
                      ↓
                总控更新正式文档、技术债和复盘 → 用户签收
                      ↓
                只有用户确认后才允许进入下一Phase
```

### 7.1 开始某个Phase：启动门禁

- 只有用户明确启动当前Phase才能开始实现。P0允许进行工程兼容PoC，P1只能在P0真实PoC与用户签收之后开始；“文档审查完”不等于“代码已通过”。
- 总控确认依赖Phase已经签收、当前功能和未来功能边界、需要哪一个SQL迁移版本/接口分册/协议/测试文件；不可因实施方便修改阶段顺序。
- **默认一个Phase只发布一份完整实现合同、一次最终代码交付及Code Review**。合同可附E01～E04等检查维度，但这些是**同一交付中的内部验收项，不是4个独立编码批次或4次Git提交**。只有遇到高风险兼容门禁、不可逆数据库变更或真实阻塞时，才安排最多1～2次中间检查，而不是机械切成小任务。
- 如需修复可多次提交代码，但**只有一个最终Phase签收**。减少提交频率并不省略当期全部接口/数据库/安全与回归验收。P0采用用户在IDEA的教学操作节点，**不是**独立工作包，也不要求每节点提交Git。

### 7.2 P1～P12总控下发给本地AI的完整Phase合同必须包含

| 字段 | 必须明确的内容 |
|---|---|
| 任务身份 | `Pxx-Exx` 或 `P0-COMPxx`；任务Goal、允许开始的前置条件、当前要打通的具体业务主链 |
| 修改范围 | 本次可以新建/修改的Java模块、类职责、受控配置、Flyway或其他代码资产；明确禁止修改的正式`docs/**`和未来Phase源码 |
| 数据合同 | 本次迁移文件及权威SQL文档、既有列/唯一索引/外键、事务边界；不能由执行AI自行增表改字段 |
| 接口合同 | 指向具体API分册、受信RPC、Gateway method+path允许集，以及精确请求/响应/状态/错误行为 |
| 执行流程 | 从HTTP进入、认证与ACL、Service、MySQL、返回值、失败回滚的步骤；并发/幂等/安全由权威协议约束 |
| 依赖和选型 | 明确固定版本、当前允许引入的技术、为何需要；未进入对应Phase的Redis/MQ/Provider不得提前安装 |
| 测试与完成条件 | 有关caseId，Happy Path和当前必须具备的负例、独立启动/迁移/集成命令、预期DB/网络事实与退出条件 |
| 交付与停工条件 | 变更文件清单、真实命令/日志、Git SHA与发现问题；如DDL/API/协议相互冲突立即暂停受影响子任务，反馈总控 |

本地AI应按合同自主处理常规Java语法、框架API用法、可读性修正和测试实现；**不得自主创造业务字段、鉴权策略、资金规则、接口兼容别名或新架构**。需要做出新的业务/架构取舍时，先交总控定稿再编码。

### 7.3 一次工作包的实施顺序

1. **最小可运行链路**：从一个真实调用入口到一个可检查的结果；已有的身份/账务/安全硬约束不许临时绕过。
2. **当期完整性**：主线跑通后，对照该工作包既定测试补参数校验、合法错误、权限、并发和幂等；不因“先做Happy Path”留下可以付费/越权的通道。
3. **本地真实验证**：运行当前所依赖的MySQL、Gateway/Core、Redis、MQ等（仅首次实际使用的组件），记录命令、测试结果与关键数据库/网络证据。编译成功不代表运行成功，Mock不等于真实组件测试。
4. **Git提交**：提交源码、配置、数据库迁移、测试；实验性Secret、真实Prompt和Provider凭证绝不提交。真实日志若会泄漏密钥则先脱敏。正式设计文档由总控更新，不由本地AI覆盖。
5. **Code Review回合**：当前Phase整体交付后，用户告知“已提交”即可触发总控读取仓库最近提交及差异；不要求用户重复已经说明的Phase和执行成功信息。总控检查需求实现、方法边界、真实SQL、授权、异常、测试覆盖和架构漂移；发现问题下发针对性修复包，再提交复查。

**状态语义**：`CODE_SUBMITTED`表示代码已提交；用户说明测试已通过可以记为“用户报告本地PASS，待总控复核”，不得无运行日志就声称总控亲自执行过测试。`PASS`/`FAIL`/`BLOCKED`需可复现证据；`NOT_RUN`不允许被视为通过。

### 7.4 每次提交后的教学与复盘

总控在完成本工作包Code Review后，按以下顺序向用户解释本次新增内容：

- **业务**：这次要解决谁的什么问题；此次新增了哪些业务行为、API、表/列及重要数据流。
- **原理**：本次真正新出现的Java/Spring/MySQL/网络/分布式概念是什么、为什么出现、解决了什么、没有它会怎样。
- **对比**：当前项目为什么用它，与更简单/更复杂的替代方案相比有什么收益和代价。
- **代码落点**：实际实现在哪个Controller/Service/Mapper/迁移/配置；一条请求如何走完，重要异常怎样处理。
- **验证**：本次通过/失败的是哪些测试，是否发现真实问题，留下什么技术债；可怎样在面试中准确描述。

重复出现且用户已掌握的概念不必每次重新讲一遍；重点是**本次业务功能与新技术**。一次提交先讲清楚核心新增点，不提前灌输未来Phase的整套高级技术。

### 7.5 Phase关闭审查与用户签收

当阶段内所有工作包完成后，总控依次执行：①功能清单逐条比对；②Git diff/代码审查；③真实测试case与环境证据检查；④架构/依赖/接口/DB一致性检查；⑤记录技术债；⑥更新`10-progress.md`；⑦更新`03-architecture.md`中已实现与待设计差异（有变化时）；⑧必要时新增/修订ADR；⑨整理本阶段知识点；⑩更新面试表达。只有通过阶段门禁后才提交用户确认是否进入下一Phase。

如测试失败/依赖不可用，阶段保持`BLOCKED`或`IN_PROGRESS`，总控给定下一次修复/证据任务，不自动宣布Phase完成。设计变更由总控同步到当前权威的Requirements/DB/API/Protocol/Phase/Tests，再允许本地AI继续实现。

## 8. P0：用户在IntelliJ IDEA逐步亲手完成，不交给本地AI

**P0执行方式与P1～P12不同。** 由总控以[IDEA手把手P0指南](./guides/p00-idea-hands-on.md)按操作节点逐次教学，用户亲自clone Git、配置JDK21、创建聚合父POM及Gateway/Core两个Maven子模块、连接MySQL8.4并运行Flyway V1六表、验证HTTP/Security/Jackson3/SSE/异常与隔离。每个节点先得到实际结果，遇到错误先排查；**P0不能让本地AI生成工程或替用户测试**。

操作过程的八个学习节点仅作为IDEA引导顺序，**不是八次任务下发，也不是八次Git提交**。P0整个阶段一次最终提交/总控Code Review（必要时可临时保存中间提交，但不按节点强制提交）。原P0-A/B/C划分废止，不再作为开发包；COMP01～10仍为单次P0验收中必须实际通过的独立测试条件。详细技术与版本规定见[P0兼容测试合同](./tests/p00-technology-compatibility.md)。

P0教学从**“IDEA Clone Repository→确认Git远程→设置JDK21”**开始，一次只教一个操作节点。P0最终必须有真实MySQL/HTTP/SSE证据、复查和用户签收后才能开启P1。

## 9. 最简沟通协议

- **总控→本地AI**：P1～P12每个Phase一份完整开发任务书；可直接复制执行；以Phase、SQL、API、协议及验收ID的现行文档为准。P0不向本地AI下发代码任务，而是由总控逐步教用户使用IDEA。
- **本地AI→用户**：实际修改文件、执行命令、通过/失败用例、Commit SHA、无法自行解决的合同冲突。不得把“待修”冒充“已完成”。
- **用户→总控**：P0可逐节点告知IDEA操作结果/具体错误，整个P0完成后说“P0已提交”；P1以后说“已提交”或给出Commit SHA；总控应利用已知进度和GitHub仓库定位提交，开始Review，而不是重新追问任务背景。
- **总控→用户**：明确`已实现/有问题/待验证`，讲清本次业务与新知识，必要时发给本地AI精确修复任务；仅在该Phase最终审查后询问用户是否签收下一Phase。
- **阻塞时**：给出具体错误、第一次失败步骤、最小重现与受影响设计；总控判断是代码Bug、环境问题还是设计冲突。不得让本地AI通过偷偷升级框架、关闭安全或放宽验收“解决”问题。

本流程只管理真实开发与学习闭环，详细业务合同仍以[Roadmap](./08-roadmap.md)、[各Phase](./phases/README.md)、[测试计划](./09-test-plan.md)和[正式API/数据库/协议](./README.md)为准。
