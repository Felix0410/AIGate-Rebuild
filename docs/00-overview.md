# 00 · Project Overview

## 业务场景

一家有大量员工、不同部门和既有 Agent 的企业，希望统一连接多家模型 Provider。员工使用代码助手、客服助手、知识检索助手等现成 Agent，向 AIGate 发送模型调用；系统先核对实际员工身份与 Agent 身份，再校验授权、资金、合规政策，选择模型部署完成请求，最后记录可确认的 Token 和成本。

## 核心定位

AIGate 负责：
1. 员工、团队、Agent(Application)、Provider、逻辑 Model、具体 Deployment 的纳管。
2. Agent Key 与员工独立 Key 双重验证、员工可用 Agent 权限和 Agent 模型白名单。
3. 按实际 Token 计量和内部积分价格结算；个人周额度、团队补充额度、企业保底预算和应急预算。
4. 流量治理、受控模型路由、SSE 增量响应和网关可观测性。
5. 企业敏感信息发送前的安全策略和合规审计。
6. FinOps 成本归集、趋势、异常告警和人工优化决策。

AIGate 不负责开发 Agent、执行 Agent 工作流、管理 RAG 知识库、自训练模型、代替企业支付供应商账单或直接管理外部 Provider 的 GPU。

## 业务角色

Employee：凭个人授权使用现有 Agent 调用模型、看本人积分、申请补充额度。
Team Manager：审批或主动发放 Team 池积分，管理 Team 的内部资源预算。
Platform Admin：管理组织身份、Agent、Provider、Model、Deployment、定价、安全政策与审计。
FinOps Reader：查看员工实际消耗、各 Team 发放支出和外部 Provider 费用估算。
Managed Agent：现有软件客户端；每个 Agent 与 Application 一对一，拥有独立密钥，但不能冒充员工。

## 核心用户故事

员工在代码 Agent 中选择允许的逻辑模型。Agent 携带自身 Key 与员工独立凭证。网关完成认证、权限和安全检查，预留足够积分后路由至同一逻辑模型的健康部署，转发 JSON 或 SSE 响应。收到可信 usage 就准确结算并释放剩余预留；断线后费用不明则保留待核对状态。结算事件用于后续成本报表，而不是由异步消费者决定实际扣费。

## 不变量

- 不能仅凭请求体传入 employeeId 证明员工身份。
- 不能调用 Agent 白名单以外的模型，也不能在降级、紧急状态绕过敏感数据政策。
- 内部积分资金余额和账本只由 MySQL 的账务边界更新。
- 企业付费预算耗尽时不继续无授权付费请求。
- 团队发放积分成功即扣团队池；积分到期未使用不返还。
- 实际模型使用归真实员工，Team 发放内部预算支出归发放 Team，供应商费用单独按 Token 和价格估算。
- 默认不保存原始 Prompt、模型完整回复和明文密钥。

## 部署与规模

第一版为单企业模块化单体。上万名员工只代表需求场景，不代表已支持上万连接。先经可复现测试验证多实例；只有独立扩容/故障隔离的收益大于成本，才从候选五个业务边界拆分微服务。

## 设计默认

企业统一账务时区采用可配置参数，默认 Asia/Shanghai；数据库事件时间用 UTC。初期支持 OpenAI 风格 Chat Completions，另行扩展 Provider Adapter。新项目所有功能从零实现，历史旧代码不再视为当前工程资产。
