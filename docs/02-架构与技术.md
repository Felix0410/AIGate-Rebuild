# AIGate 架构与技术设计

> **当前唯一实现起点：Java 模块化单体。** 本文包含主要架构选择及其理由，既是设计约束，也代替当前单独分散的 ADR 文件。本次已确定 Redis 为基础设施，P1 即集成连接与测试，实际容量/限流能力跟随相关业务块一次交付；MQ 等其余技术按明确业务需求接入。

## 一、总体架构

以 **Java 21 + Spring Boot 4.1.x + Spring MVC + Spring Security + MyBatis-Plus + MySQL 8.4/Flyway** 实现一个可运行应用。业务模块内聚、通过公开服务接口调用；管理面和 Agent 运行面分开处理认证、超时与并发资源。外部 Provider 经过统一受控 Adapter；第一种协议为 OpenAI 兼容 Chat Completions。

```text
现有 Agent + Employee
       ↓（双身份）
  Gateway Runtime → Identity/Control 授权 → Governance 出站安全规则
       ↓
  Quota & Billing：MySQL 短事务原子预留
       ↓
  Gateway：模型 Deployment 路由 → Provider JSON/SSE
       ↓
  Quota & Billing：结算 / 待核对 + 同事务 Outbox
       ↓
  RabbitMQ（按阶段引入）→ FinOps 异步报表与告警
```

**不能把一次模型调用设计为对五个微服务逐 Token 远程请求。** 配置/安全策略以后可用受控版本快照执行，财务预留/结算在单次请求粒度进行。不能在 Provider HTTP 或 SSE 持续传输期间持有 MySQL 行锁。

## 二、五个领域边界（先五个代码模块）

| 模块 | 唯一职责 | 禁止事项 |
|---|---|---|
| Gateway Runtime | runtime 鉴权入口、路由、SSE、流控、Provider I/O、调用元数据 | 直接 UPDATE 积分余额 |
| Identity & Control | Team、Employee、Agent、凭证、Model/Provider/Deployment 配置、基础权限 | 根据请求体 employeeId 认定身份 |
| Quota & Billing | 周额度、Team 授额、公司保底/紧急池、预留、结算、账本、对账、Outbox | 由 Redis 或 MQ 决定已扣积分 |
| AI Governance | 数据分类、内容/模型准入规则版本、受控例外与最小审计 | 默认存储敏感 Prompt 原文 |
| Analytics & FinOps | 通过确定事实异步建立使用、发放、采购估算的分析读模型 | 回写权威余额或把三口径直接相加 |

Java 推荐包：bootstrap、common、identity、catalog、gateway、quota、governance、analytics、integration、observability。各领域内部按 controller/dto/application/domain/repository 分层；跨域只经公开 Facade，不跨模块直接 Mapper 修改他域表。

## 三、关键架构决策

**决策 A：模块化单体先行。**
候选方案有大单体、模块化单体、起步五微服务。当前选择模块化单体：让双身份、账本、Provider 代理先形成可测试闭环，避免早期五个应用导致网络依赖、身份传递和分布式数据一致性负担。代价是部分模块初期一起部署；需严格遵守边界。后续要拆必须提供压测和故障隔离证据。

**决策 B：MySQL 为唯一权威积分账本。**
行锁/唯一业务键/短事务保证团队发放、资金预留、结算原子化。Redis 快但故障/淘汰/持久化语义不适合作权威资金余额；MQ 可能至少一次投递，不能直接负责扣积分。代价是热点余额争用、SQL 索引与死锁重试，需要测试及监控。

**决策 C：账本 + Outbox 后异步分析。**
团队发放和调用结算在 MySQL 提交时，同事务写安全的待发布事件；异步投递给 FinOps。Broker 不可用账本仍正确且事件留待补发，消费者按 eventId 去重。代价是延迟一致性、Outbox/Inbox、重试、死信、版本和积压管理。财务计量不能宣称 RabbitMQ 提供跨 MySQL 的“恰好一次”。

**决策 D：Spring MVC SSE 起步。**
先沿用现有编程模型，使用异步请求和有界执行器；WebFlux 不是为了长连接就必选。若实测 Servlet 写阻塞、线程和连接瓶颈，再比较响应式方案。必须监控活跃连接、取消、超时、压力和尾部 usage 丢失的账务处理。

## 四、技术引入表：问题、替代、代价与阶段

| 技术 | 解决 AIGate 哪个问题 | 不用时的做法 / 引入代价 | 阶段 |
|---|---|---|---|
| Java 21 / Boot 4 / MVC | API 与模型代理主服务 | 纯 Servlet 成本高；Boot 配置/版本兼容需维护 | P1 |
| Spring Security | 管理员角色及 Agent+Employee 双凭证 | 手写过滤器可能遗漏，初期 opaque Key 需安全管理 | P1～P4 |
| MySQL/Flyway | 组织管理与权威资金事务 | 内存/Redis 不提供相同可靠财务语义；需行锁索引 | P1、P5～P6 |
| Testcontainers / Docker / CI | 在可重建数据库中验证和持续构建 | 手工测试无法稳定证明 AI 写的代码 | P1 |
| Redis + Lua | 网关多实例共享限速、推理容量许可和有界等待队列 | 不再开发 JVM/MySQL 容量协调临时代码；额外承担 Redis 故障、租约与脚本测试 | P1 集成；P7 网关与容量、P9 流控深化 |
| SSE（MVC） | 模型增量输出、低首字节延迟 | 普通 JSON 简单；SSE 多连接、断连计费较复杂 | P8 |
| Micrometer、Prometheus、Grafana | Deployment 延迟/压力、SSE 和资金运维指标 | 只有日志难量化问题；需控标签基数 | P8，基础 Actuator 可更早 |
| RabbitMQ | 异步通知、已结算事件、成本聚合告警 | Outbox+轮询可先用；需 ACK、Confirm、重试/DLQ | P11 主要阶段 |
| Kafka | 大规模保留/重放事件流和多个分析消费者 | 当前 RabbitMQ+权威账本足够；分区/Offset 运维成本高 | 有实测需求再评估 |
| OpenTelemetry | 拆服务后的链路追踪 | 单体 traceId 先够用；采样与上下文传播更复杂 | P12 条件 |
| Spring Cloud | 真实独立服务后 RPC、负载、配置及故障治理 | 简单 HTTP + Compose 可能已够；兼容和部署成本增加 | P12 条件 |
| Elasticsearch / ClickHouse / Nacos / K8s | 特定搜索、OLAP、发现/配置、大集群运行问题 | 当前无强需求；增加数据一致性/运营复杂度 | 不预装 |

**消息队列选型**：RabbitMQ 是当前**设计默认**，不是用户要求必须使用的最终产品承诺；Kafka/RocketMQ 是备选，不同时引入多套。引入 RabbitMQ 前证明使用场景并做 Spring Boot 4.1 的兼容集成测试。

## 五、服务演进与容量证明

阶段路径：**可测试单体 → 两个同版本单体副本 → Redis 共享限流和真实 SSE/数据库压测 → 测出管理面、账本和网关独立资源问题 → 按证据拆分**。候选为 Gateway、Control、Quota、Governance、FinOps；Worker 进程不是凭空多出一个业务领域。

微服务拆分评审必须回答：当前方案、遇到的可测问题、单体内优化为何不够、候选拆法及数据归属、实际收益、RPC/异步一致性/故障/运维代价。即使最终保持两个副本单体，只要指标证明适合，也属于正确架构决策。

## 六、尚未授权的技术行为

目前只批准**设计规划**，没有批准依赖安装、拆微服务或开始 P1 编码。价格配置、预算数字、公司真实模型/Provider Key 不编造；设计默认公司时区 Asia/Shanghai、时间存 UTC、资金额度以 DECIMAL 表达，细节见数据设计。

## 七、完整业务块交付约束（2026-10-21）

项目实施方法已变更：**编码前冻结全部七份文档；之后每个完整业务块一次交付所承诺的业务、保护和测试**。模块化单体起步是经过设计的目标部署形态，不是“先写只能跑成功场景的临时代码”。每个业务领域要在分配工作包前得到明确 API、持久化模型、异常处理、权限和故障测试合同。可以按多个 Git commit 完成一个业务块，但业务块直到完整验收之前都不视为已交付。

为了保证首个实际付费出站具有全套保护，当前**待用户确认的新依赖排序**将 Employee/Agent 双身份、模型目录、账本、团队发放和企业出站安全策略放在 Gateway 实际收取外部费用之前；调用记录与 SSE 与 Runtime 业务块一起完整交付。安全治理虽然独立业务领域，不意味着已满足基础认证就可绕开内容规则。

一个重大**未解决的架构门禁**：积分账本的可用 Points 和企业对 Provider 的实际采购风险（供应商币种）不是同一个资产。公司保底应同时符合两个硬预算（内部 points + 真实 Provider 成本上限），Provider 费用风险预留/结算需要独立建模。完成前不得将“积分额度正确”宣传为“企业外部现金成本不会超预算”。Redis 只做共享限流，不能补救真实现金限额缺失。

## 八、P0 D-02：统一网关支持外部 API 与企业自部署推理（业务已确认，技术细节设计中）

### 部署类型与计费模式分离

拟在 Deployment Catalog 中区分 `hosting_mode = THIRD_PARTY_API | SELF_HOSTED`。业务上还需独立保存 `cost_model`（首版为 PER_TOKEN_API / INTERNAL_RESOURCE），避免将“接口协议”“算力所有者”“内部积分单价”“企业实际资源成本”混为一谈。SELF_HOSTED 的推理服务可能同样提供 OpenAI 兼容 API，如 vLLM；因此 Gateway 的 Provider Adapter 可在安全受控端点下复用 JSON/SSE 解析，不能为了区分两类来源复制整条网关业务链。

**EXTERNAL / THIRD_PARTY_API**：Identity/Policy → 选择部署、冻结两种价格 → 单 MySQL 事务同时预留 POINTS+公司原币种采购风险额度 → 发出供应商 API → 依据可信 Token 双账结算或双账待核对。

**SELF_HOSTED 正常**：Identity/Policy → 选择获准自部署节点 → 检查推理健康/有限并发/队列，并授予有有效期的容量许可 → 预留本次员工内部 POINTS（或受批准的本地补贴 Token 配额）→ 推理 JSON/SSE → 释放容量许可，按可信 usage 结算 POINTS/补贴额度或待核对。**不占用逐次第三方 Token API 采购预算**，但需有独立算力容量约束及后续真实云 GPU 费用管理。

**SELF_HOSTED 保底**：正常积分和企业付费保底无法继续支撑时，只有公司明确授权的低成本基础模型、员工独立周限额及推理集群可用容量同时满足，才允许继续有限服务。不能静默把模型路由到更贵的收费外部 Provider。

### 路由与并发的关键失败边界

- **先定 Deployment 再定预算合同**：按是否会产生逐次外部供应商 API 费用，选择 Points+Provider Cost 或 Points/补贴+自部署资源许可。不同来源或价格变化需要重新授权及重新预留。
- **本地许可不是财务数据库**：本地并发许可属于具有租期/心跳的容量治理状态。单体时可在本地推理服务队列/网关有界信号量做一层准入；多副本时需要 MySQL 行锁等共享原子容量准入、Redis/Lua 或集中推理调度器，不能各副本各自放开同一集群的并发上限。容量许可申请与 MySQL 事务没有天然原子性：获取资金失败必须释放许可；许可失败且未出站，资金 reservation 必须释放，重复/超时请求需要许可过期回收并配测。
- **GPU 指标来源**：网关指标反映可观测吞吐/错误/等待；自运营 GPU 节点若使用 vLLM，可从其 /metrics 获取 running/waiting/KV cache；若为 NVIDIA GPU，可考虑 DCGM Exporter 获取硬件电源和利用率，但没有硬件就不能宣称有真实 GPU 指标。外部 Provider 不可观测它的内部真实 GPU 指标。
- **内部与外部网络安全**：SELF_HOSTED 只允许管理员登记的受控私有端点，使用专门的内部服务鉴权、网络白名单和 SSRF 防护，不信任 Agent 任意上传内网 URL；外部第三方使用供应商鉴权/HTTPS。
- **不主动引入新的微服务**：自部署模型运行服务是 AIGate 管理的**后端推理资源**，不是必须额外增加一个 AIGate 业务服务。若后期扩展容量运营业务需要独立服务仍须有故障隔离/独立扩容证据与 ADR。

技术备选：vLLM（生产推理与指标丰富）或其他 OpenAI 兼容推理服务 / 可靠 Fake Server。是否真实部署 GPU 取决于可用资源与用户最终选择，不能以引入技术名词代替可运行测试。

### D03 容量协调实现取舍（待冻结）

业务确认自部署普通消耗 Points、本地基础保底消耗每员工跨 Agent 共用的有限周 Token 补贴。建议此处原先的 MySQL 容量池计数/持久队列临时方案**已被 2026-10-21 新决策取代**：直接由 Redis Lua 实现跨 Gateway 的原子容量许可和有限等待队列；MySQL 只保存容量策略版本、Invocation 执行意图与故障恢复审计，不再以热行锁维护 active/waiting。省去一次计划内的技术替换；新增 Redis 故障、租约续期和重建协同复杂度。实际推理服务自身必须执行硬并发上限；网关租约超时不证明 GPU 任务已停止。详细字段和状态见《03-数据与接口》。


## 九、ADR-003：直接引入 Redis 共享治理（用户已确认原则，详细算法待冻结）

**背景**：项目采取“全部详细设计先完成，再按业务块全量实现并测试”，而双身份 Agent 模型代理、公司自部署 GPU 容量、两份 Gateway 副本和全局限流是已经确定的业务能力。

**问题**：若先用单 JVM Semaphore/计数器，第二台网关上线即不具备全局约束；若先使用 MySQL 高频计数和等待队列，后续切 Redis 又要迁移并发/排队协议，产生可预见的返工。

**候选**：A JVM 本地状态；B MySQL 锁表管理高频容量；C Redis 原子脚本 + MySQL 保留财务与调用事实；D 自建独立推理调度服务。选择 **C**。

**选择原因**：Redis Lua 支持服务端原子执行，适用于固定窗口/令牌桶、并发租约、有界等候的共享状态；Spring Data Redis 有脚本执行能力。项目 P1 就准备 Redis 连接、配置及 Testcontainers，P7 在 Gateway JSON/SSE 和 SELF_HOSTED 业务块一次完整使用 Redis 容量许可与基础全局 RPM，P9 完成企业保底多档全局流控，避免交付临时 JVM 实现。**不是强制早期在每个模块里用 Redis**。

**权威数据边界**：
- MySQL：员工周桶、Team Grant/Pool、外部采购月预算、价格版本、Invocation 状态及唯一幂等记录、财务预留结算与对账。
- Redis：入口 RPM、共享推理池 ACTIVE 许可、按优先级的有限 WAITING 请求与心跳/租期。Redis 状态可失效/重建，绝不能以其计数补写积分真实余额。
- 推理引擎：必须独立执行物理 max active/queue 上限；Redis TTL 到期不是 GPU 计算终止证据。

**脚本原则**：使用 RedisTemplate+RedisScript，脚本存版本化资源文件，以 KEYS/ARGV 参数化、短时原子执行。相同 Pool 的键需统一 Redis Cluster hash tag；领取/续期/释放必须验证 invocationId+唯一 lease token，旧请求/旧持有者不得释放新持有者许可。有限队列使用有界 Redis 数据结构与明确优先级、FIFO 顺序；不可在 Lua 里等待网络或执行长循环。

**失效策略**：Redis 不可用或故障切换状态不可信时，**拒绝新的 SELF_HOSTED 容量领取和依赖全局限流的收费入场**，正在运行的调用尽力完成/取消，MySQL 原有预留不因 Redis 数据丢失而抹除。恢复时暂停新入场、依据数据库 Invocation 执行意图及推理服务器状态查询重建/核验租约；服务不能确认推理终止前，仍由推理引擎硬并发上限防止物理过载。不能把 Redis 复制/持久化描述成可证的强一致账本。

**收益**：直接满足多实例共享限额、避免预知的 MySQL 容量热行与两套代码维护；可用 Lua 编写原子演进。**新增代价**：Redis 高可用、TTL/心跳、启动依赖、故障恢复、跨状态源幂等补偿、排队公平性与脚本测试。

**不扩大边界**：不把积分余额、Team 发放、供应商现金预算、财务预留迁入 Redis；暂不为了该方案引入 Redisson 分布式锁、Redis Streams、Nacos 或额外业务微服务。

官方依据：Redis Lua https://redis.io/docs/latest/develop/programmability/eval-intro/ ；Spring Data Redis Script https://docs.spring.io/spring-data/redis/reference/redis/scripting.html 。

**决策状态**：Redis 提前成为基础设施已被用户原则批准；键结构、TTL/续租、单/多实例恢复协议、默认超时与逐用例测试仍需 P0 设计冻结。

## 十、P0-D05：额度来源与流量优先级解耦（业务方案已认可）

普通员工账本、公司付费保底积分池、公司紧急积分池、员工本地模型 Token 补贴是不同的资金/资源权限，分别由 MySQL 账务和策略管理。Redis 的 NORMAL/LOW/EMERGENCY 是**请求调度优先级**，不是资金授权来源；Redis 排队许可不能替代 MySQL 资金/采购预算原子预留。

拟为 Provider 原币种月度采购总预算增加 NORMAL/EMERGENCY 两类份额，普通与企业付费保底共同使用 NORMAL，紧急任务只能用预留的 EMERGENCY 份额；保证普通调用不能提前耗尽已经划给紧急任务的现金风险空间。各分区和公司月度总限额**同一个 MySQL 事务**核验及更新，不能依赖 Redis 或 MQ 做财务双扣控制。份额下界不得低于已有结算+预留。

企业 LOW 付费保底是“重新选择获得授权的低价模型 → 冻结该部署价表 → 正常员工积分与公司补贴积分（仅不足部分）联合作为资金来源”；EMERGENCY 是“已有明确任务授权 → 使用专门紧急资金和采购预算”，不自动抽走员工普通积分。两者任何时候都不能跳过 Employee-Agent/Model 权限、数据治理和 Provider 采购硬限额。详见《01-业务与规则》D05、《03-数据与接口》D05。

用户已认可 D05 三类资金路径及紧急采购专属份额；数据库最终 DDL 和具体调度参数仍待 P0 全量设计冻结，P1 尚未开始。

## 十一、P0-D06：紧急任务与三档加权公平排队（详细设计提案）

### 为什么不是简单严格优先队列？

严格让 EMERGENCY 永远插队，持续出现紧急任务时可能导致 NORMAL 和 LOW 永远无法开始。也不应强行停止已有付费 SSE 请求抢占 GPU；真实推理可能已产生账单和部分响应，取消后的费用未知将增加对账风险。

**推荐第一版：Redis Lua 有界三队列 + 同档 FIFO + 加权轮转。** EMERGENCY、NORMAL、LOW 默认权重 4:2:1，依共享 Pool 的原子轮转指针按空闲执行名额分配，有空档则把名额让给其他档；队列总容量、每员工/Agent 等待数、最大等待时间均有限。权重只是名额份额，不是 GPU 秒数或保证紧急几秒就能开始。如果以后要求硬保障紧急任务启动时延，必须另外预留物理推理槽位并承担空闲资源成本，不能只调整队列优先级虚构 SLA。

### 已认可的资金优先级与调度优先级分离

- NORMAL：Employee×Agent 免费、个人基础、Team Grant；Provider 收费使用月度 NORMAL 采购份额。
- LOW：有条件选获授权便宜模型，先尽可能使用尚存员工积分、不足由公司有界付费保底池补齐；与 NORMAL 共享 NORMAL 采购份额。
- EMERGENCY：管理员批准的指定 Employee+Agent+Task、Model 范围、有限额度与有效期；调用派发时从公司紧急积分池和该任务授权额度原子预留；付费 API 使用公司月度 EMERGENCY 专属份额，不能自动动用普通 Employee 资金。

### 执行顺序已修订

为避免排队时间过长冻结积分、采购月预算或跨周/跨月归属错误，**新流程统一为**：身份/模型/治理预检 → Redis 入口速率检查并进入有限等待队列 → 取得执行容量许可 → 派发前重新验证身份、政策、紧急授权和价格 → MySQL 同事务预留 Points+必要的原币种采购预算 → 持久写一次派发意图 → Provider JSON/SSE → 可信结算/未知对账 → 上游任务确认完成后释放许可。此前 D03 的“额度预留后才入队”等旧顺序正式被本节与《03-数据与接口》D06 覆盖，不可同时实现两条顺序。

**例外处理**：NORMAL 在排队期间由于资金变化无法支付，可以在未出站且符合安全授权的情况下**最多一次**改选 LOW 模型并重新入队；已发送请求绝不可作为这种重新入队进行第二次收费发送。Redis 宕机/状态不可信则拒绝新的入场，MySQL 账本不从 Redis 恢复。多个 Redis rate-limit 维度跨 Cluster key slot 不天然属于同一个 Lua 原子事务，不可以把多脚本流水宣称为跨 MySQL 的强一致处理。

### 新技术引入七问摘要

Redis + Lua 是服务端原子执行多键限流/队列操作的机制，解决多 Gateway 实例竞争同一 Model/GPU 池的共享容量和公平问题。若只用单 JVM 锁会在两个实例各自放行；MySQL 行锁虽然可做到共享，但高频排队容易形成热点；第三方调度器则增加额外部署依赖。Redis 现已纳入 P1 基础环境并会在 Gateway 完整业务块直接实现，代价是高可用、脚本版本、TTL/租约和崩溃恢复的复杂性。**MySQL 依然是唯一积分和采购预算资金事实源。**

D06 的审批和调度方向获得用户认可，4:2:1 等技术参数仍待 P0 完整测试与设计冻结，不代表生产 SLA。

## 十二、P0-D07：逻辑模型与部署路由设计（提案）

三个对象严格分开：LogicalModel 是员工/Agent 获准使用的模型身份、版本和能力合同；Provider 是第三方供应商或企业自运营的推理服务主体；ModelDeployment 才是实际的 URL、remoteModelName、凭证、价格、区域、托管模式、健康和容量池。多个第三方托管或自部署实例仅在模型身份/版本/能力确实等价时，才可属于同一个 LogicalModel；仅有 OpenAI-compatible HTTP 协议并不等于模型等价。

路由执行顺序：先验证 Employee-Agent-Model ACL 与内容安全；按 Model 版本/协议、地域/数据等级、JSON/SSE、可靠 usage、Token 风险上界与部署启用状态筛选候选；再按实际健康、容量、错误率、网关观测延迟、管理员权重和成本选择同型号 Deployment；通过 Redis 取得该部署/供应商的执行许可；派发前重新验证权限、健康、实际 Deployment 与生效价表；MySQL 按最终部署的 POINTS 和必要的原币种采购价格原子预留，保存路由和价格快照，然后唯一出站。

不同 LogicalModel 的切换仅允许已批准的 LOW/本地保底策略，不能把模型替换伪装成同型号路由。不同 Deployment 可能具有不同采购价格/币种和资源池，不能在入队时就冻结不再更新资金与价格；跨池切换必须先释放旧许可再重新入队（有界次数、统一截止时间）。

可靠性：健康状态包括 HEALTHY、UNHEALTHY、UNKNOWN，探测过期显示 UNKNOWN，不假装知道第三方 Provider GPU 利用率；可用被动错误/延迟与受控主动检查，收费的生成探测不得在预算外自动产生。上游可能已收到请求、已出 SSE 内容或真实用量未知时不得自动重发到另一 Deployment；只有可证实未出站才可安全重新选路。运营指标与财务/身份快照保持可审计，但不得默认记录 Prompt 和密钥。

相关替代方案：随机轮询最简单但忽略健康/成本；复杂预测路由需要质量数据且可解释性差。建议首版采用可配置健康过滤+加权负载/成本评分，不引入额外网关服务。代价是策略版本、价格快照、健康 TTL、跨池许可与故障恢复，随 P7/P8 完整业务块一次测试。
