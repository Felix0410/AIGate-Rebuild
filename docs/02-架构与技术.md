# AIGate 架构与技术设计

> **当前架构起点（D15/ADR-008 已批准）：aigate-gateway + aigate-core 两个真实可独立运行的微服务，P11 新增 aigate-finops。** 本文包含主要架构选择及其理由，既是设计约束，也代替当前单独分散的 ADR 文件。本次已确定 Redis 为基础设施，P1 即集成连接与测试，实际容量/限流能力跟随相关业务块一次交付；MQ 等其余技术按明确业务需求接入。

## 一、总体架构

以 **Java 21 + Spring Boot 4.1.1 + Spring MVC + Spring Security + MyBatis-Plus + MySQL 8.4/Flyway** 实现两个初始 Spring Boot 服务（Gateway、Core），在 P11 增加第三个 FinOps。业务模块内聚、通过公开服务接口调用；管理面和 Agent 运行面分开处理认证、超时与并发资源。外部 Provider 经过统一受控 Adapter；第一种协议为 OpenAI 兼容 Chat Completions。

```text
现有 Agent + Employee
       ↓（双身份）
  Gateway Runtime → Identity/Control 双身份/Model 权限
       ↓
  Governance：完整输入分类/策略和具体数据出站边界
       ↓
  Router：确定合规候选 → Redis 全局限流/有界队列/执行许可
       ↓
  派发前身份、治理策略、实际 Deployment/价格复检
       ↓
  Quota & Billing + Governance PolicyRevision：同一 MySQL 短事务安全版本校验、原子资金预留与唯一派发意图
       ↓
  Gateway Provider Adapter → JSON / SSE（已批准模式的输出审查）
       ↓
  Quota & Billing：可信使用量结算 / 未知待核对 + 同事务 Outbox
       ↓
  RabbitMQ（按阶段引入）→ FinOps 异步报表与告警
```

**不能把一次模型调用设计为对五个微服务逐 Token 远程请求。** 配置/安全策略以后可用受控版本快照执行，财务预留/结算在单次请求粒度进行。不能在 Provider HTTP 或 SSE 持续传输期间持有 MySQL 行锁。

## 二、五个业务领域（D15 起按 3 个微服务部署，不是一域一服务）

| 模块 | 唯一职责 | 禁止事项 |
|---|---|---|
| Gateway Runtime | runtime 鉴权入口、路由、SSE、流控、Provider I/O、调用元数据 | 直接 UPDATE 积分余额 |
| Identity & Control | Team、Employee、Agent、凭证、Model/Provider/Deployment 配置、基础权限 | 根据请求体 employeeId 认定身份 |
| Quota & Billing | 周额度、Team 授额、公司保底/紧急池、预留、结算、账本、对账、Outbox | 由 Redis 或 MQ 决定已扣积分 |
| AI Governance | 数据分类、内容/模型准入规则版本、受控例外与最小审计 | 默认存储敏感 Prompt 原文 |
| Analytics & FinOps | 通过确定事实异步建立使用、发放、采购估算的分析读模型 | 回写权威余额或把不同 POINTS/货币口径直接相加或把自部署成本与其分摊重复合计 |

Java 推荐包：bootstrap、common、identity、catalog、gateway、quota、governance、analytics、integration、observability。各领域内部按 controller/dto/application/domain/repository 分层；跨域只经公开 Facade，不跨模块直接 Mapper 修改他域表。

## 三、关键架构决策

**决策 A（已由 D15/ADR-008 修订）：从 P1 起采用两服务微服务，P11 增加第三服务。** 不拆五个业务域为五个独立数据库：Gateway 负责独立长 SSE/IO，Core 同库保留权限/政策/双资金/Invocation 派发许可的原子事务，FinOps 异步隔离。业务理由、服务间 RPC 和代价参见 D15。

**决策 B：MySQL 为唯一权威积分账本。**
行锁/唯一业务键/短事务保证团队发放、资金预留、结算原子化。Redis 快但故障/淘汰/持久化语义不适合作权威资金余额；MQ 可能至少一次投递，不能直接负责扣积分。代价是热点余额争用、SQL 索引与死锁重试，需要测试及监控。

**决策 C：账本 + Outbox 后异步分析。**
团队发放和调用结算在 MySQL 提交时，同事务写安全的待发布事件；异步投递给 FinOps。Broker 不可用账本仍正确且事件留待补发，消费者按 eventId 去重。代价是延迟一致性、Outbox/Inbox、重试、死信、版本和积压管理。财务计量不能宣称 RabbitMQ 提供跨 MySQL 的“恰好一次”。

**决策 D：Spring MVC SSE 起步。**
先沿用现有编程模型，使用异步请求和有界执行器；WebFlux 不是为了长连接就必选。若实测 Servlet 写阻塞、线程和连接瓶颈，再比较响应式方案。必须监控活跃连接、取消、超时、压力和尾部 usage 丢失的账务处理。

## 五、服务演进与容量证明

阶段路径（D15 已批准）：**P1 Gateway+Core 两个独立微服务 → P7 Gateway 可单独多副本扩容/真实 SSE 与 Core RPC → P11 FinOps 异步独立微服务 → P12 分别故障/容量/发布演练**。候选为 Gateway、Control、Quota、Governance、FinOps；Worker 进程不是凭空多出一个业务领域。

微服务拆分评审必须回答：当前方案、遇到的可测问题、单体内优化为何不够、候选拆法及数据归属、实际收益、RPC/异步一致性/故障/运维代价。即使最终保持两个副本单体，只要指标证明适合，也属于正确架构决策。

## 六、尚未授权的技术行为

目前已批准**从 P1 直接拆成真实微服务的架构方向**，但没有批准依赖安装、具体微服务实施编码或开始 P1。价格配置、预算数字、公司真实模型/Provider Key 不编造；设计默认公司时区 Asia/Shanghai、时间存 UTC、资金额度以 DECIMAL 表达，细节见数据设计。

## 七、完整业务块交付约束（2026-10-21）

项目实施方法已变更：**编码前冻结全部七份文档；之后每个完整业务块一次交付所承诺的业务、保护和测试**。**D15 改为 P1 起两个独立微服务**是经过设计的目标部署形态，不是“先写只能跑成功场景的临时代码”。每个业务领域要在分配工作包前得到明确 API、持久化模型、异常处理、权限和故障测试合同。可以按多个 Git commit 完成一个业务块，但业务块直到完整验收之前都不视为已交付。

为了保证首个实际付费出站具有全套保护，当前**待用户确认的新依赖排序**将 Employee/Agent 双身份、模型目录、账本、团队发放和企业出站安全策略放在 Gateway 实际收取外部费用之前；调用记录与 SSE 与 Runtime 业务块一起完整交付。安全治理虽然独立业务领域，不意味着已满足基础认证就可绕开内容规则。

一个重大**未解决的架构门禁**：积分账本的可用 Points 和企业对 Provider 的实际采购风险（供应商币种）不是同一个资产。公司保底应同时符合两个硬预算（内部 points + 真实 Provider 成本上限），Provider 费用风险预留/结算需要独立建模。完成前不得将“积分额度正确”宣传为“企业外部现金成本不会超预算”。Redis 只做共享限流，不能补救真实现金限额缺失。

## 八、P0 D-02：统一网关支持外部 API 与企业自部署推理（业务已确认，技术细节设计中）

### 部署类型与计费模式分离

拟在 Deployment Catalog 中区分 `hosting_mode = THIRD_PARTY_API | SELF_HOSTED`。业务上还需独立保存 `cost_model`（首版为 PER_TOKEN_API / INTERNAL_RESOURCE），避免将“接口协议”“算力所有者”“内部积分单价”“企业实际资源成本”混为一谈。SELF_HOSTED 的推理服务可能同样提供 OpenAI 兼容 API，如 vLLM；因此 Gateway 的 Provider Adapter 可在安全受控端点下复用 JSON/SSE 解析，不能为了区分两类来源复制整条网关业务链。

**EXTERNAL / THIRD_PARTY_API**：Identity/Policy → 选择部署、冻结两种价格 → 单 MySQL 事务同时预留 POINTS+公司原币种采购风险额度 → 发出供应商 API → 依据可信 Token 双账结算或双账待核对。

**SELF_HOSTED 正常**：Identity/Policy → 选择获准自部署节点 → 检查推理健康/有限并发/队列，并授予有有效期的容量许可 → 预留本次员工内部 POINTS（或受批准的本地补贴 Token 配额）→ 推理 JSON/SSE → 释放容量许可，按可信 usage 结算 POINTS/补贴额度或待核对。**不占用逐次第三方 Token API 采购预算**，但需有独立算力容量约束及后续真实云 GPU 费用管理。

**SELF_HOSTED 保底**：正常积分和企业付费保底无法继续支撑时，只有公司明确授权的低成本基础模型、员工独立周限额及推理集群可用容量同时满足，才允许继续有限服务。不能静默把模型路由到更贵的收费外部 Provider。

### 路由与并发的关键失败边界

- **先定 Deployment 再定预算合同**：按是否会产生逐次外部供应商 API 费用，选择 Points+Provider Cost 或 Points/补贴+自部署资源许可。不同来源或价格变化需要重新授权及重新预留。
- **本地许可不是财务数据库**：本地并发许可属于具有租期/心跳的容量治理状态。单体时可在本地推理服务队列/网关有界信号量做一层准入；多副本时需要 MySQL 行锁等共享原子容量准入、Redis/Lua 或集中推理调度器，不能各副本各自放开同一集群的并发上限。容量许可申请与 MySQL 事务没有天然原子性：获取资金失败必须释放许可；许可失败且未出站，资金 reservation 必须释放，重复/超时请求需要许可过期回收并配测。
- **GPU 指标来源**：网关指标反映可观测吞吐/错误/等待；自运营 GPU 节点若使用 vLLM，可从其 /metrics 获取 running/waiting/KV cache；若为 NVIDIA GPU，可考虑 DCGM Exporter 获取硬件电源和利用率，但没有硬件就不能宣称有真实 GPU 指标。外部 Provider 不可观测它的内部真实 GPU 指标。
- **内部与外部网络安全**：SELF_HOSTED 只允许管理员登记的受控私有端点，使用专门的内部服务鉴权、网络白名单和 SSRF 防护，不信任 Agent 任意上传内网 URL；外部第三方使用供应商鉴权/HTTPS。
- **不主动引入新的微服务**：自部署模型运行服务是 AIGate 管理的**后端推理资源**，不是必须额外增加一个 AIGate 业务服务。若后期扩展容量运营业务需要独立服务仍须有故障隔离/独立扩容证据与 ADR。

技术备选：vLLM（生产推理与指标丰富）或其他 OpenAI 兼容推理服务 / 可靠 Fake Server。是否真实部署 GPU 取决于可用资源与用户最终选择，不能以引入技术名词代替可运行测试。

### D03 容量协调实现取舍（待冻结）

业务确认自部署普通消耗 Points、本地基础保底消耗每员工跨 Agent 共用的有限周 Token 补贴。建议此处原先的 MySQL 容量池计数/持久队列临时方案**已被 2026-10-21 新决策取代**：直接由 Redis Lua 实现跨 Gateway 的原子容量许可和有限等待队列；MySQL 只保存容量策略版本、Invocation 执行意图与故障恢复审计，不再以热行锁维护 active/waiting。省去一次计划内的技术替换；新增 Redis 故障、租约续期和重建协同复杂度。实际推理服务自身必须执行硬并发上限；网关租约超时不证明 GPU 任务已停止。详细字段和状态见《03-数据与接口》。


## 九、ADR-003：直接引入 Redis 共享治理（用户已确认原则，详细算法待冻结）

**背景**：项目采取“全部详细设计先完成，再按业务块全量实现并测试”，而双身份 Agent 模型代理、公司自部署 GPU 容量、两份 Gateway 副本和全局限流是已经确定的业务能力。

**问题**：若先用单 JVM Semaphore/计数器，第二台网关上线即不具备全局约束；若先使用 MySQL 高频计数和等待队列，后续切 Redis 又要迁移并发/排队协议，产生可预见的返工。

**候选**：A JVM 本地状态；B MySQL 锁表管理高频容量；C Redis 原子脚本 + MySQL 保留财务与调用事实；D 自建独立推理调度服务。选择 **C**。

**选择原因**：Redis Lua 支持服务端原子执行，适用于固定窗口/令牌桶、并发租约、有界等候的共享状态；Spring Data Redis 有脚本执行能力。项目 P1 就准备 Redis 连接、配置及 Testcontainers，P7 在 Gateway JSON/SSE 和 SELF_HOSTED 业务块一次完整使用 Redis 容量许可与基础全局 RPM，P9 完成企业保底多档全局流控，避免交付临时 JVM 实现。**不是强制早期在每个模块里用 Redis**。

**权威数据边界**：
- MySQL：员工周桶、Team Grant/Pool、外部采购月预算、价格版本、Invocation 状态及唯一幂等记录、财务预留结算与对账。
- Redis：入口 RPM、共享推理池 ACTIVE 许可、按优先级的有限 WAITING 请求与心跳/租期。Redis 状态可失效/重建，绝不能以其计数补写积分真实余额。
- 推理引擎：必须独立执行物理 max active/queue 上限；Redis TTL 到期不是 GPU 计算终止证据。

**脚本原则**：使用 RedisTemplate+RedisScript，脚本存版本化资源文件，以 KEYS/ARGV 参数化、短时原子执行。相同 Pool 的键需统一 Redis Cluster hash tag；领取/续期/释放必须验证 invocationId+唯一 lease token，旧请求/旧持有者不得释放新持有者许可。有限队列使用有界 Redis 数据结构与明确优先级、FIFO 顺序；不可在 Lua 里等待网络或执行长循环。

**失效策略**：Redis 不可用或故障切换状态不可信时，**拒绝新的 SELF_HOSTED 容量领取和依赖全局限流的收费入场**，正在运行的调用尽力完成/取消，MySQL 原有预留不因 Redis 数据丢失而抹除。恢复时暂停新入场、依据数据库 Invocation 执行意图及推理服务器状态查询重建/核验租约；服务不能确认推理终止前，仍由推理引擎硬并发上限防止物理过载。不能把 Redis 复制/持久化描述成可证的强一致账本。

**收益**：直接满足多实例共享限额、避免预知的 MySQL 容量热行与两套代码维护；可用 Lua 编写原子演进。**新增代价**：Redis 高可用、TTL/心跳、启动依赖、故障恢复、跨状态源幂等补偿、排队公平性与脚本测试。

**不扩大边界**：不把积分余额、Team 发放、供应商现金预算、财务预留迁入 Redis；暂不为了该方案引入 Redisson 分布式锁、Redis Streams、Nacos 或额外业务微服务。

官方依据：Redis Lua https://redis.io/docs/latest/develop/programmability/eval-intro/ ；Spring Data Redis Script https://docs.spring.io/spring-data/redis/reference/redis/scripting.html 。

**决策状态**：Redis 提前成为基础设施已被用户原则批准；键结构、TTL/续租、单/多实例恢复协议、默认超时与逐用例测试仍需 P0 设计冻结。

## 十、P0-D05：额度来源与流量优先级解耦（业务方案已认可）

普通员工账本、公司付费保底积分池、公司紧急积分池、员工本地模型 Token 补贴是不同的资金/资源权限，分别由 MySQL 账务和策略管理。Redis 的 NORMAL/LOW/EMERGENCY 是**请求调度优先级**，不是资金授权来源；Redis 排队许可不能替代 MySQL 资金/采购预算原子预留。

拟为 Provider 原币种月度采购总预算增加 NORMAL/EMERGENCY 两类份额，普通与企业付费保底共同使用 NORMAL，紧急任务只能用预留的 EMERGENCY 份额；保证普通调用不能提前耗尽已经划给紧急任务的现金风险空间。各分区和公司月度总限额**同一个 MySQL 事务**核验及更新，不能依赖 Redis 或 MQ 做财务双扣控制。份额下界不得低于已有结算+预留。

企业 LOW 付费保底是“重新选择获得授权的低价模型 → 冻结该部署价表 → 正常员工积分与公司补贴积分（仅不足部分）联合作为资金来源”；EMERGENCY 是“已有明确任务授权 → 使用专门紧急资金和采购预算”，不自动抽走员工普通积分。两者任何时候都不能跳过 Employee-Agent/Model 权限、数据治理和 Provider 采购硬限额。详见《01-业务与规则》D05、《03-数据与接口》D05。

用户已认可 D05 三类资金路径及紧急采购专属份额；数据库最终 DDL 和具体调度参数仍待 P0 全量设计冻结，P1 尚未开始。

## 十一、P0-D06：紧急任务与三档加权公平排队（详细设计提案）

### 为什么不是简单严格优先队列？

严格让 EMERGENCY 永远插队，持续出现紧急任务时可能导致 NORMAL 和 LOW 永远无法开始。也不应强行停止已有付费 SSE 请求抢占 GPU；真实推理可能已产生账单和部分响应，取消后的费用未知将增加对账风险。

**推荐第一版：Redis Lua 有界三队列 + 同档 FIFO + 加权轮转。** EMERGENCY、NORMAL、LOW 默认权重 4:2:1，依共享 Pool 的原子轮转指针按空闲执行名额分配，有空档则把名额让给其他档；队列总容量、每员工/Agent 等待数、最大等待时间均有限。权重只是名额份额，不是 GPU 秒数或保证紧急几秒就能开始。如果以后要求硬保障紧急任务启动时延，必须另外预留物理推理槽位并承担空闲资源成本，不能只调整队列优先级虚构 SLA。

### 已认可的资金优先级与调度优先级分离

- NORMAL：Employee×Agent 免费、个人基础、Team Grant；Provider 收费使用月度 NORMAL 采购份额。
- LOW：有条件选获授权便宜模型，先尽可能使用尚存员工积分、不足由公司有界付费保底池补齐；与 NORMAL 共享 NORMAL 采购份额。
- EMERGENCY：管理员批准的指定 Employee+Agent+Task、Model 范围、有限额度与有效期；调用派发时从公司紧急积分池和该任务授权额度原子预留；付费 API 使用公司月度 EMERGENCY 专属份额，不能自动动用普通 Employee 资金。

### 执行顺序已修订

为避免排队时间过长冻结积分、采购月预算或跨周/跨月归属错误，**新流程统一为**：身份/模型/治理预检 → Redis 入口速率检查并进入有限等待队列 → 取得执行容量许可 → 派发前重新验证身份、政策、紧急授权和价格 → MySQL 同事务预留 Points+必要的原币种采购预算 → 持久写一次派发意图 → Provider JSON/SSE → 可信结算/未知对账 → 上游任务确认完成后释放许可。此前 D03 的“额度预留后才入队”等旧顺序正式被本节与《03-数据与接口》D06 覆盖，不可同时实现两条顺序。

**例外处理**：NORMAL 在排队期间由于资金变化无法支付，可以在未出站且符合安全授权的情况下**最多一次**改选 LOW 模型并重新入队；已发送请求绝不可作为这种重新入队进行第二次收费发送。Redis 宕机/状态不可信则拒绝新的入场，MySQL 账本不从 Redis 恢复。多个 Redis rate-limit 维度跨 Cluster key slot 不天然属于同一个 Lua 原子事务，不可以把多脚本流水宣称为跨 MySQL 的强一致处理。

### 新技术引入七问摘要

Redis + Lua 是服务端原子执行多键限流/队列操作的机制，解决多 Gateway 实例竞争同一 Model/GPU 池的共享容量和公平问题。若只用单 JVM 锁会在两个实例各自放行；MySQL 行锁虽然可做到共享，但高频排队容易形成热点；第三方调度器则增加额外部署依赖。Redis 现已纳入 P1 基础环境并会在 Gateway 完整业务块直接实现，代价是高可用、脚本版本、TTL/租约和崩溃恢复的复杂性。**MySQL 依然是唯一积分和采购预算资金事实源。**

D06 的审批和调度方向获得用户认可，4:2:1 等技术参数仍待 P0 完整测试与设计冻结，不代表生产 SLA。

## 十二、P0-D07：逻辑模型与部署路由设计（提案）

三个对象严格分开：LogicalModel 是员工/Agent 获准使用的模型身份、版本和能力合同；Provider 是第三方供应商或企业自运营的推理服务主体；ModelDeployment 才是实际的 URL、remoteModelName、凭证、价格、区域、托管模式、健康和容量池。多个第三方托管或自部署实例仅在模型身份/版本/能力确实等价时，才可属于同一个 LogicalModel；仅有 OpenAI-compatible HTTP 协议并不等于模型等价。

路由执行顺序：先验证 Employee-Agent-Model ACL 与内容安全；按 Model 版本/协议、地域/数据等级、JSON/SSE、可靠 usage、Token 风险上界与部署启用状态筛选候选；再按实际健康、容量、错误率、网关观测延迟、管理员权重和成本选择同型号 Deployment；通过 Redis 取得该部署/供应商的执行许可；派发前重新验证权限、健康、实际 Deployment 与生效价表；MySQL 按最终部署的 POINTS 和必要的原币种采购价格原子预留，保存路由和价格快照，然后唯一出站。

不同 LogicalModel 的切换仅允许已批准的 LOW/本地保底策略，不能把模型替换伪装成同型号路由。不同 Deployment 可能具有不同采购价格/币种和资源池，不能在入队时就冻结不再更新资金与价格；跨池切换必须先释放旧许可再重新入队（有界次数、统一截止时间）。

可靠性：健康状态包括 HEALTHY、UNHEALTHY、UNKNOWN，探测过期显示 UNKNOWN，不假装知道第三方 Provider GPU 利用率；可用被动错误/延迟与受控主动检查，收费的生成探测不得在预算外自动产生。上游可能已收到请求、已出 SSE 内容或真实用量未知时不得自动重发到另一 Deployment；只有可证实未出站才可安全重新选路。运营指标与财务/身份快照保持可审计，但不得默认记录 Prompt 和密钥。

相关替代方案：随机轮询最简单但忽略健康/成本；复杂预测路由需要质量数据且可解释性差。建议首版采用可配置健康过滤+加权负载/成本评分，不引入额外网关服务。代价是策略版本、价格快照、健康 TTL、跨池许可与故障恢复，随 P7/P8 完整业务块一次测试。

**D07 设计状态：PROPOSED。** 精确评分公式、健康阈值、探测频率与 ModelIdentity 版本约束仍须 P0 设计审查，未开始编码。


## 十三、P0-D07.1：可解释路由算法和健康检查（实施默认待审）

### 健康状态

先执行模型身份/版本、Employee-Agent-Model ACL、内容安全、部署状态、区域与数据等级、JSON/SSE 能力、Token 风险上界和有效价格等硬过滤，然后才检查健康和打分。健康不能覆盖任何硬限制。

健康枚举：HEALTHY、DEGRADED、UNHEALTHY、UNKNOWN、THROTTLED、CONFIG_ERROR，人工 DISABLED/MAINTENANCE 在最外层直接排除。

- HEALTHY：有新鲜的成功/健康证据，没有触发以下故障阈值。最后可信健康证据超过120秒视为 UNKNOWN。
- DEGRADED：60秒窗口内至少20次有效样本、上游故障率达到20%但未到50%。只在没有 HEALTHY 时谨慎选择。
- UNHEALTHY：60秒内至少20样本且故障率达到50%，或连续3次真实上游连接/服务故障；30秒后进入受控 PROBING，每个部署同时只准1次探路，成功后恢复健康、失败再次冷却。
- UNKNOWN：新建部署、观测证据过期；不假装 HEALTHY。若没有健康候选且管理员允许，可以用1个经过完整安全/资金/速率检查的真实业务请求进行受控试运行，费用照常计算。已确认不收费的安全健康端点可以用于连接探测，但不自动发收费模型生成探测。
- THROTTLED：收到 Provider 的429/Retry-After 或可信限额信号，冷却窗口内不再继续按无限容量派发。CONFIG_ERROR：确定的凭证、证书、协议、端点安全错误，只能由管理员排除配置故障。
- 用户非法请求400、客户端主动断开不记为模型服务本身故障；Provider 5xx和连接错误进入健康窗口。故障需要尽可能准确归属 Provider/Deployment，别家的错误不能自动让所有模型都 UNHEALTHY。

窗口60s、最小样本20、降级20%、熔断50%、连续失败3、冷却30s、健康证据TTL120s、探路并发1均为**初始设计参数**，可在管理配置按版本调整，不是假装已验证的生产阈值。

### 同逻辑模型候选的明确排序算法

1. **先按健康等级**选择：优先 HEALTHY；无 HEALTHY 才考虑 DEGRADED；两者都没有时仅允许单并发、完整预算授权的 UNKNOWN 试运行。**只在同一健康等级中**选择人工配置的最低 routingPriority（数字越小越优先）。
2. 同一优先组比较标准化负载：effectiveCapacity = min(Deployment并发上限,实际共享Pool并发上限)；weightedLoad = (该Deployment活跃任务数 + 该Deployment等待任务数 + 1) / (max(1,effectiveCapacity) * max(1,routingWeight))。routingWeight 为1至100正整数。对于第三方 Provider 使用其可验证且由网关管理的并发上限，不虚构 GPU 容量。Redis 维护多实例共享任务计数。
3. 两个候选 weightedLoad 差距小于10%时，比较最近有可靠样本的网关首Token P95；无法观测的延迟不填0。再相近时，可比较**同币种**且同类可计算的最高 Provider 采购风险费用；不同币种不强行比较价格。
4. 仍相同则用 Deployment ID 作为稳定决胜依据。打分本身不获得执行名额，必须成功领取目标 Redis Pool 许可并在派发前重新验证授权、价格和采购预算。若候选禁用或队列满，可在相同总排队截止前有限重新选路，不可以跨不同资源池同时占用许可。

这种容量感知、低成本、可解释的排序优于仅随机轮询；暂不需要机器学习路由、质量预测或额外微服务。代价是观测窗口、冷启动、限流、健康策略版本及跨池许可一致性，需要自动测试支撑。

**积分定价不随同型号部署选路变化**：内部积分价绑定 LogicalModel 的生效版本；Provider 采购价绑定实际收费 Deployment 与供应商原币种。无论采购价差多少，普通路由不能改变用户所选模型的积分单价。模型降级属于另一 LogicalModel、需要重检权限/重新计价。SSE 已输出或上游可能已收费的请求绝不可自动改路重发。

**状态：D07.1 PROPOSED**。这些参数与公式是准备冻结的设计默认，还需要与完整API/DDL、Fake Provider 及负载/安全测试做一致性审核。

## 十四、P0-D08：Provider Adapter、MVC SSE、状态恢复架构（技术设计提案）

### 技术选择的业务原因

Spring MVC 的异步 HTTP 输出（可使用 SseEmitter 或等价受控 Writer）承担第一版文本 Chat Completions JSON/SSE。为什么需要异步：单次生成可能持续数十秒，若每个在途 SSE 都固定占一个同步 Servlet 请求线程，容量很快被限制；异步返回+有界专用 I/O 执行器允许尽早释放 Servlet 请求线程。**但 MVC 异步不自动意味着所有 socket 写都是非阻塞**，慢客户端、上游读取、输出队列和执行器必须各自有界。替代方案是 Reactor/WebFlux，适合真实测到大量长连接线程/背压瓶颈后再评估；本项目不为技术栈而提前整站重写响应式。

Gateway Runtime 只编排六个明确合同：
1. Identity/Control：Agent+Employee 双 Principal、Model allowlist、紧急授权与安全元数据；
2. Governance：派发前的 PolicyVersion 和内容安全检查，不保存敏感全文；
3. Catalog/Router：LogicalModel 到合法 Deployment、价格/协议/能力的版本化快照；
4. Redis Admission：各档全局 RPM/有界等待/执行许可、续期与真实任务终止后的安全释放；
5. QuotaBilling：派发前同 MySQL 事务预留内部 Points + 外部采购预算，完成后原子结算/待对账与 Outbox；
6. ProviderAdapter：实际端点的安全请求映射、JSON/SSE 增量解析、经认可的 usage 证据与可审计错误分类。

每个 Adapter 对外提供同一组受控操作：buildRequest（只允许支持字段）、dispatchOnce（受 attemptToken 限制）、decodeJson、readSseFrames、parseTrustedUsage、classifyTransportFailure、cancelBestEffort。Provider 认证与用户 Agent/Employee 密钥必须严格隔离。客户端传入的 modelCode 不直接作为远端端点与 URL。Service 不直接从 Controller 字符串拼装 Provider URL，所有出站凭证只通过 Catalog 安全引用注入。

### JSON 与 SSE 两条输出通道，一套业务账务

入站校验和全局队列→实际执行许可→派发前权限/价格安全复核→MySQL 双账原子预留→持久唯一 DISPATCH_INTENT→Provider 调用。JSON 等待整个上游响应再返回兼容对象；SSE 增量转化响应帧、及时 flush；二者都只在收到可信 usage 后走同一 QuotaBilling.settle，缺失则原账保持待对账。

不能用 Provider 断线或 SSE 的 [DONE] 代替真实 Token 结算证据；两条独立状态轴（executionState / billingState）使得 OUTPUT_COMPLETED+PENDING_RECONCILIATION 合法。SSE 数据发完后 MySQL 短时不可用，需要安全持久化的恢复/对账途径；不允许直接认为已经结算成功。已经派发意图且是否出站未知不能无界 HTTP 重试。

**费用预估与真实计费不等价**：最大风险由经过验证的输入 Token 上界、max_tokens 输出上界、所有支持收费类别的最大价格获得；短文本的字节长度/简单 tokenizer 估算若无法证明是上界，就不能作为月度采购预算硬控制依据。Provider 额外计费维度不受支持时拒绝此次请求，先补 Adapter+PriceVersion+验收再开放。

### 安全与故障成本

Spring MVC + HTTP client 需要 connect timeout、首 Token timeout、上游 idle timeout、全局请求期限、下游写阻塞期限、执行器和活跃 SSE 最大数；客户端流断开尽力取消上游，不把网关 Redis lease TTL 当作本地推理已经停止。Provider 原始异常不能泄露给员工。对于已提交 SSE 头的响应，使用受控 SSE 错误数据帧/断连+查询状态，不试图晚发 HTTP 502。

替代方式如“先缓存整段回复再拆成伪流式”会丢失实时体验；“将整段 Prompt/生成结果写消息队列”增加隐私面；“收到 HTTP200 就扣费”无法处理 usage 缺失；“超时直接释放所有预留”可能使已收费请求变免费。当前方案代价是必须实现异步资源/背压、幂等收据、Provider 兼容矩阵、调用恢复和资金对账，这是全量业务块的必要复杂性而非装饰技术。

**D08 状态：PROPOSED；精确线程池、超时/缓冲、Adapter 白名单和完整 SSE 测试固件待 P0 最终冻结。**

## 十五、P0-D09：治理模块的组件边界、运行流程与策略版本（待冻结）

### 为什么 AIGate 必须独立执行安全策略

业务已有 Employee/Agent/Model 双身份和多个 Deployment：**认证只回答是谁，治理必须回答这批内容是否可以发往目标托管边界**。System Prompt 指令不是安全机制，不能给 LLM 自己决定有无出站权限，也不能根据用户消息里的“已获批准”提升分类。参考 OWASP LLM01 Prompt Injection/LLM02 Sensitive Information Disclosure/LLM07 System Prompt Leakage。技术候选为 A 只依赖 Provider 安全选项（不能约束出站）、B 先接外部 DLP 审核服务（会把未批准内容发往另一个第三方）、C 模块化单体内部规则引擎 + 版本化企业策略与审计；**选择 C**。代价是规则误报/漏报、策略发布、审核职责与性能测试；未来确有真实数据资产目录或外部合规规则时再集成相应安全基础设施，不为技术丰富而提前加入 NLP/外部审核模型。

### 设计组件

- GovernancePolicyRepository：MySQL 权威的 policy_revision（DRAFT/APPROVED/PUBLISHED/SUPERSEDED）、egress_rule、例外授权、作用域、版本快照；所有修改留审批元数据。
- ClassificationService：在受限内存里对本次**全部 system/user/assistant messages**做规范化与有界规则匹配，结合服务端可信业务/Agent 标签取最大数据等级，产出 effectiveClass、matchedRuleId、scannerVersion，不返回命中的原文片段。
- EgressDecisionService：在真正路由时检查 effectiveClass + LogicalModel / Provider / Deployment + approvedRegion / dataBoundary + Agent 出站授权 + 企业发布策略，返回 DENY/ALLOW/REQUIRE_BUFFERED_RESPONSE；授权判定发生在所有积分/采购预算预留之前和派发前复检时。
- OutputReviewService：只有政策明确要求时、仅对 stream=false JSON 的生成全文在返回前进行规则审查。拒绝返回内容仍可能产生上游费用，必须结算；stream=true 只能匹配明确允许“不保证全文出站前审查”的低敏政策，不使用看似实时 DLP 但实际已泄露数据的伪保障。
- GovernanceAuditWriter：与 Invocation 关联的最小元数据安全审计，规则发布/例外批准与调用决策分开记录，禁止写完整 Prompt/response、密钥或 matched substring。

### 与 D06～D08 的精确顺序

HTTP 入站双身份/完整请求参数检查 → 受限内存扫描全文并确定初始分类 → 校验逻辑 Model 和审批可出站策略、是否允许 stream → Redis 有界等待只存无敏感正文 ticket → ACTIVE 后**重新读取 MySQL 已发布的策略指针**、依据当前实际 Deployment/地区/Provider 重新核验全部安全条件 → 进入财务短事务前保留评估后的 strategyRevision + scannerVersion。为了避免“缓存仍是旧允许、管理端已撤销”的竞态，**最终 DispatchIntent 持久化时必须与已发布策略指针在同一受控 MySQL 事务中校对版本**（可选择共享读锁策略指针，管理发布/撤销以独占锁更新）；版本不符则不得提交出站授权，必要时重新评估、释放 Redis permit 并有界重新准入。完成授权事务后发生的新政策变更不追溯当前已授权调用，执行中可尝试取消和留审计，但不能宣称物理网络可百分之百同步撤销。

**重要边界**：即使成功鉴权与策略评估，Redis 排队和计算期间仍不能落盘原始 Prompt。Gateway 实例本地用有界内存持有原请求，Redis 只管共享 ticket、lease 与时限；owner 进程死亡，WAITING ticket 可取消清理，因为没有已预留财务，也没有跨进程可恢复的 Prompt。不要为了多网关调度把 Prompt 发入 Redis 或 MQ。若 owner 在 DISPATCH_INTENT 后崩溃，依 D08 不能自动重发，资金风险仍待对账。

### 版本、缓存与撤销

策略发布用 MySQL 短事务切换 ACTIVE revision 指针、记录发布人/审批人与历史版本，保证任一时刻每个公司作用域只有一个 active revision；发布后 Redis 可以缓存只读快照和发送失效提示，但**最终出站不能只凭 Redis Pub/Sub 缓存已失效版本**。管理的主机允许列表、敏感数据等级和 Provider 批准地域必须在最终实际 Deployment 选定后再次匹配；从合规本地模型向外部 Provider 的路由或 LOW 降级始终需要重新执行 EgressDecision，不可沿用之前的 ALLOW。

审计保留审查与调整权限，不默认记录原文。日志指标按 rule category/decision 低基数聚合，禁止把员工 ID、Prompt hash 或 Invocation ID 作为高基数 Prometheus 标签。拒绝时服务可返回 GOVERNANCE_DENIED 等安全错误与 traceId，但不回显触发规则的秘密。

### 信任边界与无法保证的事情

- 纯文本规则引擎无法完美识别隐藏编码、变形密钥、未知商业秘密、复杂提示注入。可信来源标签/资产标注、Provider allowlist、组织 RBAC 与真实审计不可省略；
- 不会因为“在公司网络”就默认自部署可信。必须明确所用云 GPU/内部推理供应方、机密等级、数据区域、凭证、模型操作日志等隔离能力；
- SSE 内容已经流出就无法“收回”，因此要求输出审查的机密请求在入口阶段直接拒绝 stream=true。JSON 可以在发送下游之前审查完整文本，不代表准确防止全部泄露；
- 紧急任务或保底模式只改变资金/调度资源，不授予数据出站例外；安全拒绝前不得产生 Provider 外呼或采购风险预留。

**D09 细节属于 PROPOSED**：具体匹配词库与版本、规则引擎效率上限、治理权限与发布分离、政策失联 fail-closed 和跨实例审计时序要在 P0 全表/接口测试冻结后实施。

## 十六、ADR-004：MySQL Outbox + RabbitMQ 派生 FinOps 读模型（P0-D10 详细方案，待冻结）

### 背景、业务问题与候选

AIGate 的额度扣减/Team 授额/Provider 采购预算是真正的资金事实，运营部门又需要按日期、Team、员工、Agent、模型和 Provider 查询聚合。直接让运行时每次事务更新大量统计汇总会增大资金行锁与出站延迟；如果在 MySQL 账本提交后立即向 RabbitMQ 发布，**数据库已经提交但 MQ 不可用会丢失业务事件**；如果先发 MQ 再提交 MySQL，回滚时又会形成假的统计。

候选 A：每次报表直接在线聚合所有资金 Ledger（实现简单但成本随明细增长，报表抢线上数据库资源）；B：每次账本事务中同步更新完整多维报表（强同步但增加热路径锁和维度复杂度）；C：**账本同事务写 Outbox → RabbitMQ 异步推送 → 幂等消费构建 MySQL FinOps 读模型**；D：Debezium/CDC + Kafka（可以但为当前体量增加运维/跨组件复杂度）。本轮建议选择 C；按照已批准的 D15/P11 拓扑，Core 内运行 Relay、FinOps 独立运行 Inbox/查询和 finops_db；报表消费高峰不能抢占 Core 的资金事务池。最小技术栈继续 Java21/Spring Boot、MySQL8.4/Flyway、Spring AMQP/RabbitMQ。

### 权威数据与事件事实

- **权威来源按服务分开**：Core 拥有 Quota/TeamGrant/ProviderSpend Ledger、结算后的 Invocation/价格快照、团队发放 Ledger；FinOps 拥有独立的有据可查自部署运营费用凭证与批准修订（D17）。FinOps 使用/发放/采购 aggregate 来自 Core 事件、自部署费用 aggregate 来自 FinOps 本地凭证事实；它们仅是可重建的统计投影，**不得写回扣费余额或作为 API 采购预算判断**。
- 原子提交：Core 账务 Transaction 在 core_db 中把 Ledger + 状态结算 + 对应 Outbox event 写在**同一事务**；Grant 发行事务同理。D17 的自部署运营费用审核在 finops_db 一次本地事务写 Expense/Revision/Fact/Aggregate/Audit，不产生伪造的 Core Outbox 跨库事务。发放成功写 TEAM_GRANT_ISSUED；真实使用结算写 INVOCATION_USAGE_SETTLED（含积分来源拆分和本地补贴Token等安全量化元数据）；外部 Provider 有真实可信费用结算写 PROVIDER_COST_ESTIMATE_SETTLED（同一个 Invocation 只表达一次实际外部成本估算）。待对账/预算预留不写虚假的 SETTLED 事件，可写独立状态告警事件但不入确认消费汇总。
- 账务更正使用显式引用原事件的 REVISION/CORRECTION 事件，含 delta 与递增事实版本；同一 Invocation 或 Grant 有唯一业务操作号与账本约束。消费者仍必须独立幂等，不能信任生产者永远一次送达。
- P4/P5 开发资金和 Team Grant 时就创建 Outbox 表及相应写事实事件合同，**不发布也要保留未投递记录**；P11 统一接上 RabbitMQ relay/读模型并追赶既有未发布事件，避免先实现没有事件的旧账、将来重新改写财务事务。这是已知业务依赖，属于从一开始按全量合同开发，而不是提前在 P1 启动 MQ。

### Publisher / Relay（至少一次而非恰好一次）

运行在现有应用的受控后台 worker，可选独立进程副本但不另拆领域服务。每轮用 MySQL 事务 SELECT ... FOR UPDATE SKIP LOCKED 领取有限 PENDING 或重试到期的行，记录 owner、leaseUntil、attempts 和 CLAIMED（和《03-数据与接口》的 Outbox 状态枚举保持一致）；**领取事务立刻提交**，不能在锁住 Ledger/Outbox 行时发网络消息。消息属性设 persistent、exchange/queue durable、消息 id=outbox.eventId 和 schemaVersion；Routing Key 只来自内部受控 eventType。

使用 Spring AMQP correlated publisher confirms + mandatory returns：只有确认 RabbitMQ 已接管**且未被 return 为无法路由**，Relay 才将 Outbox 按 eventId+leaseToken 条件更新为 PUBLISHED。NACK、RETURN、超时、确认结果丢失、进程崩溃都恢复为待重试（指数退避+上限+抖动、超过上限进入运维待干预）；收到 broker confirm 却在更新数据库前崩溃可能重发同一 eventId，**这是预期的至少一次语义，不是逻辑错误**。不要把 publisher confirm 当成消费者已经统计完成。

持久化交换机/队列使用业务命名空间和独立 FinOps routing；运行 RabbitMQ 停机时资金交易照常提交且事件留 Outbox，队列积压要告警。重试必须限制批量/并发、Outbox 存储量与错误后退避，禁止无限同步阻塞模型响应。

### Consumer / Read Model

RabbitMQ 消费者使用 manual ACK、有限 prefetch。单条处理：
1. 验证 eventType/schemaVersion/required fields、source ledger引用和不含敏感原文；
2. 在一个 MySQL 事务中对 processed_finops_event 使用 (consumerName,eventId) 唯一键插入，成功者写入安全的不可变 FinOpsFact 或追加修正事实，再按 businessAt/company timezone/company currency 与维度对 finops_daily_aggregate 做原子增量 upsert；
3. **提交后才 ACK**。重复消息因唯一键跳过聚合后 ACK；数据库失败不得 ACK，使用受控 retry queue / delayed redelivery（不要即时 requeue 无限风暴）；确定不可修复的 schema/坏消息经过有限次数进入 DLQ/隔离事件并报警，不能默默丢弃。
4. 同一聚合键的并发更新用 MySQL 原子 UPSERT 增量，不先读后写；异步乱序不能破坏 Grant issued / Usage Settled 的独立事实或跨月归属。更正事务通过引用原 source revision 做一次 delta，并支持按事实重新构建汇总。

Broker delivery ACK、publisher confirm 和 MySQL consumer 事务**三者相互独立**；不宣传 RabbitMQ+MySQL 提供 exactly-once 分布式事务，用户视角通过唯一业务事件+Inbox idempotency 达成“效果一次”。这种实现与 RabbitMQ 官方 consumer acknowledgement/publisher confirm、Spring AMQP correlated confirms / returns 和 Transactional Outbox/Idempotent Consumer 模式一致。

### 失败恢复、追账与重建

- Broker down：Ledger/Outbox 不丢，查询 FinOps 可能陈旧，展示 watermark/积压；真实资金余额不依赖报表。
- Relay confirm 已成功但 MySQL 回写状态失败：相同 eventId 可能再次投递，consumer 去重防重统计。
- Consumer MySQL commit 成功但 ACK 丢失：重投后 processed_finops_event 防重复增量。
- 大量迟到 usage 对账或追溯价格修正：按事实 businessAt 的原业务日统计，reportProcessedAt 单独显示，允许旧报表日的 aggregates 经更正/补录变化。
- 重建：冻结一个 event sequence/checkpoint，在独立版本命名空间根据 MySQL 账本/运营成本事实有序回放（或由持久 Outbox 事件重放），比较四口径和原币种合计，再在权限受控的原子 read-model pointer 切换，不能边清表边向管理员展示假的零成本。
- 监控：outbox_pending、oldest_pending_age、publish_retry_count、publisher_returns、consumer_lag、inbox_duplicate_count、dlq_count、rebuild_drift、budget_pending_reconciliation；报警和运维 API 不暴露敏感 Prompt。

### 引入技术七问及复杂度

RabbitMQ 是可靠消息 Broker，解决已发生账务事实到不同分析消费者的解耦、削峰、异步重试；不用 MQ 可由定时 SQL 报表直接从 Ledger 查询，适用于小规模，但与多种报表/告警订阅方隔离弱。Outbox 是与 MySQL 账务同事务持久保存“要发的事件”，专门解决数据库+RabbitMQ 无法天然原子双写的问题；没有 Outbox 会出现扣费成功却无报表事件。Redis 不适合替代 Ledger 或 durable outbox。最终选择 C 因为已有明确 FinOps 异步订阅与可靠性目标，代价是至少一次消息、去重、投递确认、DLQ、回放和最终一致延迟。若实际只有低频单张报表，此选择的收益需在 P11 Review 中如实评估，但不应先写一套将来必换的业务账本流程。D17 澄清：Core 原子 Outbox 仅负责 Core 权威资金/Grant/调用事实；FinOps 自有运营费用凭证经其本地 DB 事务批准/建事实，不存在跨 Core+FinOps 的单事务。

**实施顺序**：P4/P5 的真实资金事务包含 Outbox 插入；P11 完整实现 Spring AMQP/RabbitMQ Publisher、Consumer、FinOps 汇总与回放。待 P0 最终审核版本、批量参数、交换机/队列持久化和错误模式后实施。

资料：RabbitMQ 官方 https://www.rabbitmq.com/docs/confirms ；Spring AMQP https://docs.spring.io/spring-amqp/reference/amqp/template.html ；Transactional Outbox https://microservices.io/patterns/data/transactional-outbox.html 。

## 十七、P0-D11 / ADR-005：生产故障隔离、观测与可恢复部署（提案）

### Business Goal 与候选方案

目标不是“永不宕机”，而是证明**关键系统故障时财务、安全不变量仍成立，且有明确恢复步骤、告警与测量证据**。方案 A 是五微服务加完整云基础设施，功能边界尚未形成独立规模，运维与 RPC 成本过高；方案 B 是仅一个没有故障恢复的单体，容易把 SSE 和控制面混合耗尽资源；方案 C 是**模块化单体 + 明确线程/连接/资源配额 + 两副本压测 + Redis/MySQL/RabbitMQ 独立基础设施 + 受控故障演练**，本轮选择 C。部署规模可根据真实实验条件从单副本测试渐进到两个同版本副本，不提前宣称实际多 AZ 高可用。

### 运行态和启动顺序

- Java 21、Boot 4.1.x 作为当前兼容候选；统一时区的业务日期换算由注入 Clock + ZoneId 完成，DB 用 UTC 存时间；构建/运行同 JDK 主版本，在 CI 测试镜像、Flyway 迁移和启动健康行为。
- Docker Compose 作为可复现开发与测试环境，真实部署可以采用经企业批准的 VM/容器平台。MySQL 8.4 作为唯一资金写主；Redis 负责可丢失的速率/租约/队列；RabbitMQ 负责有重投语义的派生事件。不能用开发 Compose 的单节点 MySQL/Redis/RabbitMQ 声称生产 HA。
- 配置项分组：SERVER/DB/JDBC、REDIS、AMQP、PROVIDER_SECURITY、GOVERNANCE、BUDGET、SSE、ADMISSION、OBSERVABILITY；强制验证环境/必需配置和端点白名单，不把秘钥提交 Git/Docker 镜像或回显到 Actuator。Provider Key 加密存放时版本化轮换，运行时只通过受控凭证引用读取；Employee/Agent Key 与 Provider Key 永不共用前缀、日志与传输。
- **Liveness 仅针对不可恢复的本地进程失败；Readiness 针对接收新运行时请求是否安全**。Redis/DB 断连可使 Runtime admission 不可用，但不一定需要杀掉进程/放弃在途对账与运维诊断。管理只读与运行时 readiness 可分离描述，不以HTTP健康的单布尔值掩盖“资金不可执行”的状态。MySQL/Redis 无法验证权威入场时拒绝新出站。
- 发布流程：先通过 CI + 空库 Flyway 校验和 Testcontainers 回归；先执行向后兼容的数据库扩展迁移，部署同版本兼容镜像，两个 Gateway 轮流摘流/排空，最后清理只在无历史引用/待核对时处理。任何迁移不能破坏旧 Ledger/Outbox/PolicyVersion/Invocation 解码。数据库 schema 或 MQ 消息版本不兼容时不执行自动回滚到会误读数据的旧镜像。

### 有界资源与隔离

- Servlet 和 SSE 线程池、Provider HTTP 客户端连接池、JSON/SSE 网络写等待/单帧缓冲、最大活跃 SSE、Redis 等待票、MySQL 连接池、后台 Outbox/FinOps Worker 要设置**分别的限额、合理超时和可测拥塞拒绝**。不能让异常长 SSE、单个 Provider 卡死、FinOps 回放长查询抢光财务事务的 DB 连接。
- **D15/D17 更新**：Core Outbox Relay 和 FinOps Inbox/ReadModel 分别属于不同应用和数据库，P11 必须独立部署，不能回退为同一 Spring profile 假微服务；Ledger 仍只由 Core MySQL 权威事务管理。
- MySQL 历史库存与活动事务的锁争用需监控 lock wait/deadlock/事务时长；发生死锁只重试**尚未派发**的幂等事务，绝不因重试整个 Controller 而再次发起收费 Provider 请求。
- Redis Cluster 多键 Lua 同槽/lease fencing、延迟心跳、故障切换丢状态必须演练，恢复前暂停新许可。推理引擎硬并发限制独立于 Redis；RabbitMQ publisher confirm/inbox 去重分别演练。

### Observability 的完整数据合同

统一结构化日志保留 traceId、invocationId（仅限日志、非时序标签）、agent/model/deployment安全ID、executionState、billingState、eventType、错误分类、policyRevision、发生时间，**绝不存放原始 messages、响应内容、员工/Agent/Provider密钥、完整 HTTP body 或命中敏感文本**。Tracing 不允许将 Prompt 作为 Span attribute，跨 HTTP/AMQP traceId 只作为定位线索。Prometheus/Micrometer 指标：
- 网关：request_total{routeClass,result,serviceClass}、request_duration_seconds、active_sse_connections、sse_abnormal_disconnect_total、provider_first_token_seconds、upstream_error_total{providerClass,statusFamily}；
- 运行协调：admission_waiting{pool,serviceClass}、admission_active{pool}、redis_script_failures_total、capacity_unknown_lease_count；
- 权威账务：pending_reconciliation_count/oldest_age_seconds、provider_budget_headroom{currency,serviceClass}（公司单租户/受控少量标签）、overrun_count、reservation_cleanup_pending；
- FinOps：outbox_pending_count/oldest_age、publish_confirm_timeout_total、consumer_lag_count、inbox_duplicate_total、dlq_messages、read_model_lag_seconds。
尽量不对每次请求的 employeeId、invocationId、promptHash、API Key、taskId 等高基数值建标签；量值中区分 POINTS、Token、原币种货币，绝不无单位混算。Provider/Model/Deployment 标签数量需有有界注册目录并在爆炸前受指标 cardinality 预算约束。

### 告警和人工恢复 Runbook

- 采购风险 OVERRUN、币种月预算异常、待对账老化、未知上游派发大幅增加 → 冻结相应受影响采购新入场、保留双账预留、检查 Provider 可信证据；不能自动退款未知费用。
- Redis 数据丢失/租约归属不明 → 新入场停用、读取 MySQL DispatchIntent 与真实推理任务事实、保守恢复容量租约，不能因为 Redis key 为空直接发满池。
- RabbitMQ 不可用或 DLQ/Outbox 老化 → 资金链照常写 Ledger+Outbox，处理 Broker/路由问题后用同一 eventId 重投，消费者 Inbox 去重并对账重建；不直接重写 Employee Points。
- MySQL 主写失效 → 新收费出站暂停；如数据库快照恢复存在“已发 Provider 但对应账本快照未保存”的风险，需要外部 Provider 账单和操作日志对齐已派发尝试，不能简单恢复并开放原积分额度。
- Gateway 滚动更新/进程停止 → 停新 Redis admission、撤销可证明未出站的 WAITING，受控排空 JSON/SSE，逾期尽力取消，保留资金/任务待核对。信号关闭不等于上游已停止。

### 性能测量与升级判定

**不得预设已达成的 SLO**。压测分别测 1 和 2 个同版本网关实例，固定 Fake Provider JSON/SSE 的延迟/生成速率、入站 Token、错误分布与并发，报告 Gateway RPS、P50/P95/P99、TTFT、CPU、JVM 堆/GC、活跃连接/线程、连接池/DB锁、Redis队列/许可、PENDING敞口及 ACK/Outbox积压。任何可复现性能缺陷先定位：JVM 线程、慢连接、MySQL热点、上下游延迟、外部 Provider 上限、Redis热点与消费者瓶颈。若同机资源或 Provider Mock 不稳定，测到的瓶颈不能直接推论是微服务拆分问题。

**D15 已取代“是否要首次拆分”的门禁**。进一步从三个部署单元扩展到第四服务时，仍只有在给出基线测试、量化问题、单体内隔离/索引/线程池扩容为何不足、候选拆分数据所有权、跨服务授权/事务成本、预期收益和回退策略后才允许 ADR 提议微服务。项目保持模块化单体且完整验收同样是可接受的结果。

**D11 设计仍为 PROPOSED**：需确认真实部署环境、备份 RPO/RTO、告警路由、API限额阈值、Metric 标签预算、实际压测负载和所有 Testcontainers/Chaos 测试工况。ADR-005 暂记录于本文件，不新建独立 ADR 文档。

## 十八、P0-D12 / ADR-006：P1 管理认证与角色范围（提案）

**业务背景 / 问题**：P1 既要能从空数据库引导出第一个管理员，也要证明 Manager 不越权访问别的 Team；但 P2 运行时双身份尚不存在，更不应该靠一把通用管理 Key 代表真实员工和 Agent。

**候选**：A. 永久共享一个管理员环境 Token（最简单但没有独立员工主体和可撤销 Team RBAC）；B. P1 同时实现完整账号密码/会话/SSO（可用于门户，但当前没有门户及企业 IdP，对本项目过早引入）；C. 显式短期 Bootstrap + 员工独立管理 API Key（每次由 MySQL 核实当前角色范围）。

**决定（待审）**：选 C。Bootstrap 默认关闭，只用于初始管理员建档/恢复。常规管理请求使用独立 mgt_ Key，HMAC-SHA256+部署 Pepper 的安全摘要存储；Spring Security 独立管理 FilterChain，解析的是管理 Employee Principal，而不是 Runtime Employee+Agent 复合 Principal；授权是 GLOBAL ADMIN 或具体 Team MANAGER。写操作在事务内复核即时角色、员工和 Team 状态，审计与变更同事务。P2 运行时凭证和双身份再作为另一条明确隔离的运行时安全链引入。

**为何是这项技术**：HMAC 摘要能不保存明文也可稳定匹配高熵随机 Key；Spring Security 管理过滤器负责认证与访问边界，MySQL 负责真实角色和状态。若不用 HMAC，明文 Token 失窃风险高；如果把 Redis 当 RBAC 权威，禁用/撤销传播和故障边界难证实。比密码登录/完整 OIDC 少会话、CSRF、刷新 Token 和身份提供商运维。

**收益**：P1 是真实可管理、可审计、可越权测试的完整业务块；不需要 P2 Agent 已编码，也不会误开放收费出站。**代价**：引入管理 Key 生命周期、Pepper 轮换、Bootstrap 恢复流程、MySQL 逐请求鉴权成本和并发撤销检查；未来如有 UI/企业身份源，再单独 ADR 评估 OAuth2/OIDC 替代，而不是让管理 Key 假装是永久 SSO。

**执行流程**：Bootstrap 初始化员工/管理员 → 管理员签发一次性展示的管理 Key → 管理请求鉴权查 DB → 当前角色与 Team 作用域判定 → 写事务再次确认角色/状态 → 业务修改+审计原子提交。P1 Compose 随系统配置 Redis 和 Testcontainers 验证连接，但管理认证/RBAC/审计不依赖 Redis；Runtime 端口不因此具备模型派发能力。

**尚待 P0 复核**：管理 Key 有效期策略、真正部署时 Bootstrap 的开关保护、与后续 P2 凭证安全工具复用、严格并发撤销的锁序与 Boot 4.1 的真实依赖兼容。此 ADR 仅记录方案，不代表代码已实现。

## 十九、P0-D13：总体架构交叉审查与唯一执行链（REVIEWED / NOT FROZEN）

> 本节统一此前 D01～D12 的架构口径。结论是：目标业务和模块化单体方向可继续；但这不是全项目 P0 设计冻结。遇到旧段落与本节相冲突时，设计评审以本节提出的后置修订为准，并应同步更新旧段落，而不是让编码 AI 猜测。

### 19.1 从业务闭环检查服务边界

**历史 D13 模块化单体方案已被 D15/ADR-008 替代**：首个交付形态为两个独立 Spring Boot 微服务（Gateway+Core），P11 第三个 FinOps；Core 保留同一 MySQL 的授权/资金/派发意图原子事务。单数据库 MySQL 8.4 为身份、配置发布、额度、审计与账务写主；Redis 是可恢复的共享 RPM/执行许可/等待队列，不是授权/账本；RabbitMQ 在 P11 启用异步分析，之前先由 MySQL 事务写 Outbox。五大领域与实际 Java package 的关系：

| 领域 | 包/子模块归属 | 唯一写主（例） | 对外应用层 Facade |
|---|---|---|---|
| Identity & Control | identity + catalog | Employee、Team、Role、Agent/双 Key/ACL、Provider/LogicalModel/Deployment、价表发布 | authenticate / authorize / resolveCatalogSnapshot |
| AI Governance | governance | PolicyRevision、activePolicyPointer、Agent 出站审批、Deployment 数据边界与安全审计 | classifyAndAuthorize / assertCurrentPolicy |
| Quota & Billing | quota | 周 Points 桶、TeamPool/Grant、公司/员工保底、紧急授权资金约束、Provider 原币种预算、Reservation/Ledger/Settlement/Outbox | reserveAndAuthorize / settle / markPending / reconcile |
| Gateway Runtime | aigate-gateway | Redis 队列 ticket/lease、本地 SSE/Provider I/O、短暂 Prompt 内存；**Invocation/派发意图已改归 Core** | admit / providerDispatchOnce / callCorePermit |
| Analytics & FinOps | analytics | Inbox、Fact、每日聚合、运营成本来源与报表构建版本 | queryReports / processEvent / rebuildReadModel |

bootstrap、common、observability 是支撑包，不是额外微服务或第二个业务事实源。任何跨领域写数据都通过对方公开 Application/Facade；绝不以跨模块 Mapper 直接改表。

### 19.2 唯一可执行主链（覆盖早期顺序歧义）

1. **接受请求**：管理 API 由 P1 独立 mgt_ Key 认证；模型 Runtime 由 P2 真实 Agent Key 与 Employee Key 双认证。应用请求 body 的 employeeId、priority、Provider URL/Key 一律不产生安全权力。
2. **PREQUEUE**：构造唯一 Invocation/幂等收据；校验 Agent-Employee 与 Agent-Model 两道权限、LogicalModel 能力及合法参数；按最新治理规则完整扫描 messages，筛掉不合规服务和部署；按 NORMAL/LOW/EMERGENCY 的受控资格选择可候选模型/资源池。任何拒绝都不得发生 Provider 出站。
3. **WAITING（Redis）**：校验全局入口限制，按容量池和权重进入有界共享等待；Redis 只放非敏感 ticket、owner、截止时间/许可 token，Prompt 仅驻留收件 Gateway 的有界内存。**此时零积分/采购风险预留**；崩溃或超时原 ticket 作废，不跨实例重播缺失的消息。
4. **ACTIVE/PREDISPATCH**：拿到与真实 Deployment/Provider 限流范围匹配的 Redis 许可，复核真实双 Key、Employee/Agent/Model 权限、当前治理版本与原消息安全扫描、Deployment 数据边界、价格/币种和相应服务档预算。许可绑定容量池；换 Pool 必须先安全释放旧许可并在原 deadline 内最多一次受控重选。
5. **同一个 MySQL 短事务**：锁/验证当前派发权（Key/ACL、Governance activeRevision、受信 Deployment/价格版本、紧急授权状态），对内部 Points 或本地基础保底 Token 与外部采购原币种月预算（仅 THIRD_PARTY_API）做原子预留，写唯一 Invocation DispatchIntent/Attempt Token 和必要 Outbox/audit 证据；一方不符就全部回滚、零上游发送。发布策略/吊销权限与派发事务必须通过兼容行锁/条件校验产生可证明的先后顺序，不能仅靠最终一致 Redis 快照做安全决策。
6. **网络执行**：提交后在事务外只允许一次不确定/可收费上游发送，按 Adapter 的受限 JSON/SSE 合同增量读写。资金事务不覆盖任何 Provider HTTP/长 SSE 网络 I/O。提交的 DispatchIntent 不代表一定发出了字节：出站结果未知不得盲重试。
7. **终态**：得到可信 usage 时从冻结价与原账户原周/月结算、Ledger+Outbox 同事务记录一次；可证明零费用/未出站才 RELEASE；任何可能收费且无法确认的情况 PENDING_RECONCILIATION，**同时保留积分/本地补贴与对应货币预算风险**。Redis 真实容量许可需要收到可验证的上游任务结束/取消证据才能释放，TTL 仅作保守恢复信号。
8. **异步派生**：P11 起 Outbox Relay→RabbitMQ→Inbox 去重→FinOps 四口径 Fact/Aggregate；MQ 中断不回滚已提交的资金事实，FinOps 延迟绝不意味着已确认账务为零。

注意：第 5 步治理/身份并发授权的线性化点是权威数据库派发事务成功提交，不保证在第 6 步网络传输期间实时撤回已经合法提交的请求；管理员可尽力取消并记录证据。P1 管理角色、P2 运行时员工与 Agent 两种 Key、P6 治理发布角色是三类不同的授权，不可混成一个信任标记。

### 19.3 供给、资金、审批、调度是四条独立坐标

| 路径 | Model 选择 | 内部资金/限制 | 第三方采购月预算 | Redis 执行级别 |
|---|---|---|---|---|
| NORMAL 第三方 | 明确授权的所选 LogicalModel | Agent 周免费→个人周额度→有效 Grant | 原币种 NORMAL 份额+总额 | NORMAL |
| NORMAL 自部署 | 同上、经批准 SELF_HOSTED | 同样的内部 POINTS | 无按次 API 采购则不占（运营成本另算） | NORMAL |
| LOW 付费保底 | 单独获准的较便宜 fallback LogicalModel，须重新鉴权和数据出站检查 | 员工剩余普通积分→公司付费保底池，公司的补足部分占员工周保底 cap | 收费 API 占 NORMAL 份额+总额 | LOW |
| LOW 本地基础保底 | 特批 BASIC_FALLBACK，自部署且容量可信 | 独立员工周 Token 补贴，与普通 Points 不混账 | 无按次 API 采购则不占 | LOW |
| EMERGENCY | 审批指定 Employee+Agent+Task+Model，有效且未撤销 | 公司紧急 Points 池+任务核准上限（不是 Team Grant） | 收费 API 占 EMERGENCY 份额+总额 | EMERGENCY |

**补充约束**：选用 LOW fallback 既改变 Model，也可能改变费用及资源池，必须有明确的、可审核的 Agent/业务侧降级授权边界，不能只凭 Router 觉得更快/更便宜就替换。NORMAL/LOW/EMERGENCY 的名额权重与积分资金来源不是一回事。过期 Grant/跨周桶/跨月现金预算的已合法预留必须从原来源核算，不释放到新期间。真实公司金额、周额度和模型价格均为管理员配置，不在源码硬编码。

### 19.4 版本与数据所有权一致性

- 只有 Catalog 能发布不可变价表；内部 POINTS 价表绑定 LogicalModel，Provider 采购价绑定具体收费 Deployment；同 LogicalModel 不因部署切换改变员工积分价格。
- 只有 Governance 能发布不可变政策和当前 activeRevision；管理编辑、审核者不能同人自批；发布/例外失效在派发事务与资金准入竞态上遵守同一数据库序列。
- 只有 Core/Quota 更改余额、预留和账本；**Core 同库同时持有 Invocation/Idempotency/DispatchIntent 权威记录**，Gateway 只有远程申请 permit 的能力，不能直连核心账本；FinOps 只从 Ledger/Outbox 派生，不反向修正余额。
- Gateway 是 Prompt 的短期有界内存所有者；D15 的 Core 治理预检内部 RPC 可短暂在 Core 有界内存扫描文本，但两者都不得持久化 Prompt，也没有跨节点“从 Redis 队列恢复 Prompt”的能力。Invocation 可长期存安全元数据/幂等收据，不存完整上下文/回复。
- Catalog/Identity/治理审批等可使用版本化配置快照做预检；最终派发校验必须基于权威 MySQL 当前状态，绝不因为 Redis/Caffeine 缓存未失效就放行已撤销权限。

### 19.5 故障策略统一

MySQL 不可安全写/治理 activeRevision 不可核实→新出站拒绝；Redis 不可用、真实共享容量不可信→新入场拒绝；RabbitMQ/FinOps 不可用→已授权业务仍可在 MySQL 提交 Ledger+Outbox，报表显式 DELAYED；Provider/GPU 不可信或无法确认是否收费→已可能出站请求保持待对账，禁止透明重发。重启/排空时 WAITING 零资金，已写 Intent 的请求不能当作取消成功；避免锁住整个数据库等待网络。

## 二十、P0-D14 / ADR-007：技术选型正式确认与工程兼容门禁（2026-10-21）

### 20.2 为什么是这套技术（引入前七问）

**Spring Boot/MVC**：它是 Java Web 应用的自动配置与 Servlet 控制器技术；解决管理接口、HTTP Provider 代理和已计划 SSE 的统一开发。若不用，需要自己维护 Web 容器、事务/安全与配置；替代方案是 Micronaut/Quarkus 或 WebFlux。首版业务偏事务管理和受控 SSE，选择 MVC 较易测试；代价是需要显式管理慢 SSE 的线程、连接、缓冲与阻塞压力。**不因为 SSE 存在就切换 WebFlux。**

**MyBatis-Plus**：在 MyBatis 上增加常见 CRUD、Wrapper 等能力；组织、模型目录多表管理与显式财务 SQL 都需要可靠 JDBC 映射。若不用可用 Spring JDBC/JPA/MyBatis 原生；当前选择 MyBatis-Plus 减少大量重复 CRUD，同时保留复杂锁/账本使用明确 SQL 的控制力。代价是升级时需要验证 Boot4 Starter、映射器扫描、分页插件、事务语义；**不能让 ORM 自动更新绕过资金行锁**。禁止再重复引入其他版本 MyBatis Starter。

**MySQL + Flyway**：MySQL 负责 Team/Employee/权限、资金账本、价格/政策版本的 ACID 与唯一键；Flyway 负责不可逆替换的历史 schema 演进。若只用 Redis/内存不可保障权威资金事务；PostgreSQL 是可行替代，但本项目既定 MySQL 业务/学习路线更直接。代价是锁序、索引、死锁重试和迁移审查，所有业务事务坚持短事务。**Flyway MySQL 模块不可漏掉。**

**Redis + Lua**：Redis 是共享键值状态，Lua 在服务端以单次脚本原子管理同一容量池的 RPM、WAITING、ACTIVE 和 lease；否则第二个 Gateway 副本会破坏 JVM 本地并发限制。替代 JVM Semaphore（只单副本有效）、MySQL 热行队列（写放大）、单独排队服务（过早复杂）；当前选择 Redis。复杂度为 TTL/fencing、跨键脚本、故障恢复与多实例集成测试。它绝不作已扣积分、可用资金或最终安全授权的事实源。

**RabbitMQ + Spring AMQP**：消息代理解耦账本提交与 FinOps 的派生报表；若不用 MQ 可以同步汇总或数据库 polling，前者增加主事务响应开销，后者难管理多个消费者/重试。Kafka、RocketMQ 适用于更高事件留存/回放诉求，但目前一个主要 FinOps 消费链 RabbitMQ 够用。代价是 Publisher Confirm/Mandatory Return、Inbox 去重、手动 ACK、DLQ/重试和报表最终一致；**MQ 不能代替资金事务的 MySQL Outbox**。该选型从先前“候选”升级为已批准。

**Testcontainers/Compose/CI**：测试必须依赖真实 MySQL CHECK/事务、Redis Lua 与 RabbitMQ 重投，而非 H2/纯 Mock。替代手工本地容器或统一共享测试数据库均难复现；选择一次性容器确保一致性，代价是 Docker/CI 启动成本及依赖镜像安全管理。CI 输出真实通过/失败/跳过数，不能把拟定测试清单冒充已执行。

**Actuator/Micrometer/Prometheus/Grafana/JFR**：分别负责运行健康、应用指标、时序采集、展示和 JVM 性能分析。没有这些工具可先看日志，但无法回答 SSE 资源/账本热点的可测量问题；初期只用基础 Actuator，不在 P1 就搭完整监控栈。代价是指标基数、部署/告警配置和观测数据脱敏。

## 二十一、P0-D15 / ADR-008：从初期直接采用三服务微服务架构（用户已确定；设计合同待全量冻结）

**状态：ARCHITECTURE CHOICE APPROVED / DETAILED CONTRACT PENDING。** 用户在 2026-10-21 明确要求“直接拆，并确定拆分理由”，因此**撤销此前 ADR-001 与 D11/D13/D14 中“先部署一个模块化单体、P12 看性能再决定是否拆”作为实施目标的决定**。这并非经性能测量宣称单体无法使用，而是明确选择以真实服务部署隔离、远程通信和分布式运维作为 AIGate 产品目标/学习目标；不能将学习目标冒充实际高并发瓶颈。

### 21.1 背景、问题、候选和最终决定

**背景**：AIGate 同时包含长时间持续占用 HTTP/SSE 的模型代理、需要强一致 SQL 的授权/账务、可延迟执行的财务统计。业务协议有真实第三方收费风险，必须避免因服务拆分引入“两次分别扣款”“授权已撤销却从缓存放行”“失败盲重试重复计费”。

**问题**：从项目初期如何建立**真正独立运行/部署/扩容/故障隔离的服务边界**，同时保留资金及派发决策的一次原子 MySQL 提交？也要让用户能够实际讲解服务调用、远程故障、独立数据库、消息幂等，而不是项目结束只在 PPT 里介绍微服务。

**候选方案**：
- A 一个模块化单体：研发部署与事务简单，但长 SSE/管理负载一起发布；缺少真实跨进程通信实践。不再满足用户明确选择的演进目标。
- B 起步五个域一域一服务：Identity、Governance、Quota、Gateway、FinOps 全独立；接口过多，撤销/政策/预算与唯一 DispatchIntent 将跨不同数据库，得引入复杂且当前没有业务理由的分布式事务/补偿，付费风险难证明。
- C **初期 2 个服务，最终固定 3 个部署单元**：Gateway 专注外部接入/SSE，Core 同库保留强事务域，FinOps 异步单独部署。此方案是最终选择。
- D 把 Quota 和 Gateway 放一服务、Control/Governance 放一服务：运行时资金可本地提交，但吊销/治理发布成为跨库即时权限问题；相比 C 更难保证已撤销权限在派发线性化点被拒。

**决定**：**从 P1 就部署两个可独立构建/运行/重启的 Spring Boot 服务：aigate-gateway 与 aigate-core。P11 增加真实 aigate-finops，形成三个独立部署单元。** 五个既定业务领域继续存在，但不一对一变成五个微服务。初期所有代码保持一个 Git 仓库、多 Maven 模块与三个独立 Spring Boot 可执行应用；没有伪造进程内 Facade 来替代真实 HTTP 调用。

### 21.2 三个部署单元的职责/数据库/发布边界

| 部署服务 | 归属职责 | 数据存储与严格边界 | 何时必须真实运行 |
|---|---|---|---|
| aigate-gateway | 唯一外部 HTTP 入口；管理 API 安全透传/路由；P7 起模型 Runtime JSON/SSE、Redis 限流/WAITING/ACTIVE lease、受控路由、Provider 适配与上游网络 I/O、有限 Prompt 内存 | 无权访问 core 数据库和 Mapper；Redis 只放票据/lease，无正文/密钥；Gateway 可独立多副本/滚动重启 | **P1**：已有可访问的管理 API 转发链；P7 完整模型 Runtime |
| aigate-core | 组织、Employee/Agent/Key、Model Catalog/Price、治理规则/发布、Team/Grant、Points+Provider 预算/结算、紧急审批、**Invocation/Idempotency/DispatchIntent 的权威事实**、Ledger+Outbox | 唯一写 core_db（一个 MySQL 数据库，一个事务）；五领域中 Identity/Control、Governance、Quota 与 Invocation 财务关键事实为 Core 内的模块；不能让 Gateway 或 FinOps 直连该库 | **P1**：P1 管理 API/五表 V1；P2～P10 逐业务块完善 |
| aigate-finops | Outbox 经 RabbitMQ 传送后：Inbox 去重、日报/查询/费用来源/迟到修正、FinOps 告警 | 只写独立 finops_db，数据库用户没有 core_db 表访问权限；消息体禁止 Prompt/Key；绝不能回写 core 余额 | **P11**：提供真实消费者与报表服务 |

**数据隔离实施默认**：Docker Compose 开发可共用一个 MySQL 8.4 容器，但至少两个独立 Database/Schema 与独立最低权限账号；禁止跨库 SQL JOIN、共享 ORM 实体或 FinOps 直查 core 表。P11 要能单独迁移、停止、重建 finops_db，Core Ledger 和 Runtime 正常。Gateway 不必为“每服务必须有数据库”另建无意义数据库。服务独立部署与数据所有权并不要求每个服务拥有单独物理 MySQL 服务器。

**外部路由**：只有 Gateway 暴露外部入口。P1 对 /api/v1/** 的管理请求通过 Spring Cloud Gateway **Server Web MVC** 转发到 Core，由 Core 自己验证 mgt_ Key 和授权；Gateway 不接受客户端自报的已验证身份。P7 的 /v1/chat/completions 和 /v1/invocations/** 为 Gateway 原生 Runtime 接口，真正付费许可必须由 Core 内部 API 签发。P11 的 /api/v1/finops/** 报表和费用命令由 Gateway 代理至 Core，Core 独立认证用户、决定范围，再以 svc_core_finops 凭证调用 FinOps 内部 API（D17）；FinOps 不直接接收外部管理凭证。

### 21.3 核心分布式业务主链：拆服务但不拆派发事务

~~~text
Agent + Employee
       |
       v
aigate-gateway  -- 管理 API route --> aigate-core
       |
       | Runtime JSON/SSE 原请求，仅临时有界内存
       | POST /internal/v1/invocations/preflight
       +---------------------------------------> aigate-core
       |       core: 双身份认证、Agent/Model ACL、治理分类、候选资格
       |       core: 原子创建唯一 Invocation/幂等收据
       <--------------------------------------- 初检收据 / 安全许可候选
       |
       | Redis 全局等待队列：WAITING 零资金 → ACTIVE lease
       |
       | POST /internal/v1/invocations/{id}/dispatch-permits
       +---------------------------------------> aigate-core
       |       核查最新 Employee/Key/ACL/治理/Model/Deployment/资金
       |       仅在 Core 中开启一次 MySQL 事务：
       |       授权版本校验 + Points/现金原币种双预算预留
       |       + Invocation 唯一 DispatchIntent/Attempt + Outbox
       <--------------------------------------- permitId / 实际 Deployment/冻结价
       |
       | 只允许本次有许可上游请求发出一次
       +------------> Provider / SelfHosted 推理 → JSON/SSE 返回
       |
       | POST /internal/v1/invocations/{id}/usage-or-pending
       +---------------------------------------> aigate-core
       |       core: 同一个 DB 事务完成双账 Settlement/Ledger/Outbox
       |       usage 不可信则保持原账 PENDING_RECONCILIATION
       |
       +-- Redis 实际任务结束许可释放
                                          Core Outbox --P11--> RabbitMQ
                                                               |
                                                               v
                                                      aigate-finops / finops_db
~~~

**服务间事务最重要的边界**：Gateway 获取 permit 前绝不能发送 Provider；Core 的 permit 提交与资金/唯一 DispatchIntent 必须原子。跨网络没有所谓“RPC 和 Provider 请求在同一个分布式事务”；**Core 提交 permit 后 Gateway 崩溃或超时，不能盲目获取第二次 permit 并重发模型**。Gateway 必须用原 invocationId/reportAttemptToken 报告和查询状态；若是否发送不明，Core 保持双账待对账。请求只能在获得 ACTIVE 许可后申请 permit。PREQUEUE 的治理扫描可通过 Gateway→Core 受控内部 RPC 将原消息短暂放入 Core 有界内存供安全规则评估；Core 不存 Prompt/Reply/密钥，不跨 MQ 发布正文。派发前再次重评；完整扫描与最后锁校验采用“扫描在事务外、当前策略版本/授权/价格与资金在同事务内验证”，不能把长文本扫描/HTTP I/O 放在 MySQL 行锁中。

**统一存储迁移**：D13 曾建议 Gateway 拥有 Invocation 表，现**改为 Core 拥有所有权威 Invocation、Attempt、Idempotency 与 DispatchIntent**，仅 Gateway 记录本机连接/队列临时状态与非敏感运行观测。P4 的独立 requestRef 与 P7 的 Invocation 对应关系仍必须保证无碰撞/可回溯；P7 将 Core Invocation 注册和 P4 财务 requestRef 由 Core 同库约束为一对一，不需跨库 FK。

### 21.4 内部 RPC 安全、超时和故障处理

- Gateway→Core 的内部接口独立于公开 /api/v1 和 /v1，路径固定 /internal/v1/**；不受外网路由，不信任用户携带的 X-Employee-Id、X-Internal-*、priority、permitId。
- Core **自行**查 MySQL 验证两份原始运行 Key、员工/Agent 状态、ACL；不接受 Gateway 自造的 Principal 作为账务和准入依据。服务到服务身份在开发 Compose 使用隔离网络 + 专用服务凭证、生产目标使用 TLS/mTLS 或等效可信内部网关身份；签发/轮换/重放防护和证书配置作为 P0-P1/P7 详细合同，不用裸内网地址等于可信身份。
- 内部 HTTP 用 Spring 的受控阻塞 RestClient/HTTP interface + DTO 明确超时、连接池上限、状态码/错误码；网关只对**可证明没有产生服务端副作用的读请求**有限重试。permit 这类写操作在超时后必须按业务幂等 token 查 Core 原状态，不能重试成第二次财务预留。
- 每个 HTTP 请求通过 traceId、invocationId、attemptToken 串联；不把员工 ID、高熵 Key 或 Prompt 写追踪属性/Metric 标签。两个服务的健康/readiness 独立，Core 不可用时 Gateway 模型新出站 503 fail closed；已送 Provider 且费用未知，保存/核对 Core 权威事实。FinOps 停机不阻止 Core 写 MySQL Ledger+Outbox。
- Gateway 独立承载长 SSE/慢客户端连接和容量压力；Core 的短事务只在 RPC 期间执行，不因客户端持续读取流而长时间持有连接/DB 行锁。若 Core 负载受治理扫描影响，先在 Core 内独立有限执行器、线程池、资源池和长度限制；确有实测问题再讨论第四服务，不默认把 Quota 拆出去。
- 各服务代码与 DB migration 独立；shared contract 模块只包含版本化 DTO/schema/错误码、基础不敏感追踪字段，不放共享 JPA Entity/Mapper/数据库驱动逻辑，防止以公共 jar 偷偷耦合内部实现。

### 21.5 新技术选择七问：Spring Cloud Gateway Server Web MVC / 内部 RPC / 服务发现

**Spring Cloud Gateway Server Web MVC 是什么？** Spring Cloud 提供的基于 Servlet/WebMvc.fn 的 HTTP 反向代理与路由组件，不是 AIGate 业务模型路由器。解决外部单一入口和把管理/FinOps 的公开路径统一转发到 Core 授权代理的问题；如果不用，可以用 Nginx/Traefik 或自行写代理。选其 Web MVC 版是因为它适应已确定的 Spring MVC/Tomcat 技术栈、可以在 P1 就真正转发管理 API。代价是引入兼容 Spring Cloud BOM、网关路径/头透传安全、额外一个网络跳、路由测试；必须确保 SSE Runtime 是 Gateway 原生业务 Controller，不能把模型流式请求当普通反向代理来做账务。

**Spring Cloud BOM**：官方 Spring Cloud 项目明确 2025.1.x（**至少 2025.1.2**）兼容 Spring Boot 4.1.x。选择 **Spring Cloud 2025.1.2 为初始兼容验证基线**，只在 gateway 应用声明 Spring Cloud Gateway Server WebMVC 需要的依赖，Core 不因“微服务”而引用全家桶。禁止使用 Boot4.2 对应的 2026.0.0-M1 预览版本来替换已批准 Boot4.1.1；实际依赖组合必须按 TECH 检查编译、启动和路由。官方依据：https://spring.io/projects/spring-cloud/ 与 https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webmvc/starter.html 。

**内部 RestClient/HTTP 接口是什么？** Spring 生态的 HTTP 客户端，Gateway→Core 在业务请求级远程调用。解决跨进程审批、派发许可和用量报告；不用只能同进程 Facade，违反直接拆服务要求。替代 OpenFeign、gRPC；先选 RestClient，因为一个固定 Core 目标、几类明确 DTO，减少新的框架/服务发现依赖。代价是超时、幂等、连接池、可用性与兼容演进。**不能按 Token 每片增量 RPC 到 Core**，只在请求前/派发/结算及受控状态查询调用。

**Nacos/注册中心/配置中心是什么？** 集中维护动态服务实例地址和配置版本；当大量动态扩缩实例需要注册发现、环境多且配置中心成为真实需求时有价值。目前 P1/P7 用 Docker Compose 内部 DNS service name 和明确受限的配置即可稳定定位 Gateway/Core；不用 Nacos 的代价是开发环境不能自动展示动态注册/集中配置功能，但并不阻止真正的微服务独立进程、RPC 和数据库隔离。Eureka/Consul/Kubernetes Service/DNS 是替代；本次**明确不强制引入 Nacos**，后续若要学习注册中心，需要作为有验收目标的业务/基础设施增强做独立 ADR，且验证 Spring Cloud Alibaba 与 Boot4.1 版本兼容，不能为了名称“微服务”就强装。

**MQ 选择不变**：MySQL Outbox + RabbitMQ + FinOps Inbox 仍已选定；拆出 FinOps 不额外引入 Kafka 或分布式事务管理器。RabbitMQ 真正启用在 P11；之前 Core 内已持久积累可靠事件。

### 21.6 明确新增的收益和成本

**收益**：模型长 SSE 和受限控制面分开弹性扩容/故障定位；独立构建/部署/启动的真实微服务经验；Core 保留安全+财务一次事务；FinOps 可独立停机、重建、扩容而不修改核心账本；项目拥有可验证的网络故障、服务身份、接口兼容、消息重复消费和服务可观测性案例。

**成本**：从 P1 起必须有两份应用配置/日志/健康/部署；管理请求多一次 Gateway→Core 网络跳；内部 RPC 安全、超时、traceId 传播、配置/证书、联调和独立版本发布都需真实测试；Gateway 崩溃与 Core 资金预留的不确定状态更加明显，需要严格保留待对账。与单体相比会增加开发/运行成本，不能宣称这对一个人开发必然更高效。

**变更门禁**：不自动扩展到五个/更多微服务；任何进一步从 Core 拆出 Quota/Identity/Governance 的提议必须提供为什么当前 Core 原子派发决策不能满足、跨库一致性怎么保证、回滚/恢复怎样测试的 ADR。**三服务部署边界本轮经用户确认；微服务 API/数据库迁移和完整工程兼容测试仍在 P0 设计中，未批准本地 AI 编码。**

## 二十二、P0-D16 / ADR-009：Gateway→Core 服务信任、一次性派发及 Provider 凭证边界（详细提案）

> 状态 **PROPOSED / NOT FROZEN**。D15 的三服务拓扑已经确认；D16 是让两服务能够安全合作的细节选择，不代表已经测试或用户批准了所有凭证/生产证书管理默认。原文所有“Core 信任 Gateway 已鉴权员工”或“Gateway 通过 HTTP 超时重试派发”式理解一律不符合本节。

### 22.1 业务问题与候选方案

**背景**：外部客户端只有 Gateway 入口；Core 拥有 Employee/Agent 身份、策略、内部 Points+采购风险预算和唯一 DispatchIntent；Gateway 执行长 SSE 与 Provider HTTP。管理 API P1 需真实代理；P7 一次收费调用需要有限次内部 RPC，且 RPC 结果可能丢失。

**问题 A：谁被允许调用 Core？** 内网 URL 不等于授权，攻击者可伪造 HTTP Header。候选：仅 Docker 私网（不足以抵御被入侵容器）；mTLS 双向证书（强身份但初始证书管理复杂）；**TLS + 高熵短期/可轮换 Service Credential + Core 自己验证业务 Key**（最少新技术但需要密钥管理）。初期选最后方案，Compose 开发可以使用标明不具生产级保密性的私有网络明文 HTTP，**生产 profile 未提供服务端 TLS/可信证书即拒绝启动内部付费通道**。当存在成熟证书自动化时可追加 mTLS，但不能用“以后会 mTLS”掩盖当前无加密链路。

**问题 B：如何处理一次收费派发的网络不确定性？** 候选：失败自动重试 Provider（可能双重收费，不可用）；用 MQ 最终一致发布 dispatch（无法阻止重复与仍需账务）；分布式事务覆盖 Provider（外部 Provider 不参与，不现实）；**Core 事务写一次性 Permit+预留，Gateway 只在本进程收到明确成功响应后尝试发出一次，所有超时返回状态查询与保守对账**。选择最后方案：更保守，可能暂时占用预算，但不把不确定性变成重复收费。

**问题 C：Provider 凭证谁保存/谁实际使用？** 候选：各 Gateway 复制全部 Provider Key（运维泄露面大）；Core 代理 Provider 网络 I/O（又把长 SSE 放回 Core，破坏隔离）；独立 Vault/云 Secret Manager（有效但初期新依赖且公司无现成资源）；**Core 管理/加密保存凭证，仅在明确已提交的 Permit 对应 Deployment 上，通过受认证加密内网向该 Gateway 返回短暂执行凭证，Gateway 只驻内存使用**。初期选最后方案；没有短期上游 Token 机制的真实供应商返回的仍可能是其长期 API Key，**不得称其变成了临时密钥**。因此 Gateway 属于能短期接触 Provider Secret 的高信任执行端，遭攻陷仍会有泄露风险，需日志脱敏/权限/最小暴露/轮换，生产可迁移现成 Secret Manager。

### 22.2 三种认证彼此不可替代

| 层次 | 具体身份 | Core 能信任什么 | Core 绝不能信任什么 |
|---|---|---|---|
| External Management | Authorization: Bearer mgt_... / 受控 Bootstrap | Core 自己查 DB 的员工、管理角色和 Team scope | Gateway 生成的 X-Employee-Id、X-Role 或“已认证”声明 |
| External Runtime | Authorization: Bearer agk_... + X-Employee-Key: empk_... | Core 每次 preflight 和最终 dispatch 独立核验两份 Key、EmployeeAgent 与 AgentModel 两道 ACL | 客户端 body 的 employeeId / providerId / serviceClass；Gateway 缓存的过时权限 |
| Internal Gateway→Core | X-AIGate-Service-Authorization: Bearer svc_... | 当前请求出自持有效 Service Credential 的 Gateway 进程（或持有者） | 持有 svc_ 就一定获 Employee/Agent 授权、一定可出站/扣钱 |

**服务身份实施默认**：P1 起在 Gateway/Core 注入同一可轮换服务凭证，svc_ 前缀 + 32 字节 CSPRNG Base64URL 字符串；Core 仅从外部配置读取 active/previous 版本并常量时间比较，不在 MySQL 保存明文。previous 只用于受控滚动窗口（默认上限 24 小时且必须显式设置淘汰时间），调完即删除。服务 Key 与 mgt_/agk_/empk_、HMAC Pepper、Provider Secret 分开生成，不可互用。配置使用独立 secrets/env 注入，Compose 提供不提交 Git 的本地开发示例占位符；生产所有服务链路至少验证 HTTPS 服务端证书并走私有网络/防火墙，禁止明文 Service Key 出公网。

**P1 管理路由**只转发原 Authorization: mgt_ 给 Core，由 Core 独立鉴权；不额外信任 Gateway 声明的管理角色。**P7 /internal/** 必须同时验证 Service Credential 与操作所需 Runtime 双 Key/调用归属，/internal/ 的读写和 Credential 领取还须验证 permitId/attemptToken 与用途；少一个维度都拒绝。

### 22.3 必须设计为显式隔离的路由

- 网关外部明确允许 /api/v1/**（仅到已注册 Core 管理资源）、P7 /v1/chat/completions 与 /v1/invocations/**；永远拒绝外部 /internal/**、/actuator/** 中非批准健康用途以及任意 upstream 目标地址。不能有把 /** 全部转发到 Core 的 fallback route。
- 所有入站 X-AIGate-Service-*、X-Internal-*、X-Authenticated-*、Forwarded/X-Forwarded-* 中**可伪造的信任相关内容**都删除/按真正可信前置代理设置重建；不能让外部客户端伪造 Service Credential 与内部用户。标准 HTTP hop-by-hop Header 在代理中按协议处理；不在日志打印完整 Authorization、Idempotency-Key、Prompt、签发时只展示一次的 mgt_ Key。
- Core 管理路径鉴权和 /internal/v1/** 的 Service Credential 使用不同 SecurityFilterChain/访问策略。Core 容器默认不映射业务端口到宿主机公开网络；网络隔离是第二层防护，不替代 Core 自己鉴权。
- Gateway 与 Core 都允许按 traceId 关联错误，但不把密钥放 Header 透传链路追踪；敏感请求/响应体不留 Access log。P1 管理 Key 签发响应禁止 Gateway 缓存、重放或 retry。

### 22.4 单次 Provider 请求的可证明边界

1. 只有 **Core** 能创建 Invocation/幂等收据并决定最终 Employee/Agent/Model ACL、PolicyRevision、价表、资金；Gateway 只持有真实客户端 Key/原文的短暂内存副本和 Redis lease。
2. PREQUEUE Core 接受受限 64 KiB 以内受控完整消息，完成分类及首检并创建 Invocation；**不预留资金**。Gateway 排队 ticket 不包含原文。preflight 响应丢失时即使同客户端重试也只能找回原 Invocation/409，不派发第二次请求。
3. Gateway 获真实 Redis ACTIVE lease 后，在受控 deadline 内向 Core 提交 dispatch-permit。Core 先对原文按当前策略重评，最后短事务中锁定真实权限/治理发布指针/账户并一次写预留+唯一 DispatchIntent+Attempt。一次 Invocation 的收费 Attempt 最多一条；所有后续重复 permit 请求均不能再颁发“允许重新网络发送”的新令牌。
4. **只有正在处理首次 permit 成功响应的同一 Gateway 执行流程**才允许开始首次 Provider 网络发送。Core GET dispatch-state 的 PERMIT_COMMITTED 只用于诊断/对账，**不是可再次发送的授权**。如果 permit POST 响应丢失，即使 Core 已提交资金，Gateway 也不得自动把查到的 Permit 当作发新请求的依据；同请求只能返回状态/等待人工或 Provider 可信对账。
5. Gateway 必须在 Provider 发送前再核验本机未发送标记、原 Redis lease 是否仍有效及经授权的 Deployment；如已无许可/进程退场则不得发送，但 Core 资金可能已经预留，需保守待对账，不能凭客户端断开自行认定零费用。
6. Provider 结果与可信 usage 以同一个 Core Invocation+Attempt 业务键作**幂等 result report**；相同结果丢 ACK 可以重报账务结果，不代表重发 Provider。Gateway 在内存中有限次数重试 Core result；如果 Gateway 崩溃导致这份使用证据丢失，Core 将保留原预留待 Provider 可验证账单/人工对账，**首版不能保证崩溃后自动恢复未持久化的 Usage**。
7. Provider/自部署推理可能已经收到请求但回执未知时，禁止用 HTTP timeout、Gateway crash、Redis TTL 到期或用户重新连接宣称零账单；客户端查 Core 最小账务状态。不能保证对不支持服务端幂等的外部 Provider 实现“物理上 exactly once”；我们提供的是**只有一次授权+禁止不确定重发**与财务风险留存策略。

### 22.5 阶段引入与新增代价

P1 只完整实现管理路由、Core mgt_ 权限和内部 svc_ 安全探针（无真实调用/Provider）；Spring Cloud Gateway MVC 路由过滤、安全 Header 去除、Core 的管理 Key 明文一次签发测试，Core 失联 503。P2/P3 在 Core 实现 Runtime Key 和 Provider Secret 的安全保存；P7 才完整交付 preflight / dispatch permit / result / Credential Fetch 以及双身份、Redis、结算集成。P11 FinOps 需要独立的报表服务信任与数据范围授权，但不得直接复用 Runtime Key 或任意客户端 scope header。

**七问结论**：新增的 Service Credential 本身是高熵 bearer 身份，不是完整用户身份；它解决合法 Gateway 进程访问 Core 私有 API，而不替代双身份/RBAC；不用它会让任意可达内部地址的应用发 permit/读密钥，替代 mTLS/服务网格，选它是初期成本更低但需要 TLS、轮换和泄露监控。一次性 Permit 是 Core 持久化“可能有费用”的网络出站授权记录；没有它 Gateway 失联后容易重复计费，替代供应商原生 idempotency（仅少数供应商提供）或复杂消息协议；选它保留 Core 资金事务强一致，但新增 PENDING 处理和 Provider 对账工作。所有保守故障状态是刻意的资金风险控制，不应通过无限重试换表面高可用。

**尚需 P0 详细门禁**：每个内部 RPC 的完全 JSON DTO/字段约束、时间/状态码、服务证书与生产部署边界、具体 Provider 凭证表/一次性领取事务、防并发再发送状态、外部 Gateway 公网路径路由和测试 fixture。这些在《03-数据与接口》D16 与《05-测试与验收》D16 中逐项细化；当前不是可直接启动 P1 的实现授权。

## 二十三、P0-D17 / ADR-010：FinOps 服务的权限代理、事实归属和读模型可靠性（PROPOSED）

### 背景与问题

D15 已确认 P11 把 aigate-finops 单独部署、写 finops_db，D16 已确定 Gateway/Core 服务身份体系。与此同时 P1 的 mgt_ Key、PLATFORM_ADMIN/TEAM_MANAGER/FINOPS_READER 角色权威在 Core MySQL；FinOps 不可连接 core_db。业务要求管理员/财务人员查询公司/Team/Employee 范围费用，员工只查本人，历史员工转 Team 和历史 Team Grant 仍按发生时事实归属。**问题：怎样让完全独立的报表服务不复制授权数据库，也不相信客户端的 teamId、employeeId？**

### 候选方案及最终方案

| 方案 | 优点 | 现实问题 |
|---|---|---|
| Gateway→FinOps 直连，FinOps 直接验证客户端 mgt_ | 少一次 HTTP 跳转 | FinOps 必须复制管理 Key、角色及撤销状态，违反 Core 的身份权威；需要跨库同步与滞后窗口 |
| Gateway→Core 签短期权限 Token→FinOps | 少一次 Core 代理的网络停留，可横向扩展读流量 | Token 签发/受众、有效期、撤销时延、重放/密钥轮换和客户端带回 Token 都是新协议；短期无明显收益 |
| **Gateway→Core（授权）→FinOps（内部读 API）** | 沿用现有 mgt_ RBAC 和服务凭证；权限在 Core 每请求读取，FinOps 只按可信范围执行查询 | 报表多一跳，Core 持有轻量代理连接/请求时延；Core 不可用则无法授权报表 |
| FinOps 查询时反向 RPC Core 鉴权 | FinOps 直接向外提供报表 | 将公网暴露/身份转发和 Core 权限调用耦合至每种报表、易发生多次鉴权及身份透传问题 |

**选第三种，称为 Core 授权代理（BFF）**。P11 所有外部 /api/v1/finops/**（包括只读、运营费用操作、重建）均由 Gateway 路由到 Core，而不是直接路由给 FinOps。Core 验证 mgt_ 和当前角色/员工/Team 状态后，构造**不可由客户端直接提交的 typed AuthorizedFinopsQuery/Command**，通过独立的 svc_core_finops 凭证和内部受信 TLS 调用 FinOps 的 /internal/v1/finops/**。FinOps 不接收/存储客户端 mgt_、员工运行 Key 或完整 Prompt。Gateway 不自己签授权断言，也不能把外部 /internal/** 透传给 FinOps。

这是微服务**权限集中管理、数据物理隔离**的设计：FinOps 的报告查询与资源账单修改事务在 finops_db；身份授权事实只在 core_db。Core 不 SELECT finops_db，FinOps 不 SELECT core_db，查询范围由 Core 可信内部协议明确限定。跨服务没有大事务，权限撤销按请求授权裁决先后定义；不能承诺远程已放行的操作在角色并发吊销后物理回滚。

### 精确权限边界（建议默认）

- PLATFORM_ADMIN（GLOBAL、ACTIVE）：公司范围四口径汇总、受限事实明细、权威待对账及 Outbox 运维；可创建自部署运营费用草稿、提交审批、执行受控重建。费用批准必须是**另一名 ACTIVE PLATFORM_ADMIN**（不能自己审批自己录入的费用），批准人仍需具备当前角色；不为学习而另造金融审批微服务。
- FINOPS_READER GLOBAL：公司范围四口径汇总和允许的安全明细；TEAM scope：仅被授权 Team 的汇总与按其归属的安全明细；全部只读，无运营费用批准、重建、Outbox 修改、实时资金操作。
- TEAM_MANAGER：只读其目前仍有 TEAM_MANAGER 授权且 Team ACTIVE 的历史 Team 归属业务日汇总和 Team 发放；员工级明细仅在提供特定 employeeId，且 Core 验证该员工**当前仍属于该授权 Team**并在查询中强制 employeeId+事实历史 Team 快照同时匹配时允许。其他历史 Team 员工级细目不可透视，但已归属该 Team 的聚合金额仍保留不重算。
- 普通 Employee：仅通过 GET /api/v1/finops/me/usage-summary 查看**本人**历史消费积分/本地补贴量；Core 使用认证 employeeId，忽略/拒绝客户端自报 identity。员工转 Team 后其自有用量仍可跨历史 Team 被本人查看；不能查他人、Team Grant 发出总额和公司采购估算明细。
- TEAM_MANAGER 的 Team Grant “发放”一律按事件 issuerTeamId 过滤；Employee Usage 一律按 usageTeamSnapshotId 过滤；Team scope 查询两类报告**各用独立归属谓词**，不得把 Grant 领取员工的当前 Team 当发行归属。
- 被吊销管理凭证/角色或停用员工/Team：Core 后续新鉴权请求拒绝；一次已经在 Core 成功授权并派往 FinOps 的请求按授权完成时点视为已接受的在途命令，不宣称与 Core DB 撤销形成跨库瞬时线性化。敏感写命令需要缩短内部 RPC 截止、审计 authorizationCheckedAt+actorId；若业务未来要求对撤销提交之后在途写全部拒绝，必须在 Core 本地落审批意图或新的跨服务协调协议，另写 ADR。

### 数据所有权必须重新统一的一处旧假设

**Core 是权威**：Employee/Team/RBAC、TeamPool/Grant、Invocation、Points/Provider 采购预算、Ledger、Reservation、Reconciliation、Outbox。其授权的相关账务事务同一个 core_db 提交。

**FinOps 是权威（仅此类运营费用）**：SELF_HOSTED_OPERATING_COST 的外部账单来源、草稿/独立审批/更正/作废和受限审计，位于 finops_db 的 self_hosted_operating_expense。它不是 Core 的实时 Points 或采购预算来源。运营费用批准成功时，在**FinOps 自己一个事务中**写 Expense 状态+运营费用 Fact+聚合/审计（必要时本地事件 Outbox）；**不能错误声称 Core 必须同一 MySQL 事务为它写 Outbox**。Core 只在 HTTP 前验证 Actor/范围，FinOps 负责本地费用业务不变量及明确的 trusted Core command。Core 与 FinOps 没有一个横跨两库的事务。

**FinOps 派生（可重建）**：EMPLOYEE_USAGE_POINTS、TEAM_GRANT_ISSUED_POINTS、PROVIDER_API_COST_ESTIMATE 等来自 Core Outbox→RabbitMQ；LOCAL_FALLBACK_TOKENS_USED 同样按已确认资源事实派生。FinOps 已批准运营费用的 Fact 与 Aggregate 可从本地权威 Expense 的 append-only 修订重建；**两类源分别重建，汇总时保持四口径单位不混加**。FinOps 无权回写 Core 已消费资金。

### 数据新鲜度与实时接口的分离

- GET /api/v1/finops/summary、/trends、/facts、/me/usage-summary：Core 授权后由 FinOps 读取其读模型；Core 可以附带源账本/Outbox 的最小滞后元数据；返回 readModelStatus 与 processedAt，不把“MQ 没收到”解释成0元。
- GET /api/v1/finops/pending-exposure、/outbox-status：**只由 Core 直接读自己的权威 core_db**，不再以 FinOps 作为数据源，也不要求 FinOps 服务在线。页面如需和 summary 一起展示则明确发起两次查询/分区合成，单个 summary 失败不能伪造 pending=0。
- 未能证明所有源事件均到达的时间戳只能叫 lastProcessedAt，不可以称为“历史无缺口 watermark”。出现 Core Outbox 未投递、FinOps Queue/DLQ/Inbox 漏洞、Rebuild 中或对账未知时分别展示 DELAYED/UNKNOWN/REBUILDING，并披露数据不完整；只有完成事件源/Inbox/事实口径核对且没有已知异常，才允许使用 FRESH。
- 按初次派发时公司时区业务日统计，沿用当时 usageTeamSnapshotId；Grant 沿用 issuerTeamId。迟到对账按原业务日修正，绝不把处理日当消费日。为了在权限较窄的 Team Manager 查询中保持一致，读模型必须留足可过滤的原始 attribution，不能只有公司总额一张表。

### 技术是什么、为何需要、替代和代价

Core 授权代理是**以真正的业务授权服务作为访问门槛的后端中转**，并不是再装新的 Spring Cloud Security 产品；Core 的 RBAC/MySQL 与 Spring RestClient 已存在，FinOps 只需要按服务凭证验证受信调用和严格查询范围。若不加授权代理而直接给 FinOps 暴露公网，必须自建角色/Key 同步与撤销机制；替代方案是短期签名 Token 或成熟 OAuth2/OIDC，当前公司单租户/少量管理读 API 没必要另上 IAM。选 Core 代理简化权限事实源，代价是 Core 额外连接占用、报表可用性依赖 Core、不能自动保证远程在途权限撤销；需要明确 bounded requests、连接池/独立执行器、读请求和写命令不同重试、错误语义及可观测性。**FinOps 不是资金付款服务**，新增自部署费用“批准”只是持有证据的运营成本录入，不能凭一个草稿改变 Core 额度。
