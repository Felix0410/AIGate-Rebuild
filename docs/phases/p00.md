# P0 · 全量设计定稿、文档治理与工程兼容基线

> 当前状态：DESIGN_REVIEWED / NOT_FROZEN。该状态只证明静态设计已有候选；没有 PoC、Flyway 或真实 E2E PASS。用户签收前，不启动 P1 业务实现。

## Business Goal

把 AIGate-Rebuild 的业务、功能模块、数据、API、运行协议与测试从逐次追加草稿变成可被本地 AI 一次执行的稳定开发合同，同时以最小真实工程证据确认 Java/Spring/MySQL 基线是否可行。P0 的成果是**明确的设计与可复现的前置工程验证**，不是提前实现 12 个业务 Phase。

## Scope

本阶段包含需求/领域/架构/数据库 62 表的分版本设计、外部和内部 API 契约、Gateway allowlist、Provider/SSE、Redis Lua、资金/幂等、MQ/FinOps 和 P12 恢复协议、P1～P12 实施任务、测试案例、ADR、文档权威与历史草稿替换关系，以及最小兼容性 PoC 设计与运行验收。

不在 P0 编写实际 P7 Chat、P11 FinOps 或 P12 灾备业务；不提前建立全量 62 张实库表；不声称所有未来版本组件已在当前时间点验证。

## Main Flow

需求冻结候选 → 业务闭环与信任边界审查 → Phase/DDL/API/状态与异常矩阵交叉核对 → 主题式规范归并 → 旧文档引用清理 → 最小双进程兼容 PoC → 记录真实结果及调整 ADR → 用户确认 P0 FROZEN → 才发布 P1 执行包。

## Architecture

P1 起采用 Gateway + Core 两独立进程、Core 独占 MySQL；P7 引入 Redis；P11 引入 RabbitMQ/FinOps；P12 多实例。相关不变量参见[完整开发说明书](../00-development-specification.md)、[系统架构](../03-architecture.md)、[ADR](../adr/README.md)。P0 不修改该批准的服务边界，任何实际 PoC 不兼容都通过总控评审决定替代方案。

- [ ] 旧追加式设计草稿已完全被业务主题规范承接；确实过时的文件从当前树移除但可由 Git 历史追溯。
