# 14 · Local Coding AI Protocol

## 任务角色

总控（本对话）：唯一的产品设计、架构选型、任务合同和 **docs/** 维护者；决定 Phase 何时开始、何时通过验收，向用户解释新业务与技术，Review 本地 AI 代码。

本地编码 AI：高效率执行明确工作单的工程师。可修改 src、pom.xml、Flyway 迁移、测试、Docker/CI 等，**不可自行增删改 docs、改需求、重排 Phase、创造额外技术栈或决定微服务边界**。

用户：确认业务、重大选型与 Phase 开始/关闭。主要目标是理解业务流程、技术原理和能独立答辩的架构理由。

## 开发任务接收规则

每个任务从 10-task-contracts 中复制 Phase/Task 编号，并引用 02 业务规则、06 Schema、07 API、08 模块设计和 11 测试要求。任务必须明确：
1. Business Goal 和 Scope（做什么/不做什么）。
2. 执行 Main Flow 与错误流程。
3. 需要的表、字段、索引、接口、状态机。
4. 允许的新依赖及技术原因。
5. 必须验证的单测、集成测试和 E2E。
6. 交付文件清单及 git commit 要求。

本地 AI 如果发现接口或表设计冲突：**停止有歧义的部分，报告具体不一致的文档和候选影响；不得自己拍板。** 没有阻碍的测试/清理可以继续。源代码变更必须容易 Code Review，不混入多个 Phase 的功能。

## 提交格式

每次回复总控：
- TASK：Phase、任务编号、提交 SHA；
- CHANGES：实际完成的业务行为和改动文件；
- API/DB：新增接口/迁移及它们符合文档的证据；
- TESTS：准确执行命令、通过/失败/跳过数量，失败日志关键内容；
- LIMITS：未完成点、设计阻塞、技术债候选；
- RUN：最短复现步骤与环境要求。

没有通过测试不得使用“已完成”。总控必须检查功能、Code Review、测试、架构、技术债、progress、architecture、必要 ADR、知识与面试整理，用户同意再进入下一 Phase。

## 安全边界

不把真实密钥/员工数据提交仓库；本地或 CI 用 Fake Provider、Testcontainers。禁止运行破坏生产数据的脚本。任何无法确认的外部采购费用都不能擅自写为 0。避免在日志/数据库/消息中存储原始敏感 Prompt。不能通过“为了快速开发”跳过收费前预算检查和双身份认证。
