> 本项目交付质量以**实际自动化结果与可重现证据**衡量，不以新增中间件数量或规划的上万人规模替代验收。

## 二、不可缺少的业务验收用例

- 管理员 Team/Employee CRUD、唯一约束、禁用；新的空库执行所有迁移后 API 可正常工作。
- Agent Key 有效、Employee Key 无效或缺失；或任意人伪造 employeeId：**401/403，Fake Provider 请求计数为 0**。
- Employee 对 Agent 无权或 Agent 对 Model 无权；或者出站内容被安全策略拦截：**Provider 请求数 0**，不产生成功扣费。
- 两笔并发调用争同一周额度/Team Grant，**余额−预留始终非负**，任一业务键只完成一次可收费发送和结算。
- 重复 Idempotency-Key：进行中、已经发出但结果不明、已经完成 SSE 都不能第二次扣款或重复出站。
- 周一公司时区边界初始化一次且周额度不结转；历史 Ledger/PriceVersion 不覆盖。
- Team B 给 Team A 的员工发 1000 点，Team B 当时扣 1000 记发放支出；员工后来实际使用 300 归员工，700 到期不退；公司 Provider 采购成本另算。
- 已出站 Provider 超时，或 SSE 客户端断开没有可信 usage：进入待对账，不直接全额释放预留或记为 0。
- 保底公司总池与员工周上限任一不足，收费 Provider 请求计数为 0；未经批准紧急请求不可使用独立应急资金。
- 部署 A 不健康、同逻辑模型部署 B 健康：允许路由 B，不未经许可改选另一个逻辑 Model。
- 安全规则更新后在明确时限内失效/生效，安全审计、指标及消息不得包含完整 Prompt、输出或明文 Key。
- RabbitMQ 发布失败，MySQL 结算仍正确且 Outbox 保留；恢复后补发、重复消费时 FinOps 只统计一次。
- Redis 下线时按审批的安全策略 fail-closed 或受控降级；不能由 Redis 余额代替积分事实。
- 模拟 1 万名员工数据库数据不等于 1 万 SSE 并发：报告真实活跃用户模型、硬件、Provider mock 行为和测得结果。

## 三、CI 和本地运行

**P1 建立最小可运行工程**：Maven Wrapper、Java 21、Spring Boot 4.1 兼容依赖、MySQL Docker Compose、Flyway、Testcontainers，GitHub Actions 运行编译、单测、集成测试及迁移验证；全部通过后才能提交“已完成”。

后续 Compose 只在对应 Phase 增加：P7 Redis、P8 Prometheus/Grafana、P11 RabbitMQ/Worker。配置从不提交实际密钥；Provider Mock 与测试凭证只能在测试环境使用。CI 需要输出真实执行命令、通过/失败/跳过数和 commit SHA。

## 四、可观测性与性能证据

必须能监控入口 RPS、拒绝原因、活跃 SSE 连接、模型/Deployment 请求成功率、TTFT（首 Token 延迟）、延迟分位数、资金预留和待对账队列、Team 授额金额、Outbox 待发布数量、MQ 消费积压与重试。指标标签不能把 EmployeeId、InvocationId 等高基数字段直接放进时序标签；日志保留 traceId 但不能包含用户 Prompt。

P12 压测报告至少列出：环境 CPU/内存、JDK、数据库连接池、Gateway 副本数、Provider Mock 响应时延和 Token 数据、活跃请求/SSE 长连接数、RPS、P50/P95/P99、错误率、堆/GC/线程/CPU、账本一致性、预留/待对账积压，以及微服务与多副本单体的对比。如缺真实测量结果，就只能写“未验证”。

## 五、交付检查

每个 Phase 交付**业务闭环 + 关键失败路径 + 可重跑测试 + 架构合理性**，随后总控执行功能、Code Review、测试、架构、技术债、文档更新、必要的架构决策记录、知识复盘和面试表达。测试通过并不自动授权进入下一 Phase。

## 六、开发方式变更：每业务块与功能同步测试（2026-10-21）

**固定测试门禁**：编码前先冻结全部测试方案、每块测试名称/数据/预期结果；本地 AI 实现每个功能时**同一工作包**编写、运行和提交对应测试。一个业务块的完成标准不是“接口通了”，而是该块功能、权限、参数、异常、并发/事务、幂等、必要的负载或基础运维指标均交付，且本块所有规定测试通过。不能把必要校验/安全/失败路径留下让后续另一个 Phase“优化”。

| 业务块（新排序待确认） | 单元与数据层 | HTTP / E2E、并发与故障 |
|---|---|---|
| P1 组织管理 | Team/Employee 唯一键、状态变更、主团队变更、管理员角色 | 全 CRUD/分页、跨 Team 越权、停用、空数据库迁移、CI |
| P2 Agent 双身份 | 密钥随机性/摘要/有效期/撤销，Employee-Agent/Agent-Model 授权 | 两 Key 缺一拒绝、已撤销拒绝、伪造 EmployeeId 不通过、零 Provider 出站 |
| P3 模型目录 | 多部署注册、价格版本不可交叉、禁用、AES-GCM/安全配置 | 模型/部署 CRUD、Provider HTTPS/SSRF、密钥不泄漏、价表边界测试 |
| P4 个人周积分账本 | 周周期、价格精度、预留/释放/结算、唯一流水与未知费用 | 并发余额不负、同幂等键不双扣、到周一只初始化一次、待对账不可清零 |
| P5 Team Grant | 池扣减/Grant 创建原子性、审批状态机、过期顺序 | 跨团队发放、重复审批并发只发一次、余额不足整体拒绝、到期不返 |
| P6 Governance | 敏感规则、策略版本、权限例外和状态机 | 违规请求阻断、Policy 更新失效、审计无 Prompt/Key 明文 |
| P7 Gateway JSON+SSE | 调用生命周期、模型授权、路由基线、Trusted Usage 解析/settle | 全链路 Fake Provider、SSE 分片/断连/超时、不二次收费、无使用凭证拒绝 |
| P8 智能路由与观测 | 权重/健康/负载策略、延迟分位、熔断边界 | 同 Model 多部署模拟、容错与监控图表、长连接资源上限 |
| P9 企业保底/Redis | 双资金硬预算、员工周上限、全局入场规则 | 两副本 Redis 速率原子性、失联行为、无额度收费 Provider 0 次出站 |
| P10 紧急任务 | 授权/过期/临时池、优先调度公平性 | 未批准不可提权、拥塞下受限优先、资金不能越界 |
| P11 FinOps/RabbitMQ | 分类费用聚合、事件唯一消费、版本兼容与对账 | Broker 宕机账本正确、恢复补发、重复消息不多计、三口径不混加 |
| P12 生产可靠性与拆分评估 | 全自动回归、JVM/JFR、指标数据正确性 | 1/2 副本负载、RPC/故障隔离实测、拆分仅有 ADR 时实施 |

**每块测试交付格式**：测试 ID、前置数据/Mock 及容器版本、步骤、预期状态码和 DB 不变量、实际结果、运行命令、测试通过/失败/跳过数、覆盖了哪些异常/并发场景、Git commit。集成测试不得依赖真实 Provider 密钥和不可控网络。真实资金/安全场景未测则本块验收不通过。

**P0 需要先审完测试设计，再开工**；测试矩阵目前仍是目标/验收级，离所有逐 API 可直接执行的测试规格还有细节缺口。

## 七、P0 专题设计 D-01：双预算验收用例（待确认）

| 测试 ID | 前置条件 / 动作 | 必须断言 |
|---|---|---|
| BUD-01 | Employee 有 100 POINTS、公司本币当月预算 0.20 USD；一次调用预留 30 POINTS + 0.06 USD，确认实际 12 POINTS + 0.024 USD | 同一 invocation 双预算预留后原子结算；员工剩余 88 POINTS，采购估算 0.024 USD，采购可用 0.176 USD；两类 reserved 均归零 |
| BUD-02 | Employee 有足够免费积分，但同币种公司采购预算耗尽 | 收费 Provider 出站计数 0；不能把免费积分视作公司无成本 |
| BUD-03 | 公司外部预算充足，Employee 各允许资金桶不足且无保底授权 | Provider 出站 0，双预算未被占用 |
| BUD-04 | 两个并发请求各要相同公司采购风险额度，二者合计超过可批余额 | 至多一个成功预留，公司的 `settled+reserved<=limit`（正常情形） |
| BUD-05 | Points 预留成功但 Provider 预算不足（或相反） | 同一个 MySQL 事务全部回滚，无任何一方预留残留，也不出站 |
| BUD-06 | Provider JSON 或 SSE 已可能收费、客户端取消且可信 usage 缺失 | 两套 Reservation 都为待对账且不自动归零；有调用与价格版本证据 |
| BUD-07 | 某次请求在月末发送，下个月才提供可信 usage | 结算/释放旧月份预算行，不凭新月份额度抹除旧风险 |
| BUD-08 | 同一 invocation 结果重复回调 / 重复结算 | 两套账各结算一次，唯一 Ledger/Outbox，统计不重复 |
| BUD-09 | 调用期间价格版本更新，最终可信 usage 返回 | 用发起时冻结的积分价和 Provider 采购价计算，历史不追溯改价 |
| BUD-10 | 无本币采购预算、币种不匹配、未批准的风险上界、供应商报价类型未支持 | 付费 Provider 出站计数均为 0，返回受控错误；无负数账 |
| BUD-11 | 紧急授权或企业保底允许额外 POINTS，但公司外部采购币种预算耗尽 | 紧急/限流也不能突破真实外部费用上限，Provider 出站 0 |
| BUD-12 | Provider 可信计量超过已预留的保守成本估算 | 不隐藏超额；产生 OVERRUN 对账/告警并冻结受影响采购预算；不能继续授权新增外部付费请求 |
| BUD-13 | Team 发放 1000 POINTS；员工以后消费其中 300，Provider 估算外部采购费用 | Team 只记录 1000 POINTS 的内部发放支出；员工实际使用 300 POINTS 单列，只有真实 Token 产生外部 Provider 采购成本 |

上述是**P0 预定义用例**，待 D-01 方案确认后再补全具体 SQL fixtures、HTTP JSON、独立测试方法名和执行命令。任何验证“公司外部费用硬上限”的测试，必须注明本系统只能严格控制**按已验证保守风险上界批准的新付费请求**，不保证供应商最终发票不会因异常/合同外计费超出。

## 八、P0 D-02：自部署推理与 API 分账验收（待确认）

| 测试编号 | 行为 | 必须断言 |
|---|---|---|
| MOD-01 | 同一逻辑 Model 同时存在 THIRD_PARTY_API 和 SELF_HOSTED Deployment，配置相同 OpenAI 风格 JSON/SSE 协议 | Gateway API 不变；选定部署后使用正确预算/容量策略，记录实际部署 |
| MOD-02 | 第三方供应商模型正常调用 | 必须 Points+Provider 采购风险双原子预留；不申请 GPU 资源许可 |
| MOD-03 | 自部署模型常规调用 | 必须员工 Points+本地有界容量许可；没有逐次 ProviderSpendReservation，不虚构 0 USD 供应商采购支出 |
| MOD-04 | 自部署服务并发容量已满、等待队列已满 | 限时排队或拒绝，不无界堆积、不默认收费外部回退；未发出模型请求则资金/许可安全释放 |
| MOD-05 | 积分和企业付费保底均耗尽；员工有已批准的本地基础模型补贴额度、本地容量可用 | 允许限速、限 Token 的本地基础服务；不新增第三方供应商 API 请求；审计正确 |
| MOD-06 | 同 MOD-05，但无员工本地补贴额度或无自部署节点或已禁用 | 拒绝且不产生收费 Provider 请求 |
| MOD-07 | 自部署模型安全策略拒绝、员工/Agent/Model 未授权 | 自部署端点入站计数 0，和外部 Provider 一样不可绕过安全 |
| MOD-08 | 本地推理已开始、SSE 中途断连且推理服务确认取消失败 | 保持容量租约至受控回收，不能假设算力瞬间释放；员工 Points 或补贴用量按可信证据/上界核对 |
| MOD-09 | 自部署云算力服务按小时租赁，未提供实时 GPU 指标 | 运营成本按云账单/已知租赁记录展示；网关 GPU 压力显示 UNKNOWN 而非假指标 |
| MOD-10 | 外部 API 采购费用与本地 GPU 月租费用同时计入 FinOps | 两种来源分类，不能将“按 Token 分摊的估算”和同一原始 GPU 费用再次加总重复计费 |
| MOD-11 | 两个 Gateway 副本同时向同一本地模型实例申请容量 | 聚合不突破节点/集群硬并发上限；本地单进程计数方案不得在双副本被误标为全局生效 |

上述测试前需 P0 冻结容量许可具体超时、配额单位与可信使用量获取方式。若无实际 GPU，前期测试使用 Fake SelfHosted Provider；最终简历不可把 Mock GPU 指标称为真实 GPU 压测。
