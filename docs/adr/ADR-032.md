# ADR-032 · Core MySQL全局阻断与Readiness证据

> 状态：设计已选定，待用户P0最终冻结；工程行为未验证。决策不意味着运行测试通过。

## 1. 背景

P12多个Core/Gateway需要一致的停止新付费请求和灾难恢复机制，不能只依赖单进程变量。

## 2. 需要解决的问题

Redis丢Key/旧Gateway版本会绕过本地运营开关，尤其真实Provider收费可能持续。

## 3. 候选方案

1. 本地配置/网关内存标记
2. 只用Redis BLOCK Key，冷恢复有失效风险
3. Core V11全局singleton+审计Receipt+Core最终Permit FOR SHARE，Admin BLOCK FOR UPDATE（选择）

## 4. 最终方案

初始BLOCKED，受控readiness-probes生成Core审计签名证据，30秒内复核并CAS恢复；global epoch与perPool epoch分别验证。

## 5. 选择原因

MySQL资金事实与全局开关同强一致域，Permit与Block之间的锁相容性具有可说明的提交先后。

## 6. 优点

多节点共享事实和可审计恢复，未知外部费用不会因重启清零。

## 7. 缺点与引入的复杂度

每个Permit有一次singleton共享锁，运营Block要等待当前短事务，P12必须压测热点与断网混部。

## 8. 对未来的影响

真实P12性能证据揭示瓶颈时再做新ADR，不能用缓存成功标志替代最终强锁验证。

## 10. 实施证据与重新评审触发条件

| 项目 | 明确规则 |
|---|---|
| 首次相关阶段 | P12 |
| 必须真实验证 | 运营BLOCK提交与Permit FOR SHARE/UPDATE锁序符合全局安全先后；Readiness审计HMAC30秒有效，旧Core混部不能旁路BLOCK |
| 最低证据 | Core×2/Gateway×2、真实MySQL行锁、Redis重启、过期/伪造证据和恢复审计日志 |
| 何时重审本ADR | 若单例锁真实出现严重吞吐热点，再按正确性证据评估分片/新准入机制 |
