# ADR-033 · P3 目录配置与独立审批事实

状态：2026-10-26 用户授权设计，已实现并通过本地验证；待用户整体签收，测试与限制见 [Progress](../10-progress.md)。

## 背景与问题

P3 的 Adapter 配置含自增 Deployment ID，创建时不能由客户端预知；eligibility 原来只有路径；P6 审批尚未上线，不能让普通 Catalog 管理请求自我批准私网、无鉴权服务或计费兼容性。

## 候选

1. 把管理请求及审计直接视为批准：无法区分配置与批准，拒绝。
2. 提前引入 P6 审批表/角色：扩大阶段与表结构，拒绝。
3. Core 启动只读加载受保护的精确配置批准清单：本次选择。

## 决策与理由

服务端回填 Deployment ID；HTTP 配置为候选；独立安全运维提供短期 Manifest，SHA-256绑定无秘密的完整规范配置。无清单默认拒绝激活，精确截止到点失效。普通请求不能增加批准事实。P3内网GET eligibility使用当前双身份和双ACL，只返回目录就绪候选。

字段、摘要顺序、审批时窗与密钥配置的唯一权威为[管理API](../api/p01-p03.md#p3-实施闭合合同2026-10-26)，RPC字段唯一权威为[内部RPC](../api/internal-rpc.md#p3-目录就绪检查)。不在本ADR复制另一份schema。

## 优点与代价

保留V3七表和现有技术栈，明确独立审批边界、可撤回和可测试；代价是清单变更需要受控重启，管理写仍沿用保守串行锁。文件本身不是公开API或Secret仓库，部署方需保护注入链路及独立审批身份。

## 后续影响

该批准只负责技术配置，不能替代P6数据治理；P7仍要真实连接前核验DNS/IP、唯一Permit、双预算和费用硬上界。P3测试只证明无Provider出站，不能声称已经测试真实DNS固定连接/重定向栈。用户签收前不推进P4。
