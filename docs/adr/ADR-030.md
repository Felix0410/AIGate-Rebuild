# ADR-030 · Redis容量池共享Lua与Epoch恢复

> 状态：设计已选定，待用户P0最终冻结；工程行为未验证。决策不意味着运行测试通过。

## 1. 背景

两Gateway同时派发会超真实GPU/第三方额度，Redis冷重启丢失Lease时旧任务可能仍在跑。

## 2. 需要解决的问题

仅用进程Semaphore不跨JVM；仅用Redis TTL会把物理任务误判停止。

## 3. 候选方案

1. 进程本地Semaphore
2. MySQL长事务排队占用资金锁
3. 同slot Redis Lua短期队列/RPM/租约 + Core DB最终许可、Guard runId和Pool epoch（选择）

## 4. 最终方案

P7只有NORMAL，P9 LOW，P10使用EMERGENCY/NORMAL/LOW 4:2:1；池创建默认DISABLED并核对真实资源identity；Core自己再INSPECT Redis。

## 5. 选择原因

软件短期许可与真实物理工作状态不同，必须有epoch+隔离机制。

## 6. 优点

多副本共享有限额度、简化排队原子性。

## 7. 缺点与引入的复杂度

Redis runId读取/Lua主切换并非一个原子操作，必须不确定即拒绝；资源恢复需要人工证据。

## 8. 对未来的影响

后续多集群Redis/更大规模队列要先证明当前Pool算法真实瓶颈，不凭空引入额外锁服务。

| 项目 | 明确规则 |
|---|---|
