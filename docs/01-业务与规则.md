# AIGate 业务与需求设计

> **状态：完整业务蓝图，尚未编码。** 本文记录重做后的产品目标及必须遵守的规则；实施参数和技术约束以其余文档为准。

## 一、产品定位

AIGate 是企业内部已有 Agent 的 **AI 模型统一接入、安全治理、额度计费、流量调度与成本运营平台**。员工通过已有 Agent 调用受管理的模型，AIGate 处理认证、授权、资金控制、Provider 代理、可信计量和审计。

**不做** Agent 创建、工作流编排、工具执行、RAG 知识库、模型训练、真实供应商付款或未经批准的自动 GPU 采购。万人员工是容量场景，不等于一万人同时在线或已达到特定 QPS。

| 角色 | 主要职责 |
|---|---|
| Employee | 使用独立员工凭证调用已授权 Agent/Model，查看个人余额与用量，申请补充积分 |
| Team Manager | 审批或主动发放其负责 Team 的额度，可跨团队发放 |
| Platform Admin | 管理身份、Agent、Provider、Model、Deployment、定价、策略、紧急预算和对账 |
| FinOps Reader | 查看经授权的成本分析报表，不修改权威账本 |
| Managed Agent | 企业现有的 Agent 软件，每个 Agent 对应一个 Application，通过其独立密钥访问网关 |

## 二、核心业务主流程

员工通过已纳管 Agent 选择获准的 LogicalModel → Agent 携带独立的 Agent Key 与 Employee Key → 网关双身份/Model 权限验证，Governance 对完整 messages 分类并筛选准许的 Deployment 出站边界 → Redis 全局限流和有界排队（无资金预留、Redis 无 Prompt）→ 获得执行许可，派发前重新校验实时身份/模型/治理策略及具体 Deployment、有效价表 → MySQL 短事务核验发布策略版本并同时预留所需积分与第三方采购预算、记录唯一派发意图 → Provider JSON/SSE → 可信 usage 原账结算或待对账 → 最小治理/账务审计与 FinOps 异步分析。

认证、额度或安全拒绝必须发生在发出收费 Provider 请求**之前**。降级、紧急任务同样不能绕过身份和数据安全。

## 三、身份与模型权限

- Agent/Application 一对一；Agent Key 与 Employee Credential 独立签发、过期、禁用、撤销；不信任用户自行提交的 employeeId。
- 运行时必须同时验证 Agent 与 Employee，才能得到真正的调用者和所属 Agent；单个 Key 不足以执行付费请求。
- 员工是否可使用某 Agent，及该 Agent 可用哪些逻辑 Model，是两套独立授权。用户选模型必须在交集内。
- 管理 API 与运行时 API 分离。管理员、Team Manager、员工自助、FinOps 只读角色最小授权；密钥明文仅创建时展示一次。

## 四、积分与团队额度

**每周一公司统一时区 00:00 刷新、不结转**：① Employee×Agent 免费周积分；② Employee 个人基础周积分。公司账务时区可配置，设计默认 Asia/Shanghai，瞬时时间持久化为 UTC。

正常扣点顺序：**Agent 专属周免费 → 员工个人基础周额度 → 已获发放且未过期的 Team Grant（先到期先消费）**。单次请求可跨来源，但预留必须原子成功或整体失败。

Team Manager 可审批申请、主动发放，允许跨团队。成功发放必须同一 MySQL 事务扣**发放 Team** 的池并创建接收员工的有效期 Grant 和唯一流水；不允许重复发放。**到期未消费部分作废，不退 Team 池**；员工实际使用时不再扣发放 Team 池。

## 五、三级流量、保底与紧急

- **普通档**：员工正常获授权资金与模型。
- **限流档**：正常积分不足，若公司受控保底池和该员工的周保底限额都有余额，则使用 Agent 预设且获授权的较低成本保底模型，以受限速率/并发/优先级服务，并提醒员工。
- **紧急档**：基于事前批准的 Employee、Agent、任务、明确额度、有效期和独立有限预算，提高资源优先级。

企业付费保底达到硬上限后**禁止新增收费 Provider 请求**；只有公司实际具有、且安全批准、有独立容量限制的自部署基础模型才可提供受控服务，否则明确拒绝。自部署模型仍有硬件/运营成本。最低速率绝不意味着可以突破资金硬上限。

## 六、计价和费用状态

内部积分价格与 Provider 采购价格是不同价表；均按生效版本、Token 类别（输入/输出/缓存等）计算。实际积分结算与采购费用估算只使用可信 Provider usage 或经认可的对账证据。

收费调用出站前应预留保守且有界的最大可能支付风险；不能界定风险上界时拒绝新的付费请求。网络 I/O **不在数据库余额事务内执行**。Provider 可能已计费但网关没有收到可信 usage 时进入 **待对账**，不能假设 0 元/0 积分、不能任意释放预留。相同业务幂等键不会再次发送可能收费的请求。

## 七、SSE、多部署和安全治理

SSE 必须支持增量透传、及时 flush、连接上限、超时、客户端断开时尽力取消上游。只有可信的最终 usage 才进入正常结算；缺失则待核对。已流出的数据不可撤回。

模型路由只在**同一逻辑 Model** 的多个健康 Deployment 中比较权重、时延、错误、负载与成本；保底切换到其他模型必须按专门规则重新授权。不能盲目重试已可能收费的模型请求。

企业合规治理提供数据分类、模型/Provider 准入、安全规则版本、敏感字段或密钥模式识别、拒绝/受控例外与必要审计。第一版重点是**请求发往 Provider 前的检查**，不承诺对已流出的 SSE 输出进行完整实时阻断。日志、队列、分析数据默认不保存 Prompt/完整回复/明文 Key。

## 八、FinOps：四类独立统计口径（D10 补充自部署运营费用）

| 统计口径 | 计算与归属 |
|---|---|
| 员工实际使用积分 | 已确认分类 Token × 调用时生效的内部积分价格；**谁用归谁**，可按当次员工主 Team 汇总 |
| Team 发放内部额度支出 | 成功发放积分总数；**谁发放归谁**，发放时确认，之后消费或到期不冲回 |
| 公司 Provider 采购成本估算 | 已确认分类 Token × 对应供应商生效价格，保留币种/版本；不是供应商最终发票 |
| 自部署算力运营成本 | 受控的 GPU 租赁/折旧/能源/运维费用，保留原币种、服务期间和来源凭证；没有真实成本资料不能伪造；同一原始费用与其分摊不再相加 |

例：客服 Team 发放 1000 点给研发 Employee；客服 Team 内部支出 1000 点，员工后来使用 300 点记员工用量，700 点到期不退。**不能把 1000+300 说成公司的模型总费用**。成本报表按 Team、Employee、Agent、Model、Deployment 和日期分析趋势、异常和优化机会；异步统计无权修改积分账本。

## 九、验收总原则

双身份、模型白名单、预算资金、合规四项任一不满足，收费 Provider 接收请求数为 0；并发不能透支；Team 发放仅扣一次；未知用量可对账；不同口径不双计（自部署运营成本详见 D10）。具体测试见《05-测试与验收.md》。

用户正式要求：**全部文档先完成并冻结后才开始编码；每次按业务块交付该业务块约定的全部功能及测试**。业务块必须同时完成参数校验、权限、状态/异常、幂等、并发事务、自动测试与验收，而非先成功路径后补防护。依赖关系驱动的 Phase 重排**属于总控提案**，见《04-阶段与任务》；本节不代表已获批准调整原先阶段编号。

需要在 P0 冻结前落实的资金分账细节：**员工内部积分预算**与**公司在 Provider 支付的真实费用预算（按供应商计价币种）**不能混用。尤其企业付费保底要同时满足受控内部资金来源、员工保底周限制以及公司/Provider 对外采购风险限额。仅证明“积分池未透支”，不等于证明公司现金采购预算未超出。公司现金预算应基于有效 Provider 采购单价、请求风险上界与安全结算建立独立权威约束；具体账户结构、币种、预留与对账状态需在《03-数据与接口》完整冻结。真实预算限额由公司配置，不得凭空猜测。

## 十一、P0 专题设计 D-01：双预算准入与结算（详细方案待确认）

**当前为总控设计提案，非新增已确认业务事实。** 业务已确认的是：用户积分、团队发放和 Provider 采购费用不同；付费调用不得在缺少可控预算时无限发起。

1. **使用授权预算（POINTS）**：首先确定可用资金来源（Employee×Agent 周免费、Employee 本人周额度、未过期 Team Grant；用尽后才评估授权的企业保底/紧急池）。发放 Team 池是授额来源，不是每次员工调用时再扣一次 Team Pool。
2. **外部采购预算（货币）**：每次调用收费 Provider，无论员工花哪种积分，都必须同时占用公司的 Provider 费用风险限额。允许的供应商计价币种各自有独立的公司采购风险限额；未配置币种/限额，不发送该币种的收费 Provider 请求。内部 POINTS 不能替代货币预算。
3. **预算的意义**：这是 AIGate 依照*有效 Provider 价格和受控请求范围*进行的**预计采购成本准入**，不是银行现金余额，更不是已经确认的供应商最终账单。供应商违反 token 上限、价格合同外收费等可能造成额外费用，需要异常冻结/告警和账单核对；不得虚假宣称绝对控制最终供应商发票。
4. **准入前置**：选择具体 Deployment 并验证身份、权限和数据政策，冻结内部积分价/供应商采购价版本，计算两种资金的有界最高风险。**同一 MySQL 短事务同时预留 Points 和该币种 Provider Cost Budget**；一方不足则全体回滚，Provider 出站为零。模型 JSON 与 SSE 都走同样的资金合同。
5. **结算**：根据可信的分类 Token 用量，按照预留时冻结的双方价格版本分别结算 POINTS 与 Provider 费用估算，并释放两套多余预留。服务端可证明未出站/未收费时释放；可能已收费但无可信 usage 时两套预留保持待对账，不能因为客户端断开而认作免费。
6. **公司付费保底**：是员工积分不足时申请使用受控内部资金额度的路径，依旧同时占公司 Provider 采购风险额度，且要满足员工周保底上限和企业保底硬上限。紧急授权同样不可跳过外部采购预算。
7. **不同货币**：设计默认每个公司采购预算期间分别为 USD、CNY 等供应商**原币种**设上限，不能跨币种直接加总或无汇率转换就声明一个统一金额硬限额。企业若未来要求折算到单个本位币总限额，需要另外冻结汇率快照/超额归属规则。财务报表继续按币种展示。
8. **期间归属**：设计默认采购预算按公司时区**自然月**，每次调用消耗发起出站时所属期间的额度，月底未结算的预留保留在旧期间，之后完成结算/核对不能凭新月份的额度抹除旧欠账。

### 例子（虚构数字，仅解释逻辑）

某员工有 100 点余额，某公司本月同币种采购预算上限为 0.20 USD，本月先前结算/预留均为 0。新请求评估的最高风险分别为 **30 POINTS + 0.06 USD**，因此两本账同时预留；Provider 最终可信用量需扣 **12 POINTS + 0.024 USD**。账务一次性扣 12 点、采购估算累计 0.024 USD，分别释放预留差额 18 点和 0.036 USD。员工剩余余额 88 点，公司预计采购预算剩余可批准额度为 0.176 USD。若因 SSE 断线丢失 usage，则 **30 点和 0.06 USD 预留仍挂起待核对**。

**设计门禁**：Provider 对该协议的输入和输出 Token 数量、有效价格及可能收费内容必须有可信的保守最大上限；无法确定时付费调用拒绝并告知“无法验证费用上界”。Provider 异常超出预留时记录外部真实风险/异常，禁止隐藏负账、冻结受影响采购预算与追加请求，人工复核。下一步由总控在《03-数据与接口》冻结具体表/事务/测试；本节尚待用户确认后转为 APPROVED。

## 十二、P0 专题 D-02：第三方 API 与企业自部署模型两种供给方式（已确认，2026-10-21）

**用户明确要求讨论并区分两种模型**：①第三方供应商提供的按次计费 API；②企业自己运营的推理服务。两者都可通过 HTTP/OpenAI 兼容协议访问，不能仅凭“是不是 HTTP API”区分。更准确的责任边界为**谁运营算力与如何产生费用**。

| 属性 | THIRD_PARTY_API | SELF_HOSTED |
|---|---|---|
| 部署与 GPU 运营方 | 供应商 | 企业自管/租用并自管 |
| 外部采购预算 | 逐次调用按供应商报价产生费用；用公司采购风险月预算按币种原子预留与结算 | **没有第三方按请求 Token API 账单时不占用同一个 Provider 采购风险预算**；自有/租赁算力费用进入独立运营成本核算 |
| 员工使用额度 | 员工内部积分；正常不足时可申请受控付费保底 | 常规调用也按照所选 Model 的**内部积分/额度政策**限制；经特别批准的“本地基础模型保底”可改用独立、有限的每员工周期补贴额度 |
| 核心容量约束 | Provider 限额及网关 RPM/并发 | 本地推理 Deployment 的有限并发、等待队列、KV Cache/GPU 资源、输入/输出上限与工作状态 |
| 成本统计 | 已确认 Token × 生效 Provider 采购价，**估算采购支出** | GPU 租金、折旧、电费/托管/维护等经配置并有来源的运营成本；初期按部署/时间段统计，不把它伪装成按次 API 账单 |

**统一规则**：
1. Employee、Agent 双身份、员工 Agent 授权、Agent Model 白名单与内容安全在两类调用中完全相同。自部署“内网可信”不能免除权限或合规。
2. 路由按业务允许的**逻辑 Model** 选择具体 Deployment。若同一逻辑模型可兼容地部署在两类平台，路由前明确选具体 Deployment 和资金/容量政策；跨逻辑 Model 切换只允许已审批的保底，须告知实际模型并重新检查权限/安全/额度。
3. 自部署请求要受**本地容量准入**保护：健康节点、最大活跃推理数、队列容量、每员工限速/Token 限额；没有可用容量就限时排队或拒绝，不能无界堆积。容量故障不应默默切到会收费的第三方 Provider，除非用户/管理员事前批准、对应两套预算仍通过原子预留。
4. **本地基础保底已确认规则**：员工正常积分和有界企业付费保底都用尽后，如公司真实配置了获授权、有限容量的本地基础模型，允许按独立的每员工周本地保底 Token/请求限额提供低优先级服务；此例外无需逐次外部 API 采购预算，但仍要检查本地容量、员工/Agent/Model 权限、内容策略和额度限额。不能宣称“本地模型零成本”。
5. 常规本地模型请求仍可按内部积分价格消耗员工余额，内部积分用于业务公平和资源分摊；**内部积分不等于 GPU 能耗或供应商账单**。本地保底是否设置价格为零属于“独立限额+补贴”策略，不应全局把所有本地模型永久设为零积分。
6. 自部署费用分两个层次：实时限流容量由推理服务/网关可观测指标控制；月度算力账单/折旧是 FinOps 管理费用。只有能实际取得 GPU 运行/租赁/能源等数据并规定分摊口径时，才可给每次本地推理分摊费用，报表明确 `ESTIMATED_ALLOCATED`，不是精确逐次采购发票。
7. **真实部署条件**：没有企业 GPU 的学习/开发环境，可以使用 Fake Local Inference Endpoint 测权限、容量、流式与计量契约；真实 GPU 指标、GPU 扩缩容和 GPU 成本分析不能由模拟数据冒充已实施生产能力。

**与 D-01 的关系**：用户已同意按币种/自然月的采购预算、第三方 API 对积分与采购金额双原子预留。D-02 进一步规定 SELF_HOSTED 常规业务走内部积分/本地容量治理，不必误占用“第三方按次 API 采购风险”账户；这并不是取消内部员工授权，也不是默认无预算。用户已确认**普通自部署模型消耗员工积分；只有明确批准的本地基础保底模型提供独立、有限的员工周补贴额度**，且不占用按 Token 计费的第三方 Provider API 采购预算；本地推理容量必须有界，运营成本与 API 采购成本分开统计。容量租约技术实现、补贴精度、真实算力成本归集方法属于 D-03 及后续详细设计，不因此自动批准。

### D-02 正式决策边界

同一网关保持统一双身份/权限/合规入口，Deployment 类型决定准入分支：`THIRD_PARTY_API → 员工积分 + 采购金额月预算`；`SELF_HOSTED 常规 → 员工积分 + 本地容量`；`SELF_HOSTED 获批保底 → 员工周补贴额度 + 本地容量`。仅本地保底豁免普通员工积分，**所有自部署调用仍有可验证的公平用量边界**。若部署实际还按次向第三方收费，则必须按照费用模式进入第三方采购预算流程，而非因为它在私有地址就被当成免采购费。

## 十三、P0-D03：本地推理保底额度与容量规则（业务边界已确认，实施细节待冻结）

1. 每名员工在公司账务时区的每周周期内共用一个本地基础保底额度，**不会因切换 Agent 重置**。业务设计默认采用输入 Token + 输出 Token 计量；公司实际周限额通过配置决定，不写死。
2. 当周可用 Token = 本周上限 − 已确认使用 − 所有在途/待核对预留。出站前为最大可信 Token 使用量预留，不得把未经验证的 tokenizer 估计当成硬上界；若无法验证上界，拒绝请求。
3. 正常 SELF_HOSTED 模型仍按内部 Model 积分价格扣员工积分；仅被管理员标记为 BASIC_FALLBACK 且经过 Agent/Employee/政策授权的模型，可以在正常积分和付费保底不足时使用上述周补贴。补贴调用不产生按 Token 计费的第三方 API 采购预算占用，**但也不是无成本模型**。
4. 推理资源按实际共享的算力池限制，并同时设最大运行任务数、最大等待请求数、最长等待时间和推理超时；**客户端 WAITING 阶段不预留补贴、积分或公司采购预算**，只有获得 Redis 执行许可且派发前安全复核通过后，才在 MySQL 短事务占用有界的最大使用风险（以 D06 最终顺序为准）。
5. 失败/取消若可证明请求未送达推理服务，则释放额度预留；已可能运行但未收到可信 Token 用量，则待对账。客户端断开只触发尽力取消，不自动认为 GPU 已停止。
6. 多网关副本必须使用共享的容量准入状态或真正由推理服务全局执行的并发硬限制；单实例 Semaphore 不得冒充集群限额。部署的物理容量和网关容量准入不是一回事。
7. 自部署 GPU 采购/租赁、电费、折旧等作为 FinOps 的**运营成本来源**按可验证账单/资源周期统计，不能与第三方逐请求 API 采购费用混淆或在分摊后重复加总。

D03 的具体状态机、DDL、排队协调、租约 TTL、测试步骤由《03-数据与接口》《05-测试与验收》继续冻结；未完成 P0 不授权本地 AI 编码。

## 十四、P0-D04：多来源积分、Grant 过期与跨周（业务规则已确认）

资金消费顺序保持：Employee×Agent 免费周额度 → Employee 个人基础周额度 → 未过期的 Team Grant（最早过期先消费，时间相同按 Grant ID）。一次调用可组合多个来源，原子预留最大可信积分风险；第三方 API 同时原子预留公司的对应币种采购预算。

**已确认业务边界**：Grant 在成功预留时有效即可用于当前已预留请求；即使结算时过期也允许对这部分已预留额度结算，但过期后不允许新请求再占用，释放的过期额度不再成为可用积分，原发放 Team 不退款。跨周调用亦然：周日预留的新周一返回，始终从**原周桶**结算并释放，旧周释放金额不滚入新周。可能收费但用量未知时仍在原资金来源待对账，Grant 到期和周期切换都不能直接清除预留。

成功发行 Team Grant 一次性扣 TeamPool 并记发行团队的内部支出；消费、释放多余预留、Grant 过期不再改变发行团队的这笔支出。

例：Agent 周免费剩 10、个人基础 10、Grant 20，请求最大风险 40，原子预留 10+10+20。可信实际只消耗 15，则最终使用为 Agent 10+个人 5+Grant 0，释放其余 25。若 Grant 在结算前已经过期，释放的 Grant20 不重新提供给新调用，原发行 Team 的支出记录不回冲。本节 D04 业务语义已由用户确认，但完整 DDL、异常恢复和自动化测试实现尚待 P0 全量设计冻结；目前没有代码。

## 十五、P0-D05：企业付费保底和紧急任务的资金/优先级（方案已认可，完整DDL待冻结）

**必须区分：使用权、内部资金来源、外部采购资金、调度优先级。** 紧急优先不等于可以突破公司现金采购上限；免费/自部署也不等于无需员工授权和计算资源限制。

### 三条互斥业务路径

1. **普通 NORMAL**：员工选择允许的逻辑 Model，优先使用 Employee×Agent 周免费→员工基础周额度→有效 Team Grant。如果所选 Model 的可信最大积分风险可以完全预留，保持所选 Model 和 NORMAL 档。
2. **企业付费保底 LOW**：当普通来源不足以承担原请求的最大积分风险时，仅在管理员为该 Agent 配置了明确允许的低成本保底 Model、员工符合保底条件时，重新检查该 Model 的权限、内容政策、Deployment 和最新冻结价格。按新 Model 的风险上界**先用员工尚存的普通积分，不足部分使用公司付费保底积分池**；同一事务更新员工每周保底使用上限、公司保底池和对应币种 Provider 采购预算（若收费 API）。回退请求整体为 LOW 优先级，即使降价后无需公司补足积分。保底不能直接调用比原请求更贵或无授权的模型，且不得跨多个模型在同一次 invocation 中盲目重试。
3. **紧急 EMERGENCY**：只有有效的事前审批，且 taskId、Employee、Agent、允许的 Model、有效期、任务总预算均匹配，才享受 EMERGENCY 调度档。**默认使用独立公司紧急积分池与该任务已审批的积分额度，不自动扣员工普通余额**。审批给出最高可使用额度，**不等于当时就已经扣减公司紧急池**；真正模型调用时才原子预留全局池与该任务剩余额度。审批失效只阻止新调用，原已成功预留的调用仍按原授权与期间结算。任务额度用完不得继续以紧急档收费；若希望使用普通额度，必须作为新的 NORMAL 调用重新准入，而不是自动改来源。

### 企业采购现金风险预算的紧急保障（提案）

对第三方付费 API，企业按公司时区自然月、**每个供应商原币种**设置总采购风险预算，并明确分成 NORMAL 和 EMERGENCY 两个有边界的份额。NORMAL 份额供员工正常调用和 LOW 付费保底共同使用；EMERGENCY 份额只允许获批紧急任务调用。NORMAL 不得侵占预留给 EMERGENCY 的资金，EMERGENCY 不得透支其专用份额及公司总限额。若某币种未配置紧急采购份额，该币种收费 API 不提供紧急付费保证。

示例：公司某月 USD 采购最高批准额度 100，其中 20 留给紧急业务，则 NORMAL/LOW 合计最多批准 80 USD 风险敞口、EMERGENCY 最多批准 20 USD，整体仍不超过 100。员工免费积分充足不免检 NORMAL 采购份额；紧急申请已批准也不免检 EMERGENCY 采购份额。

### 与自部署本地基础保底的关系

第三方付费保底仍受外部采购预算；若上述付费资金不足，只有经批准、员工还有独立周 Token 补贴、Redis/推理引擎仍有健康容量的 SELF_HOSTED 基础模型才可进入独立 LOW 本地保底。**不静默从自部署切回收费第三方 API**。紧急自部署调用使用任务专属紧急积分额度及真实容量许可，不需要不存在的逐次第三方 Token API 采购费用；但仍可能发生自部署运营成本。

### 数据归属和异常

- 公司付费保底积分和紧急积分是**两个公司资金池**，独立额度和期间；员工保底周上限是每 Employee 单独的限制，不是员工自己的可兑换余额；TeamPool 不会在保底/紧急发生时再被扣款。
- 任务审批只是授权额度上限，**与 Team Grant 的“发放成功立即扣 issuing Team 池”完全不同**。
- NORMAL、LOW、EMERGENCY 的限速、排队优先级由 Redis 全局共享治理；绝不能以较高优先级绕过 MySQL 积分池或 Provider 原币种预算原子预留。
- 已预留而跨周、跨月、或审批到期的请求，从原账户/原月份/原任务授权结算；未知上游用量维持待对账，不把额度偷偷返还。
- 所有降级、紧急、预算拒绝和审批变更保留审计元数据，并向客户端说明实际运行的逻辑模型/档位/受控拒绝原因，不写原始 Prompt。

**D05 已获用户认可的业务方案**：LOW 可以混合剩余个人积分和公司补足积分，EMERGENCY 独立使用公司紧急资金及任务授权，公司原币种月度采购预算为 EMERGENCY 保留单独份额。具体DDL/请求 DTO/预算份额数值仍须在 P0 冻结，不代表已经编码。

## 十六、P0-D06：紧急审批、排队与三级优先级（详细设计提案）

### 审批业务流程

1. Employee 或其 TeamManager 提交紧急任务申请，指定 taskRef、实际受益 Employee、允许使用的 Agent、可用逻辑 Model 集合、申请积分最高额、有效起止时间与业务理由；必须有可验证的 Employee/Agent 归属，不支持“所有人紧急”通配授权。
2. Platform Admin 审查请求并 APPROVE 或 REJECT；审批人不得与申请人是同一真实身份（双人复核，作为本轮设计默认）。审批必须审计操作者、时间、理由与版本；申请人不得直接签发自己的 EMERGENCY 权限。一次批准仅生成一份不可任意修改的任务授权，撤销只能阻止新调用，已合法预留部分沿原账结算。
3. APPROVED 只代表允许该 Employee+Agent+Task 在指定时段消费最多批准积分额度；**审批成功时不从公司 emergency pool 预扣积分**。真实调用时同事务检查 Task 已使用/已预留和公司 emergency pool，若收费 API 再检查本币种总采购月预算与 EMERGENCY 专用份额。
4. 运行时明确携带紧急授权 ID 供服务端查证，不能仅传 priority=EMERGENCY、employeeId 或任意 taskRef 获取资格；没有授权 ID 默认普通模式，有无效 ID 则直接拒绝，不能静默当普通请求尝试付费。
5. 已审批任务到期或被撤销时不再允许新的紧急请求进入等待队列或派发。**排队期间尚未发生资金预留，派发前仍须检查授权是否有效**；已完成预留且在出站后的请求遵循原任务/原期间完成或待对账。
6. 同一 Employee+Agent+taskRef 同时只能有一份 ACTIVE 的获批任务授权，避免叠加多个审批额度突破设计上限；修改额度/时间/Model 需要撤销旧授权并重新审批，不能覆盖已出账历史。

### 三级排队和公平策略

- 所有请求先做可信双身份、Agent/Model 权限和内容政策的前置筛查，再根据服务端可信规则确定 EMERGENCY、NORMAL、LOW；**不信任客户端直接设置优先级**。
- 所有受同一容量约束的 SELF_HOSTED Deployment 共用一个 GPU Pool；第三方 Provider 另有 Provider/Deployment 自身并发与 RPM 配额，不能用 GPU 的物理规则伪装控制外部供应商。
- Redis Lua 直接实现三个有界队列（EMERGENCY/NORMAL/LOW）、各档 FIFO、总 maxWaiting、单 Employee/Agent 同时等待及在途限制，绝不无限排队。
- **建议调度默认权重 4:2:1**：有等待任务时每 7 个释放的执行名额最多依次调度 4 个 EMERGENCY、2 个 NORMAL、1 个 LOW；空档让其他队列使用，同档先来先执行。该比例是“名额分配”，不是 GPU 计算时长严格保证。全局队列 TTL 使任何请求最多等候配置的时间后拒绝，而不是承诺一定能在等待期限内执行。
- 已经在运行的 JSON/SSE 请求**不被抢占**；高优先级只能争取之后释放的许可，不能承诺立即开工。若将来业务需要硬保证“紧急任务几秒内开始”，必须显式预留物理容量、承担闲置成本并另行审核 SLA。
- 普通/保底、紧急资金和 Redis 调度是独立状态机。无资金时即使获得 GPU 许可也不能出站；有资金却等待超时也不能长期冻结员工/公司额度。

### 执行顺序修订（覆盖 D03 旧版“先预留资金再进 Redis 等待队列”）

认证/授权/内容预检 → 校验紧急任务权限与模型、初步确认路由合法 → Redis 请求频率检查与**有界等候队列** → 领取执行容量许可 → **派发前再次校验员工/Agent/模型/内容版本与紧急授权、确定实际 Deployment 和生效价格** → MySQL 以派发时刻所属周/月原子预留积分和（若收费）Provider 币种采购风险 → 记录唯一派发意图 → 发出一次上游请求 → 可信用量结算/未知用量待对账 → 确认实际任务终止后释放许可。

此变更避免排队跨月/跨周时长期锁住资金：**月度采购预算归属实际获准派发时段，而非排队进入时段**。等待超时、队列已满、授权到期时，因为尚未财务预留，不存在要退的预留；若已经获得许可但数据库预留失败，只需释放 Redis 许可，0 次上游发送。

当 NORMAL 排队时原模型可用，但派发时积分变化导致不可支付，允许在尚未出站的同一个 Invocation 内**最多一次**重新计算允许的 LOW 保底模型与资金，并重新排队 LOW；不得伪装成对 Provider 的第二次收费重试。重新排队重新检查授权/价格/期限与有限等待截止；若用户的 Idempotency-Key 重复出现，只返回原 Invocation 状态，不创建第二个任务。

### 故障与审计

Redis 故障或共享队列状态不可信时新请求 fail closed，MySQL 持久化的执行意图、预算和账本不能随 Redis 清空；恢复先协调可能已经在计算的任务。Redis 租约过期不等于 GPU 推理结束。两份 Gateway 实例要测试相同资源池并发、FIFO、优先份额、旧租约令牌不得释放新许可，以及审批撤销和超时的竞争。

**D06 方案方向已获得用户认可**：紧急任务审批、分档调度、不抢占、派发前重新授权和财务预留；双人复核与 4:2:1 为本轮推荐的可配置默认，仍需在 P0 全量 DTO、脚本及测试审查时冻结具体参数。未编码。

## 十七、P0-D07：逻辑模型、部署来源和路由边界（设计提案）

### 逻辑模型不是供应商连接地址

- **LogicalModel** 是员工/Agent 选择和权限审核的稳定“模型身份”，包含可用能力及受控版本/上下文约束。例如“某个明确版本的开源指令模型”可以配置多个第三方托管或自部署实例。
- **Provider** 是运行服务的运营方/供应商与接入协议配置；不等于 LogicalModel，某 Provider 可提供多个模型。
- **ModelDeployment** 才是可调用的具体服务：属于一个 LogicalModel，绑定 Provider、实际 remoteModelName/Endpoint、THIRD_PARTY_API 或 SELF_HOSTED、计价模式、性能健康与容量池。员工不可在请求中直接传任意 Deployment ID 或 Endpoint 绕过控制。
- **同一逻辑模型只容纳业务上明确等价、兼容同一模型版本/能力合同的 Deployment**。仅有 OpenAI-compatible HTTP 协议并不等于模型等价。对不同模型的切换只能由 D05 明确授权的 LOW 模型降级等产品策略执行，并重新审核权限/安全/价格。
- 逻辑 Model 有组织统一状态，Deployment 另外有启用/禁用/维护/健康状态；禁用模型拒绝全部新请求，禁用单个 Deployment 只将它从候选池移除，不修改调用历史。

### 常规路由

1. 根据真实员工、Agent 权限、请求 logical model 和内容安全要求筛出允许的 LogicalModel。
2. 在该 LogicalModel 的 Deployment 列表中过滤：有效配置、运行模式、地区/数据等级准入、模型版本和请求参数能力、流式支持/可信 usage、价表/币种、实际健康与可接入容量。缺少可信最高费用风险上界的收费部署不能参与收费选路。
3. 对健康候选综合考虑可用容量、近期成功率/超时、实际网关观测的等待/延迟、管理员权重和成本，在允许范围内选择最合适 Deployment。所有输入来自可观测事实，**不宣称知道第三方供应商内部真实 GPU 利用率**。
4. **进入 Redis 有界队列时绑定路由版本和容量池**。获得执行名额后必须再次验证该 Deployment 是否仍允许/健康；若需换到另一容量池，应先释放原池许可，再重新取得新池许可，且不得持有两个池名额无限等待。
5. 获得许可后冻结**实际 Deployment**、该调用内部积分价、供应商采购价格及币种、许可版本和风险上界，在 MySQL 原子完成预算预留，再记录一次派发意图并出站。不同候选即使属于同一 LogicalModel，价格和风险也可能不同。
6. Model 的主动降级和“付费 API 切至自部署基础保底”是**独立业务决策**，必须按相关授权、积分/补贴及容量规则处理，不能把普通路由选择伪装成自动免费回退。

### 健康与失败切换

- 第三方 API：以可安全实施的有限探测、受控出站错误、HTTP 响应码、延迟和连接超时进行**被动与必要时主动健康判定**。不能使用无限免费的模型生成探测；可能收费的探测也要纳入预算。
- 自部署：可以从推理服务自己的健康端点与实际存在的指标获取健康/等待/运行信息，缺指标时显示 UNKNOWN 而不是“GPU 空闲”。
- **只允许对可证明未发送到上游的尝试重新路由**；若已发送或网络异常无法确认对方是否开始计费/推理，不能盲目重发到同型号或另一个 Provider，Invocation 进入待对账。SSE 已输出部分内容，更不得透明切换上游继续拼接另一个模型的输出。
- 健康失联且没有候选：按统一 503/429 等受控错误返回；错误路径释放可证明未发生调用的许可及额度，不私自绕过权限换模型。
- 每次请求持久化路由决策的 modelId/deploymentId、hostingMode、价表版本、业务选择原因、健康/路由策略版本、实际开始时间和唯一上游尝试 ID，不能默认保存 Prompt。

**D07 PROPOSED**：逻辑模型身份、Deployment 可混合第三方托管和本地运营，但必须满足等价模型/能力合同；常规健康路由绝不偷换不同逻辑 Model；上游可能已开始计费时禁盲重试。具体排序算法、探测阈值、健康状态和接口/DDL 继续在其余文件设计；P0 未冻结。

## 十八、P0-D07.1：路由定价与故障切换的可执行规则（待最终冻结）

**本轮建议固定一个防止员工账单不可预测的规则：同一个 LogicalModel 使用同一套内部积分 PriceVersion，无论实际路由到哪个 Deployment；第三方 Provider 采购 PriceVersion 则绑定实际 Deployment。** 因此正常同型号换部署不改变员工 POINTS 单价，但公司的原币种采购预算、用量和供应商实际成本按照真实部署计算。若替换成另一个 LogicalModel（企业付费保底或本地基础保底），属于需要重新授权、重新计算最高风险和重新排队的独立业务决策。此前文档“同型号 Deployment 可能有不同价格”应具体理解为供应商采购价可能不同，**不是内部积分随路由波动**。

**健康状态**：HEALTHY 可正常路由；DEGRADED 仅在没有更优健康候选时谨慎路由；UNHEALTHY 或 CONFIG_ERROR 不选；UNKNOWN 不假装健康，新节点只允许单并发、完整授权及资金预算保护的受控试运行。管理员禁用和维护态优先于所有健康指标。供应商 429 受 Retry-After 或有限冷却时间约束，不被当成无限可用；供应商 401/403 配置凭证错误属于配置告警，不能通过重试另一凭证暴力尝试。

**故障与重选**：
- 排队前初选只确定候选 Deployment 和容量池，派发前再核对实际候选、模型版本、策略和价格。跨不同容量池改变部署必须先放弃旧池许可，并遵守同一总排队截止时间。
- **在持久写入 DISPATCH_INTENT 以前**，如果可靠证明还没有任何上游字节发送，可以放弃候选、释放许可并最多重选一次同型号候选；任何真实/可能的网络派发之后禁止自动调用第二个收费部署。
- 派发意图已提交，即使客户端在真正发送前崩溃、网络是否发出不明，也必须按风险未知处理、先核查，不执行盲重试。已经向下游发送 SSE chunk 更不能切到另一模型继续拼接。
- 自部署容量满可以在等待截止之前换其他**等价模型部署**，不能将“免费的本地保底”偷偷改成收费 Provider；若新部署有第三方采购成本必须走对应采购预算和业务授权。
- Provider 失败的真实成本/可信 usage 未确定时保留原 invocation 的积分与 Provider 预算预留待对账。最终使用的 modelId、deploymentId、hostingMode、报价币种和两种价表版本必须持久留痕。

以上为 D07.1 新增详细设计提案，默认阈值与计算公式在《02-架构与技术》《03-数据与接口》中描述。

## 十九、P0-D08：JSON/SSE 业务合同与费用证据规则（设计待冻结）

**统一入口，完整业务保证**：Employee+Agent 双凭证及 Model allowlist、安全策略、Redis 全局入场、MySQL 预算准入，对 JSON 和 SSE 一视同仁。员工提交 LogicalModel.code 和纯文本消息，服务端选择可信 Provider/Deployment；首版只支持文本 Chat Completions，禁止客户端任意选 Provider URL、绕过供应商身份或使用未支持的多模态/工具调用和额外收费类型。

**两种状态不可混淆**：
- 模型执行状态描述是否排队、已派发、正在生成、已完成文本、断线/失败；
- 账务状态描述是否完成预留、结算、证明零费用释放或待对账。
HTTP 200、SSE 的 [DONE]、客户端主动停止，都不能单凭自身证明 Provider 实际免费或财务已经结算。

**SSE 完整性**：按真正收到的 UTF-8 SSE 数据帧增量输出和 flush；上游若提供经验证的最终 usage，则依冻结积分价/供应商价结算。流式最后的 usage 块可能因断连缺失，不能根据前面已经看到多少字符去猜 Token，更不能生成假的最终用量。若文本正常完成但 usage 证据暂不可得，可以向员工标明本次答案已完成、费用待核对；如中途异常则结束流并让用户通过安全的调用状态查询获取结果。已经流出的文本不可撤回，不能从第二家 Provider 拼接。

**双身份下的幂等**：每次业务请求（JSON 或 SSE）都必须携带新 Idempotency-Key；同一 Agent+Employee+Key 在已定义的幂等收据保护期内不再派发第二次模型请求，执行中/完成/待对账的重复请求均返回409并提供可查询的调用 ID。首版不保留完整 Prompt/模型回复，因此不能承诺 SSE 重放或按幂等键返回原答案；需重新生成须明确是新的计费调用且重新准入。

**合同限制**：每次请求必须有有界 max_tokens 和可验证的输入/输出 Token 上限；只允许 Provider Adapter 宣告支持的字段与可确认计价类别。前置识别输入安全规则，输出流首版不承诺“所有增量输出都能在发到客户端之前实时阻断”。日志与 FinOps/Outbox 均不能存储原始 Prompt、回复或明文密钥；只能记录已确认的 Token 分类、价格来源、状态、traceId 与必要安全元数据。

**运营原则**：Provider 返回 4xx/5xx、客户端断线、连接超时并不自动证明本次零收费；只有可信的未派发/已明确零收费证据允许资金释放，其他持有受控预留和待对账记录。失联账务必须有监控、人工复核和可审计的结算/释放操作。

本节 D08 是设计草案，完整 DTO、超时阈值及 Adapter 兼容矩阵和测试仍须 P0 最终冻结；不允许因计划“全量开发”而在没有证据的 Provider 上假定所有流式响应都会有 usage。

## 二十、P0-D09：企业敏感数据分级、出站准入与受控例外（设计提案）

> **状态：PROPOSED，等待用户确认企业数据边界及 P0 总体验收**。本文是治理业务规则，不代表已经接入 DLP 或保证所有敏感信息均能被识别。参考 OWASP 2025 LLM01 Prompt Injection、LLM02 Sensitive Information Disclosure、LLM07 System Prompt Leakage。

### 20.1 核心业务原则

**模型使用授权**与**允许把这段数据发送到该模型的授权**是两道独立门禁。Employee-Agent、Agent-Model 白名单通过仍不能跳过数据分类/Provider 的真实批准地域与托管责任。数据出站检查对 NORMAL、LOW、EMERGENCY、自部署普通、本地保底和第三方 API 一律生效；紧急额度从不授予豁免内容安全权限。

初版分类为 PUBLIC（公开）、INTERNAL（内部）、CONFIDENTIAL（机密）、RESTRICTED（严格限制）。四级由企业配置的 Agent 可处理级别、员工/业务上下文绑定的可信分级、消息文本内部扫描高置信信号综合决定，取最严格等级。客户端 JSON 中的 classification/dataLevel、Prompt 中“这是公开数据”等文本一律不是可信降级指令；**完整 messages 的 system/user/assistant 历史内容都要扫描**，不能只扫描最后一条 user 消息。

| 有效请求等级 | THIRD_PARTY_API | SELF_HOSTED |
|---|---|---|
| PUBLIC | 允许已批准的 Model/Provider/地域/Agent 策略 | 允许已批准内部部署 |
| INTERNAL | **需要 Agent 的明确出站授权 + Provider 数据处理批准 + 允许地域**，任一缺失拒绝 | 需要内部部署已获准处理 INTERNAL |
| CONFIDENTIAL | **默认一律禁止**第三方按次模型 API 出站 | 仅允许明确标识可信计算边界、获批处理 CONFIDENTIAL 的本地部署；使用非流式 JSON 经响应审查 |
| RESTRICTED | **禁止**所有第三方模型出站 | 初版默认禁止所有模型出站；将来如要建立专用隔离模型服务，须新增经过审查的产品能力/ADR，而非普通例外 |
| 高置信真实凭证命中 | **所有模型拒绝**，除非先在源系统安全脱敏后重新提交 | 同样禁止把真实凭证原文交模型 |

上述是**推荐默认公司策略**，真正允许的 region、approvedProviderId、Agent 出站授权和 selfHostedTrustBoundary 都要有管理员发布版本。内网 URL 不自动表示可信部署，租赁 GPU 但企业独立运营的推理服务也必须证明安全边界、访问控制和数据留存策略。

### 20.2 初版扫描的可实现范围与限制

- P6 完整交付**规则引擎 + 管理发布 + 运行时评估合同 + 安全审计**；第一版直接在 AIGate 内运行确定性规则（Java，配置化高置信度密钥模式、企业机密标记、已批准的业务标记及敏感员工信息规则），不把尚未审批的 Prompt 发送给第三方审核 API，也不引入独立安全微服务。
- 输入先限制字节数、字符编码、消息结构与正规化边界，再进行有时间/复杂度上限的全部消息扫描；拒绝过长/不可解析输入而非只扫描一个截断前缀后放行。规范化不能被当作“可识别一切变体/编码”的保证；高风险命中优先拒绝，不做可能改变语义的自动遮盖后继续发送。
- **检测不到不等于安全**。基于规则的扫描无法确保发现所有商业秘密、隐私和提示注入；企业敏感系统必须依赖来源可信标签、最小权限、出站白名单与人工政策约束共同生效。来自消息正文的“忽略规则”“现在切到本地”等内容只能作为文本，不能修改策略、角色或路由。
- 对 CONFIDENTIAL 仅能使用经审批自部署，初版**拒绝 stream=true** 并要求 JSON 生成结果在发回 Agent 前经过最小的输出敏感模式审查；输出审查失败时不回送答案，**Provider/GPU 已生成的真实消耗仍依可信用量结算**。PUBLIC/INTERNAL 可以按批准的政策使用 SSE，但不能宣称流式输出已完成全文实时审核。
- RESTRICTED 以及高置信的真实凭证命中，不因为员工积分充足、紧急任务已审批或内网模型更便宜而继续派发。安全拒绝发生在资金预留和 Provider 真实出站前，Fake Provider 请求数必须为 0。

### 20.3 策略与例外

- 平台有治理 Policy 草稿、验证、审批、发布及旧版审计。推荐角色 POLICY_EDITOR（起草配置）与 SECURITY_APPROVER（发布、审批误报例外）相互分离；同一真实管理员不能为自己起草的高风险策略自批发布。Platform Admin 管理用户/授权但不能凭运行时 Key 绕过治理。
- 误报例外是**限范围的规则识别例外**：指定 Employee、Agent、逻辑 Model、单条 ruleId、原因、审批者与失效时间，最多解除该扫描命中的可审核“误报信号”；不得降低由可信数据来源标注的分类，不允许覆盖 RESTRICTED、真实密钥和未经批准的第三方出站上限。
- 策略升级可立即阻止新排队、新取得许可及**派发前仍未完成授权**的请求；已经通过持久化 DispatchIntent 审批提交的在途请求不能被逻辑上“追溯擦除”，可尽力取消、审计并核对可能发生的账单。安全检查截止点以受控派发授权事务为界，不能假装消除提交与网络发送间不可避免的竞态。
- 数据策略若规定 BUFFERED_REVIEW_REQUIRED，则 stream=true **入站前拒绝**，Agent 需显式使用 stream=false；不能暗中切换协议导致客户端误以为仍在流式。若模型 JSON 输出内容扫描命中阻断，则文本不发送给 Agent，但费用仍按真实使用量结算或保留待对账。

### 20.4 最小审计与数据保留

只保存 request/invocation ID、真实 Employee/Agent/Model/Deployment、policyRevision、effectiveClass、matchedRuleId 和数量、decision（ALLOW/DENY/REVIEW_REQUIRED）、拒绝类别、安全受信输入摘要（带密钥的 HMAC，避免低熵 Prompt 可离线猜测）、scannerVersion、decisionAt、actor/审批时间、traceId。**默认不落盘原 Prompt、回复、密钥或命中片段**；Redis 共享队列只放不敏感的排队 ticket/Invocation ID，不能保存完整 messages。原始 JSON 在请求所属 Gateway 进程有界内存中存活直到真实派发或取消，跨节点不自动迁移；所在实例排队中断时清理票据、不给另一个实例从 Redis 重新生成缺失的 Prompt，且此时没有资金预留。

策略管理员查看安全事件只能看最小元数据；FinOps 报表只读脱敏汇总。日志/Tracing/Outbox 不放敏感正文。拒绝原因公开给调用者的错误码应当可诊断但不回显敏感正则命中内容；详细 ruleId 仅内部可见。安全审计应有不可覆盖版本、访问权限、保留与清理审批，具体保存期限和地区要求 P0 配置冻结。

**D09 设计冻结之前还需决定**：企业是否认可这张分级/出站矩阵、机密数据禁止 SSE 的产品限制、POLICY_EDITOR 与 SECURITY_APPROVER 分离以及误报例外不得突破强制安全边界。

## 二十一、P0-D10：FinOps 统计口径、成本来源与报表边界（设计提案）

**业务目标**：回答谁实际用了多少、哪个 Team 发出多少授额、企业对第三方 API 预计承担多少采购费用、企业运行自部署 GPU 需要多少运营费用；这些是四种独立事实，任何看板不得把 POINTS 与货币相加，也不得把发放与消费重复算为同一笔成本。该业务是对 MySQL 权威资金事实的派生读模型，不决定余额、不改变正常调用的允许/拒绝。

### 四类主要统计事实及归属

1. **EMPLOYEE_USAGE_POINTS**：以成功结算的 Invocation 实际积分消费为准，按实际 Employee、调用时主 Team 快照、Agent、LogicalModel、Deployment、服务等级/资金来源分析；即使积分由公司付费保底/紧急池承担，也可统计为“员工完成服务所消耗的积分”，但必须另列“员工余额承担”和“公司保底/紧急承担”份额，不能将公司承担伪装成员工自己付款。对独立本地免费保底，无 POINTS 消费时另记 LOCAL_FALLBACK_TOKENS_USED 资源用量，不凭空造零价 POINTS 支出。
2. **TEAM_GRANT_ISSUED_POINTS**：只有 Grant 成功发行、发放 Team Pool 真正扣减时才产生，归发行 Team（不是接收员工当时所在的 Team）；消费或到期不再形成第二笔发行或回冲。可另统计过期未使用 POINTS，但这属于存量 Grant 的后续状态而非新的发行支出。
3. **PROVIDER_API_COST_ESTIMATE**：仅在可信 usage 结算后，用真实第三方 Deployment 与冻结的 Provider 采购价计算原币种预计费用（保留 supplierPriceVersion、currency、token 分类）。这不是已支付款项/供应商发票，也不是员工 POINTS 货币价值。不同币种分开展示；无批准汇率快照不能做统一总金额。
4. **SELF_HOSTED_OPERATING_COST**：真实 GPU 采购/租赁、折旧、电费/托管/维护等有证据的运营费用，按资源池和服务期间录入/核对，保留原币种与来源。未取得真实资料的测试 Mock GPU **不生成实际运营费用**。可选按受控使用量分摊为分析维度，但分摊总额不再与来源费用相加，否则同笔成本双计。

**在途与待对账另列**：RESERVED/PENDING_RECONCILIATION/OVERRUN 不是“已确认用掉的积分或已确认的 Provider 成本估算”，应在预算风险/待核对看板单独列示，按 MySQL 当前账本实时查询，不得用异步报表缓存替代资金准入。撤回未出站预留不是负使用量；只有可信结算产生已确认使用事实。

### 日期归属和修正原则

- 员工积分实际消费及 Provider API 采购估算按**初次获准派发/预留时的公司时区业务日**归属；即使异步对账在下一周/月才完成，也回填原日期，外部公司月采购预算仍依据 D01 原月份。报表同时显示 settledAt/processedAt 方便解释延迟。
- Team Grant 发放按 issuedAt 所属公司日期计；自部署运营费用按原始资源服务期间计（可以按月）；不将财务导入当天误认为算力运行当天。
- 迟到结算、可信费用修正、取消复核都通过具有修订号与原始事件引用的**差额更正事件**重建原期间统计；不覆盖或删除原始权威 Ledger，也不发送缺少证据的任意负数冲销。
- 公司原币种采购风险预算可能含 NORMAL/EMERGENCY 分区，报表“总采购估算”**只从实际供应商费用事实计一次**；总月账户与各分区是约束层级，不是两张需要相加的外部费用发票。

### 报表与访问边界

- Platform Admin 可看公司授权范围的全部统计及未对账告警；FinOps Reader 只读获授权公司/团队范围的聚合和必要安全元数据；Team Manager 只看授权 Team 的发放、其管理范围内员工的使用，跨 Team 发放的“发出者归属”不能被接收员工所属 Team 冒领；Employee 只看本人使用/授权可见的资源摘要。
- 请求应按 periodStart/periodEnd、Team、Employee、Agent、LogicalModel、Deployment、Provider、currency、serviceClass 等受控维度筛选。高基数明细分页且需有对象级鉴权，默认不返回原 Prompt、完整 Reply、密钥、安全规则命中原文。
- 看板明确区分 ANALYTICS_AS_OF（报表已处理到哪个事件/时间）、实时权威预算与 PENDING 事项，RabbitMQ 暂时故障不得显示为真实“零消费”；可展示“同步延迟/正在补录”。
- 第一版数据需求以“每日 + 可筛选明细 + 关键预算/待对账提示”为主，按日/维度聚合；只有在确有月度成本分摊业务和可靠数据时才增加高级成本分摊算法。

**D10 仍为 PROPOSED**：四个统计类别与绝不混加原则沿用既有产品语义；具体修正权限、供应商真实费用核对/导入范围、运营费用凭证审核流程与消息交付方式需 P0 冻结。

## 二十二、P0-D11：可靠性、运维与生产服务边界（设计提案）

**Business Goal**：系统发生真实的 Redis、RabbitMQ、MySQL、供应商、Gateway 实例、GPU 推理服务故障时，必须维护“不越权、不超授权预算、不把已可能计费请求当免费、不重复出站”的核心业务不变量，向员工展示可解释的错误与恢复状态。系统可用性不能以透支资金和绕过安全换取。

### 不同依赖故障时的准入原则

| 故障/维护条件 | 新普通/保底/紧急模型调用 | 在途请求与资金 | 管理/统计 |
|---|---|---|---|
| MySQL 资金库不可用、策略发布指针不可验证 | **所有可能新出站请求 fail-closed**，即使 Redis 尚有许可 | 不重发；已可能执行仍保留上次持久证据/待核对，可靠恢复后结算 | 控制面写操作拒绝；不能凭旧 FinOps 读模型推断可用额度 |
| Redis 全局准入不可用或租约状态不可信 | 新入场 fail-closed，不退化成各 JVM 独自计数 | 尽力完成/取消，恢复时与 MySQL Invocation 和真实推理服务核对；绝不假设 GPU 释放 | 不涉及 Redis 的已授权管理读操作可以继续，但不得修改绕过运行控制的政策 |
| RabbitMQ 或报表消费者停机 | **资金与授权依赖 MySQL 时仍可正常新调用** | Ledger+Outbox 同事务成功，已确认使用不丢 | FinOps 显示 DELAYED/堆积，非实时统计不得伪装为0 |
| Provider/GPU 部署失联或限额 | 从合规、同版本 Deployment 中选择有许可候选；无法保证未执行的超时绝不自动重发 | 已可能收费保持原预算待对账 | 不虚构供应商实际 GPU 状态 |
| 仅单 Gateway 实例关闭/重启 | 由健康副本承接**新请求**，不跨实例拷贝 Prompt 重做旧请求 | WAITING 无预算可取消；已派发保持 Invocation/账务事实，必要时待对账 | 新实例 readiness 通过前不接收收费调用 |

### 管理面和运行面健康状态必须区分

- `/actuator/health/liveness` 只反映 JVM/进程能否继续工作，不把暂时的 MySQL/Redis 故障一律转换成重启风暴。
- `/actuator/health/readiness` 的运行时适用性由安全策略版本、MySQL、Redis 容量治理是否可信决定；管理面可单独展示维护/只读状态，不能因运行时未就绪就放行未授权调用。
- 管理员应能看到“系统正在拒绝新出站，但正在保护在途结算/对账”的状态；客户端收到受控 503/429、traceId 和允许的重试提示，不显示敏感内部凭证、原始 Prompt 或完整供应商错误。

### 运营与恢复不可跨越的边界

- 优雅停机先停新入场、拒绝新的远端派发，再清理属于该实例的 WAITING 排队票；给已在进行的 SSE/JSON 有界排空窗口，超时尽力取消，保留无法确认的财务预留/执行意图。不能因为 SIGTERM 直接视为上游任务已停止。
- MySQL 备份恢复时须保留资金余额/流水、Provider 原币种预算、Invocation/Idempotency 收据、价格和治理版本、Outbox；**数据库快照的一致时间点和 RabbitMQ 已消费进度必须有修复/重放计划**，不能恢复旧数据库后继续将未知新订单当未扣费。无法证明一致时暂停付费入场并按原始供应商事实核对。
- Redis 队列和许可重建只能依 MySQL 的未完 Invocation 与真实推理服务任务事实，不能把丢掉的 Redis key 当作“全部任务已退出”。恢复无法验证时拒绝新容量。
- 日志/指标/链路追踪只使用低敏元数据和有界标签；告警至少覆盖双预算待对账时间、公司采购风险/超额、Redis 队列与租约、SSE 非正常断流、Outbox 最老待发布、DLQ、不健康 Provider、MySQL 事务争用。
- 安全策略版本、资金表 schema、消息 schema 必须在发布/回滚时兼容历史在途请求与已持久化事件；不能为了回退应用镜像而删除尚未结算的财务事实。

### 架构升级条件

**D15 已取代本段旧部署目标**：初期为 aigate-gateway+aigate-core 两个独立微服务，P11 新增 aigate-finops；Gateway 可单独多副本（实际运行环境规模视可用硬件决定），独立 MySQL/Redis/RabbitMQ 和现有推理资源。若实测出现管理 API 被 SSE 占满、数据库资金热点、OOM、某模块故障互相传播等具体问题，先做实例隔离/执行器/连接池/索引/容量策略优化；仍不满足可复现目标才提出拆服务 ADR。无需为了“全量设计”预先引入 Nacos、K8s、全链路 Service Mesh 或五套微服务。

**D11 PROPOSED**：产品层的故障处理原则已明确，具体备份周期、容量阈值、SLO/恢复目标、运行环境和告警通知渠道仍需企业配置与压测证据，不能凭空宣称生产高可用已经实现。

## 二十三、P0-D12：P1 组织与管理权限业务边界（提案）

首个完整业务块不是“先有 CRUD 然后再加权限”：业务必须同时完成 Team/Employee 的创建、读取、修改、软禁用、版本并发处理、Team Manager 只读范围、管理员可控引导、独立管理凭证及最小审计。员工有唯一当前主 Team；Team 仍有 ACTIVE 主成员就不能禁用。Manager 只能看其负责 Team 的现有员工；员工属于 Team 不代表自动获得 Manager 权限。

初始只有受控 Bootstrap 能创建首个 PLATFORM_ADMIN 并为员工发管理 Key，随后关闭 Bootstrap。管理 Key 与真正使用 Agent 的员工 Runtime Key 是两个不同的安全凭证，且均不能替代 Agent Key。Employee 禁用或角色被撤销后，不得继续凭旧权力修改任何业务对象。管理操作成功与审计写入原子提交；明文密钥仅签发时展示一次，审计/响应/日志不得泄露。

本业务块**不涉及真实 Provider、员工积分、Token 计价、紧急任务和收费出站**。P1 从第一次交付起具有完整管理侧安全与测试，但不会为学习某项框架而搭建无业务依据的员工密码登录或 OIDC。详细数据与 API 见《03-数据与接口》D12，实施任务见《04-阶段与任务》D12、验收见《05-测试与验收》P1-01～P1-24。此方案尚未获最终设计冻结批准。

## 二十四、P0-D13：总体业务闭环审查与产品边界（REVIEWED / 未冻结）

这次审查从真实员工、Team Manager、管理员、Agent 的业务行为倒推需求，而不是直接从 Redis、MQ 或服务拆分倒推业务。以下 **八条**均属于最终平台必须覆盖的闭环；既有 D01～D12 的已确认业务规则不因本次评审被自动推翻。

| 闭环 | 发起者 / 输入 | 可观察业务结果 | 核心拒绝/失败结果 |
|---|---|---|---|
| BIZ-1 组织初始化 | 运维短期 Bootstrap、Admin → 创建 Team/Employee/角色 | 有可信员工/Team/Manager 数据和操作审计 | 非管理员、禁用人员、跨 Team 403；重复/状态冲突409 |
| BIZ-2 Agent 纳管 | P2 Admin 注册 Agent、授员工-Agent ACL 并发双 Key；P3 建真 Model 后授 Agent-Model ACL | 现有 Agent 可以用双身份选择获准 Model | 缺任意 Key、禁用、吊销、越权时零 Provider 出站 |
| BIZ-3 模型治理 | Admin 登记 Provider/LogicalModel/Deployment、两种价格、部署区域和批准状态 | 同一个已授权逻辑 Model 可有受控多部署候选 | 不等价模型不得混路由、无合法价表/可信边界不得出站 |
| BIZ-4 积分/Team 授额 | 每周公司时区额度初始化；Manager 审批/主动发放 | 员工×Agent 周额度、员工周额度、有效 Grant 按优先顺序可用 | 余额不足/重复操作/并发不得重复发放；过期不退发行 Team |
| BIZ-5 普通模型调用 | Agent+员工双 Key，请求纯文本 JSON 或 SSE | Redis 获许可后才在 MySQL 预留，实际 Model/Deployment 调用一次；可信 usage 结算 | 无资金/安全授权/共享容量零出站；未知费用双账待核对 |
| BIZ-6 企业低档/本地保底 | NORMAL 不足且满足授权的受控低成本模型/本地基础模型 | LOW 独立排队，正常剩余积分与公司保底额度按政策分担，或本地 Token 补贴 | 未授权降级、公司采购硬限额、员工周限制、无本地容量均拒绝 |
| BIZ-7 紧急任务 | Employee/Manager 申请；不同真实管理员审批；指定 Employee+Agent+Task+Model | 有界紧急预算授权，执行名额更优先，但不能抢占运行中的 SSE | 撤销/过期/自批/资金或安全限制不能因 EMERGENCY 绕过 |
| BIZ-8 统计与运营 | 结算/授额/运营成本来源 → Outbox/MQ/FinOps | 员工消费、Team 发放、Provider 原币种采购估算、自部署运营成本四种统计 | 延迟标 DELAYED，未知费用不作零；不同单位/重复成本不混加 |

**全局业务决议边界**：Agent 是已有客户端，不开发 Agent 编排、RAG、向量库、执行工具或 GPU 调度器；公司/员工真实额度、币种限额、单价、地域批准等一律配置，不能让本地 AI 编造真实财务数据。单企业初版；数据分类四级及 CONFIDENTIAL 禁止 SSE 仍为安全保守提案，必须由用户在 P0 冻结时确认产品接受度。

**本轮识别的重要产品缺口（待审提案）**：
- LOW 会改变最终逻辑 Model。建议默认**不自动降级**；只有 Agent 侧事先设置经管理员批准的允许 fallback 策略并明确取得终端调用方同意，或请求传入安全白名单允许的 opt-in 字段时才可执行。无 opt-in 时积分不足按 402 拒绝。具体字段与事前授权证据在 P0 API 合同定稿前不得自行猜测。
- “Manager 审批其他 Team 额度”指 **有权操作自身作为发放方的 TeamPool**，不是因为接收人属于另一个 Team 就取得对其整个 Team 的管理权限；FinOps 的 Team 发行支出也归发行 Team，历史 Team 快照不随员工调动改变。
- P6 安全策略审批、误报例外审批必须有独立治理角色，不允许“Platform Admin 天然能绕过自批禁止”或用运行时 Agent Key 改安全配置；新角色随 P6 业务块完整交付，不要求 P1 提前存在未来业务。
- 输入分类、路由健康状态、用量是否可信是三类不同证据；不能为了成功率把没有可靠用量/安全边界的 Provider 当成收费上线候选。

**审查结论**：主要商业闭环有覆盖；真正阻塞的是逐接口协议和部分产品默认授权（尤其降级 opt-in、治理四级策略）、全表详细数据合同和测试可执行化。故本轮只标总体业务 **REVIEWED**，不标 **APPROVED/FROZEN**。

## 二十五、P0-D15：直接微服务对产品能力的确定影响（架构已获批准）

用户明确要求**从项目初期直接拆微服务并确定理由**。AIGate 的业务角色、资金规则、Agent/Model 白名单和四类 FinOps 统计不变；改变的是物理部署、授权跨服务责任和故障表现。不得把微服务拆分理解为允许绕过已确认业务规则。

1. **统一外部入口**：Agent 和管理员只访问 aigate-gateway。管理 API 被 Gateway 透明路由至 aigate-core，员工与 Agent 的真实权限由 Core 校验；未来 Gateway 的 JSON/SSE Runtime 也必须获得 Core 的单次派发许可。用户不需要知道内部三个服务的 IP/端口。
2. **长连接和数据分离**：Gateway 为 JSON/SSE/Provider HTTP 与 Redis 入场负责，可以独立扩容；Core 为 MySQL 权威身份、模型策略、员工/Team 额度、Provider 原币种预算、紧急审批及派发意图负责；FinOps 从 P11 起单独消费统计事件，允许延迟，不得改变实际余额。
3. **业务审批与资金的线性化**：管理员吊销 Employee Key、Model 白名单、安全策略收紧和员工预算不足，都要在 Core 的真实派发事务中复核；Core 一次提交所有必要的预算预留与唯一 DispatchIntent。不得“一个服务扣员工积分，再让另一个服务扣公司采购预算，失败后补偿重试”作为正常路径。
4. **明确失败表现**：Core 不可达→新模型出站受控 503/不可安全执行，不得利用 Gateway 缓存权限或积分继续扣费；Gateway 已取得 Core permit 而结果不明→严禁自动第二次供应商请求；FinOps/MQ 不可达→Core 账本照常记录，报表显示延迟。
5. **数据最小暴露**：Gateway 可在短期有界内存中持有原始 Prompt；Core 为了可信治理扫描，可通过内网调用在有界内存短暂接收原消息，但不落盘、不记录日志、不进 MQ；FinOps 永远只拿脱敏事件/费用事实。任何调试服务不开放 Prompt/Provider Key 给普通管理员。
6. **业务外观不变**：原公开 API 的路径/请求 DTO/核心错误语义不因内部拆分改变；微服务只增加 traceId、受控 503/504 以及延迟状态的解释，不能让用户感知“先扣积分后供应商超时便永久失败且无状态查询”的不完整闭环。

**拆分理由最终归类**：Gateway/Core 的主要理由是**不同资源模型和故障域**（长 SSE+外部网络 I/O 对比短 MySQL 安全账务），FinOps 的主要理由是**数据最终一致/统计负载可独立运行**。这是一项明确的业务与学习目标的架构选择，并不是已经通过压测证明单体无法胜任；三服务带来真实网络错误、发布兼容、服务身份/凭证和运维成本，均须在 P0 详细设计及 MSC 集成测试中承担。五个业务领域不机械拆成五套资金/授权数据库。

**状态**：微服务部署拓扑获用户确认，但产品授权/价格等其他 P0 冻结问题仍存在；不代表 P1 已编码。

## 二十六、P0-D16：用户可见的远程故障/凭证与收费业务边界（详细提案）

这是微服务 P1/P7 的业务语义，不是技术实现流程的自我目的：**员工正常调用的目标是一次有权限、受预算限制的模型推理；系统不能因 Gateway 和 Core 的网络错误，把员工的同一个请求变成两笔供应商费用。**

1. **用户/Agent 的外部使用体验不因内部微服务数增加而变化**：管理 API 依旧统一 /api/v1/**；Runtime 一律 /v1/chat/completions + 两份运行 Key + Idempotency-Key。Core 自行认定员工/Agent 与权限，客户端 Header 不能命令 Core 用他人身份收费。
2. **Gateway 暂时连接不上 Core**：新模型调用失败并返回受控 503/504，不允许 Gateway 从上次查到的缓存余额或旧治理许可继续发送到收费 Provider；已经发出的请求只允许查询自己有权访问的 Invocation 状态。
3. **Core 已预留但 Gateway 没收到明确 Permit 成功**：客户端得到可查询的 Invocation/待核对状态，不能当成“从未收费”直接生成第二次相同模型请求。Core 不因为这种不确定性自动退款。若凭可信证据确认没有 Provider 出站/费用，才允许从原周/月资金来源释放。
4. **Provider 已返回但结算报告到 Core 丢失**：Gateway 可以使用相同的调用/报告操作键重送**用量与结算证据**，不能重送整个 Prompt 产生第二次模型调用。可信使用量正常结算，无证据保留 PENDING_RECONCILIATION，并向员工展示状态与 traceId。
5. **Provider Key 的真实隐私边界**：管理员配置密钥时在 Core 经加密存储；只有获授权的 Gateway 在实际派发许可对应的 Deployment 上才可取得执行凭证。供应商 Key 可能是长期 API Key，只是暂时传输并驻留 Gateway 内存，不能虚称供应商本身支持短期密钥；不能把它显示到外部模型返回、运营报表、日志或 Redis。
6. **不是任何内网服务都能扣费**：svc_ 证明服务调用方身份，agk_ 与 empk_ 证明真实 Agent+员工，现存 ACL/安全/资金政策最终由 Core 独立核对；微服务的内部可信 Header 不代表拥有 Employee 或 Admin 权力。

**业务不变量**：同一个 Invocation 的唯一可收费 Provider Attempt 只能得到一次明确的首次发送授权；网络交付是否发生存在不可消除的不确定窗口，系统优先维持账务风险而非盲目再次支付。保守待对账可能降低成功率并占用预算，但能避免把不确定账单误当零费用。不能保证不支持幂等的真实第三方 Provider 物理上 exactly once。

**阶段与状态**：P1 只交付管理代理、安全路由和内部服务身份；P3 完成供应商凭证安全配置；P7 一次完整交付远程 Runtime、一次性派发和结算恢复。以上 D16 为待最终冻结的设计方案，未产生代码与测试结果。

## 二十七、P0-D17：FinOps 授权、历史 Team 归属与运营成本录入规则（提案）

**使用者的业务目标**：企业管理人员了解四种独立的使用/发放/采购估算/真实自部署运营费用，Team Manager 不得越权窥视其他 Team，员工可看自己的历史用量；FinOps 故障时员工仍可受权调用模型，未知采购费用不会因报表空白被误认为0。

1. **公司范围**：ACTIVE GLOBAL PLATFORM_ADMIN 和 GLOBAL FINOPS_READER 可以查看公司授权范围内、按单位和币种分别展示的四类确认事实。Reader 永远只读，不具有费用审批、修改、重建或扣费权力。
2. **Team 范围**：TEAM FINOPS_READER 可以查看获授权 Team 的历史员工积分、团队发行积分和属于该 Team 的 Provider 采购估算；TEAM_MANAGER 只查看本 Team 的历史积分消费、本 Team 实际发行 Grant 及本地补贴 Token 的汇总，不开放公司外部采购估算和未分配给 Team 的 GPU 公司总费用。
3. **个人范围**：普通 Employee 只可查看自己跨历史 Team 的积分用量及本地基础补贴资源量；其身份来自 mgt_ 当前凭证认证，而非 URL/body 的 employeeId。Team Manager 查看员工级明细时必须指定当前仍在自己 Team 且原使用事实归属这个 Team 的员工；员工转离后旧 Team 的聚合仍保留，不因调动改写当年报表。
4. **两个不同 Team 归属字段**：使用者消费属于调用时 primary Team 历史快照；授额支出属于发行方 issuerTeamId。领取者后来调 Team，不能移动历史支出或把其它 Team 发放视作自己 Team 池消费。
5. **实时预算风险与异步已确认费用不能相互替代**：待对账/超额/原币种采购风险由 Core 权威实时读，不依赖 MQ/FinOps；报告页面可以同时显示分析已处理时间、积压/隔离和报表滞后。MQ 消费停滞不代表已确认费用为零，不能用“同步中”掩盖风险账户真实占用。
6. **真实运营费用必须有证据**：自部署 GPU 费用、租赁、电力、托管等需要可审核的来源/月度服务期/币种/金额；初期按完整自然月登记与展示，不把月租等分成未经证实的真实每日成本。跨月凭证需由管理员提供可审计的拆月金额，不能自动创造真实金额。模拟 GPU 或无财务来源的数据不能被显示成实际运营成本。
7. **费用独立审批**：ACTIVE PLATFORM_ADMIN 创建草稿，由另一名 ACTIVE PLATFORM_ADMIN 审核（不允许自批）；批准成功在 FinOps 自有数据库一次事务中生效/留痕/更新报表，不能改 Core 的 Points/TeamPool/Provider 月采购额度。更正或作废追加修订，不删除旧证据，重放不能重复增加运营费用。公司目前只有一名管理员时，草稿可以保存但不能完成自批；须有第二名合法管理员或等待正式业务规则调整。
8. **权限撤销时序**：Core 角色/凭证撤销提交后，不允许新的报表授权；已经在撤销前获得 Core 授权且正在 FinOps 执行的请求可能完成，这是跨服务现行授权边界。审批记录必须保留谁在什么时刻获授权，不能宣称两个不同数据库之间有一条天然的原子事务线。

**对外体验**：客户端仍只访问 Gateway 的 /api/v1/finops/**；Core 验证用户/角色后调用 FinOps。FinOps 失联时分析查询明确不可用，而 Core 待对账权威查询仍可返回准确风险。四类统计单位不混算，详情不含 Prompt/原始回复/明文密钥。

本节除继续沿用已确认的积分/预算/统计口径外，额外的 Team Manager 明细权限、月度运营成本范围及双人审批为**D17 实施默认提案**；P0 总审时需明确确认或修订，不能把尚未批准的公司财务审批制度当成既有事实。

## 二十八、P0-D18：P1 真微服务入口与首次管理员初始化的业务规则（提案）

D15 已批准直接两服务启动，D18 把它变成可验收的**第一阶段真实业务**：在没有任何 AI Provider/积分/Agent 运行模块时，公司仍能通过唯一 Gateway 入口创建 Team/Employee，签发管理 Key、设置 RBAC、查询审计，同时验证两个 Spring Boot 进程能独立启停。

- **首任管理员是特殊业务操作，不是普通 Team/Employee CRUD**。只有系统尚未初始化、运维显式临时启用 INIT 和受限网络，才允许一次性创建首任 Team、Employee、GLOBAL PLATFORM_ADMIN 与 mgt_ 管理凭证；该操作必须和操作审计在 Core MySQL 同一事务内完成。**即使两个运维人员同时提交不同 Team 名称，也只能有一个成功**。
- **D18 比 D12 多一张 bootstrap_control**：持久化“首任管理员初始化已完成”的唯一行并锁定，避免在两个独立请求之间出现同时查询空库、同时创建两个初始 Admin 的竞态。原来的五个组织业务实体不删，P1 物理表总数改为六张。
- **Bootstrap Token 不能当万能管理员**：运维 bst_ Token 仅用于受限的首次 initialize 或恢复已有 ACTIVE GLOBAL PLATFORM_ADMIN 的管理 Key；不能用来平时创建员工、任命普通员工为新 Admin、调用 Runtime、查账。恢复时签新管理 Key 只显示一次并有审计，不能放开一个让攻击者任选用户变管理员的后门。
- **管理功能不依赖 Redis 授权**：Core 负责真 mgt_ Key/RBAC/Employee/Team 是否 ACTIVE 的实时 MySQL 验证；Gateway 只是受控网络入口和 Header 安全边界。Redis P1 提供基础连接与故障诊断，不得把“Redis 故障”解释为任何人都具备管理权限。
- **P1 没有真实模型调用或公司收费功能**：/v1/chat/completions、/v1/invocations/**、/api/v1/finops/** 等后续业务路由此时保持关闭。Gateway 的健康/管理代理可被验证，不应为了演示微服务而构建假的 Provider 或假财务数据。
- **单企业管理访问经过两次不同的责任判断**：Gateway 校验合法路由/来源且剥离伪造的服务身份 Header；Core 独立验证 mgt_ Bearer、对象级 Team 范围及审计。跨 Team Manager 的 total/错误/列表无越权泄漏。Gateway 与 Core 相互失联时返回可诊断的安全 503/504，而不是绕过 Core 操作真实组织数据。
- **真实运行边界**：P1 交付 Gateway+Core、Core MySQL、Redis，真实 Maven/Compose/CI；只有 Gateway 对外提供管理访问，Core 和数据库不开放公网端口。普通生产管理 Key/Bootstrap Key 通过内部链路必须有受验证 TLS；开发私网明文只作为 DEV_ONLY 教学/集成环境，不宣传生产安全上线。

**本轮业务不变量**：首任初始化成功一次或彻底回滚、没有“创建管理员却没审计”的状态、管理 Key 唯一一次可见、角色撤销之后新操作不可越权、客户端不能绕过 Gateway 与 Core 的职责边界。D18 Bootstrap 运维路径和并发策略仍为待 P0 最终审查的实施默认，没有本地 AI 编码授权。

## 二十九、P0-D19：P2 Agent 纳管、真实 Employee 双身份与使用授权业务定义（PROPOSED）

### 业务背景与目标

AIGate 的 Agent 是企业已经拥有的 Application，不在 AIGate 开发 Agent 编排/工作流；企业需要知道**哪个 Agent 调用、哪个真实 Employee 在使用，以及这个 Employee 是否被明确允许使用该 Agent**。这不仅是安全问题：后续 P4 周额度、P5 Team Grant、P7 计费与 P11 FinOps 都要用不可被客户端伪造的 employeeId+agentId 归属。

**最小业务闭环（P2 完整交付而无真实模型）**：管理员登记 Agent（与已存在 Application 一对一）→给 Agent 发行 agk_→给既有 Employee 发行 empk_→授 EmployeeAgentPermission→使用可信内网身份验证接口同时验证两份 Key+关系→管理员撤销权限/Key 后后续验证拒绝。没有 LogicalModel 时完成的是**身份与 Agent 权限闭环**，不是 AI 模型调用闭环。

### 业务规则和责任

1. **身份两份、权力三重**：agk_ 只代表 Agent 身份，empk_ 只代表 Employee 身份；有效的 agk_+empk_ 仍必须有 EmployeeAgentPermission=GRANTED。普通员工属于 Agent Owner Team 并不自动 GRANT；没有双身份不能按其他员工名义收费。mgt_ 是管理员管理身份，bst_ 是受限运维身份，svc_ 是服务进程身份，都不能顶替双运行 Key。
2. **Agent 与 Application 一对一**：管理者注册已有 Application 时提供不可复用的 applicationCode、一条 Agent 记录、ownerTeam 与 displayName；P2 不实际执行 Agent 代码、不存其 Prompt 和任务、不开 Agent Studio。Agent 被禁用或所属 Team 被禁用后不能通过 Runtime 身份验证；恢复 ACTIVE 不复活已被撤销的 Key/ACL。
3. **Key 生命周期**：两份运行 Key 使用强随机数、不可逆 HMAC 摘要、各自独立 Pepper；管理员才能发行、分页查元数据、轮换与吊销。仅创建/轮换成功的首次响应一次展示完整 Key，之后永不重显。同管理员同业务操作幂等键重放只返回409，无第二把密钥/再次明文。所有有效期、grace、撤销以 Core DB 时间与配置进行判断，不把 Redis 当权限源。
4. **轮换业务**：每 Owner 最多同时两把可认证 Key，新 Key 创建后旧 Key 最多有24h过渡窗口，以支持企业外部 Agent/员工配置更新。旧 Key 在窗口末失效；主动撤销立即失效。超量发放被拒绝，不借并发绕过阈值。
5. **Employee-Agent ACL 生命周期**：管理员 PUT 授予/重复幂等、DELETE 撤销/重复幂等；同 Employee×Agent 只有一条当前关系，regrant 改回 GRANTED 并产生新管理审计记录。权限已撤销后新的运行身份验证不通过，Key 有效也不行。
6. **管理边界第一版从简**：只有有效 GLOBAL PLATFORM_ADMIN 执行 Agent、运行 Key 和 ACL 写操作；TEAM_MANAGER 继续采用 P1 只读 Team/Employee 范围，不因为 Agent 属于本 Team 就自动拥有 Key 管理权；普通员工也不因被授 Agent 使用权而能发自己的 empk_。以后出现确切自助或 Team Manager 代管需求，再审核范围/审批/审计扩展。
7. **零 Provider 出站**：P2 不建 Provider、Model、价表，不开 /v1/chat/completions，不预留积分、不分发 Redis 资源许可。P3 建真实 LogicalModel 后才添加 Agent-Model 白名单；正式 P7 发模型前须同时通过 Employee-Agent 和 Agent-Model 两个 ACL，且重评治理/资金。

### 失败与验收判定

- 任一 Key 缺失、错误、自然过期、吊销、Owner DISABLED →401；两份有效 Key 但没有 Employee-Agent GRANTED →403（只在可信服务内部得到安全业务码，不泄漏别人的 ID/密钥）。
- Agent、Employee 和 Permission 无法从 Core MySQL 权威读取时 fail closed，不能用 Gateway 缓存身份或客户端自报的 employeeId 继续收费。
- 管理员每次成功发行/轮换/吊销/授予/撤销/修改 Agent 都在 Core MySQL 同一事务写最小成功审计，审计 INSERT 失败整体回滚；错误/log 不记录完整 Key 或 HMAC Pepper。
- 首次身份认证业务可通过仅内网受 svc_ 保护的 Core /internal/v1/runtime-identities/verify 验证，**公开验证/真实收费入口都未启用**。P7 最后签发一次性 Permit 前再复检当前 DB 的两份 Key、两套 ACL/治理/预算，不能把 P2 verify200 当成永久收费许可。
- P2 完成的真实标准是 V2 四表、全部 15 个管理接口、私有验证接口、P2-01～P2-40/旧 P1 回归及双进程 E2E 全部有真实运行证据；不能以文档写完替代业务可运行。

**本轮 D19 的业务默认（尚待 P0 总审）**：GLOBAL PLATFORM_ADMIN 独占 P2 管理写权限、1h～90d 的运行 Key 有效期、24h overlap/每 Owner 最多2把有效 Key。以上不改变已确认的“双身份、Agent/Application 一对一、Employee-Agent 必须显式授权”基本业务事实。P1 尚未启动，P2 也没有源码。

## 三十、P0-D20：P3 模型目录与授权的业务闭环（PROPOSED）

**业务目标**：管理员在不实际向供应商收费的前提下，登记可信 Provider、统一 LogicalModel、实际 Deployment、内部 POINTS 价、供应商原币种采购价以及 Agent-Model 白名单；P7 真实出站只能消费已发布、仍有效的目录事实。

**主流程**：GLOBAL PLATFORM_ADMIN 创建 Provider（THIRD_PARTY_API 或 SELF_HOSTED）→创建明确身份和版本的 LogicalModel→登记绑定唯一 Provider、远端 model 名称、批准的 endpoint/region/能力的 Deployment→配置受控 ProviderCredential→发布 LogicalModel 的内部 POINTS PriceVersion 和各第三方 Deployment 的原币种 PurchasePriceVersion→对 P2 已存在 Agent 授予指定 LogicalModel 白名单→管理员可通过受限只读能力检查“是否可被候选选择”；不能调用真实模型。

**业务不变量**：
- LogicalModel 表示业务选择的**同一模型身份+明确版本+能力合同**；仅 OpenAI-compatible 协议相同，不能把两个不同模型视为同一 LogicalModel。Deployment 是实际 Provider/URL/remoteModelName 的执行地点，可多实例；正常路由不跨 LogicalModel。模型 code 不能复用给新模型版本。
- 一个 LogicalModel 当前唯一**已发布**内部 POINTS 单价版本，部署切换不变更员工单价；不同第三方 Deployment 可有不同 USD/CNY 等原币种采购价，且仅其所在 Provider 实际收费分支使用。SELF_HOSTED 不伪造逐次供应商购买费用。
- 仅 ACTIVE Provider、ACTIVE LogicalModel、ACTIVE Deployment、对应 Agent-Model GRANTED、发布价表可用、审批边界合格时**才可能**进入 P7 候选；P3 只校验目录/ACL，不开 /v1/chat/completions 或真实 HTTP Provider 出站。
- Third-party endpoint 必须 HTTPS、可信域名和受控 DNS/IP/重定向限制；self-hosted 私网地址必须显式 allowlist 和可信部署审批，不能因为是私网就默认 CONFIDENTIAL 合规；P6 进一步实现真正治理策略。
- 供应商凭证 Core 加密保存，管理接口只在首次提交接收明文，之后不回显、不被 Gateway 配置/Redis/MQ/日志携带；P7 有真实 Permit 才由受信 Gateway 获取执行凭证。修改 URL、鉴权、价格、区域时必须通过版本/审批，已发布旧版本不能就地改写。
- Agent-Model 权限独立于 P2 Employee-Agent 权限；必须两者同时允许才具备调用资格。禁止所有同 Team 员工或 Agent 自动继承所有模型。

**Phase 边界**：P3 完成配置/状态/版本/白名单/安全凭证管理 API、SQL、审计和测试；P4 才使用冻结价计算额度，P6 才完成真实内容治理，P7 才上游出站，P8 才做复杂健康评分和动态路由。权限和价表版本在 P7 最终 Core 资金许可事务复核。

**仍需 P0 审查**：真实供应商凭证格式/端点安全名单、价格精度与“已发布不可重写”策略、能否证明实际 Token 费用上界均为设计/测试门禁；不得虚称第三方都支持完全可靠 usage 或硬输入 Token 预算。

## 三十一、P0-D21～D24：从周额度到首次收费调用的四业务块衔接（PROPOSED）

### D21 / P4：员工周额度 + 第三方采购月预算

一名真实 Employee 使用指定 Agent 调用已被批准的 LogicalModel：首先可使用本人×Agent 的免费周积分，其次使用本人跨 Agent 共享的每周基础积分。公司不是给员工“一份无限量的第三方 API 余额”，而是在 Employee Points 之外另外设置按供应商原币种、公司自然月的采购风险预算。每次第三方调用必须在**同一个 Core MySQL 事务**同时占用积分与该币种公司总采购预算及 NORMAL 份额，任一额度不够都不允许出站；普通自部署只消耗积分并受容量上限，不伪造一笔供应商费用。按公司时区确定旧周/月，跨期在原桶结算；有效价格由 P3 历史版本冻结。无可证明输入/输出 Token 最坏费用上界，不得为了“先跑起来”用平均字符长度或未经验证 tokenizer 估算冒充硬约束。P4 完整交付的是金融规则/管理端/账本/测试 Facade，不向 Provider 真实收费。

### D22 / P5：Team 发放积分

TeamPool 是 Team 可以**发放**的积分总池，Grant 是已经发行给某个 Employee 的独立消费来源。Manager 发放100积分时 TeamPool 立即占100，记 issuerTeam 的发行事实；员工后来使用30，记**员工的使用**30，不能让公司采购或 Team 发行报表把100+30当成一笔实际费用。员工的第三顺位积分来源是按 expiresAt/id 最早到期优先的未过期 Grant，前两层为 Agent 周/个人周。Grant 在合法派发时已预留、结算才过期仍可扣已保留资金；到期释放余额不退发放 TeamPool，也不滚入新周。跨 Team 授额的支出始终属于 issuerTeam，不能因 recipient 调 Team 改历史。授权 Manager 必须在 TeamPool 与 Grant 同一个本地事务中通过，并完成防并发重复发行/幂等与审计。P5 不真正调用模型。

### D23 / P6：真正的企业 AI 数据治理

Employee-Agent 和 Agent-Model 两道使用许可回答“谁可以调用模型”，**并不回答“能否把这一批数据发给实际 Provider”**。Core 治理必须基于可信数据源等级、完整文本消息扫描、明确 Agent 出站审批与 Deployment 受信边界综合裁决。分类 PUBLIC、INTERNAL、CONFIDENTIAL、RESTRICTED；其中 CONFIDENTIAL 默认只允许已批准 SELF_HOSTED + 非流式输出缓冲审查，RESTRICTED/高置信真实凭证拒绝所有目标。紧急业务、付费保底和管理员高角色不能豁免真正不可豁免的限制。策略编辑人和审批人不同，发布为不可变版本，撤销生效竞争以 Core 发布指针和最终派发事务的数据库锁顺序为准。Prompt 原文不能进入 Redis/MQ/日志/账务；P6 使用受控 FakeEgress 完成业务验证，无真实模型调用。

### D24 / P7：第一次真实 JSON/SSE 模型调用

统一入口仅支持纯文本 Chat Completions，用户携真实 agk_、empk_ 和 Idempotency-Key，选择 LogicalModel 而不是指定供应商 URL。Gateway 负责请求网络连接、Redis 有界队列和 SSE；Core 独立确认身份/两道 ACL/治理/当前价/资金，取得 Redis ACTIVE 资源许可后，**在一个 MySQL 本地事务中预留双账并写唯一 DispatchPermit**，仅首次明确成功的 permit 响应可以驱动一次 Provider HTTP 发送。上游可信 usage 结算积分和采购风险，超额/无可信账单进入待对账。Permit 请求已提交却丢响应，不能把后续“查询到 committed”当作重复 Provider 网络发送授权；result 报告的 ACK 丢失可以幂等重报**结果**，不能重复向供应商发 Prompt。JSON 输出完成与账务 SETTLED 是两个不同状态；SSE 完成或下游断开也不能自动判定零费用。Gateway/SSE 不绕过公司安全治理。

### 业务阶段串联与不能提前实现的内容

- P4 就建立 Ledger/Outbox 安全事实，为 P11 的 RabbitMQ/FinOps 准备历史，但不部署 MQ。P5 Grant 发行是不同于真实使用的事件，P11 不双计。
- P7 第一次实际出站时必须具备 P2 双身份、P3 真实模型与价表、P4 两账、P5 Grant 和 P6 安全政策。缺任意一项、Provider 实际收到请求数必须为0。
- P8 的复杂健康评分、P9 LOW 公司补足及本地保底、P10 EMERGENCY 审批与三档激活都是**独立的完整业务**；P7 的基础路由/共享队列仍必须是真 Redis、不是单 JVM 伪实现。
- 用户最终真实公司预算额、Token 价格、合规数据地区、GPU 容量均是运行配置/审批事实，本轮测试用数字只作 Mock，不能写成公司真实政策。

**状态**：P4～P7 业务约束已明确，物理 DDL/DTO/测试还需最终冻结；本轮没有运行或提交这些业务代码。

## 三十二、P0-D25～D29：P8～P12 剩余业务模块完整闭环（PROPOSED）

### D25 / P8：动态路由必须服从业务硬准入

员工已经有权使用某个 LogicalModel，实际可以存在两个身份/能力完全等价但供应方不同的 Deployment。P8 能根据健康、连接错误、共享容量、延迟和同币种采购成本选择它们；**不能改变模型身份、员工 POINTS 单价，不能把高健康分当成突破 AgentModel 白名单、内容等级、地区限制或采购资金上限的理由**。没有可验证的健康数据应标 UNKNOWN，不用历史一次成功永久宣布健康。熔断与冷却发生在**未出站之前的候选选择**；若同 Invocation 已得到可能收费的 Permit/Provider 曾可能收到请求，不能因为供应商出现5xx自动向另一家再次请求。管理员可以发布路由版本，禁用部署立即影响新请求；已冻结历史使用及风险按原部署/报价归属。探路请求如果可能收费，也必须按一次真实收费调用预留双账，不准“系统自己做免费探测”私自消费公司采购额度。

### D26 / P9：企业保底是经批准的独立资金，不是无限重试

员工某次 NORMAL 模型风险超出普通 Agent周→员工周→Grant FEFO 的余额时，只有 Agent 管理方事先批准可接受的低成本 fallback Model，且本次发起者通过 Runtime 的 fallback_mode=ALLOW_APPROVED **明确同意型号可能变化**，才可进入 LOW。LOW 在替代型号重新检查两道 ACL、治理/地域、可信费用上界和容量后，先用员工剩余普通积分，缺口由公司 paid fallback POINTS 月池承担且计入该员工的周公司补足 cap；若是第三方采购还必须有对应原币种公司总月预算和 NORMAL 份额，不能使用应急采购份额。降价后若原普通余额完全够，仍按已同意降级的 LOW 等待队列执行但公司补足为0。普通无法承担时，应先在**尚未排队、预留或获 Permit**的只读预评估中决定付费 LOW 还是获准 SELF_HOSTED BASIC_FALLBACK 其中**一个**目标；只有付费候选预评估不可行，且员工跨 Agent 周 Token 补贴/真实GPU许可具备可行资格时，才选本地 LOW。已进入LOW队列后若付费预算变化而失败，不自动二次跨型号切到本地；本地支路占Token补贴与容量而非假0货币账，GPU 月运维账照常在 P11 收有证据费用。任何降级都不得无限重排，风险可能已出站后不能重新送上游。

### D27 / P10：紧急优先权来自真实的另一人审批

Employee 提交受益员工/Agent/Task/批准型号/Points 上限/期限请求，不能自己向运行头写 EMERGENCY 就获得额外资金或 GPU 优先。当前 RoleAssignment 有权限的 Manager 可替合法 Team 成员申请，另一名有效 Global Admin 审核并且**审批人不得是申请人**；一项 Employee+Agent+Task 同时只能有一份当前有效授权。批准时只是授任务额度上限，**并未预扣**公司紧急积分池；实际得到 Redis EMERGENCY ACTIVE 后，Core 仍按一次 MySQL 事务锁该任务 cap、公司 emergency pool 与第三方所需的币种总采购预算 + EMERGENCY 专用份额。自部署不伪造逐次 API 采购费，仍须真实 GPU 上限。Redis 4:2:1 是对释放的新执行名额的加权分配，不抢占已经执行的 NORMAL SSE，也不保证精确完成时间。审批撤销/任务到期只挡新 Permit，旧未知收费继续挂原风险。只有一名管理员且他是申请人时，不为演示绕过双人审批。

### D28 / P11：独立财务统计不替代真实采购风险

确认的员工 POINTS 消费、Team Grant **发行**、第三方采购原币种成本估算来自 Core 的 Ledger/Outbox→RabbitMQ→FinOps Inbox，四类指标各自用不同金额单位和归属维度，不把发行100 + 个人消费30 当作同一口径总费用，也不把公司预算限额/已保留金额误说成供应商发票。自部署 GPU 租金/能源/折旧等，只有**真实可审核费用凭证**且不同管理员批准后，才在 finops_db 本地事务变为真实运营费用；没有 GPU/真实票据的测试环境不能冒充公司生产成本。员工和 TeamManager 报表范围由 Core 当前 RBAC/Employee/Team 认证决定，FinOps 通过 Core 内部受信授权范围查询自己的数据库；普通 Employee 只能看自身历史积分/本地补贴；Team 使用按调用当时 Team 快照，Grant 发放按发行方 Team。FinOps/RabbitMQ 失联只使报表 DELAYED/UNKNOWN，不影响 Core 真实资金入场/权威待对账；没有源事件缺口验证绝不自称 FRESH。

### D29 / P12：真实系统可靠性而不是再人为拆第四个服务

从 P1 就已经有真实 Gateway+Core 两 JVM，P11 再加入独立 FinOps，P12 要验证真正多实例运行及停止/故障/部署安全、资源上限和架构隔离收益。生产入口只允许一个受控 Gateway 访问表面，Core 管理现时授权、唯一派发、账务和恢复，FinOps 掌管自己的读模型/运营费用。Redis丢失时**新**请求 fail closed；旧实例退出、SSE断开、缓存失效都不能把未知 Provider 费用归零；MySQL资金主库不可达时禁止新收费出站；RabbitMQ/FinOps 失联与采购预算错误必须分别处理。两 Gateway 副本压测要记录真实吞吐、TTFT、P95/P99、内存/GC、锁/连接池、Redis active/queue 和账本超额次数；先基于实测优化线程池/索引/限额，无真实证据不自动拆分 Identity/Quota/治理为更多跨库服务。

**产品边界**：P8 改进同型号 Deployment 路由，不偷偷更换型号；P9 只在真实公司政策与请求同意下低优先回退；P10 独立审批不等于保证执行；P11 报表的 eventually consistent 不能替代 Core 的资金权威；P12 真实单机 Compose 不等于企业生产级多 AZ HA。新阈值均是可测试配置提案，并非用户公司已批准的金额/SLA/安全合规事实。P8～P12 均未写业务代码/未运行测试。

## 三十三、P0-D30～D33：业务冻结前的三处现实边界（不是新增功能）

1. **“硬预算”是收费请求准入硬上界，不是能命令第三方供应商绝不超费**。Core 在发任何第三方请求前，对可信 Token 最大上界和原币种采购月总预算+对应 NORMAL/EMERGENCY 份额进行同库事务预留；正常账户不能超限。但外部 Provider若真实额外收费、用量报告超出可信预估，上游物理付款不可用数据库事务回滚，系统必须显示 OVERRUN、冻结该采购币种后续准入、记录可靠债务证据，不能因DB CHECK超限就拒绝记录实际供应商事实。员工正常周 Points账户仍不允许新准入透支；有真实超额Points无法合法分配时必须标异常待对账，而不能给员工生成负余额或假无限额度。
2. **业务价格历史只要有已确认使用就必须可解释**。一笔Invocation的员工Points价绑定LogicalModel当前发布版本、公司第三方采购价绑定真正Deployment已发布原币种版本；实际出站许可后不随管理员调价变化。新价发布通过切换模型/部署的当前指针，不改历史已发布价行，即使两个管理员并发发布也只能成功一个目标revision。
3. **财务已确认数字与未知费用是不同结果**。Core可能出站却无usage时是PENDING，余额保留风险；FinOps报表没有源事件完整核对时是UNKNOWN/DELAYED，不能从lastProcessedAt最新或Outbox自增连续推断完整；公司SelfHosted费用没有真实财务证据/第二审批人时不作为真实运营成本。这些限制比给用户展示漂亮的0金额更重要。

本轮正式逻辑SQL基准与职责见《03》D30～D33、《02》ADR-023，**不改变 P0 全量冻结需要真实数据库、API和跨进程故障验证的原则**。

## 三十四、P0-D34～D41：全部核心业务的数据不变量审查成果

P1组织与Bootstrap、P2双运行身份、P3同LogicalModel多真实Deployment与两套价格、P4每员工周Points和独立采购货币预算、P5 Team发行Grant、P6数据治理、P7第一次真实JSON/SSE/唯一Permit、P8健康安全路由、P9公司LOW资金和本地Token保底、P10独立双人审核紧急池、P11四口径FinOps+可重建报表，已经分别对应一个**明确增量迁移阶段**；P12为真实故障/容量和架构收益核对，不强制新造数据库表。

在业务层不能为了统一口径做三种错误：**发行Grant和员工使用重复计为消费**、**供应商采购原币种与POINTS/无凭据GPU支出相加**、**Provider未知收费/FinOps未知事件缺口显示为0**。D40为真实报表重建增buildId隔离，D41为治理审计多次合法复评增ordinal、为真实Token更正保留负向delta。这是维护历史事实和应对外部不可回滚行为所必需的复杂度，不是为了增加技术组件。
