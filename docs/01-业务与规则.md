# AIGate 业务与需求设计

> **状态：完整业务蓝图，尚未编码。** 本文记录重做后的产品目标及必须遵守的规则；实施参数和技术约束以其余文档为准。

## 一、产品定位

AIGate 是企业内部已有 Agent 的 **AI 模型统一接入、安全治理、额度计费、流量调度与成本运营平台**。员工通过已有 Agent 调用受管理的模型，AIGate 处理认证、授权、资金控制、Provider 代理、可信计量和审计。

**不做** Agent 创建、工作流编排、工具执行、RAG 知识库、模型训练、真实供应商付款或未经批准的自动 GPU 采购。万人员工是容量场景，不等于一万人同时在线或已达到特定 QPS。

| 角色 | 主要职责 |
|---|---|
| Employee | 使用独立员工凭证调用已授权 Agent/Model，查看个人余额与用量，申请补充积分 |
| Team Manager | 审批或主动发放其负责 Team 的额度，可跨团队发放 |
| Platform Admin | 管理身份、Agent、Provider、Model、Deployment、定价、策略、紧急预算和对账 |
| FinOps Reader | 查看经授权的成本分析报表，不修改权威账本 |
| Managed Agent | 企业现有的 Agent 软件，每个 Agent 对应一个 Application，通过其独立密钥访问网关 |

## 二、核心业务主流程

员工在 Agent 里选择获准的逻辑模型 → Agent 同时携带自己的 Key 和员工独立 Key → 网关认证双方、检查 Employee×Agent 权限与 Agent×Model 白名单 → 出站前执行内容安全策略 → 选择适用资金来源并原子预留可支付风险额度 → 在同一个逻辑模型的健康 Deployment 中路由 → Provider 返回 JSON 或 SSE → 使用可信 Token 完成结算、释放未用预留；若费用不明则待对账 → 安全元数据与已确认事件进入运营分析。

认证、额度或安全拒绝必须发生在发出收费 Provider 请求**之前**。降级、紧急任务同样不能绕过身份和数据安全。

## 三、身份与模型权限

- Agent/Application 一对一；Agent Key 与 Employee Credential 独立签发、过期、禁用、撤销；不信任用户自行提交的 employeeId。
- 运行时必须同时验证 Agent 与 Employee，才能得到真正的调用者和所属 Agent；单个 Key 不足以执行付费请求。
- 员工是否可使用某 Agent，及该 Agent 可用哪些逻辑 Model，是两套独立授权。用户选模型必须在交集内。
- 管理 API 与运行时 API 分离。管理员、Team Manager、员工自助、FinOps 只读角色最小授权；密钥明文仅创建时展示一次。

## 四、积分与团队额度

**每周一公司统一时区 00:00 刷新、不结转**：① Employee×Agent 免费周积分；② Employee 个人基础周积分。公司账务时区可配置，设计默认 Asia/Shanghai，瞬时时间持久化为 UTC。

正常扣点顺序：**Agent 专属周免费 → 员工个人基础周额度 → 已获发放且未过期的 Team Grant（先到期先消费）**。单次请求可跨来源，但预留必须原子成功或整体失败。

Team Manager 可审批申请、主动发放，允许跨团队。成功发放必须同一 MySQL 事务扣**发放 Team** 的池并创建接收员工的有效期 Grant 和唯一流水；不允许重复发放。**到期未消费部分作废，不退 Team 池**；员工实际使用时不再扣发放 Team 池。

## 五、三级流量、保底与紧急

- **普通档**：员工正常获授权资金与模型。
- **限流档**：正常积分不足，若公司受控保底池和该员工的周保底限额都有余额，则使用 Agent 预设且获授权的较低成本保底模型，以受限速率/并发/优先级服务，并提醒员工。
- **紧急档**：基于事前批准的 Employee、Agent、任务、明确额度、有效期和独立有限预算，提高资源优先级。

企业付费保底达到硬上限后**禁止新增收费 Provider 请求**；只有公司实际具有、且安全批准、有独立容量限制的自部署基础模型才可提供受控服务，否则明确拒绝。自部署模型仍有硬件/运营成本。最低速率绝不意味着可以突破资金硬上限。

## 六、计价和费用状态

内部积分价格与 Provider 采购价格是不同价表；均按生效版本、Token 类别（输入/输出/缓存等）计算。实际积分结算与采购费用估算只使用可信 Provider usage 或经认可的对账证据。

收费调用出站前应预留保守且有界的最大可能支付风险；不能界定风险上界时拒绝新的付费请求。网络 I/O **不在数据库余额事务内执行**。Provider 可能已计费但网关没有收到可信 usage 时进入 **待对账**，不能假设 0 元/0 积分、不能任意释放预留。相同业务幂等键不会再次发送可能收费的请求。

## 七、SSE、多部署和安全治理

SSE 必须支持增量透传、及时 flush、连接上限、超时、客户端断开时尽力取消上游。只有可信的最终 usage 才进入正常结算；缺失则待核对。已流出的数据不可撤回。

模型路由只在**同一逻辑 Model** 的多个健康 Deployment 中比较权重、时延、错误、负载与成本；保底切换到其他模型必须按专门规则重新授权。不能盲目重试已可能收费的模型请求。

企业合规治理提供数据分类、模型/Provider 准入、安全规则版本、敏感字段或密钥模式识别、拒绝/受控例外与必要审计。第一版重点是**请求发往 Provider 前的检查**，不承诺对已流出的 SSE 输出进行完整实时阻断。日志、队列、分析数据默认不保存 Prompt/完整回复/明文 Key。

## 八、FinOps：三种绝不混加的口径

| 统计口径 | 计算与归属 |
|---|---|
| 员工实际使用积分 | 已确认分类 Token × 调用时生效的内部积分价格；**谁用归谁**，可按当次员工主 Team 汇总 |
| Team 发放内部额度支出 | 成功发放积分总数；**谁发放归谁**，发放时确认，之后消费或到期不冲回 |
| 公司 Provider 采购成本估算 | 已确认分类 Token × 对应供应商生效价格，保留币种/版本；不是供应商最终发票 |

例：客服 Team 发放 1000 点给研发 Employee；客服 Team 内部支出 1000 点，员工后来使用 300 点记员工用量，700 点到期不退。**不能把 1000+300 说成公司的模型总费用**。成本报表按 Team、Employee、Agent、Model、Deployment 和日期分析趋势、异常和优化机会；异步统计无权修改积分账本。

## 九、验收总原则

双身份、模型白名单、预算资金、合规四项任一不满足，收费 Provider 接收请求数为 0；并发不能透支；Team 发放仅扣一次；未知用量可对账；三口径不双计。具体测试见《05-测试与验收.md》。

用户正式要求：**全部文档先完成并冻结后才开始编码；每次按业务块交付该业务块约定的全部功能及测试**。业务块必须同时完成参数校验、权限、状态/异常、幂等、并发事务、自动测试与验收，而非先成功路径后补防护。依赖关系驱动的 Phase 重排**属于总控提案**，见《04-阶段与任务》；本节不代表已获批准调整原先阶段编号。

## 十一、P0 专题设计 D-01：双预算准入与结算（详细方案待确认）

**当前为总控设计提案，非新增已确认业务事实。** 业务已确认的是：用户积分、团队发放和 Provider 采购费用不同；付费调用不得在缺少可控预算时无限发起。

1. **使用授权预算（POINTS）**：首先确定可用资金来源（Employee×Agent 周免费、Employee 本人周额度、未过期 Team Grant；用尽后才评估授权的企业保底/紧急池）。发放 Team 池是授额来源，不是每次员工调用时再扣一次 Team Pool。
2. **外部采购预算（货币）**：每次调用收费 Provider，无论员工花哪种积分，都必须同时占用公司的 Provider 费用风险限额。允许的供应商计价币种各自有独立的公司采购风险限额；未配置币种/限额，不发送该币种的收费 Provider 请求。内部 POINTS 不能替代货币预算。
3. **预算的意义**：这是 AIGate 依照*有效 Provider 价格和受控请求范围*进行的**预计采购成本准入**，不是银行现金余额，更不是已经确认的供应商最终账单。供应商违反 token 上限、价格合同外收费等可能造成额外费用，需要异常冻结/告警和账单核对；不得虚假宣称绝对控制最终供应商发票。
4. **准入前置**：选择具体 Deployment 并验证身份、权限和数据政策，冻结内部积分价/供应商采购价版本，计算两种资金的有界最高风险。**同一 MySQL 短事务同时预留 Points 和该币种 Provider Cost Budget**；一方不足则全体回滚，Provider 出站为零。模型 JSON 与 SSE 都走同样的资金合同。
5. **结算**：根据可信的分类 Token 用量，按照预留时冻结的双方价格版本分别结算 POINTS 与 Provider 费用估算，并释放两套多余预留。服务端可证明未出站/未收费时释放；可能已收费但无可信 usage 时两套预留保持待对账，不能因为客户端断开而认作免费。
6. **公司付费保底**：是员工积分不足时申请使用受控内部资金额度的路径，依旧同时占公司 Provider 采购风险额度，且要满足员工周保底上限和企业保底硬上限。紧急授权同样不可跳过外部采购预算。
7. **不同货币**：设计默认每个公司采购预算期间分别为 USD、CNY 等供应商**原币种**设上限，不能跨币种直接加总或无汇率转换就声明一个统一金额硬限额。企业若未来要求折算到单个本位币总限额，需要另外冻结汇率快照/超额归属规则。财务报表继续按币种展示。
8. **期间归属**：设计默认采购预算按公司时区**自然月**，每次调用消耗发起出站时所属期间的额度，月底未结算的预留保留在旧期间，之后完成结算/核对不能凭新月份的额度抹除旧欠账。

### 例子（虚构数字，仅解释逻辑）

某员工有 100 点余额，某公司本月同币种采购预算上限为 0.20 USD，本月先前结算/预留均为 0。新请求评估的最高风险分别为 **30 POINTS + 0.06 USD**，因此两本账同时预留；Provider 最终可信用量需扣 **12 POINTS + 0.024 USD**。账务一次性扣 12 点、采购估算累计 0.024 USD，分别释放预留差额 18 点和 0.036 USD。员工剩余余额 88 点，公司预计采购预算剩余可批准额度为 0.176 USD。若因 SSE 断线丢失 usage，则 **30 点和 0.06 USD 预留仍挂起待核对**。

**设计门禁**：Provider 对该协议的输入和输出 Token 数量、有效价格及可能收费内容必须有可信的保守最大上限；无法确定时付费调用拒绝并告知“无法验证费用上界”。Provider 异常超出预留时记录外部真实风险/异常，禁止隐藏负账、冻结受影响采购预算与追加请求，人工复核。下一步由总控在《03-数据与接口》冻结具体表/事务/测试；本节尚待用户确认后转为 APPROVED。

## 十二、P0 专题 D-02：第三方 API 与企业自部署模型两种供给方式（已确认，2026-10-21）

**用户明确要求讨论并区分两种模型**：①第三方供应商提供的按次计费 API；②企业自己运营的推理服务。两者都可通过 HTTP/OpenAI 兼容协议访问，不能仅凭“是不是 HTTP API”区分。更准确的责任边界为**谁运营算力与如何产生费用**。

| 属性 | THIRD_PARTY_API | SELF_HOSTED |
|---|---|---|
| 部署与 GPU 运营方 | 供应商 | 企业自管/租用并自管 |
| 外部采购预算 | 逐次调用按供应商报价产生费用；用公司采购风险月预算按币种原子预留与结算 | **没有第三方按请求 Token API 账单时不占用同一个 Provider 采购风险预算**；自有/租赁算力费用进入独立运营成本核算 |
| 员工使用额度 | 员工内部积分；正常不足时可申请受控付费保底 | 常规调用也按照所选 Model 的**内部积分/额度政策**限制；经特别批准的“本地基础模型保底”可改用独立、有限的每员工周期补贴额度 |
| 核心容量约束 | Provider 限额及网关 RPM/并发 | 本地推理 Deployment 的有限并发、等待队列、KV Cache/GPU 资源、输入/输出上限与工作状态 |
| 成本统计 | 已确认 Token × 生效 Provider 采购价，**估算采购支出** | GPU 租金、折旧、电费/托管/维护等经配置并有来源的运营成本；初期按部署/时间段统计，不把它伪装成按次 API 账单 |

**统一规则**：
1. Employee、Agent 双身份、员工 Agent 授权、Agent Model 白名单与内容安全在两类调用中完全相同。自部署“内网可信”不能免除权限或合规。
2. 路由按业务允许的**逻辑 Model** 选择具体 Deployment。若同一逻辑模型可兼容地部署在两类平台，路由前明确选具体 Deployment 和资金/容量政策；跨逻辑 Model 切换只允许已审批的保底，须告知实际模型并重新检查权限/安全/额度。
3. 自部署请求要受**本地容量准入**保护：健康节点、最大活跃推理数、队列容量、每员工限速/Token 限额；没有可用容量就限时排队或拒绝，不能无界堆积。容量故障不应默默切到会收费的第三方 Provider，除非用户/管理员事前批准、对应两套预算仍通过原子预留。
4. **本地基础保底已确认规则**：员工正常积分和有界企业付费保底都用尽后，如公司真实配置了获授权、有限容量的本地基础模型，允许按独立的每员工周本地保底 Token/请求限额提供低优先级服务；此例外无需逐次外部 API 采购预算，但仍要检查本地容量、员工/Agent/Model 权限、内容策略和额度限额。不能宣称“本地模型零成本”。
5. 常规本地模型请求仍可按内部积分价格消耗员工余额，内部积分用于业务公平和资源分摊；**内部积分不等于 GPU 能耗或供应商账单**。本地保底是否设置价格为零属于“独立限额+补贴”策略，不应全局把所有本地模型永久设为零积分。
6. 自部署费用分两个层次：实时限流容量由推理服务/网关可观测指标控制；月度算力账单/折旧是 FinOps 管理费用。只有能实际取得 GPU 运行/租赁/能源等数据并规定分摊口径时，才可给每次本地推理分摊费用，报表明确 `ESTIMATED_ALLOCATED`，不是精确逐次采购发票。
7. **真实部署条件**：没有企业 GPU 的学习/开发环境，可以使用 Fake Local Inference Endpoint 测权限、容量、流式与计量契约；真实 GPU 指标、GPU 扩缩容和 GPU 成本分析不能由模拟数据冒充已实施生产能力。

**与 D-01 的关系**：用户已同意按币种/自然月的采购预算、第三方 API 对积分与采购金额双原子预留。D-02 进一步规定 SELF_HOSTED 常规业务走内部积分/本地容量治理，不必误占用“第三方按次 API 采购风险”账户；这并不是取消内部员工授权，也不是默认无预算。用户已确认**普通自部署模型消耗员工积分；只有明确批准的本地基础保底模型提供独立、有限的员工周补贴额度**，且不占用按 Token 计费的第三方 Provider API 采购预算；本地推理容量必须有界，运营成本与 API 采购成本分开统计。容量租约技术实现、补贴精度、真实算力成本归集方法属于 D-03 及后续详细设计，不因此自动批准。

### D-02 正式决策边界

同一网关保持统一双身份/权限/合规入口，Deployment 类型决定准入分支：`THIRD_PARTY_API → 员工积分 + 采购金额月预算`；`SELF_HOSTED 常规 → 员工积分 + 本地容量`；`SELF_HOSTED 获批保底 → 员工周补贴额度 + 本地容量`。仅本地保底豁免普通员工积分，**所有自部署调用仍有可验证的公平用量边界**。若部署实际还按次向第三方收费，则必须按照费用模式进入第三方采购预算流程，而非因为它在私有地址就被当成免采购费。

## 十三、P0-D03：本地推理保底额度与容量规则（业务边界已确认，实施细节待冻结）

1. 每名员工在公司账务时区的每周周期内共用一个本地基础保底额度，**不会因切换 Agent 重置**。业务设计默认采用输入 Token + 输出 Token 计量；公司实际周限额通过配置决定，不写死。
2. 当周可用 Token = 本周上限 − 已确认使用 − 所有在途/待核对预留。出站前为最大可信 Token 使用量预留，不得把未经验证的 tokenizer 估计当成硬上界；若无法验证上界，拒绝请求。
3. 正常 SELF_HOSTED 模型仍按内部 Model 积分价格扣员工积分；仅被管理员标记为 BASIC_FALLBACK 且经过 Agent/Employee/政策授权的模型，可以在正常积分和付费保底不足时使用上述周补贴。补贴调用不产生按 Token 计费的第三方 API 采购预算占用，**但也不是无成本模型**。
4. 推理资源按实际共享的算力池限制，并同时设最大运行任务数、最大等待请求数、最长等待时间和推理超时；客户端等待时占用的补贴/积分风险也应有界。
5. 失败/取消若可证明请求未送达推理服务，则释放额度预留；已可能运行但未收到可信 Token 用量，则待对账。客户端断开只触发尽力取消，不自动认为 GPU 已停止。
6. 多网关副本必须使用共享的容量准入状态或真正由推理服务全局执行的并发硬限制；单实例 Semaphore 不得冒充集群限额。部署的物理容量和网关容量准入不是一回事。
7. 自部署 GPU 采购/租赁、电费、折旧等作为 FinOps 的**运营成本来源**按可验证账单/资源周期统计，不能与第三方逐请求 API 采购费用混淆或在分摊后重复加总。

D03 的具体状态机、DDL、排队协调、租约 TTL、测试步骤由《03-数据与接口》《05-测试与验收》继续冻结；未完成 P0 不授权本地 AI 编码。

## 十四、P0-D04：多来源积分、Grant 过期与跨周（业务规则已确认）

资金消费顺序保持：Employee×Agent 免费周额度 → Employee 个人基础周额度 → 未过期的 Team Grant（最早过期先消费，时间相同按 Grant ID）。一次调用可组合多个来源，原子预留最大可信积分风险；第三方 API 同时原子预留公司的对应币种采购预算。

**已确认业务边界**：Grant 在成功预留时有效即可用于当前已预留请求；即使结算时过期也允许对这部分已预留额度结算，但过期后不允许新请求再占用，释放的过期额度不再成为可用积分，原发放 Team 不退款。跨周调用亦然：周日预留的新周一返回，始终从**原周桶**结算并释放，旧周释放金额不滚入新周。可能收费但用量未知时仍在原资金来源待对账，Grant 到期和周期切换都不能直接清除预留。

成功发行 Team Grant 一次性扣 TeamPool 并记发行团队的内部支出；消费、释放多余预留、Grant 过期不再改变发行团队的这笔支出。

例：Agent 周免费剩 10、个人基础 10、Grant 20，请求最大风险 40，原子预留 10+10+20。可信实际只消耗 15，则最终使用为 Agent 10+个人 5+Grant 0，释放其余 25。若 Grant 在结算前已经过期，释放的 Grant20 不重新提供给新调用，原发行 Team 的支出记录不回冲。本节 D04 业务语义已由用户确认，但完整 DDL、异常恢复和自动化测试实现尚待 P0 全量设计冻结；目前没有代码。

## 十五、P0-D05：企业付费保底和紧急任务的资金/优先级（方案已认可，完整DDL待冻结）

**必须区分：使用权、内部资金来源、外部采购资金、调度优先级。** 紧急优先不等于可以突破公司现金采购上限；免费/自部署也不等于无需员工授权和计算资源限制。

### 三条互斥业务路径

1. **普通 NORMAL**：员工选择允许的逻辑 Model，优先使用 Employee×Agent 周免费→员工基础周额度→有效 Team Grant。如果所选 Model 的可信最大积分风险可以完全预留，保持所选 Model 和 NORMAL 档。
2. **企业付费保底 LOW**：当普通来源不足以承担原请求的最大积分风险时，仅在管理员为该 Agent 配置了明确允许的低成本保底 Model、员工符合保底条件时，重新检查该 Model 的权限、内容政策、Deployment 和最新冻结价格。按新 Model 的风险上界**先用员工尚存的普通积分，不足部分使用公司付费保底积分池**；同一事务更新员工每周保底使用上限、公司保底池和对应币种 Provider 采购预算（若收费 API）。回退请求整体为 LOW 优先级，即使降价后无需公司补足积分。保底不能直接调用比原请求更贵或无授权的模型，且不得跨多个模型在同一次 invocation 中盲目重试。
3. **紧急 EMERGENCY**：只有有效的事前审批，且 taskId、Employee、Agent、允许的 Model、有效期、任务总预算均匹配，才享受 EMERGENCY 调度档。**默认使用独立公司紧急积分池与该任务已审批的积分额度，不自动扣员工普通余额**。审批给出最高可使用额度，**不等于当时就已经扣减公司紧急池**；真正模型调用时才原子预留全局池与该任务剩余额度。审批失效只阻止新调用，原已成功预留的调用仍按原授权与期间结算。任务额度用完不得继续以紧急档收费；若希望使用普通额度，必须作为新的 NORMAL 调用重新准入，而不是自动改来源。

### 企业采购现金风险预算的紧急保障（提案）

对第三方付费 API，企业按公司时区自然月、**每个供应商原币种**设置总采购风险预算，并明确分成 NORMAL 和 EMERGENCY 两个有边界的份额。NORMAL 份额供员工正常调用和 LOW 付费保底共同使用；EMERGENCY 份额只允许获批紧急任务调用。NORMAL 不得侵占预留给 EMERGENCY 的资金，EMERGENCY 不得透支其专用份额及公司总限额。若某币种未配置紧急采购份额，该币种收费 API 不提供紧急付费保证。

示例：公司某月 USD 采购最高批准额度 100，其中 20 留给紧急业务，则 NORMAL/LOW 合计最多批准 80 USD 风险敞口、EMERGENCY 最多批准 20 USD，整体仍不超过 100。员工免费积分充足不免检 NORMAL 采购份额；紧急申请已批准也不免检 EMERGENCY 采购份额。

### 与自部署本地基础保底的关系

第三方付费保底仍受外部采购预算；若上述付费资金不足，只有经批准、员工还有独立周 Token 补贴、Redis/推理引擎仍有健康容量的 SELF_HOSTED 基础模型才可进入独立 LOW 本地保底。**不静默从自部署切回收费第三方 API**。紧急自部署调用使用任务专属紧急积分额度及真实容量许可，不需要不存在的逐次第三方 Token API 采购费用；但仍可能发生自部署运营成本。

### 数据归属和异常

- 公司付费保底积分和紧急积分是**两个公司资金池**，独立额度和期间；员工保底周上限是每 Employee 单独的限制，不是员工自己的可兑换余额；TeamPool 不会在保底/紧急发生时再被扣款。
- 任务审批只是授权额度上限，**与 Team Grant 的“发放成功立即扣 issuing Team 池”完全不同**。
- NORMAL、LOW、EMERGENCY 的限速、排队优先级由 Redis 全局共享治理；绝不能以较高优先级绕过 MySQL 积分池或 Provider 原币种预算原子预留。
- 已预留而跨周、跨月、或审批到期的请求，从原账户/原月份/原任务授权结算；未知上游用量维持待对账，不把额度偷偷返还。
- 所有降级、紧急、预算拒绝和审批变更保留审计元数据，并向客户端说明实际运行的逻辑模型/档位/受控拒绝原因，不写原始 Prompt。

**D05 已获用户认可的业务方案**：LOW 可以混合剩余个人积分和公司补足积分，EMERGENCY 独立使用公司紧急资金及任务授权，公司原币种月度采购预算为 EMERGENCY 保留单独份额。具体DDL/请求 DTO/预算份额数值仍须在 P0 冻结，不代表已经编码。

## 十六、P0-D06：紧急审批、排队与三级优先级（详细设计提案）

### 审批业务流程

1. Employee 或其 TeamManager 提交紧急任务申请，指定 taskRef、实际受益 Employee、允许使用的 Agent、可用逻辑 Model 集合、申请积分最高额、有效起止时间与业务理由；必须有可验证的 Employee/Agent 归属，不支持“所有人紧急”通配授权。
2. Platform Admin 审查请求并 APPROVE 或 REJECT；审批人不得与申请人是同一真实身份（双人复核，作为本轮设计默认）。审批必须审计操作者、时间、理由与版本；申请人不得直接签发自己的 EMERGENCY 权限。一次批准仅生成一份不可任意修改的任务授权，撤销只能阻止新调用，已合法预留部分沿原账结算。
3. APPROVED 只代表允许该 Employee+Agent+Task 在指定时段消费最多批准积分额度；**审批成功时不从公司 emergency pool 预扣积分**。真实调用时同事务检查 Task 已使用/已预留和公司 emergency pool，若收费 API 再检查本币种总采购月预算与 EMERGENCY 专用份额。
4. 运行时明确携带紧急授权 ID 供服务端查证，不能仅传 priority=EMERGENCY、employeeId 或任意 taskRef 获取资格；没有授权 ID 默认普通模式，有无效 ID 则直接拒绝，不能静默当普通请求尝试付费。
5. 已审批任务到期或被撤销时不再允许新的紧急请求进入等待队列或派发。**排队期间尚未发生资金预留，派发前仍须检查授权是否有效**；已完成预留且在出站后的请求遵循原任务/原期间完成或待对账。
6. 同一 Employee+Agent+taskRef 同时只能有一份 ACTIVE 的获批任务授权，避免叠加多个审批额度突破设计上限；修改额度/时间/Model 需要撤销旧授权并重新审批，不能覆盖已出账历史。

### 三级排队和公平策略

- 所有请求先做可信双身份、Agent/Model 权限和内容政策的前置筛查，再根据服务端可信规则确定 EMERGENCY、NORMAL、LOW；**不信任客户端直接设置优先级**。
- 所有受同一容量约束的 SELF_HOSTED Deployment 共用一个 GPU Pool；第三方 Provider 另有 Provider/Deployment 自身并发与 RPM 配额，不能用 GPU 的物理规则伪装控制外部供应商。
- Redis Lua 直接实现三个有界队列（EMERGENCY/NORMAL/LOW）、各档 FIFO、总 maxWaiting、单 Employee/Agent 同时等待及在途限制，绝不无限排队。
- **建议调度默认权重 4:2:1**：有等待任务时每 7 个释放的执行名额最多依次调度 4 个 EMERGENCY、2 个 NORMAL、1 个 LOW；空档让其他队列使用，同档先来先执行。该比例是“名额分配”，不是 GPU 计算时长严格保证。全局队列 TTL 使任何请求最多等候配置的时间后拒绝，而不是承诺一定能在等待期限内执行。
- 已经在运行的 JSON/SSE 请求**不被抢占**；高优先级只能争取之后释放的许可，不能承诺立即开工。若将来业务需要硬保证“紧急任务几秒内开始”，必须显式预留物理容量、承担闲置成本并另行审核 SLA。
- 普通/保底、紧急资金和 Redis 调度是独立状态机。无资金时即使获得 GPU 许可也不能出站；有资金却等待超时也不能长期冻结员工/公司额度。

### 执行顺序修订（覆盖 D03 旧版“先预留资金再进 Redis 等待队列”）

认证/授权/内容预检 → 校验紧急任务权限与模型、初步确认路由合法 → Redis 请求频率检查与**有界等候队列** → 领取执行容量许可 → **派发前再次校验员工/Agent/模型/内容版本与紧急授权、确定实际 Deployment 和生效价格** → MySQL 以派发时刻所属周/月原子预留积分和（若收费）Provider 币种采购风险 → 记录唯一派发意图 → 发出一次上游请求 → 可信用量结算/未知用量待对账 → 确认实际任务终止后释放许可。

此变更避免排队跨月/跨周时长期锁住资金：**月度采购预算归属实际获准派发时段，而非排队进入时段**。等待超时、队列已满、授权到期时，因为尚未财务预留，不存在要退的预留；若已经获得许可但数据库预留失败，只需释放 Redis 许可，0 次上游发送。

当 NORMAL 排队时原模型可用，但派发时积分变化导致不可支付，允许在尚未出站的同一个 Invocation 内**最多一次**重新计算允许的 LOW 保底模型与资金，并重新排队 LOW；不得伪装成对 Provider 的第二次收费重试。重新排队重新检查授权/价格/期限与有限等待截止；若用户的 Idempotency-Key 重复出现，只返回原 Invocation 状态，不创建第二个任务。

### 故障与审计

Redis 故障或共享队列状态不可信时新请求 fail closed，MySQL 持久化的执行意图、预算和账本不能随 Redis 清空；恢复先协调可能已经在计算的任务。Redis 租约过期不等于 GPU 推理结束。两份 Gateway 实例要测试相同资源池并发、FIFO、优先份额、旧租约令牌不得释放新许可，以及审批撤销和超时的竞争。

**状态：D06 PROPOSED**。审批双人复核、4:2:1 调度权重、派发前预留以及 NORMAL→LOW 单次重新入队是本轮新设计默认，需与完整 API、异常矩阵一起审查冻结；实际权重/速率/超时/真实审批限额由配置确定。
